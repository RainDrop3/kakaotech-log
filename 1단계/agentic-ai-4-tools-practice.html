도구와 실무

에이전트를 실제로 만들 때 필요한 실무 지식입니다. 모델을 고르고 조합하는 법, Claude Code와 Codex 같은 AI 코딩 도구 활용법, 개발 환경과 Git 협업, 주차별 실습 프로젝트 기록, 현업 조언과 자주 묻는 질문을 담았습니다.

주제 1

모델 고르기와 여러 모델 조합

어떤 모델을 쓸지 감이 아니라 벤치마크와 지표로 고르는 법, SLM을 Ollama로 직접 돌려 보며 배우는 것, effort(thinking 정도)를 정하는 기준, 그리고 상위, 하위 모델과 다른 회사 모델을 섞어 토큰을 아끼는 분업 방식을 정리한다.

모델은 감이 아니라 지표로 고른다

생성 모델은 감으로 성능을 평가하기 매우 어렵다. 그래서 소문이나 느낌으로 모델을 고르지 말고 그래프, 벤치마크, 평가 지표를 보고 고르며, 가능하면 직접 벤치마킹하면서 진행하는 게 훨씬 정확하다. 테크 블로그를 자주 보며 이런 실험 결과를 확인하는 습관도 도움이 된다.

나중에는 모델 하나만 쓰지 않는다. 벤치마크를 직접 분석해 "이건 이 모델, 저건 저 모델"로 고르는 루틴을 만들어 두는 것이 좋다. 코드로 만들 때도 특정 에이전트는 특정 모델로 동작하게 따로 구현할 수 있다. 토큰도 아끼고 성능도 좋아진다.

정리 모델, effort 선택은 지표로 한다. 생성 결과는 매번 달라서 "써 보니 좋던데"로는 비교가 안 된다.

벤치마크 읽는 법

새 모델이 발표되면 함께 공개되는 벤치마크 표를 이렇게 읽는다.

  1. 모르는 벤치마크 이름은 복사해서 물어본다. GPT 등에 "이 벤치마크가 어떤 벤치마크인지" 붙여 넣으면 된다.
  2. 벤치마크마다 평가 대상이 다르다는 것을 확인한다.
  3. 내가 풀고 싶은 문제와 가장 비슷한 벤치마크를 찾고, 거기서 가장 성능이 좋은 모델을 고른다.
벤치마크 예 평가 대상
에이전트 평가용 벤치마크 툴, 파일 검색 같은 RAG로 문제 풀기
툴콜 시나리오 벤치마크 툴콜을 많이 하는 시나리오
법률 문서 작성, 시장 조사, 금융 해당 도메인 업무
MMLU 일반 지식, 대화(Ollama 모델 페이지에서 볼 수 있는 항목)

각 회사는 자기 모델이 다 좋다고 하지만, 세부 테스트에서는 다른 모델이 더 높은 경우가 있다. 예를 들어 코딩은 다른 회사 모델이 더 잘한다는 식이다.

최상위 모델이 늘 정답은 아니다

최상위 모델이 모든 벤치마크에서 무조건 높은 것은 아니다. 그리고 낮은 모델과 차이가 크지 않으면 낮은(싼) 모델을 써도 된다.

같은 맥락에서 Fable 같은 최상위 모델은 특별한 경우가 아니면 잘 쓰지 않고, Opus 정도면 충분한 성능이 나온다.

벤치마크도 의심하라

벤치마크도 100% 정확하지 않다. OpenAI가 어떤 벤치마크 세트에 문제가 있다고 발표한 적도 있다. 그러니 벤치마크 자체에 이슈가 없는지도 확인해야 한다.

정보 과잉 시대에는 항상 의심하고 검증해야 한다. 벤치마크도, 누군가의 설명도 틀릴 수 있다.

롱 컨텍스트 벤치마크: "입력된다"와 "인식한다"는 다르다

컨텍스트 길이도 모델을 고를 때 보는 지표다. 그런데 1M 토큰이 입력된다고 해서 그만큼 다 인식하는 것은 아니다. 롱 컨텍스트 벤치마크 수치가 그 차이를 보여 준다(컨텍스트 관리 전략은 → 컨텍스트 엔지니어링과 하네스).

모델 구분 수치
최상위 LLM 롱 컨텍스트 벤치마크에서 Claude가 약 79~80%로 가장 높았다. Claude(Fable)는 약 256K 토큰 이하에서 90% 이상, 512K를 넘으면 77~79% 정도
이전 세대 모델 실험 Claude 4.5, GPT-5, Gemini 3 무렵 실험에서 긴 컨텍스트에서도 90% 이상 유지한 건 Gemini뿐, 나머지는 70~80%(대략적인 수치)
SLM(가장 좋은 모델) 128K 벤치마크에서 약 66% → 실질 6만~7만 토큰 유지
SLM(작은 모델) 약 13% → 약 1.5만 토큰 정도만 인식

정리 컨텍스트 길이는 "최대 입력량"이 아니라 롱 컨텍스트 벤치마크의 실제 인식률로 본다. SLM은 이 수치가 특히 낮다.

SLM이란: 어떤 모델이 있고 무엇이 약한가

SLM(소형 언어 모델)으로는 Mistral, DeepSeek, Gemma, Phi, Llama, EXAONE(LG), Kanana(카카오) 등이 있다. 한 번쯤 직접 써 보기를 권한다.

SLM의 약점은 두 가지로 정리된다.

  • 작은 모델은 실사용이 어렵다. 사양 문제로 클라우드나 작은 모델을 쓰게 되는데, 13B, 20B 이하 모델은 쓰기 어렵다(오류가 많고 잘 동작하지 않는 부분이 있다).
  • 컨텍스트 유지 능력이 많이 떨어진다. GPT-4.1 같은 모델은 상당히 좋지만, 회사, 창업에서 마주칠 SLM은 같은 내용을 프롬프트에 중복해서 써 줘야 할 때가 있다. 시스템 프롬프트에만 써 두면 툴, Pydantic description이 쌓이며 "까먹으니" 툴 description이나 유저 프롬프트에도 다시 쓴다(프롬프트 계층은 → 프롬프트 엔지니어링). 구조상 이유는 → GPT-2에서 현대 LLM으로에서 다룬다.

그래도 회사, 창업에서는 SLM을 마주칠 수밖에 없고, 현업에서는 SLM을 파인튜닝하고 요즘은 강화학습까지 하게 된다(학습 쪽은 → 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝).

SLM을 에이전트로 쓰는 조건: tools 지원

에이전트로 쓰려면 모델이 tools(Function Calling) 기능을 지원해야 한다. 툴콜은 모델이 학습한 능력이라 지원하는 모델만 에이전트가 된다. Gemini, Claude 같은 주요 LLM은 대부분 지원하지만 SLM 중엔 지원하지 않는 모델이 있다.

  • 지원하지 않는 모델도 출력 형식을 학습시키는 파인튜닝으로 툴콜이 되게 만들 수 있지만 시간이 들고, 처음부터 학습한 모델과는 차이가 날 수 있다.
  • 거꾸로 tools만 지원하면 SLM을 에이전트로 다 활용할 수 있다.
  • 구조화된 출력도 비슷하다. response_format의 기본 ProviderStrategy는 모델이 구조화된 출력을 지원하지 않으면(SLM 등) ToolStrategy로 넘어간다(→ 구조화된 출력과 Pydantic).

팁 Ollama 모델 페이지(예: Gemma)에서 그 모델이 tools를 지원하는지 먼저 확인한다.

옛 멀티에이전트가 흐름을 코드로 고정했던 것도 "이 LLM, SLM은 펑션콜로 툴이나 서브에이전트를 잘 못 부르겠다"고 판단했기 때문이다(→ 서브에이전트, 멀티에이전트, 워크플로).

Ollama, Hugging Face로 SLM 돌려 보기

SLM은 Hugging Face에서 직접 내려받거나, Ollama로 양자화된 모델을 테스트할 수 있다. Ollama 등에서는 계산을 빠르게 하고 공유하기 쉽게 INT4, INT8로 양자화한 모델을 올려 둔다(양자화 개념은 → 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝).

Ollama 모델 페이지(예: Gemma)에서 볼 것은 다음과 같다.

  • 벤치마크: MMLU(일반 지식, 대화), 코딩, Function Calling 벤치마크가 있다.
  • thinking / no-thinking 구분: 에이전트로 쓰면 ReAct 프롬프트(→ 에이전트란 무엇인가)가 동작해 thinking과 비슷하게 움직이므로, no-thinking 모델도 "반 정도는 동작"한다고 보면 된다.

Ollama Cloud로 이런 모델을 쓸 수도 있다. Ollama로 배포된 모델이 있다면 API 키나 서버를 연결해 Ollama, LM Studio, Codex 등 여러 앱에 붙여 직접 써 볼 수 있다.

SLM 컨텍스트 길이 설정: 1.5만~2만 토큰

SLM은 컨텍스트 길이를 직접 정할 수 있다(서버에서 파라미터로 조정). 롱 컨텍스트 벤치마크 결과가 있으면 그에 맞춰 1.5만~2만 토큰 정도로 설정한다. 어차피 그 이상은 제대로 인식하지 못하니, 이렇게 맞추면 메모리 낭비도 줄이고 성능도 최대로 끌어낸다.

예시 작은 SLM은 128K 벤치마크에서 약 13%, 즉 약 1.5만 토큰만 인식한다. 그렇다면 컨텍스트 길이를 128K로 열어 둘 이유가 없다.

SLM으로 프롬프트 연습하기

SLM은 실사용보다 프롬프트 연습에 매우 좋다. LLM은 프롬프팅을 잘 알아듣지만 SLM으로만 내려가도 답변을 잘 못한다. 그래서 프롬프트를 더 빡세게, 아주 디테일하게 써야 동작하고, 그 과정에서 모델 이해도가 "강제로" 올라간다.

SLM으로 해 볼 연습은 다음과 같다.

  • few-shot, CoT의 큰 구조는 유지하되, 얼마나 더 자세히 쓸지, 예시를 더 만들지를 연습한다(→ 프롬프트 엔지니어링).
  • 툴 간 출력 제어: max tokens 제어, "800토큰만 만들어라" 같은 프롬프트.
  • LLM이 얼마나 잘 동작하는지 체감한다. 좋은 모델에서 잘 되던 것도 SLM에서는 난이도가 크게 올라간다.

샘플링 설정도 다르게 본다. temperature 0(가장 확률이 높은 토큰만 쓰기)은 SLM에서 꽤 괜찮은 전략이다. 확률 분포 자체가 애매하기 때문에 오히려 강력하게 동작한다(temperature 원리는 → Transformer 블록 해부).

SLM을 붙일 때 주의: 무거운 도구와 프롬프트 언어

기본 툴, 스킬이 많은 도구와 조합하지 말 것. 기본으로 들어가는 툴, 스킬 양이 많은 도구로 SLM을 쓰면 성능이 확 떨어질 수 있다. 인식 범위가 좁은 SLM의 컨텍스트를 기본 툴, 스킬 정의가 먼저 차지하는 셈이다. Claude Code를 한 번 거쳐 쓰는 등의 방법이 있다(→ 아래 Ollama, alias).

프롬프트 언어 차이도 SLM에서 커진다. 요즘 프런티어 모델은 영어, 한국어 프롬프트 차이가 크게 줄었지만 SLM, 저성능 모델은 차이가 있다.

예시 2024년 GPT-4o mini 시절, 2023년 인구 통계를 8억 명으로 내놓는 오류가 유명했다. "생각은 영어로, 출력은 한국어로"라고 지시하자 고쳐졌다. 영어 프롬프트 작성이 어렵다면 "생각, 툴 통신은 영어로, 답변은 한국어로"라고 지시하는 방법이 있다.

effort(thinking 정도)의 정체

모델 옵션의 medium, high, xhigh 같은 effort 단계는 thinking을 얼마나 하느냐다. 그 정체는 이렇게 그려 볼 수 있다.

thinking 모델의 출력은 커스텀 토큰으로 형식이 정해진 시퀀스다(커스텀 토큰은 → 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝).

<think> ...여기서부터 여기까지 생각한다... </think> <answer> ...답변... </answer> <EOS>

thinking은 여러 번 할 수 있다. effort 단계는 thinking 토큰이 몇 번 예측되는지 카운팅해 제약을 거는 것으로 만들 수 있다. 예를 들어 10번, 5번, 3번까지로 제약하면 thinking/answer 쌍이 그만큼 생성되면 끝낸다. "ultra" 같은 단계면 제약이 100번이다. 그래도 끝까지 다 도는 게 아니라 중간에 EOS 토큰을 예측하면 생성을 중단한다.

정리 effort가 높을수록 생각(thinking 토큰)을 더 많이 허용한다. 품질이 오를 여지가 생기지만 토큰도 그만큼 쓴다.

effort 고르기: max가 늘 좋은 건 아니다

Anthropic 가이드의 후속 부분에 effort, 모델 선택 실험 그래프가 있다.

태스크 결과
아주 어려운 태스크 작은 모델을 max로 쓰는 것과 큰 모델을 mid로 쓰는 것이 거의 비슷한 품질을 냈고, 토큰 사용량에는 차이가 있었다
심플 태스크 차이가 거의 없었다

즉 무조건 max나 high가 좋은 건 아니다. 태스크 난이도에 따라 토큰 사용량이 꽤 차이 나므로, 쉬운 일에 max를 거는 건 낭비다.

권장 설정은 주로 high나 xhigh를 기준으로 놓고, 대부분 mid로 내리거나 max로 올려 쓰는 것이다. high와 max도 조금 차이가 있다.

팁 effort도 모델처럼 감으로 정하지 말고, 이런 테크 블로그 실험이나 직접 만든 평가 세트로 확인한다(평가 세트는 → 에이전트 평가와 LLM-as-a-judge).

여러 모델을 전략적으로 쓰는 두 방식

에이전트에서 높은 모델만 쓰면 토큰 소모가 너무 커서 부담된다. 토큰 자체를 줄이는 방법(외국어 사용 등)도 있지만, 그보다 모델을 조합하는 방식을 많이 쓴다. 예: Opus, Sonnet, Haiku 조합, 여기에 OpenAI 모델이나 Antigravity 모델을 섞는다.

여러 모델을 쓰는 방식은 두 가지다.

방식 내용 평가
① 메인 LLM + 특정 태스크만 다른 모델 메인 모델을 정하고, 서브에이전트, 팀메이트마다 다른 모델을 준다 실용적. 코딩 에이전트 안에서 CLI로 구현하기 쉽다
② MoA(Mixture of Agents) 한 질문을 여러 에이전트에 동시에 주고 종합한다 비효율적(워크플로로서의 병렬화는 → 서브에이전트, 멀티에이전트, 워크플로)

분업 기준은 단순하다. 복잡한 작업은 좋은 모델, 가벼운 작업은 작은 모델. 좋은 모델이 기획하고 상대적으로 작은 모델이 직접 코딩하는 식이다.

모델 분업 사례

토큰 여유가 빠듯할 때는 항상 모델 레벨을 나눠 쓴다.

모델 맡는 일
Fable 특별한 경우가 아니면 잘 안 씀
Opus 주로 계획 수립(상위 모델)
GPT 계열 Opus가 짠 계획이나 하위 모델 작업을 검증
Sonnet 검증된 내용을 구현 계획으로 분할
GLM(Claude Code에 연결) 실제 코드 구현
Haiku 세부 테스트
Antigravity Flash 계열 Haiku 대신 자주 씀. 이미지 분석, 검색 정보 종합

이를 파이프라인으로 이으면 이렇다. 오류가 나면 다시 위 단계로 되돌린다.

Opus(계획) → GPT(검증) → Sonnet(구현 계획 분할) → GLM 등(코드 구현) → Haiku(세부 테스트)
     ↑__________________________ 오류 시 되돌림 __________________________|

매번 손으로 시켜도 되지만 이 흐름을 스킬 하나에 넣어 자동으로 돌릴 수 있다. 스킬은 프로젝트 전용이나 전역으로 둘 수 있다(스킬 만드는 법은 → AI 코딩 도구 활용(Claude Code, Codex)).

CLI, 스킬로 모델 파이프라인 만들기

여러 회사 모델을 한 작업 흐름에 묶는 열쇠는 CLI다.

  • Claude Code는 원래 CLI 기반이고, Codex, Antigravity, Gemini도 모두 CLI가 있다. CLI를 모두 설치해 두면 일을 분배하는 스킬을 직접 만들 수 있다.
  • CLI에는 플래그(예: 권한 bypass 여부)를 줄 수 있어, 이를 조합하면 CLI로 바로 명령을 줄 수 있다.
  • Claude Code 안에서 다른 모델 CLI를 호출하는 스킬을 만든다. "검색하는 태스크는 Antigravity로" 같은 요청이 스킬을 통해 해당 CLI를 부른다. OpenAI가 Claude Code용 Codex 플러그인을 공식으로 만들어 두기도 했다.
  • 서브에이전트나 에이전트 팀이 불릴 때 Claude 모델이 CLI 명령을 실행하고 결과를 보고 답하는 구조다. 서브에이전트가 Sonnet이든 Haiku든 bash로 다른 모델 CLI만 실행하면 Claude Code와 Antigravity 등을 함께 쓸 수 있다.

장점은 토큰 절약이다. 모든 태스크를 Opus로 돌릴 수도 있지만, 서브에이전트, 팀메이트에게 다른 모델 CLI로 실행시키면 그 모델의 토큰으로 답을 얻는다. Claude Code의 서브에이전트, 에이전트 팀 자체는 → AI 코딩 도구 활용(Claude Code, Codex)에서 다룬다.

Claude Code에 다른 모델 붙이기: Ollama, alias

다른 회사 모델이나 로컬 SLM을 Claude Code의 "엔진"으로 붙일 수도 있다.

  • Ollama를 쓰면 Claude Code(또는 OpenCode)에 SLM을 붙여 실행할 수 있다. Ollama를 설치했다면 Ollama로 Claude Code를 런치하는 명령도 있다. 스킬로 Claude Code에 Gemma 같은 모델을 연결할 수도 있다.
  • 로컬 모델도 CLI로 묶으면 Codex, Antigravity처럼 키워드로 호출할 수 있다.

예시 GLM을 그대로 쓰지 않고 alias를 만든다. 그 alias로 실행하면 "GLM 모델을 가진 Claude Code"가 뜨고, claude로 실행하면 Opus가 뜬다. 하네스 구성에서도 claude / claude-glm처럼 따로 실행하고 스킬, md로 "계획은 Claude, 구현은 GLM"으로 나눌 수 있다(하네스는 → 컨텍스트 엔지니어링과 하네스).

메인 LLM + 서브 SLM 구성과 비용

에이전트 코드로 시스템을 만들 때도 같은 분업이 통한다. 메인 에이전트는 ChatGPT, Claude 같은 좋은 모델, 서브에이전트는 SLM으로 두어 비용을 낮춘다.

  • SLM은 vLLM, llama.cpp로 서빙하거나 Ollama로 서빙할 수 있고, 이런 아키텍처를 구현해 배포하는 일도 실무에 포함된다.
  • 잘 튜닝된 SLM은 일반 대화 성능은 떨어져도 특정 태스크나 의도한 기능은 생각보다 잘 수행한다(튜닝 방법은 → 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝).

비용을 따지는 이유는 숫자로 보면 분명하다. 일반 채팅 모델 대비 싱글 에이전트는 약 4배, 멀티에이전트는 약 15배의 토큰을 쓴다. 네트워크 트래픽을 개선하듯 토큰도 고려해 시스템을 구성해야 하고, 멀티에이전트 일부를 SLM으로 바꾸는 식으로 조절한다(싱글, 멀티 선택 기준은 → 서브에이전트, 멀티에이전트, 워크플로).

SLM의 미래와 평가자로서의 SLM

좋은 모델이 나올수록 SLM도 좋아진다. 프런티어 모델(Fable, GPT 5.x 등)이 나오면 많은 회사가 SFT에 쓰려고 답을 대량 생성하고, 그게 새 데이터이자 자산이 된다. 데이터가 워낙 많아 큰 모델 → 작은 모델 증류가 잘 동작하고, 작은 모델은 증류 없이 알려진 데이터셋으로 RL만 해도 잘 동작한다는 이야기도 있다(학습 방법은 → 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝).

평가자(judge)로 쓸 때는 다르게 본다. 최상위 모델(Opus, GPT 최상위 모델)은 벤치마크로 이미 검증돼 있고 이를 넘는 모델도 많지 않아 judge 신뢰성 검증을 생략해도 된다. 반대로 SLM을 judge로 쓴다면 사람이 만든 정답과 비슷하게 맞추는지 검증이 필요하다(LLM-as-a-judge는 → 에이전트 평가와 LLM-as-a-judge).

정리 모델 선택의 기본값은 "충분히 좋은 모델 하나 + 일에 맞춘 하위 모델들"이다. 어떤 조합이 맞는지는 벤치마크와 직접 만든 평가로 확인하고, 모델이 빠르게 바뀌니 주기적으로 다시 본다.

주제 2

AI 코딩 도구 활용(Claude Code, Codex)

Claude Code, Codex 같은 코딩 에이전트에 "끌려가지 않고" 내 통제 아래 두는 법을 모았다. 플랜 모드, 스킬과 CLAUDE.md, AGENTS.md 튜닝, 컨텍스트 아끼기, 서브에이전트, 에이전트 팀, CLI로 여러 모델 섞기, 브랜치 병렬 개발까지 다룬다.

이 노트의 실습은 LLM을 만드는 것이 아니라, 결국 Claude Code, Codex가 하는 동작을 LangChain 코드로 직접 구현해 보는 것이다. 동시에 실습 과제를 Claude Code나 Codex로 진행하는 경우가 많아서, 코딩 에이전트를 다루는 법을 함께 정리한다. 목표는 하나다. "내 통제 하에 에이전트가 움직이고 있다"는 감각을 갖는 것. 에이전트의 동작 원리는 → 에이전트란 무엇인가, 컨텍스트, 하네스 이론은 → 컨텍스트 엔지니어링과 하네스에서 다룬다.

코딩 에이전트가 예제 코드 스타일을 벗어나는 이유

  • 실습 코드 스타일(LangChain 새 버전)은 2025년 10월에 구성된 것이라 Claude Code, Codex의 모델이 충분히 학습하지 못했다. 그래서 예제와 다른 스타일로 "튀어나갈" 수 있다.
  • 같은 이유로 문서를 참조시키지 않으면 에이전트가 특이한 함수를 많이 만든다. 학습 데이터에 LLM 기반 에이전트, 툴콜 코드가 많지 않기 때문이다.
  • 대응은 세 가지다.
    1. 플랜 모드나 마크다운 계획 문서로 구조를 먼저 잡아 모델을 강제한다.
    2. 문서를 찾아 넣기 어려우면 노트북의 "기본 개념 실습", "확장 예제" 패턴을 프롬프트에 넣거나 그 파일을 참조하게 한다. 예제 코드 스타일을 충실히 따를수록 구현이 잘 된다.
    3. "뭐뭐 되게 구현해 줘" 대신 Pydantic, Literal, None 타입, 툴 구현 규칙처럼 배운 기초 지식을 프롬프트에 넣는다.
  • 그래도 가장 좋은 공부는 예제를 보고 직접 만들어 보는 것이다.

비유 말을 타 보면 말은 생각보다 말을 안 듣고 자기 가고 싶은 대로 간다. 고삐를 잘 쓰는 사람은 달리게도 하고 끌고 가기도 한다. 에이전트를 잘 쓴다는 것은 도메인 지식을 얼마나 주입하면서 끌고 가느냐다. "하네스(harness)"라는 이름도 여기서 왔다. (하네스 개념은 → 컨텍스트 엔지니어링과 하네스)

플랜 모드로 주도권 잡기

Claude Code와 Codex 모두 플랜 모드가 있고, 생각보다 굉장히 중요하다. 머릿속에 있는 것을 플랜과 함께 디벨롭해 나가면 된다.

  • 기획서를 먼저 쓴다고 생각하라. 실습 프로젝트에 구현 가이드를 아주 자세히 적어 두는 이유도 플래닝을 돕기 위해서다.
  • 신입 개발자는 기존 코드를 받으면 문서, 주석을 읽고 함수 호출을 따라가며 하루 종일 읽는다. 이 이해 작업을 플랜과 함께 하면 빨라진다.
  • 플랜으로 하는 연습은 다음과 같다.
    1. 플랜을 짜면 내 도메인 지식과 어긋나는 계획이 보인다. 경험이 쌓일수록 더 잘 보인다.
    2. 그 차이를 고친다. 예: "DB와 툴이 이렇게 연결돼야 하는데 왜 함수 두 개를 끼워 넣었지?" → "이 함수 진짜 필요해?"라고 물으면 설명해 준다. 정말 필요 없는 경우도, 필요한 경우도 있다.
    3. 예제 원형대로 구현되도록 가이드를 맞춘다.
    4. "이런 입력이면 이런 결과" 같은 테스트 시나리오를 넣어 검증을 요청한다.
  • 이렇게 하면 "끌려간다"는 느낌이 줄고 주도적으로 구현할 수 있다. 뭘 하고 있는지 모르겠으면 항상 플랜 모드를 켜고, 안 되면 롤백한다.
  • 처음엔 플러그인, 스킬 없이 프롬프트만으로 진행하고, 남이 만든 플러그인을 보며 "이게 잘 안 되니까 이걸 쓰는구나"를 배우며 확장한다.

정리 플랜 모드 = 기획서 먼저 → 내 도메인 지식과 다른 계획 찾기 → "이거 진짜 필요해?" 묻기 → 테스트 시나리오로 검증 요청.

작은 단위로 쪼개 맡기기

  • SNS에서 보이는 "화면에 에이전트 9개 띄워 놓고 구현하기"는 비효율적일 때가 많다. 실제로는 아주 작은 단위부터 완벽히 통제하며 만드는 게 좋다. 머릿속 로직을 하나씩 구현하고 참고 자료를 넣어 주는 방식이다.
  • 무작정 던지면 "정말 오버해서" 만든다. 체크할 것들을 작은 형식으로 쪼개서 맡겨라.
  • 스킬 모음을 쓰더라도 한 번에 끝까지 가지 말고 하나의 태스크가 그 토큰 안에서 끝나게 하라. 잘못 쓰면 토큰비가 어마어마하게 나간다.
  • 에이전트가 주목받은 지 1~2년밖에 안 돼서, 이런 도구를 잘 쓰는 법을 모두가 함께 찾아가는 중이다. 빨리 적응하면 강력한 무기가 되니, "어떻게 썼더니 시간이 더 걸렸다, 코드 품질이 좋아졌다" 같은 경험을 활발히 공유하는 것이 좋다.

룰베이스 헬퍼 함수 경계하기

코딩 에이전트에 에이전트 코드를 맡기면 LLM이 판단할 일을 코드(룰베이스)로 바꿔 버리는 경향이 있다. 사례별로 보면 다음과 같다.

  • 삭제 버그 예: 새 대화에서 일정 ID를 몰라 삭제가 안 되는 버그는 시스템 프롬프트에 "조회 → ID 찾기 → 삭제" 흐름을 써서 푸는 문제다(→ 프롬프트 엔지니어링). 그런데 Codex, Claude Code에 "해결해 줘"라고 맡기면 별도 함수를 만들거나 룰베이스로 찾아 지우는 로직을 짠다. 그러면 에이전트를 만들었는데 실제로는 룰베이스로 도는 경우가 많다. 자연어 처리 영역은 최대한 툴 쪽으로 끌어와 에이전트 판단으로 동작하게 하라.
  • 1주차 베이스라인 리뷰: 헬퍼 함수를 많이 만들고 키워드 추출, 반복문 같은 룰베이스 구현으로 흐르는 경향이 보인다. 동작은 다 하겠지만, LLM이 프롬프트에서 직접 추출하게 할지 필터링 규칙을 둘지는 스스로 판단해 수준을 정하라. 코드가 얼마나 복잡하거나 간결한지도 체크하라.
  • 판단 기준: 예전엔 헬퍼, 인터페이스 함수로 데이터를 정리해 던졌지만, 지금은 Pydantic 클래스 하나를 만들고 description으로 조절할 수 있다. 다만 description만으로 다 되지는 않으니 ① 함수로 직접 변환하거나 ② LLM 성능을 믿고 맡긴다. 어느 쪽이 맞는지는 경험적으로 테스트해야 한다.
  • 실험 결과: 일정 에이전트 뼈대로 테스트해 보면 흔한 문제가 거의 다 나온다.

LLM이 처리할 수 있는 일을 코드로 만듦 에이전틱 vs 룰베이스 수준을 내가 결정
데이터 구조를 유지하지 못해 기능이 멈춤 CLAUDE.md만으로는 부족, 테스트를 설계해 잡는다

정리 동작한다고 끝이 아니다. "이 부분을 LLM이 판단하게 할지, 코드로 고정할지"는 에이전트가 아니라 내가 정한다.

"의도대로 됐는가"를 검증하기

  • 에이전트를 다룰 때 가장 중요하게 보는 것은 내가 가진 의도대로 동작했는지다. 베이스라인 코드도 "이렇게 짜야 한다"는 정답이 아니라 의도대로 구현됐는지 확인하는 기준이다.
  • 예: 구현이 Pydantic 대신 JSON으로 넘어오게 바뀌어 있어도 동작은 똑같다. JSON이든 Pydantic이든 모델에 넘어가는 건 결국 텍스트이기 때문이다. 문제는 동작이 아니라 의도와 다르게 구현됐다는 것이다. "툴콜에 Pydantic 필터를 써야 하는데 에이전트가 JSON으로 바꿔 버렸네" → 수정하고, 안 되면 롤백한다.
  • 생성 모델은 원래 의도대로 움직이기 어렵다. 이미지, 영상 생성하는 사람들도 수십, 수백 번 생성한다. 그래서 먼저 머릿속에 동작을 그리고, 결과가 "정답"이라기보다 "최선"인지 확인한다.
  • "일단 동작은 한다"가 함정이다. 트레이스로 최적화됐는지 직접 검증하라.
  • 테스트 케이스는 직접 설계한다(어떤 테스트를 어떤 결과로 통과해야 하는지). 구현, 검증 흐름을 강제하면 모델이 구현할 때 사용자 컨펌(승인)을 구하게 된다.

테스트를 짧게 하다가 실습 코드 버그를 놓친 사례는 → 주차별 실습 프로젝트에 정리했다. 평가 설계 자체는 → 에이전트 평가와 LLM-as-a-judge에서 다룬다.

나만의 스킬, 문서로 규칙 관리하기

  • 예전엔 Git 수칙 같은 주의사항을 직접 기억해야 했다. 지금은 이를 마크다운 문서나 스킬로 만들어 Claude Code, Codex에 넣어 두면, 도구가 작업할 때 한 번씩 체크하고 넘어간다.
  • 남이 만든 스킬을 써도 되지만, 내 작업에 최적화하는 방향으로 직접 만들어 가는 연습이 코드 스타일을 잡아 준다. 문제가 생겼을 때 고치기도 쉽다.
  • 나만의 스킬을 최대한 많이 만들어라. 앞으로 누적해야 할 것은 스킬, 에이전트 구현 방법론, 모델을 컨트롤하는 나만의 방법이다. 문제 해결 방식을 적고 "스킬로 저장해 줘"라고 하면 저장된다.
  • Superpowers 같은 인기 스킬, 플러그인을 그대로 쓰지 말고, 어떻게 구현됐는지 보고 내 상황에 맞게 넣고 빼라. 안 그러면 토큰만 날아간다.
  • 퓨샷이 가장 강력한 프롬프트 기법이므로(→ 프롬프트 엔지니어링), "LangChain 에이전트 구현은 이런 패턴으로 해 줘" 같은 패턴을 스킬로 묶어 두면 매번 코드 예시를 주지 않아도 된다. 이 트릭은 LLM 웹서비스에서도 쓸 수 있다.
  • 스킬을 로컬 MCP 서버에 모아 두고 Claude Code, Codex에서 툴로 그때그때 불러 쓰는 방식도 가능하다. 스킬은 프로젝트 전용이나 전역으로 둘 수 있다.

스킬이 컨텍스트에 들어가는 방식은 "스킬을 툴로 구현"해 보면 이해하기 쉽다. description을 보고 툴이 선택될 때 MD 내용이 컨텍스트에 추가되는 구조다.

(파일명은 예시)

@tool
def load_writing_skill() -> str:
    """에세이를 쓸 때 따라야 할 작성 규칙을 불러온다."""   # 모델은 이 설명을 보고 선택한다
    return open("essay_skill.md", encoding="utf-8").read()  # 선택될 때만 MD 내용이 컨텍스트에 들어간다

정리 반복되는 지시, 예시, 수칙은 스킬로 묶는다. 단, 남의 스킬은 뜯어보고 필요한 것만 남긴다.

CLAUDE.md, AGENTS.md와 /init, /context

  • CLAUDE.md(Claude Code)와 AGENTS.md(Codex)는 코드 에이전트가 동작할 때 참고하는 지침 문서다. 시스템 프롬프트까지는 아니지만 프롬프트로 들어간다. 둘은 이름만 다르고 역할이 같다.
  • 이 파일을 튜닝하는 것이 에이전트를 제어하는 첫걸음이다. 튜닝은 직접 글을 써서 고치는 방법과 모델에게 "이런 형식으로 바꿔줘"라고 시키는 방법을 모두 포함한다.
  • 과제나 작업을 시작할 때 Claude Code를 켜고 "분석해서 해 주세요"라고 하기보다, CLAUDE.md에 어떻게 구현해 달라고 적고 실행하는 게 훨씬 좋다.
  • 넣을 내용 예: 학습 자료 요약, 필수 코드, RAG를 만드는 코드 정리, LangChain 문서를 참조해 동작하게 하는 지시. 그러면 모델이 스스로 판단하기보다 예제 기반 코드 스타일로 구현한다.
명령 하는 일
/init CLAUDE.md를 만들어 준다. 파일을 어느 정도 만든 뒤 써도 되고, 만들기 전에 써도 된다
/context 지금 로드된 MD 파일 등 컨텍스트 구성을 보여 준다
/doctor CLAUDE.md, 스킬이 너무 커졌을 때 모델이 스스로 검사해 정리한다
/compact 이전 대화를 중요한 내용 위주로 요약, 압축한다
  • CLAUDE.md는 매 세션마다 로드되고 위치에 따라 동작이 조금 다르다. 연습할 때는 프로젝트 최상단에 만든다. 생성된 파일은 직접 고쳐도 되고 프롬프트로 고쳐도 된다.
  • 이전에는 AGENTS.md와 CLAUDE.md를 공유해 같이 참조하게 하는 방법을 썼는데, 이후 업데이트로 적용하기 어려워졌다. MD 작성법조차 일주일 만에 바뀌는 분야라는 예시다.

Karpathy 기반 CLAUDE.md 4원칙과 프로젝트 맞춤 튜닝

Andrej Karpathy의 지침을 바탕으로 한 CLAUDE.md가 널리 공유됐다. 번역본으로 정리하면 4원칙이다. "어떻게 하면 코딩을 잘할 수 있을까"에 대한 일종의 철학이다.

원칙 뜻
1. 코딩 전에 생각하기 정확히 무엇을 만들지 먼저 정의한다
2. 단순함 우선 가장 단순하게, 최소한의 코드로 만든다
3. 수술적 변경 수술하듯 정밀하게, 수정 범위를 줄인다
4. 목표 중심 목표를 기준으로 진행하고 검증한다
  • 핵심은 추상화, 요청하지 않은 유연성, 기능에 붙는 추가 기능을 쓰지 않게 하는 것이다. 신나서 막 쓰다가 함수 몇 개 안 써도 되면 줄이게 한다. 이런 지침이 없으면 에이전트가 마음대로 함수와 이상한 인터페이스를 추가한다.
  • 4원칙은 큰 틀(전체 가이드라인)이고, 그 밑에 프로젝트에 맞춘 작은 주제(참고 사항, 진행할 때 체크할 부분)를 채워 넣는다. 그대로 넣고 돌리면 큰 효과가 없다.
    • 무엇을 만들지, 어디를 직접 구현할지 정의하지 않으면 에이전트에 "끌려가게" 된다.
    • 한꺼번에 많은 코드를 넣기보다 최소 코드로 만들고, 수정이 필요하면 확인 후 수정하도록 지시한다.
    • 테스트 케이스를 직접 설계해 넣는다.
    • 코드 스타일은 CLAUDE.md에 넣어도 되고 별도 스킬로 정의해도 된다. LangChain 문서나 Context7 같은 문서 로딩 플러그인을 쓰고 "에이전트 구현 시 그 파일을 참조하라"고 지시해도 된다.
  • 정답이라 생각하지 말고 직접 튜닝한다. "새로 코딩하는 방법이 하나 추가됐다"고 생각하면 된다. 직접 쓰기 어려우면 "이런 지침을 추가하고 싶은데 어떻게 넣으면 좋겠냐"고 물어본다(이것도 플랜이다).
  • 웹 LLM에는 자료를 매번 붙여 넣어 퓨샷으로 요청할 수도 있지만, 반복해서 쓸 내용은 MD 파일로 정리해 두는 편이 낫다. 꼭 CLAUDE.md가 아니어도 그때그때 참조할 MD 파일이나 스킬로 만들어도 된다. 플러그인, 스킬부터 쓰기보다 MD 파일을 직접 튜닝해 보는 것이 먼저다.
  • 활용 맥락: Claude Code를 쓰는 경우는 결국 다른 분야나 코드에 코드 에이전트를 붙이는 작업이다. 도시공학, 이상탐지(머신러닝, 통계 방식, 정형, 비정형 데이터)처럼 데이터를 어떻게 처리할지를 지침으로 구성하면 된다.

팁 권장 실습: Karpathy 가이드라인을 바탕으로 CLAUDE.md(또는 AGENTS.md)를 프로젝트에 맞게 고친 뒤, 그 상태로 만든 코드를 기존 코드와 비교해 본다.

"그때 vs 지금": 모델이 똑똑해진 뒤의 CLAUDE.md 원칙

처음에는 "지침을 직접 튜닝하라"는 흐름이었는데, 이후 Anthropic이 CLAUDE.md 작성법을 바꾸는 글(7월 24일)을 내면서 방향이 달라졌다. 번역본의 비교표는 다음과 같다. Opus 5, Fable 모델을 대상으로 한 글로 읽힌다(자세한 배경은 → 컨텍스트 엔지니어링과 하네스).

그때 지금 해석
규칙(rule)을 준다 Claude의 판단에 맡긴다
구현 예시를 준다 인터페이스를 설계한다 코드 구현체보다 "에이전트는 create_agent로 만든다" 같은 설계를 준다
모든 데이터를 넣고 시작한다 컨텍스트를 비운 채 시작한다 스킬, 코드, 툴 description을 미리 넣지 말고 서브에이전트나 툴콜로 필요할 때 불러오게 한다
반복으로 강조한다 심플하게 쓴다 이제는 간단한 tool description만 넣어도 알아서 잘 가져온다
메모리를 직접 지정한다 auto memory에 맡긴다 예: "커밋해 줘" 하면 diff를 보고 메시지를 넣어 커밋하는 방식을 스스로 저장한다
스펙 문서 rich reference 단순 스펙 대신 문서를 참조하게(RAG처럼 필요한 값을 가져오게)
  • 근거로 읽은 문장은 "80%를 삭제해도 성능이 유지됐다" 였다. 더 좋아진다기보다 굳이 안 써도 된다는 뜻이다. 결론은 "모델이 똑똑해졌으니 규칙을 빼라", "컨텍스트를 비우고 시작하라".
  • 모델 회사 쪽은 "건드리지 마라", 사용자 쪽은 "우리 의도대로 하고 싶다"는 입장이라 계속 화두가 될 것이다.
  • 실전 방식은 코드 레벨 구현에서는 세세한 가이드를 프롬프트로 주고, MD 쪽에는 프로젝트 정도의 제약만 두는 것이다. 결국 코드 레벨에서 세세한 가이드를 주라는 뜻으로 읽을 수 있다.
  • 컨텍스트를 비우는 것 자체가 예전부터 성능에 크게 도움이 되는 원칙이었으니 이 흐름에 맞추는 게 최선이다. 다만 Codex 등 다른 에이전트에 어떤 영향을 줄지 모르니 우선 Claude에만 적용해 본다.
  • 이 흐름은 "LLM을 믿는 쪽으로 가고 있다"고 정리할 수 있다. "CLAUDE.md를 최소화하라"는 것도 "Claude Code가 알아서 하게 둬라"에 가까워지는 흐름이다.

정리 처음엔 지침으로 에이전트를 붙잡으라고 배웠고, 모델이 좋아진 뒤엔 지침을 가볍게 하고 세부 통제는 그때그때 프롬프트로 주는 쪽으로 옮겨 갔다.

컨텍스트 윈도우 구조와 CLAUDE.md 경량화, /doctor

해당 글의 컨텍스트 구조 그림은 우리 프롬프트가 제일 위에 있고, 그다음 레퍼런스, 시스템 프롬프트, CLAUDE.md, 스킬, 메모리 순으로 들어간다. 성능 측면에서는 프롬프트와 메모리, 스킬이 강하게 작용하는 구조로 볼 수 있다.

구성 요소 권장
CLAUDE.md 전체 목적 같은 내용은 스킬, 메모리, 레퍼런스에 많이 들어가니 최대한 가볍게, 최대한 줄인다
시스템 프롬프트 가장 강력한 맥락. CLAUDE.md보다 여기에 공을 들인다. 하네스를 만든다면 시스템 프롬프트로 인식시킨다(Claude 자체 시스템 프롬프트인지 사용자가 넣는 것인지는 확인이 필요하다)
레퍼런스 우리가 추가로 주는 코드, 문서 등. 툴 기반으로 그때그때 프롬프트를 잘 실행할 수 있게 하는 정보
메모리 알아서 저장한다
스킬 꼭 필요한 것만 추가한다
  • 결론: MD 파일에 데이터를 너무 넣지 말고, 시스템 프롬프트와 레퍼런스를 잘 전달하도록 구조를 바꾼다.
  • /doctor: 해당 폴더에서 실행하면 모델이 스킬, 불필요한 플러그인 등을 정리하고, CLAUDE.md와 스킬을 검사해 적정 크기로 만들어 준다. 먼저 기존 MD 파일을 백업해 두고 Opus나 Fable로 정리한다. MD를 잘 정리하는 건 확실하지만 구현을 얼마나 잘하는지는 더 써 보며 확인해야 한다.
  • Codex도 플러그인, 스킬이 많으면 이를 2K 정도로 요약해 컨텍스트를 정리한다.
  • MCP, 플러그인도 같은 문제다. Claude Code나 Codex에 플러그인, MCP를 여러 개 연결해 두면 툴 이름, 설명, 인자가 미리 들어가서 "이미 요만큼 컨텍스트를 먹고 시작해 사실상 손해"다. 필요한 것만 연결하라 (→ MCP와 A2A).

컨텍스트를 아끼는 작업 습관

Claude Code 해커톤 우승자 인터뷰에서는 서브에이전트, 훅(human-in-the-loop 확인, 중단), MCP 관리, 플러그인이 언급됐다. 물리적 환경은 편한 걸 쓰면 되고 중요하지 않다. 그중 거듭 강조된 항목이 "컨텍스트를 잘못 쓰면 모델 성능이 뚝뚝 떨어진다"였다. 이론은 → 컨텍스트 엔지니어링과 하네스에서 다루고, 여기서는 도구를 쓸 때의 습관만 모은다.

  • 한 단계 작업이 끝나면 내용을 마크다운 파일로 정리하고 새 대화에서 그 파일로 이어 간다. 작업 단위가 줄고 토큰도 아낀다.
  • 목표 하나를 달성하면 새 컨텍스트를 만든다. 요약해서 계속 이어 가는 것보다 새로 시작하는 쪽이 손실이 적다. 쓰는 툴, 스킬 양도 줄인다.
  • /compact로 압축해 정리한 뒤 컨텍스트를 비운 상태에서 다시 시작하면 성능이 더 좋다.
  • 컨텍스트를 더 자주 압축해 보는 등 사용법을 직접 실험해 보라.

Claude Code의 서브에이전트

  • 메인 에이전트가 서브에이전트에 작업을 할당하면 컨텍스트가 분리되어 성능을 유지하기 쉽다. 코딩 툴에서 컨텍스트 관리에 따라 성능 차이가 크게 나기 때문에 서브에이전트를 별도 주제로 다룬다.
  • 싱글 에이전트가 툴콜로 쉽게 구동되자 이를 이용한 서브에이전트 방식이 나왔고, 이를 잘 정립하고 사실상 상용화한 것이 Claude Code라고 볼 수 있다.
  • Claude Code 서브에이전트는 툴콜 방식 서브에이전트와 같은 방식이다(→ 서브에이전트, 멀티에이전트, 워크플로). 툴콜 기반이라 에이전트, 서브에이전트는 항상 병렬 처리가 가능하다.
  • 문서상 최대 5번까지 중첩된다(서브에이전트가 또 서브에이전트를 만드는 식). 직접 구현할 때도 넣을 수는 있지만 너무 촘촘해져 실제로 그렇게까지 쓰지는 않는다.
  • 보통은 프롬프트만 잘 입력해도 서브에이전트가 수행된다. 예: "Sonnet 모델로 이것들을 조사해 줘". 결과는 툴콜 방식이나 report로 공유되는데, 그 report가 컨텍스트로 오는지 MD 파일인지는 확인이 필요하다.
  • 비용: 하위 에이전트로 많은 일을 시키면 서브에이전트들이 각자 컨텍스트를 갖고 돌기 때문에 메모리 사용량이 폭발할 때가 있다. 컴퓨터가 느려지고 뜨거워진다. 너무 많이 만드는 건 좋지 않다.
  • Claude Code에서 서브에이전트가 돌도록 직접 입력해 보거나 스킬을 작성해 보는 것을 권한다.

비유 서브에이전트에 일을 맡기는 건 팀장이 업무 지시하는 것과 같다. 적극 쓰면 토큰은 순식간에 없어지지만 일을 금방 처리할 수 있다.

Claude Code의 에이전트 팀(Agent teams)

  • 처음에는 설정에서 실험(experimental) 옵션을 켜야 했지만, 이후 문서에서는 별도 설정 없이 쓸 수 있게 바뀌었다.
  • 서브에이전트와 달리 멀티에이전트 방식(Swarm과 비슷)이다. 문서에는 teammate 간 communication, shared task가 나온다. 메인 에이전트 아래 공통으로 해결할 shared task가 있고 각 부분을 다른 에이전트가 맡는다.
  • 서로의 커뮤니케이션은 MD 파일로 이뤄졌고, 최근엔 직접 쿼리로 주고받을 수도 있다. Claude 임시 폴더에 파일이 만들어졌다가 세션이 끝나면 삭제되는 경우도 있다.

CLI로 다른 모델, 도구를 섞어 쓰기

  • Claude Code는 원래 CLI(커맨드라인 인터페이스) 기반이고, Codex, Antigravity, Gemini도 모두 CLI가 있다. OpenAI는 Claude Code용 Codex 플러그인을 공식으로 만들어 뒀다.
  • CLI에는 플래그(예: 권한 bypass 여부)를 줄 수 있고, 이를 조합하면 CLI로 바로 명령을 줄 수 있다.
  • Claude Code 안에서 다른 CLI를 호출하도록 스킬을 만들 수 있다. 예: "검색하는 태스크는 Antigravity로 해 줘"라고 하면 스킬을 통해 해당 CLI가 불린다.
  • 서브에이전트나 팀메이트가 불릴 때 Claude 모델이 CLI 명령을 실행하고 결과를 보고 답한다. 서브에이전트가 Sonnet이든 Haiku든 bash로 다른 모델 CLI만 실행하면 여러 도구를 함께 쓸 수 있고, 그 모델의 토큰으로 답을 얻으니 토큰이 절약된다.
  • 여러 모델을 쓰는 방식은 두 가지다. ① 메인 LLM을 정하고 특정 태스크만 다른 모델로 처리 ② MoA처럼 한 질문을 여러 에이전트에 동시에 주기. ②는 비효율적이고, 서브에이전트마다 다른 모델 CLI를 주거나 팀메이트를 구성하는 방식이 실용적이다.
  • 환경 예: Claude Code에 GLM 모델을 연결해 claude와 claude-glm처럼 따로 실행하고, 스킬, MD로 "계획은 Claude, 구현은 GLM"처럼 나눈다. alias, Ollama로 로컬 모델을 붙이는 법과 모델 분업 파이프라인은 → 모델 고르기와 여러 모델 조합에서 다룬다.

Git 브랜치로 병렬 개발하고 모델 분업하기

  • 병렬 처리 구현에는 Git을 쓰는 방식이 가장 보편적이다. 서브에이전트들은 대부분 같은 기능이 아니라 서로 다른 기능을 병렬로 만들기 때문에, 기능마다 Git 브랜치를 하나씩 만들어 각 브랜치에서 구현하게 한다.
  • 한 폴더에서 브랜치를 여러 개 나눠 기능을 동시에 구현하고, 나중에 메인 에이전트가 커밋을 보고 브랜치를 머지한다. 토큰은 많이 쓰지만 여러 기능을 동시에 만들어 붙일 수 있다.
  • Codex는 이렇게 브랜치를 만들어 처리하는 데 가장 특화돼 있고, Claude Code는 하나의 기능을 만드는 데 더 특화돼 있는 느낌이 있다. 물론 둘 다 가능하다.
  • 분업 원칙: 복잡한 작업은 좋은 모델, 가벼운 작업은 작은 모델. 좋은 모델이 기획하고 상대적으로 작은 모델이 직접 코딩하는 식으로 나눈다.
main ──┬── 기능 A 브랜치 ← 서브에이전트 1 ──┐
       ├── 기능 B 브랜치 ← 서브에이전트 2 ──┼── 메인 에이전트가 커밋을 보고 main에 머지
       └── 기능 C 브랜치 ← 서브에이전트 3 ──┘

브랜치, 커밋 관례 자체는 → 개발 환경과 Git 협업에서 정리한다.

정답은 아직 없다: 사용 전략의 갈래와 도구 동향

  • Claude Code 사용자는 성향이 나뉜다.
    • Superpowers 같은 유명 스킬, 프롬프트 모음파: 기능 하나를 만들면 테스트를 돌리는 식으로 흐름을 가이드해 준다.
    • 직접 입력파: 원래 개발을 해 온 사람들. 그때그때 필요한 스킬, 프롬프트를 직접 넣고 토큰을 최대한 아낀다.
    • 루프파: 토큰이 넉넉한 사람들. 반복 루프 기능으로 멈추지 않고 계속 돌며 체크한다.
  • 전략도 갈린다. 토큰을 많이 녹일수록 좋다는 토큰 맥시, 모델을 나눠 쓰는 토큰 절약형(예: 검색은 Antigravity, 교차 검증은 Claude Code와 Codex), 모델 레벨을 나눠 스킬로 만드는 모델 레벨 분리. 어떤 게 정답인지는 아직 알기 어렵다. 중요한 건 무엇을 만들고 싶고 어떤 전략으로 접근할지다.
  • 도구 동향: 최근 loop, goal 같은 기능이 Claude, Codex 등에 업데이트됐다. 입력해 둔 목표를 달성할 때까지 동작 → 달성 여부 체크 → 다음 단계 분기를 반복하는 ReAct와 비슷한 구조다. Antigravity도 비슷한 형태를 갖췄다.
  • 하네스, 에이전트 도구에는 정답이 없다. 남의 말보다 직접 써 보고 평가하고, 안 맞으면 버리고 다시 쌓아라. Claude Code, Codex 등 유명 도구는 한 번씩 써 보고, 스킬을 직접 만들어 토큰 소모량 등을 정리해 보면 빨리 성장한다.
  • 모델 API로만 구현해도 되지만 가능하면 Claude Code를 써 보며 "내 스타일에 맞게 툴을 맞춰 나가는 시간"을 가지는 것이 좋다.

정리 도구 사용법은 일주일 만에도 바뀐다. 특정 설정을 외우기보다 "컨텍스트를 아끼고, 작게 쪼개고, 의도대로 됐는지 검증한다"는 원칙을 들고 직접 실험하라. 학습 태도는 → 현업 조언과 학습 태도에서 이어진다.

.env와 .env.example, PROXY_TOKEN

  • .env는 API 키, 인증서, SSH 접근 정보, DB 비밀번호, 액세스 토큰 같은 민감 정보를 담는 로컬 파일이다. 코드에서는 .env를 불러와 "키 값"으로 실제 값을 읽는다.
  • 이름은 다양하게 둘 수 있다. .env 하나에 다 넣거나, .env.local, .env.dev(개발), .env.production(배포)처럼 환경별로 나눈다.
  • .env.example은 "코드가 이 키들을 쓸 테니 각자 값을 채워라"는 견본이다. 이름을 용도에 맞게 바꾸고 키 값을 직접 넣어 쓴다.
  • 실습용 .env는 PROXY_TOKEN만 직접 채우면 된다. 프록시 URL, 임베딩 프록시, 임베딩 모델 같은 나머지 값은 미리 채워져 있다. 키는 다른 사람과 공유하면 안 된다.

1주차 노트북의 "준비" 셀은 .env에서 토큰, URL, 모델명을 불러와 모델을 만든다. OpenAI 키를 직접 쓰면 api_key만 주면 되지만, 이 실습은 요청을 모아 응답해 주는 프록시 서버를 쓰므로 base_url을 함께 지정한다.

(변수명, import 경로는 일반적 사용법 기준)

import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI

load_dotenv()                                   # .env의 키 값을 읽어 온다

def make_model(temperature=0, max_tokens=None):
    return ChatOpenAI(
        model=os.getenv("<모델명 키>"),
        api_key=os.getenv("PROXY_TOKEN"),       # 각자 발급한 키
        base_url=os.getenv("<프록시 URL 키>"),   # 프록시 서버 주소
        temperature=temperature,                # 답변의 다양성
        max_tokens=max_tokens,                  # 답변 길이 상한
    )

temperature, max_tokens의 의미는 → Transformer 블록 해부에서 다룬다.

  • 2주차 과제 코드의 config에는 API 키가 없으면 오류를 내는 안전장치가 들어 있다.
  • Colab 실습(OpenAI Function Calling.ipynb)은 개인 API 키로 만든 예제라, 환경 설정에 등록한 프록시 서버 값을 넣으면 동작할 것이다.
  • 외부 서비스 키도 같은 원칙이다. Tavily MCP처럼 API 키가 필요한 서버를 붙이거나, 노트북에서 띄운 MCP 서버를 Claude Code에 등록할 때도 필요한 변수를 따로 넣는다 (→ MCP와 A2A).

uv로 가상환경과 패키지 설치

  • 파이썬은 프로젝트마다 가상환경(conda, 로컬 파이썬 등)을 만드는 게 보통이라 커널 연결이 골치 아프다. 요즘은 pip보다 uv 같은 패키지 관리 도구를 많이 쓴다.
  • 이 실습은 uv로 실습 환경과 파이썬(3.10) 환경을 세팅한다.
  • setup 셸 스크립트가 pyproject.toml 기준으로 전체 패키지를 설치하고 uv sync로 ipykernel, Jupyter 커널을 만든다. 설치가 끝나면 "커널이 만들어졌다"는 메시지가 뜬다.
  • 모듈 설치가 안 되면 해당 패키지를 따로 설치해도 된다.
  • 뒤 주차에서 쓰는 패키지도 기본 환경에 미리 들어 있다. 예: 5주차의 langchain-mcp-adapters는 기본 환경 설정에 포함돼 있다.

Jupyter 커널을 .venv에 연결하기

  • 노트북은 마크다운으로 된 텍스트 셀과 코드 셀로 이뤄진다.
  • IDE에서 .ipynb를 열면 오른쪽 위에 커널 선택 칸이 생긴다. 이 실습에서는 "카나메이트" 커널(프로젝트 .venv)을 쓴다. 서버를 따로 띄울 필요는 없고, 로컬에서 Jupyter Notebook/Lab을 띄워도 된다.
  • 노트북이 프로젝트 .venv에 연결되지 않으면 모듈을 못 찾는다. 커널이 안 보이면 "다른 커널 선택"에서 실제 파이썬 환경을 찾아 연결한다.
  • 셀 실행은 Shift+Enter(또는 Ctrl/Cmd+Enter), 전체 실행은 Run All.

주의 노트북 셀을 그냥 다시 실행하면 문제가 되는 경우가 있다. 4주차 ChromaDB 셀은 같은 이름의 컬렉션을 또 만들려다 런타임 오류가 난다. 시연 중 오류가 나면 처음부터 다시 실행하는 것이 확실하다. 꼬이면 커널을 재시작하고 위에서부터 다시 돌린다.

.gitignore: 올리면 안 되는 파일부터 막기

  • .gitignore에 커밋되면 안 되는 파일을 적어 두면 그 파일은 푸시되지 않는다(GitHub에 안 올라간다). 과제 저장소에도 이미 들어 있다.
  • 프로젝트를 Git, GitHub에 올릴 때 가장 먼저 하는 작업이 .gitignore 구성이다. 이게 끝나야 공유해도 민감한 파일이 제외돼 안정적으로 쓸 수 있다.

(일반적인 형태의 예)

.env
.env.*
!.env.example
.venv/

키가 유출됐을 때: 지워도 남는다, 폐기하고 재발급

  • 실수로 .env를 커밋하면 나중에 지워도 커밋 기록(히스토리)에 남을 수 있다.
  • 그래서 원칙적으로 올라간 API 키, 토큰, 비밀번호는 모두 폐기하고 새로 발급해야 한다. 푸시 후 삭제해도 기록에 남아 있을 수 있으니 항상 주의하고 확인하라.

주의 키가 올라갔다면 "파일 삭제 커밋"으로 끝내지 말고 키를 폐기, 재발급한다. 사고를 막는 첫 단추는 프로젝트 시작 시 .gitignore를 먼저 세팅하는 것이다.

커밋은 세이브 포인트: 기능 단위로 나눠 커밋하기

  • git add + git commit은 "이 작업을 이렇게 했다"는 세이브 포인트를 만드는 행위다. 다 같이 프로그램을 만들 때 "내가 이 부분을 이렇게 수정했다"는 기록을 하나씩 남기는 것이다.
  • 쭉 개발하다 한꺼번에 밀어 넣기보다, 기능 하나를 만들 때마다 정리해 커밋하고 다음 기능으로 가는 연습을 하라.
  • 세밀한 팀은 수정한 파일을 하나씩 따로 add해 커밋한다. 기능별로 묶을지 파일별로 나눌지는 팀마다 다르다.
  • add한 뒤 커밋 메시지에 어떤 작업을 했고, 어떤 기능을 만들었고, 어디를 수정했는지 적는다.

(일반적인 명령 예)

git add <이번 기능에 해당하는 파일>
git commit -m "add login page"
  • 최근 코딩 에이전트는 "커밋해 줘"라고 하면 알아서 diff를 보고 메시지를 넣어 커밋하는 방식을 auto memory로 스스로 저장하기도 한다 (→ AI 코딩 도구 활용(Claude Code, Codex)).

브랜치로 기능을 만들고 메인에 합치기

  • 실제 작업은 브랜치를 만들어 진행하는 경우가 많다. 메인을 배포본, 완성본으로 두고, 기능을 개발할 때는 checkout으로 메인 기반의 브랜치를 딴다(예: "로그인 페이지 만들기").
  • 브랜치에서 기능을 완성하면 add, 커밋 메시지를 작성한 뒤 메인에 합친다. "브랜치 생성 → 기능 구현 → 메인에 합치기"를 반복해 큰 프로그램을 만든다.
  • 브랜치 이름과 커밋 메시지는 마음대로 써도 되지만, 팀, 레포의 형상관리 규정에 정해진 규칙(fix, 기능 추가, refactor 같은 접두어)이 있으면 그대로 따른다.
  • 회사마다 코드 관리 문서, 규정이 있으니 그걸 공부하는 시간이 필요하다.
main ──── checkout으로 브랜치 생성 ──── 기능 구현, 커밋 ──── main에 합치기 ──── 다음 기능 브랜치 …

코딩 에이전트에 기능별 브랜치를 하나씩 맡겨 병렬로 만들고 메인 에이전트가 머지하는 방식은 → AI 코딩 도구 활용(Claude Code, Codex)에서 다룬다.

실습 저장소를 운영하면서도 충돌 문제를 실제로 겪었다.

  • 구현 대상 파일(student_parts)에 정답 데이터 등을 함께 올리면 conflict가 날 수 있어, 베이스라인(정답 코드)을 별도 위치로 분리했다.
  • 이미 구현한 파일이 있는 상태에서 과제 코드 버그를 고칠 때도 원본 파일은 건드리지 않고 baseline에 추가되도록 업데이트했다.

팁 남이 작업 중인 파일을 직접 고치면 충돌이 난다. 업데이트는 별도 파일, 위치로 추가하는 편이 안전하다는 것을 실습 저장소 구성이 보여 준다.

Git 수칙을 문서, 스킬로 남기기

  • Git 사용 가이드는 MD 파일로 만들어 두면 좋다. 이런 주의사항을 스킬이나 시작할 때 참고 자료로 넣어 두면 AI 도구가 작업할 때 한 번씩 체크하고 넘어가기 때문이다.

누적 구조: join_system_prompt와 프롬프트 파츠

원래는 에이전트가 하나여야 깔끔하지만, 이 프로젝트는 1~6주차에 걸쳐 에이전트를 누적 구현한다. 그래서 주차마다 그 주차에 동작하는 에이전트가 따로 있고, 뒤 주차는 앞 주차의 툴, 프롬프트를 가져다 쓴다.

  • 기능이 대체되며 일부 프롬프트는 빠지기도 하므로 프롬프트를 쪼개 두었다. join_system_prompt는 프롬프트 리스트를 받아 내부에서 합쳐 시스템 프롬프트를 만든다.
  • 뒤 주차에서도 재사용할 파트(1주차 프롬프트 등)와 그 주차에서만 쓸 파트를 구분하고, 재사용 파트는 *(언패킹)로 펼쳐 넣는다.
  • 예: 에이전트는 현재 날짜를 모르므로 시스템 프롬프트에 날짜를 넣는데, 누적된 프롬프트를 그대로 가져가면 날짜가 그냥 찍혀 버린다. 이런 것을 필요에 따라 넣고 빼려고 나눴다.
  • 그래서 1주차부터 모든 프롬프트를 week1 프롬프트 파트에서 완성하는 구조다. 시스템 프롬프트를 쓸 곳이 두 군데인데 어디에 써도 되지만, 뒤 주차가 그 파트를 가져다 쓰기 때문이다.
  • 툴도 함수로 만들어 뒤 주차에서 공유, 재사용한다. 뒤로 갈수록 안 쓰는 툴이 생길 수 있지만 감안하고 진행한다.
  • 테스트는 이 파트에 프롬프트를 넣어 보며 하는 게 가장 편하다.

1주차: 나나를 깨우다 (Tool, Function Calling)

노트북 구성

  • 준비: .env에서 토큰, URL, 모델명을 불러오고 make_model로 ChatOpenAI를 만든다(프록시 서버라 base_url 지정, → 개발 환경과 Git 협업). show_json, final_text, tool_trace 같은 헬퍼로 에이전트가 정상 동작하는지 추적, 출력한다.
  • 기본 개념 실습: 파이썬 함수에 @tool로 이름, description을 붙이고, create_agent로 nana_basic_agent를 만들어 invoke한다. 결과로 최종 답변과 툴 트레이스(tool_call 이벤트, 툴 이름, 모델이 뽑은 인자, 툴 반환 JSON)를 본다.
  • 카나메이트 확장 예제: 툴 리스트에 일정 생성, 조회(list), 삭제(delete) 툴을 함께 넣는다. 조회는 저장된 스케줄을 그대로 반환하고, 삭제는 등록 때 받은 스케줄 ID로 매칭해 지운다(ID를 정확히 넣어야 삭제됨). 마지막 셀은 프롬프트별로 기대한 툴이 불렸는지 룰 기반으로 체크한다.

  • 툴 3개(생성, 조회, 삭제)의 빈칸을 채우고, 툴 애너테이션에 이름, description을 쓴다. 그 description이 모델로 전달된다. 주로 채울 곳은 툴콜 3개와 프롬프트 엔지니어링 부분이다.

  • 시스템 프롬프트 예는 툴별 사용법과 삭제 3단계 워크플로를 적은 형태다 (→ 프롬프트 엔지니어링).
# 역할
너는 카나, 사용자의 개인 일정을 관리하는 어시스턴트야.
## 일정 등록
- personal_create_schedule을 사용해 사용자 요청에 따라 일정을 등록해 줘.
## 일정 조회
- personal_list_schedules를 사용해 조회해 줘.
## 일정 삭제: 사용자가 삭제를 요청하면 아래 지시대로 처리해 줘.
1. personal_list_schedules로 일정을 조회한다.
2. 사용자가 삭제 요청한 일정의 ID를 찾는다.
3. personal_delete_schedule로 일정을 삭제한다.
  • 반환 구조가 원하는 대로 안 나오면 description에 입력, 출력 퓨샷 예시를 넣는다(예: 입력 "내일 멘토랑 개발 미팅 잡아줘" → 출력 {"title": "개발 미팅", ...}). 툴을 언제 고르고 어떤 형태로 리턴할지가 분명해져 선택 정확도가 오른다.

  • 툴을 구현하기 전 초기 상태에서는 "안녕" 같은 일반 대화만 되고 일정 등록은 안 된다.
  • 1주차 베이스라인은 구현 대상 3개가 모두 툴이고, 스케줄을 딕셔너리로 만들어 저장, 전달하는 구조다.

2주차: 자연어를 구조화된 요청으로 (Pydantic)

노트북 구성

  • 공통 환경 설정, 데이터 확인 셀 → Pydantic 클래스 기본 개념(BaseModel, Field(description), docstring, Literal) → 단일, 중첩 클래스 → 카나메이트 확장 예제(2주차 구조).
  • 단일 클래스 한계 예: ScheduleCreate 하나에 일정 2건을 넣자 JSON 디코드 오류(Extra data)가 났고, schedules: list[ScheduleCreate]를 가진 래퍼 클래스 ScheduleList를 response_format으로 지정하자 깔끔하게 순회할 수 있었다.
  • Field(ge=1, le=3)로 중요도 star를 추가하면 "중요한 약속이다"라는 입력에 star=3이 나오고, ToolStrategy, ProviderStrategy 전략도 지정해 볼 수 있다.
  • 개념은 → 구조화된 출력과 Pydantic에서 자세히 다룬다.

구현 포인트

  • 1주차는 "툴 기반 동작 + 자연어 답변"이었고, 2주차는 그 사이에 구조화된 출력이라는 중간 단계를 만든다.
  • 필수 구조는 요청 1건 스키마 StructuredRequest와 이를 리스트로 담는 StructuredRequestBatch 두 개다. 필드는 종류, 제목, 날짜, 시간, 종료 시간, 멤버, 원본 프롬프트 등이다.
  • 각 필드 description을 쓴다. 이미 적힌 description은 참고용이라 자유롭게 바꿔도 된다. 날짜는 실행일 기준으로 저장한다.
  • Week2 에이전트는 1주차 시스템 프롬프트, 툴을 재사용한다. 이후 주차의 데이터 요청용 툴 파트는 이번엔 제외한다. 핵심 구조는 유지하되 필요하면 함수 추가나 구조 변경도 해 볼 수 있다.
  • 모델은 오늘 날짜를 모르므로 시스템 프롬프트나 툴로 오늘 날짜를 주입해야 한다. 1주차에는 OS 시간을 반환하는 함수로 가져왔다.
  • 트레이스에서 tool call과 content가 찍히고 마지막에 structured_response가 생긴다. 예: 종류=개인 일정, 제목=개발 미팅, 날짜=7월 8일, 시간=10시, 종료=미정, 참여자=민수. 구조화된 출력을 지정하지 않으면 structured_response 자체가 생기지 않는다.

(클래스, 변수명은 예시)

class ScheduleRequest(BaseModel):
    """사용자가 요청한 ..."""                        # 클래스 docstring = 동작 설명
    kind: RequestKind = Field(description="...")
    title: str | None = Field(default=None, description="일정 혹은 약속의 제목")
    date: str | None = Field(default=None, description="...")
    start_time: str | None = Field(default=None, description="...")
    end_time: str | None = Field(default=None, description="...")
    members: list[str] = Field(default_factory=list, description="일정 참여 멤버")

class ScheduleBatch(BaseModel):                      # 배치 클래스: 클래스의 리스트
    requests: list[ScheduleRequest] = Field(default_factory=list,
                                            description="사용자가 정한 일정의 리스트를 저장")
  • config에는 API 키가 없으면 오류를 내는 안전장치가 있고, tools는 week1 툴 목록을 그대로 반환한다(week2 자체 툴은 없고 week3 이상에서 쓰는 툴 자리만 있음).
  • 진행 팁: 실행 → 트레이스로 어떤 데이터로 파싱하는지 확인 → description, 프롬프트 수정. 클래스를 못 찾으면 클래스명을 프롬프트에 명시한다.
  • 추가 구현의 마지막 함수(Pydantic 데이터를 중간에 JSON으로 볼 수 있게 해 주는 모니터링용 함수)는 원래 없어도 되는 부분이었지만, 3주차 코드가 이 함수를 직접 호출하고 있어 필수 구현으로 올라갔다. 추가 구현을 하지 않아도 3주차는 동작한다.

3주차: 나나의 기록장을 만들다 (툴 입력 검증과 SQLite)

노트북 구성

  • Pydantic 검증: 요청 클래스에 source_text, kind, title, 시작/종료 시간, 날짜, members, priority, reason 등 필드. kind에 허용값(예: personal_schedule)을 넣으면 정상, "meeting"을 넣으면 검증 오류. 자유 문자열 priority를 Literal["low","medium","high"]로 바꾼다.
  • SQLite 확장 예제: sqlite3.connect(db_path) → CREATE TABLE → 툴이 추출한 데이터를 execute()로 INSERT. 툴은 name, description, args_schema=Pydantic 입력 클래스로 구성한다.
  • 노트북 뒤쪽 체크 셀: 특정 프롬프트의 기대 출력을 고정해 두고 제약대로 나오는지 확인한다(프롬프트를 바꾸면 통과 안 될 수 있음).
  • 앱 상세 페이지 예: "지금 일정이 뭐가 있어?" → list 툴, "내일 10시 민수와 1:1 미팅 취소" → list → delete 순으로 호출.
  • 설계 흐름과 개념은 → 툴 입력 검증과 SQLite 저장에서 다룬다.

구현 포인트

  • Pydantic 클래스로 툴 입력을 검증하고, 파싱된 일정을 SQLite에 저장, 조회, 수정, 삭제하는 함수를 구현한 뒤 에이전트를 구성, 테스트한다.
  • 프롬프트를 일부러 두 개로 분리했다. week3 조회, 검색 규칙 프롬프트와 툴을 조정하는 프롬프트다. 수정할 때는 각각 해당 위치에서 고친다.
  • 검증 스키마는 아래쪽 클래스로 제공되며, 2주차에 구현한 Request 클래스를 누적해 가져다 쓴다.
  • 저장, 불러오기 함수를 구현한 뒤 아래에서 불러 데이터를 지우고 다시 돌려 보는 흐름으로 만들면 SQL 저장까지 구현된다.
  • 완료 기준: 노트북에서 배운 기본 기술(툴 구조, Pydantic 필터 등)을 적용해 구현하면 된다. DB 관련 코드는 fixed 쪽에 많이 숨어 있으니 분석 요청으로 동작만 확인한다.
  • 3주차 베이스라인은 student_parts와 충돌하지 않게 별도 위치에 두었다.

4주차: 나나가 기억을 찾아오다 (RAG, ChromaDB)

노트북 구성

  • ChromaDB 클라이언트 → 임베딩 함수(키, 프록시, small 임베딩 모델) → memory_collection 생성 → add → query → 검색 툴 순서다. 같은 이름의 컬렉션을 다시 만들면 런타임 오류가 난다.
  • 실행 예: 아래쪽에 등록해 둔 프로젝트 데이터를 검색했다. 툴 query에 "프로젝트 발표 일정"이 들어가자 발표 일정과 담당자를 답했다.
  • 노트북의 RAG 검색 툴을 예로, 하단에서 쿼리를 바꿔 검색하고 결과를 정리하는 부분에 LLM 정리 단계를 넣으면 리랭킹이 된다.
  • 개념(청크, top-k, 하이브리드 검색 등)은 → RAG: 임베딩 검색과 ChromaDB에서 다룬다.

(인자명은 예시)

client = chromadb.PersistentClient(path="...")                 # 로컬 저장(주로 사용)
embedding_fn = embedding_functions.OpenAIEmbeddingFunction(
    api_key=..., api_base=..., model_name="text-embedding-3-small")
memory_collection = client.create_collection(name="...", embedding_function=embedding_fn)
memory_collection.add(ids=[...], documents=[...], metadatas=[...])

@tool
def search_memory(query: str, n_results: int = 2) -> str:
    """query는 LLM이 사용자 프롬프트에서 뽑아 채운다"""
    found = memory_collection.query(query_texts=[query], n_results=n_results)
    return "\n".join(found["documents"][0])

구현 포인트

  • 예제는 노트북에 넣은 텍스트를 검색하지만, 프로젝트는 개인 참고자료(Personal Reference)와 SQL 저장 기록을 검색하도록 되어 있다.
  • 메인 구현 대상은 두 파트다. ① 참고자료 추가(저장) ② 참고자료와 SQL 저장 기록을 출처별로 검색. 이전에 Pydantic 검증으로 저장했던 데이터를 여기서 검색하게 하면 된다.
  • 저장소 정보(reference store 등)는 위쪽에 있다. 이전 SQL 저장 요청 부분은 fixed 파트에 구현돼 있고, 일반 채팅도 검색하도록 대화 저장 부분이 들어 있다. 아래에는 구조화된 출력과 TODO 파트의 스키마가 있다.
  • 검색 대상은 2, 3주차를 거치며 SQL에 구조화해 저장한 내용과 대화 목록(이전 채팅)이다. SQL에 저장이 안 돼 있어도 이전 대화를 했다면 그 대화를 찾아 검색할 수 있고, 다시 SQL에 저장할 수도 있다.
  • 툴이 여러 개라 의도대로 안 불릴 수 있으니 description 조정과 시스템 프롬프트 CoT 워크플로("SQL 결과가 없으면 대화 목록 검색")로 튜닝한다. 목표는 질문 한 번에 두 곳을 다 검사해 오게 만드는 것이다.

5주차: 카나가 지난대화를 불러오다 (MCP)

노트북 구성

  • 노트북 안의 예제는 "툴이 이미 있다"는 가정의 더미데이터로 진행한다. 주피터 안에서 서버를 돌리기 애매해서, 구조는 노트북에서 보고 실제 예제는 별도의 MCP 서버 파일과 클라이언트 파일로 본다.
  • 노트북 앞부분에 툴 이름+description 형태로 전체 툴이 정리돼 있다. "MCP의 메인은 툴"이라는 걸 보여 주는 장치다.
  • MCP 서버는 이미 구현돼 있다("외부 멤버 대화, 일정 SQLite MCP STDIO 서버"). 클라이언트는 async 함수 안에서 선언하고 get_tools()로 서버 툴을 가져와 에이전트 툴로 연결한다.
  • 노트북 후반에서는 기존 에이전트에 공개 MCP 서버(DeepWiki)를 추가로 붙인다. 처음엔 transport 키 누락 오류가 났고, 비동기 타이밍 문제로 MCP 툴 로딩까지 await로 기다리게 고쳤다.
  • 두 가지 버전이 있다. ① MCP 툴이 일반 툴과 같다는 걸 보여 주려고 툴로 감싸서 구현한 버전 ② MCP가 바로 동작하도록 연결한 버전.
  • 개념은 → MCP와 A2A에서 다룬다.

(import 경로는 표준 사용법 기준)

from langchain_mcp_adapters.client import MultiServerMCPClient

client = MultiServerMCPClient({
    "kana_sqlite": {"command": "python", "args": ["<서버 파일>.py"], "transport": "stdio"},
    "deepwiki": {"url": "<DeepWiki MCP 서버 URL>", "transport": "http"},
})
mcp_tools = await client.get_tools()                 # 툴 이름, description, 인자 목록
tools = [*existing_tools, *mcp_tools]                # 기존 툴 리스트에 합친다
agent = create_agent(model, tools=tools, system_prompt=SYSTEM_PROMPT)
result = await agent.ainvoke({"messages": [...]})

구현 포인트

  • 이미 만들어진 함수(MCP 서버 툴)를 불러 툴로 사용하는 부분을 구현한다. 1주차 내용을 MCP를 통해 툴콜로 하는 것과 비슷하다. LangChain이 복잡한 부분을 감싸 주니 실제로는 함수를 부르는 동작이다.
  • description은 미리 작성돼 있지만 튜닝이 필요하면 고쳐도 된다. 단, description을 바꾸려면 MCP 서버 쪽 파일을 건드려야 하며 그 부분은 따로 분리돼 있다.
  • MCP 서버를 직접 만들거나 Claude Code 같은 다른 에이전트에 등록해 보는 것까지는 이 과제의 범위가 아니다.
  • 프로젝트 코드는 여러 계층을 거쳐 MCP 툴이 에이전트에 들어가므로 트레이스가 어렵다. 그래서 노트북 예제로 "MCP 서버 → 툴 → 에이전트" 연결을 직접 확인해 두는 것이 좋다.
  • 구현할 부분은 대부분 프롬프트 입력 부분과 툴 description이다. 세부 함수보다 description, 시스템 프롬프트에 힘을 쏟고, 트레이스를 보며 다양하게 테스트한다. 예: 일정을 20~30개 등록해 보고 다시 기억하는지 묻기.

6주차: 카나메이트가 약속을 결정하다 (서브에이전트, LLM-as-a-judge)

노트북 구성

6주차 노트북 흐름은 다음과 같다.

  1. 서브에이전트 워크플로와 멀티에이전트 워크플로 그림 비교.
  2. 서브에이전트 예제: 원래 메인에 있던 툴 4개를 툴 1개짜리, 툴 3개짜리 서브에이전트 2개로 분리하고, 서브에이전트를 메인의 function tool로 등록한다. 메인 시스템 프롬프트에는 서브에이전트 역할을, 서브에이전트 시스템 프롬프트에는 실제 동작을 적는다.
  3. 미들웨어: Human-in-the-loop, 툴을 병렬로 여러 개 부르지 못하게 하는 미들웨어.
  4. 트레이스: 기본 트레이스는 슈퍼바이저 결과 기준이라 서브에이전트 내부 툴은 안 잡힌다. 서브에이전트 result를 따로 받아 계층별로 추적해야 한다.
  5. LLM-as-a-judge 평가: create_agent로 judge 에이전트를 만들고 judge context(질문, 정답, 생성 답, 툴 호출 트레이스)와 판정 규칙 프롬프트를 넣어 판정한다.

서브에이전트 구조는 → 서브에이전트, 멀티에이전트, 워크플로, 평가는 → 에이전트 평가와 LLM-as-a-judge에서 다룬다.

구현 포인트

  • 슈퍼바이저 에이전트를 구현해 나나, 카나 서브에이전트로 위임하게 한다. 그동안 만든 기능(RAG 검색, MCP로 불러오는 기능 등)을 서브에이전트로 이관, 분리한다.
  • 슈퍼바이저는 나나와 카나 두 개만 보게 하고, 각 서브에이전트가 자기 툴을 관리하게 한다. 툴을 다 만들어 두고 태스크에 따라 배치하는 방식이다. 에이전트가 반드시 다른 툴을 들 필요는 없지만 동작 제어를 위해 분리하는 경우가 많다.
  • 프롬프트는 타이트하게 쓴다. 노트북에 나나, 카나 시스템 프롬프트 칸이 나뉘어 있고, 이전 주차별 프롬프트를 불러와 조합해 완성한다.
  • 완료 기준: 메인 에이전트가 나나와 카나를 잘 구분해 호출하고 아래 툴들을 잘 불러오면 완료다.
  • 추가 구현: 필요한 툴 description과 info 필터링 부분 업데이트. 서브에이전트를 다뤄 코드가 길다.
  • UI 연결 부분(웹 store 저장, 에이전트 런타임에서 외부 데이터 받기)은 UI용이고, 실제 에이전트 구현에는 입력만 넘어오면 된다.

테스트 케이스 설계의 교훈

  • 두 버그 모두 휴먼 에러(테스트 설계 실수)였다.

    • week05: 테스트 문장이 모두 "내 일정" 기준이었다. 에이전트가 "내가 쓰는 스케줄 에이전트"라는 관점으로 만들어져 있다 보니 내 일정 없이 공유 일정만 조회하는 케이스를 테스트하지 않았다.
  • 컨텍스트(툴 트레이스 포함)를 불러와 검증했다면 잡혔을 문제다. LLM이 데이터를 찾고 검색하는 과정을 정확히 평가하지 못해 버그가 생겼다.
  • 교훈: 구현하려는 기능의 정확한 동작과 유저가 쓸 상황의 테스트 케이스 설계가 문제를 많이 잡아 준다. 얼마나 다양한 형태로 테스트하느냐가 중요하다. 팀원들과 다양한 사례를 의논해 적용하고, 다음 프로젝트에서는 어떤 케이스에서 에이전트가 오동작할지 예상해 대비한다.

정리 테스트 체크리스트: ① 짧은 대화만 하지 말고 길게도 돌린다 ② 트레이스만 보지 말고 벡터DB, SQLite 같은 실제 저장소를 직접 연다 ③ "내 것 없이 남의 것만" 같은 경계 케이스를 만든다 ④ 일정을 20~30개 넣어 보고 다시 기억하는지 묻는다.

다음 프로젝트로 가져갈 것: 6주차 포맷

  • 1~6주차가 누적 구현이라 1주차 에이전트의 잔재가 남아 코드가 복잡하다. 이후 에이전트를 새로 만들 때는 6주차 포맷(서브에이전트 구조)을 추천한다.
  • 1~5주차는 단일 에이전트 연습이었고 6주차의 핵심은 기능을 서브에이전트에 어떻게 분배하느냐다. 기능을 에이전트 하나가 다 처리하게 하지 말고 위임한다. 순서대로 부를지 기능별로 부를지 전체 구성을 기획하고, 서브에이전트가 어떤 순서로 불리는지 정리한다. 실제 구현은 "슈퍼바이저 안에 툴 2개" 정도로 심플해진다.
  • 결론: 다음 프로젝트에서는 서브에이전트를 염두에 두고 구현하고, 멀티에이전트는 컨텍스트가 얼마나 쌓이는지, 대화 턴이 얼마나 많은지를 보고 선택한다 (→ 서브에이전트, 멀티에이전트, 워크플로).
주제 5

현업 조언과 학습 태도

현업에서 통하는 조언을 주제별로 묶었다. 에이전트 개발을 대하는 태도, 빠르게 바뀌는 분야를 따라가는 법, 면접, 커리어 포인트, 다음 프로젝트 준비, LLM 이후 연구 동향까지 다룬다.

같은 조언이 여러 번 반복되는 만큼 중요한 내용이다. 이 장은 그 조언을 주제별로 모았다. 코딩 도구 사용법 같은 기술 세부는 해당 장으로 넘기고, 여기서는 "어떤 태도로, 무엇을 기준으로" 일할지에 집중한다.

학습 태도: 급하지 않게, 반복하며 흐름부터

  • Function Calling은 반복해서 만나게 되므로 처음부터 다 받아들이려 하지 말고 "이런 게 있구나" 하는 흐름으로 따라가면 된다. 익숙해지는 시간이 필요하다. 포기하지 않는 것이 중요하다.
  • 에이전트 공부는 급하게 하지 않아도 된다. 현직자들도 도구를 배우듯 같은 방식으로 공부하는 중이다. "반복 학습만큼 좋은 게 없다." 볼 때마다 체크하면 된다.
  • 어렵게 느껴져도 몇 번 구현해 보면 익숙해지고, 흐름만 잡으면 된다.
  • 에이전트 분야는 구현이 이론보다 앞서 있어 둘이 잘 안 맞는 부분도 있다. 개념 설명은 공통으로 쓰는 레퍼런스를 기반으로 한다.

지금이 기회다

  • 코드 AI를 접한 시기는 학습자나 전 세계 현업 개발자나 거의 같다. 잘 다루는 사람과 낯선 사람이 섞여 있지만 "이렇게 쓰면 되겠다"는 흐름이 막 생기는 중이다.
  • AI 발전은 막을 수 없다. "수많은 박사과정 학생이 이걸 만들어내야 박사가 되기 때문에" 발전은 계속된다. 그러니 흐름에 올라타야 한다.
  • 에이전트가 주목받은 지 1~2년(2024~2025)밖에 안 됐다. 도구를 잘 쓰는 법을 모두가 함께 찾는 중이라 빨리 적응하면 강력한 무기가 된다. "어떻게 썼더니 시간이 더 걸렸다", "코드 품질이 좋아졌다" 같은 사용 경험을 활발히 공유하는 것이 좋다.
  • AI와 같이 일하는 게 어색한 건 전 세계 개발자가 다 겪는 일이다. 정답 찾기보다 도구를 손에 익히는 과정으로 생각하고 마음 편하게 쓰다 보면, 무엇을 더 알아야 잘 쓸지 고민하게 된다.
  • 누구나 업데이트를 체감할 시간이 부족해 "같이 공부하는" 입장이다.

정리 다 외우려 하지 말고 흐름을 잡은 뒤 반복한다. 모두가 같은 출발선에 있으니 지금 손에 익히는 사람이 앞서간다.

에이전트, 딥러닝은 "과학 실험"이다

에이전트 개발: 디버깅보다 끌고 가기

  • 함수를 만들고 부르는 모든 작업은 결국 모델에 들어가는 컨텍스트를 만드는 작업이다. 필요한 기능은 툴콜로 만들면 되고, 점검할 것은 거기 들어갈 프롬프트(예: 글을 잘 쓰는 법)를 어떻게 정할지, 규칙을 안 따르면 무엇을 할지다.
  • 일반 프로그래밍은 컴파일 오류나 자료형 오류를 고치면 딱 떨어진다. LLM, 에이전트는 100%가 아니라 A가 나올 수도 B가 나올 수도 있는 것을 원하는 쪽으로 끌고 가는 일이다. 그래서 디버그라기보다 평가 기준을 세우고 프롬프트를 계속 고쳐 가며 개선한다.
  • 프롬프트는 실험으로 찾는다. 설계한 흐름대로 동작하는지 테스트하고, 안 되면 프롬프트를 강화해 다시 테스트한다.
  • 생성 모델은 원래 의도대로 움직이기 어렵다. 이미지, 영상을 생성하는 사람들도 수십, 수백 번 생성한다.

딥러닝, RAG 연구도 실험에서 시작한다

  • 딥러닝은 실험 과학이다. 알고리즘, 자료구조처럼 접근하면 부딪힌다. 물리, 화학 실험처럼 "해 봤더니 잘 된다 → 왜 그런지 분석"하는 흐름으로 접근하라.
  • 딥러닝 모델은 정답을 모른다. 어떻게 해야 잘 학습되는지 데이터 조합을 넣어 보며 매번 측정해야 한다. 실험을 설계하고, 논문이나 실험 설계를 찾아 가며 직접 문제에 뛰어들어야 한다. 방법론은 알려 줄 수 있지만 찾아가는 과정은 직접 해 봐야 안다.
  • 임베딩부터 다음 토큰 예측, 커스텀 토큰 파인튜닝까지 지금도 모두 연구 중인 분야다. LLM, 에이전트를 쓰는 어느 곳에 가도 이 범위 안에서 만들게 되고, 실제로 필요한 것은 "데이터셋을 이렇게 조합했더니, 설명을 이렇게 바꿨더니 성능이 올랐다"를 찾아내는 연구다.
  • RAG 개선은 "여기를 정제하면 어떨까"에서 시작한다. query가 바로 들어가는 곳, 검색 결과가 그대로 들어가는 곳이 바꿔 볼 지점이다. 아이디어를 먼저 정리하고 구현하면 문제없이 만들 수 있고, 초기 RAG에 아이디어를 적용해 실험, 정리하면 그게 논문이다. 옛 RAG 논문은 에이전트 이전 구조(바로 invoke)라서 지금은 에이전트 구조로 옮겨 구현해야 한다. → RAG: 임베딩 검색과 ChromaDB

비유 에이전트 개발은 컴파일 오류를 고치는 프로그래밍이 아니라 화학, 물리 실험이다. 가설을 세우고, 측정하고, 조건을 바꿔 다시 잰다.

정답 프롬프트는 없다: 짧게 시작해 덧붙인다

  • 프롬프트는 처음부터 길게 쓰지 않는다. 간단히 시작해 안 되는 부분을 퓨샷, 인스트럭션, CoT로 추가한다. 기법 모음집보다 원하는 결과가 나오는지가 기준이다.
  • 처음부터 많이 쓰면 고치기가 더 어렵다.
  • 정답 프롬프트는 없다. 맥락, 데이터가 다르면 같은 프롬프트도 결과가 다르다. 결과를 보며 시스템 프롬프트, 툴 description에 "이런 경우엔 이렇게"를 하나씩 추가한다.
  • 예시(few-shot)가 가장 강력하다. CoT와 함께 연습하라. CoT를 따르지 않으면 단계를 직접 쪼개 결과를 기반으로 동작하게 만든다. 반복되는 패턴은 스킬로 묶어 두면 매번 예시를 줄 필요가 없다.
  • 코드 에이전트에 요청할 때도 "뭐뭐 되게 구현해 줘" 대신 배운 규칙(Pydantic, Literal, None 타입, 툴 구현 규칙)을 프롬프트에 넣는다. 코드 분석은 AI의 도움을 받아 함수 역할을 파악하고, 세부 구현체를 참조하는 퓨샷 프롬프트를 만들어 구현한다.

SLM으로 프롬프트 실력을 단련한다

  • 좋은 모델에서 잘 되던 것도 SLM 같은 작은 모델에서는 난이도가 크게 올라간다. 프롬프트로 모델을 의도대로 특화시키는 연습을 미리 해 두는 것이 좋다.
  • SLM은 한 번쯤 써 보라. 프롬프트를 디테일하게 쓰는 연습, 출력, max tokens를 제어하는 연습이 된다. 작은 모델은 지시를 잊으므로 툴 description과 유저 프롬프트에 중복해 쓴다. 13B, 20B 이하는 실사용이 어렵고, 컨텍스트 길이는 벤치마크를 보고 1.5만~2만 토큰 정도로 잡는다. 기본 툴, 스킬이 많은 도구와 SLM을 조합하면 성능이 크게 떨어질 수 있다.
  • Ollama로 배포되는 모델, LM Studio 등도 직접 연결해 보라. 성능이 낮을수록 프롬프트를 잘 써야 해서 모델 이해도가 "강제로" 올라간다. 잘 안 따르는 모델일수록 연습이 많이 된다(Ollama Cloud).
  • 회사나 창업 현장에서는 SLM을 마주칠 수밖에 없고, 파인튜닝, 강화학습까지 하게 된다.
  • SLM 고르기와 설정(크기, 컨텍스트 길이)은 → 모델 고르기와 여러 모델 조합, 프롬프트 기법 자체는 → 프롬프트 엔지니어링에서 다룬다.

정리 에이전트를 잘 만들려면 결국 프롬프트(조건)를 잘 만드는 연습을 해야 한다.

"일단 동작한다"는 함정: 의도대로 됐는지 확인한다

  • 에이전트는 "일단 동작은 한다"는 게 함정이다. LLM이 강력해서 툴콜이 잘못돼도 스스로 다듬어 답을 내고, 컴파일러처럼 버그를 띄워 주지도 않는다. A→B→C 순서를 기대했는데 A→A→B→C로 불렀다면 프롬프트나 description을 고쳐야 한다. 트레이스로 최적화 여부를 직접 검증하라.
  • 에이전트 디버깅의 80%는 tool call과 arguments 확인이다. 서브에이전트부터는 LangSmith나 오픈소스 트레이싱을 쓴다. 문제가 생기면 처음부터 다시 실행해 보는 게 가장 좋다.
  • 검증 기준은 "정답"이 아니라 "의도대로 됐는가, 최선인가"다. 구현이 Pydantic 대신 JSON으로 바뀌어 있어도 모델에 넘어가는 건 결국 텍스트라 동작은 같다. 문제는 동작이 아니라 의도와 다르게 구현됐다는 점이다.
  • 툴만 구현하면 "동작"은 하지만 "의도대로" 동작하지는 않는다. 툴이 많아지면 시스템 프롬프트에 순서를 적는다(CoT 워크플로). 불필요한 툴 호출이나 순서 오류가 날 때마다 CoT 형식의 절차를 description이나 시스템 프롬프트에 넣어 최적화한다.
  • 에이전트는 펑션콜을 잘해야 하는 존재다. 답이 맞았어도 툴콜이 틀렸으면 실패로 보고 description, 프롬프트를 고친다. 잘못된 툴 결과는 컨텍스트를 오염시킨다.
  • 툴 트레이스 읽는 법은 → Tool과 Function Calling, 툴콜 평가는 → 에이전트 평가와 LLM-as-a-judge에서 다룬다.

테스트는 엄밀하게: 평가 세트, 경계 케이스, 실제 저장소

  • 생성 모델을 다룰 땐 늘 검증을 생각한다. 성능 평가용 입력, 출력 세트를 구성하는 연습을 하고, 평가는 도메인별 Q&A 세트를 직접 만드는 것부터 시작한다.
  • top-k 같은 파라미터는 테스트 세트를 만들어 찾고 검증한다. 에이전트는 만들고 끝이 아니라 잘 동작하는지 확인해야 한다.
  • 평가는 정답 세트부터. 사람이 30~50개 QA를 만들고, 점수보다 항목별 O/X(pass/fail)로 설계한다. 순서를 바꿔 두 번 돌리고 길이 편향을 금지하는 문구를 넣는다.
  • 평가 에이전트를 고정해 두고 프롬프트를 튜닝하는 것이 "컴파일러를 세팅하는 일"이다. 그러려면 도메인을 잘 알아야 한다. LLM judge 설계는 아직 연구 주제이니 논문(편향 상쇄 프롬프트 등)을 찾아 직접 실험하라.
  • temperature 0을 맹신하지 않는다. API 사용자는 비결정성을 통제할 수 없으니 룰 기반 처리나 재검증을 설계한다.
  • 정보 과잉 시대이니 항상 의심하고 검증하라. 벤치마크도, 누군가의 설명도 틀릴 수 있다.

예시 실습 프로젝트의 사례다. week04는 테스트 대화를 짧게(티키타카 10번 이하) 하고 벡터DB를 직접 열어 보지 않은 채 트레이스만 봐서, 대화가 길어지면 토큰이 폭증하는 구조를 놓쳤다. week05는 테스트 문장이 모두 "내 일정" 기준이라 "내 일정 없이 공유 일정만 조회"하는 경계 케이스를 놓쳤다.

  • 교훈: 짧은 대화만으로 테스트하지 말고, 트레이스만 보지 말고 벡터DB 같은 실제 저장소를 직접 확인하라. 경계 케이스를 만들고 팀원과 다양한 사례를 의논하라. 다음 프로젝트에서는 어떤 케이스에서 에이전트가 오동작할지 미리 예상해 대비하라.
  • 평가 방법은 → 에이전트 평가와 LLM-as-a-judge, 버그 회고는 → 주차별 실습 프로젝트에서 자세히 다룬다.

컨텍스트와 토큰은 아껴 쓴다

  • 컨텍스트는 다 쓸 수 있는 게 아니다. 작업 단위를 끊고 마크다운으로 넘기며 관리하라. 지금 에이전트에서 가장 핵심적인 주제다.
  • "컨텍스트를 잘못 쓰면 모델 성능이 뚝뚝 떨어진다." Claude Code 해커톤 우승자 인터뷰에서는 서브에이전트, 훅(human-in-the-loop 확인, 중단), MCP 관리, 플러그인이 언급됐다. 물리적 환경은 편한 걸 쓰면 되고 중요하지 않다. 메인 에이전트가 서브에이전트에 작업을 맡기면 컨텍스트가 분리돼 성능 유지에 유리하고, 서브에이전트를 따로 다루는 이유도 이것이다.
  • 컨텍스트는 낮게 유지한다. 목표 하나를 달성할 때마다 새 컨텍스트를 열고, 툴, 스킬 양을 줄인다. 요약해서 이어 가는 것보다 새로 시작하는 게 손실이 적다. 잘못 쓰면 토큰비가 어마어마하다.
  • 정보를 전부 시스템 프롬프트에 넣지 않는다. 컨텍스트가 찬 상태로 시작하게 된다. 툴별 정보는 툴 description, 스키마로 보낸다.
  • MCP는 필요한 것만 연결한다. 연결하는 순간 툴 이름, 설명, 인자가 컨텍스트를 먹는다. Claude Code, Codex에 플러그인, MCP를 잔뜩 붙여 두면 시작부터 손해다.
  • 서브에이전트를 적극적으로 쓰면 일은 빨리 처리되지만 토큰이 순식간에 없어지고, 각자 컨텍스트를 가지므로 메모리, 사양을 많이 먹는다(컴퓨터가 느려지고 뜨거워진다). 일반 채팅 대비 싱글 에이전트는 약 4배, 멀티에이전트는 약 15배의 토큰을 쓴다.

정리 가장 핵심은 컨텍스트를 최대한 적게 쓰고 토큰을 아껴 원하는 결과를 만드는 것이다. 전략은 → 컨텍스트 엔지니어링과 하네스, 모델을 나눠 쓰는 법은 → 모델 고르기와 여러 모델 조합에서 다룬다.

코드 에이전트에 끌려가지 말고 주도권을 쥔다

핵심은 코드 에이전트를 정확히 다루는 법이고, 제대로 배우고 쓰면 훨씬 강력한 힘을 낼 수 있다. 관건은 "끌려가지 않는 것"이다. 구체적인 사용법(플랜 모드, /init, /doctor, 스킬 작성)은 → AI 코딩 도구 활용(Claude Code, Codex)에서 다룬다.

  • 에이전틱 구현과 룰베이스 구현을 구분하라. 코드 에이전트에게 과제나 버그 수정을 맡기면 헬퍼 함수를 많이 만들고 키워드 추출, 반복문 같은 룰베이스로 고치려 한다. LangChain 새 버전은 2025년 10월 무렵 시작돼 학습된 코드가 적기 때문이다. 툴과 에이전트 판단으로 해결되는지 확인하고, LLM이 프롬프트에서 직접 추출하게 할지 필터 규칙을 둘지는 스스로 판단해 수준을 정하라. 코드가 얼마나 복잡하거나 간결한지도 본다.
  • 예제 코드 스타일을 따르라. 이 코드 스타일은 2025년 10월에 구성돼 Claude Code, Codex가 충분히 학습하지 못했다. 예제와 다른 스타일로 튀어나갈 수 있으니 플랜 모드나 마크다운 계획 문서로 구조를 강제하라. 가장 좋은 건 예제를 보고 직접 만들어 보는 것이다.
  • 작은 단위부터 완벽히 통제하라. SNS에서 에이전트 9개를 동시에 띄워 구현하는 식은 비효율적일 때가 많다. 무작정 던지면 지나치게 크게 만든다. 머릿속 로직을 하나씩 구현하고 참고 자료를 넣어 준다.
  • 모르겠으면 플랜 모드를 켜라. 기획서를 먼저 쓰고, 계획과 내 도메인 지식의 차이를 찾아 "왜 이렇게 했냐", "이 함수 진짜 필요하냐"고 묻는다. 테스트 시나리오를 넣어 검증을 요청하고, 안 되면 롤백한다. 이렇게 하면 "끌려간다"는 느낌이 줄어든다.
  • CLAUDE.md/AGENTS.md를 직접 튜닝하라. 남의 것을 그대로 쓰지 말고 플러그인, 스킬보다 MD 파일 튜닝을 먼저 해 본다. 추상화, 요청하지 않은 유연성, 추가 기능을 막는 지침이 있느냐에 따라 결과물이 크게 다르다. 과제를 시작하기 전 "분석해서 해 줘"보다 구현 방식, 핵심 개념, 필수 코드, 참고 문서를 적어 두면 모델이 스스로 판단하기보다 예제 기반으로 구현한다. MD 파일을 대수롭지 않게 여기는 사람도 있지만 직접 생각한 기능대로 구현하게 만드는 핵심 도구다.
  • MD는 가볍게, 세부 가이드는 코드 레벨 프롬프트로. 업데이트 이후에는 CLAUDE.md를 가볍게 두고 컨텍스트를 비운 채 시작해 필요할 때 불러오게 하는 방향이 권장됐다. 코드 레벨 구현에서는 세세한 가이드를 프롬프트로 주고 MD 쪽 제약은 가볍게 두는 방식이 실용적이다.

비유 하네스(말 고삐)라는 이름처럼, 말은 생각보다 말을 안 듣고 자기 가고 싶은 대로 간다. 고삐를 잘 쓰는 사람은 달리게도 하고 끌고 가기도 한다.

나만의 스킬과 문서를 자산으로 쌓는다

  • 예전엔 Git 수칙 같은 것을 직접 기억해야 했지만, 지금은 수칙과 자주 쓰는 프롬프트를 마크다운이나 스킬로 문서화해 AI 도구에 넣어 둘 수 있다. 이 작업을 지금부터 시작하라. 남의 스킬을 쓰더라도 내 작업에 맞게 최적화하는 연습을 하라.
  • 나만의 스킬을 최대한 많이 만들어라. 앞으로 누적해야 할 것은 스킬, 에이전트 구현 방법론, 모델을 컨트롤하는 나만의 방법이다. 문제 해결 방식을 적고 "스킬로 저장해 줘"라고 하면 저장된다.
  • 남이 만든 인기 플러그인을 그대로 쓰지 말고 어떻게 구현됐는지 보고 내 상황에 맞게 넣고 빼라. 안 그러면 토큰만 날아간다. 스킬을 로컬 MCP 서버에 모아 두고 Claude Code, Codex에서 툴로 불러 쓰는 방식도 있다. 컨텍스트를 더 자주 압축해 보는 등 사용법도 직접 실험하라.
  • 스킬을 직접 만들어 토큰 소모량 등을 정리해 보면 빨리 성장한다.
  • 지식은 먼저 마크다운으로 문서화해 두면 툴, RAG, 스킬 중 무엇으로 만들지 선택지가 생긴다.

도구는 직접 써 보고 지표로 판단한다

  • 하네스, 에이전트 도구에는 정답이 없다. 남의 말보다 직접 써 보고 평가하고, 안 맞으면 버리고 다시 쌓는다(모래성 쌓고 부수기). Claude Code, Codex 같은 유명 도구는 한 번씩 써 보라. 컴퓨터 전공이면 설정은 어렵지 않다.
  • 감이 아니라 지표로. 생성 모델은 감으로 평가하기 매우 어렵다. 모델, effort는 테크 블로그의 그래프, 벤치마크와 직접 벤치마킹으로 고른다. 무조건 max/high가 좋은 게 아니다(high/xhigh를 기준으로 조절).
  • 모델 선택은 소문이 아니라 벤치마크를 직접 보고, 내 태스크와 비슷한 벤치마크에서 잘하는 모델로 한다. 차이가 작으면 싼 모델을 쓰고, 벤치마크 자체의 이슈도 확인한다. 여러 모델을 태스크별로 전략적으로 배치한다.
  • 도구 동향 예: 최근 loop, goal 같은 기능이 Claude, Codex 등에 업데이트됐는데, Anthropic "효과적인 에이전트 구축" 글의 연장선으로 보인다. Antigravity도 비슷한 형태를 갖췄다. Claude Code와 Codex는 지향점이 좀 달라 보인다.
  • 모델 고르기는 → 모델 고르기와 여러 모델 조합, 도구 사용법은 → AI 코딩 도구 활용(Claude Code, Codex)에서 다룬다.

"무엇으로 만들지" 고르는 능력과 구조 이해

  • 일일이 다 구현하지 않아도 흐름만 알면 기능은 충분히 구현할 수 있다. 중요한 것은 무엇을 툴, MCP, RAG, 스킬, MD로 만들지 결정하는 능력이다.
  • 검색해서 참고할 큰 자료는 RAG로, 흐름을 통째로 유지해야 하는 작업 지시는 스킬로 만든다.
  • MCP 서버는 만들기보다 있는 서버를 활용하라. DB 연동, 웹 검색 같은 툴을 직접 구현하기는 매우 어렵다. Docker MCP Toolkit, 상용 서비스, 개인이 만든 서버가 많다. 필요하면 AWS 같은 곳에 나만의 MCP 서버를 띄워 팀, 인증 사용자에게 툴을 제공할 수도 있다.
  • 새 용어에 당황하지 마라. MCP는 결국 펑션콜이고 오히려 더 쉽다(만든 걸 불러오기만 하면 된다). MCP는 시간을 들여 깊게 공부하기보다 사용법과 스펙 정도만 익히고, A2A는 지켜보라.
  • 미들웨어는 특수한 경우에만 쓴다. 대부분은 프롬프트와 툴 description을 잘 쓰는 것으로 해결된다.
  • 프레임워크는 계속 바뀐다. LangChain 진영은 패러다임이 바뀌면 프레임워크를 새로 낸다(LangGraph → Deep Agents). Deep Agents 같은 신규 프레임워크도 같은 패턴의 재포장이니 원리(툴콜 기반 서브에이전트, 컨텍스트 전달)를 이해하면 된다.
  • 저수준(로우레벨)부터 하네스(하이레벨)까지 이해하면 새로 나오는 도구를 더 쉽게 쓸 수 있다. 실습 프로젝트는 그 중간 단계다.
  • 정답은 아직 없다. 무엇을 만들고 싶은지, 어떤 전략으로 갈지가 가장 중요하다.

빠르게 바뀌는 분야를 따라가는 법 (BERT vs ELMo)

  • AI 트렌드는 6개월이면 바뀔 수 있다. 지금 정리한 흐름은 "현재 상태"로 받아들여라.
  • MD 작성법만 해도 일주일 사이에 바뀐다. 이전까지는 AGENTS.md(Codex)와 CLAUDE.md(Claude Code)를 공유해 같이 참조하게 했는데, 업데이트 후 그 방법을 적용하기 어려워졌다.

예시 NLP 모델이 각광받던 때 지금 쓰는 BERT 이전에 ELMo가 있었다. 둘 다 세서미 스트리트 인형 이름이다. 학회 1~2일 전에 BERT가 나와 모든 면에서 ELMo를 압도했고, 학회 당일 ELMo 시연, 설명을 준비한 사람들은 BERT 이야기를 하며 금방 넘어갔다.

  • 교훈: 다 외우려 하기보다 "이런 흐름으로 가고 있구나"를 잡고 새 내용을 빨리 업데이트하라.
  • 생성 모델에서도 "GAN보다 좋은 게 나올까" 하다가 디퓨전 모델이 나오자 GAN이 싹 사라졌고, GAN을 열심히 공부하던 사람들은 처음부터 다시 공부했다.
  • 지금 배운 에이전트 기법도 슈퍼인텔리전스 모델이 나오면 서브에이전트 없이 질의응답만으로 해결될 수 있다. 취업 직후나 2년 안에 새 모델이 나오면 새로 배워야 할 수도 있다. 매일은 아니어도 분기에 한 번은 연구가 실무에 얼마나 내려왔는지 확인하고, 아키텍처를 어떻게 바꿔야 할지 빠르게 판단하라.
  • 유명 테크 블로그의 결론도 바뀔 수 있다. 멀티에이전트를 "써라/쓰지 마라" 논쟁 끝에 서브에이전트 구조가 표준이 됐고, 롱 컨텍스트처럼 기술이 나와도 실제 사용자에게 어떤 결과로 이어지는지는 다른 이야기다.

최신 동향과 새 모델을 읽는 법

동향을 받아 보는 방법

  • arXiv도 좋지만 ICML 같은 학회를 팔로우하는 게 가장 좋다.
  • ChatGPT 예약 작업에 "주요 AI 학회 최신 에이전트, 기술을 정리해 아침 7시에 올려줘"처럼 등록해 두면 가장 편하다. 쭉 보고 관심 있는 것만 본다. 관심 도메인 위주로 받아 보면 된다.
  • 테크 블로그를 자주 본다.
  • Karpathy는 CLAUDE.md, LLM 위키 같은 사용법을 트위터, GitHub에 꾸준히 공유하니 참고하라.
  • 서베이 논문은 ChatGPT에 넣어 요약해도 잘 나온다.

새 모델, 논문을 읽는 틀

  • 새 SLM/LLM 논문은 기본 구조가 같으니 "블록의 어디를 건드렸나(정규화, 게이트 등)"를 보라.
  • 기준 구조를 "임베딩 → RoPE → 어텐션 → MoE + 정규화"로 두고 무엇이 바뀌었는지를 본다. 이 틀이 깨지는데 성능이 월등한 모델이 나오면 공부할 대상을 바꿀 때다(GAN → 디퓨전 사례).
  • 업스테이지 Solar 발표 영상은 모델링에 관심 있으면 앞쪽(구조, 벤치마크)을, 활용 쪽이면 에이전트 구현과 비슷하니 가볍게 보면 된다.
  • 중국 모델(DeepSeek 등)이 무엇을 개선했고 부족한 환경에서 어떻게 잘 동작하게 했는지 보면 "다 비슷하게 가고 있구나"를 느끼고, 파인튜닝 등에서도 유리하다. 구조 아이디어는 Claude Code, Codex로 금방 구현되니 Colab의 1B 모델과 기존 벤치마크로 직접 실험해 볼 수 있다.
  • 구조 변화의 구체 내용은 → GPT-2에서 현대 LLM으로에서 다룬다.

LLM 내부를 공부하는 이유

  • 실제 AI 필드로 가면 증류(distillation), Teacher-Student 학습, 파인튜닝 등 대부분의 연구가 트랜스포머 구조 안에서 이뤄진다. 어텐션 파트나 데이터 분포 파트를 동작시키고 그 결과를 다른 모델이 학습하는 식이다.
  • 모델을 코드뿐 아니라 공간, 그림으로 이해해 두면 데이터와 모델을 분석하기 쉽다. 처음엔 어렵지만 반복해서 보면 익숙해진다.
  • SLM 파인튜닝, 경량화, 증류를 하려면 구조를 알아야 한다. 에이전트의 동작도 트랜스포머의 특성을 따라갈 수밖에 없다. 예를 들어 어텐션의 학습 편향 때문에 컨텍스트를 고르게 보지 못하는 것(Lost in the Middle)도 구조에서 나온다.
  • 예전엔 트랜스포머를 직접 구현해야 한다고 했지만 지금은 그 정도까진 필요 없다. "어텐션에서 특징을 추출하고, MLP에서 패턴으로 문장을 만든다" 정도만 잡아도 된다.

비유 에이전트를 다루는 건 운전이고, 모델을 만드는 건 차를 직접 만들거나 튜닝하는 것이다. 차를 만들고 튜닝할 줄 알면 운전도 더 잘하게 된다.

원리는 → LLM과 딥러닝의 기본 원리, 블록 구조는 → Transformer 블록 해부에서 다룬다.

면접과 신입 시절의 현실

면접 포인트

  • LLM/SLM을 만드는 회사 면접에는 트랜스포머 디코더 구조에 기반한 질문이 나온다. 예는 다음과 같다.
  • "왜 MLP 레이어가 mixture(MoE)로 쓰이나?"
  • "디스틸할 때 어떤 분포를 가지고 해야 하나?"
  • "양자화했을 때 어떤 지표를 봐야 하나?"
  • 관련 내용은 → GPT-2에서 현대 LLM으로(MoE)과 → 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝(증류, 양자화)에서 다룬다.

신입이 마주하는 일

  • 신입 때 가장 어려운 일 중 하나는 팀의 형상관리 규정을 익히는 것이다. 회사마다 코드 관리 문서, 규정이 있으니 그걸 공부하는 시간이 필요하다. 브랜치, 커밋 메시지는 팀 규칙을 따르고, 기능 하나를 만들 때마다 커밋하는 습관을 들여라.
  • 키가 유출되면 지워도 히스토리에 남는다. 무조건 폐기하고 재발급하라. 프로젝트를 올리기 전에 .gitignore부터 세팅하라. 자세한 수칙은 → 개발 환경과 Git 협업.
  • 기존 코드를 받으면 하루 종일 문서, 주석, 함수 호출을 읽는다. 이 이해 과정을 플랜 모드와 함께 하면 빨라진다.
  • 회사에서 "이 모델을 만들 건데 파인튜닝 데이터셋을 구성해 봐라"는 과제를 받을 가능성이 꽤 높다. 요즘은 SLM을 직접 학습하는 경우가 많기 때문이다.
  • 대형 모델 학습의 현실: Slack 알림, 새벽의 학습 실패, 게이밍 GPU의 메모리 할당 오류, 수 주짜리 학습이 끊겨 재시작하는 일. 모델 개발 회사(OpenAI, 업스테이지, 카카오)는 전체 파라미터 튜닝도 하지만 활용 회사는 대부분 QLoRA를 쓴다.

주의 "실리콘밸리 프롬프트 엔지니어 연봉이 억대"라는 기사의 실체는 단순 프롬프트 작성자가 아니라, 생성형 모델을 직접 튜닝하며 데이터를 처리, 학습시키던 NLP, 딥러닝 엔지니어였다.

도메인 지식과 진로별 조언

도메인 지식이 경쟁력이다

  • AI와 함께 개발하는 흐름은 거스를 수 없다. 이 흐름에서 핵심 경쟁력은 도메인 지식(전공이나 관심 분야의 지식)이다. 에이전트를 잘 쓰는 사람은 도메인 지식을 주입하며 끌고 가는 사람이다.
  • 플랜을 짜면 내 도메인 지식과 차이 나는 계획이 보이고, 경험이 쌓일수록 더 잘 보인다.
  • 평가 에이전트를 세우는 일도 에이전트가 풀려는 도메인 문제를 이미 잘 알아야 가능하다.
  • 수학, 과학 같은 분야 전문가 데이터로 전문 모델을 학습시키고 그 결과로 일반 모델을 학습하는 흐름 때문에 도메인 지식은 점점 더 중요해질 것이다. 관심 분야에서 에이전트를 어떻게 썼는지(파라미터, 질문, 평가셋)를 잘 정리해 두면 이 생태계에서 할 일이 생긴다. 에이전트를 쓰는 이상 좋든 싫든 이 분야에 포함된다.
  • AI가 툴로 쓰이는 시대에는 그 툴을 얼마나 잘 쓰느냐가 중요하므로 도메인 지식이 각광받는다.

활용할 것인가, 만들 것인가

SLM/LLM을 직접 만들 것인지 다른 분야에 활용할 것인지에 따라 조언이 달라진다. 활용 쪽을 택하는 경우가 대부분이다.

진로 조언
다른 분야에 활용 Codex, Claude Code 같은 코드 에이전트를 더 집중해서 써라
직접 LLM/SLM 만들기 딥러닝 모델 자체를 이해해야 해서 난이도가 있다
도시공학 에이전트 활용으로 접근할 수 있다
게임 개발에는 활용하지만 내부 모델은 직접 학습해야 할 수 있다
로봇 상황판단 직접 학습(커스텀 토큰 등)이 들어간다
피지컬 AI 최근 실리콘밸리에서 가장 큰 투자를 받은 분야로 알려져 있다

데이터가 70%, 파인튜닝은 신중히

데이터를 자산으로 쌓는다

  • 체감상 AI 개발은 모델링 30%, 데이터 다루기 70%다. 최근 Meta가 AI 개발자 절반을 데이터 만드는 데 보냈다는 논란이 있었지만, 원래부터 데이터 만드는 일은 AI 개발자의 일이었다. 모델 학습은 뒷부분이고 가장 먼저 할 일은 데이터 수집이다.
  • 데이터 정제에 공을 들여라. 청크는 의미 단위로 자르고 문장이 중간에 잘리지 않게 한다. 모델 학습에서도 정제는 늘 필요하다.
  • 원하는 동작을 담은 Q&A 데이터셋을 만들어 두면 평가와 파인튜닝 모두에 쓸 수 있다. 모으기만 하지 말고 ChatGPT, Claude로 정제해 결을 맞춰 두라. 에이전트 구현은 쉽고, 어려운 것은 내 의도대로 동작하게 만드는 것이다.

자원이 한정되면 RAG가 먼저다

  • 파인튜닝으로 지식을 주입하는 건 생각보다 잘 안 된다. 지식은 RAG, Skills, 프롬프트로 넣는다.
  • 딥러닝 학습 경험이 없는 사람에게는 파인튜닝을 권하지 않는다. 파인튜닝은 지식 주입보다 커스텀 토큰으로 기능, 형식을 가르치는 데 적합하다.
  • 자원이 한정되면 RAG가 먼저다. 파인튜닝은 데이터셋 구축이 가장 어렵고, 지식 주입보다 구조, 형식 학습에 강하다. 파인튜닝 후 문장 반복이나 외국어 섞임이 나오면 오버피팅을 의심하고 temperature, frequency penalty를 조정한다.
  • 업무 가이드 데이터셋: SLM에 "A→B→C 문서 순으로 확인" 같은 업무 순서를 thinking 형식 데이터셋으로 만들 수 있다. RL 툴이 정형화돼 있어 데이터셋만 바꿔 같은 코드로 튜닝할 수 있다. 파인튜닝은 "형식 학습"에 강력하다.
  • RAG와 파인튜닝 비교는 → RAG: 임베딩 검색과 ChromaDB, 학습 방법은 → 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝에서 다룬다.

다음 프로젝트 준비: 서브에이전트 구조로

처음 만든 에이전트 다음 단계에서 직접 에이전트를 만들 때를 위한 조언이다.

  • 6주차 포맷을 추천한다. 1~6주차가 누적 구현이라 1주차 에이전트의 잔재가 남아 코드가 복잡하다. 1~5주차는 단일 에이전트 연습이었고, 6주차의 핵심은 기능을 서브에이전트에 어떻게 분배하느냐다. 순서대로 부를지 기능별로 부를지 전체 구성을 기획하고, 서브에이전트가 어떤 순서로 불리는지 정리하라. 실제 구현은 "슈퍼바이저 안에 툴 2개" 정도로 단순해진다.
  • 기본은 싱글, 큰 일은 서브에이전트가 디폴트. 여러 일을 동시에 처리하거나 RAG, 데이터 등 역할을 나눌 때 서브에이전트로 만든다. 서브에이전트는 확장성과 성능을 주는 대신 프롬프트 양과 디버깅 비용을 늘리고, 트레이스는 계층별로 직접 챙겨야 한다.
  • 선택 기준은 대화 턴과 컨텍스트. 짧게 끝나는 일은 싱글 에이전트, 대화 턴이 10번 이상 이어지거나 주제 변화가 매우 크면 서브에이전트가 유리하다는 연구가 있다. 서비스가 확장될 것 같으면 처음부터 서브에이전트를 염두에 두고 기획하라.
  • 기능 할당을 실험으로 조정하라. 서브에이전트로 만드는 것 자체보다 관리 에이전트 하나에 기능을 얼마나 할당할지를 실험, 테스트로 조정하는 것이 핵심이다.
  • 프롬프트는 한곳에 일관되게. 실제 에이전트는 하나의 에이전트에 일관된 시스템 프롬프트와 여러 툴(description)로 만드는 것이 가장 좋다. 누적 구현 실습처럼 주차별로 시스템 프롬프트, 툴 설명을 흩어 두면 사람이 헷갈려 디버깅과 튜닝이 어렵다. 모델 입장에서는 툴과 시스템 프롬프트의 개수와 양만 영향을 주니, 툴이 늘어나면 서브에이전트로 나누거나 프롬프트를 정제하라.
  • 비용을 같이 보라. API를 쓰는 단계에서는 성능뿐 아니라 토큰 비용(싱글 약 4배, 멀티 약 15배)도 봐야 한다. 메인은 좋은 LLM, 서브는 SLM으로 구성해 비용을 줄일 수 있다.
  • RAG 데이터는 나눠 설계하라. 한 벡터DB에 모든 데이터를 넣으면 검색이 흔들리고 느려진다. 데이터 구조를 직접 보고 계층, 분리해 컬렉션별 툴로 만든다.
  • 오동작 케이스를 미리 예상하라. 팀원과 다양한 테스트 사례를 의논하고, 어떤 케이스에서 에이전트가 오동작할지 대비한다.

정리 다음 프로젝트는 "슈퍼바이저 + 서브에이전트" 구조로 기획하고, 기능 할당, 프롬프트, 비용, 테스트 케이스를 실험으로 조정한다. 구조 자체는 → 서브에이전트, 멀티에이전트, 워크플로, 실습 코드는 → 주차별 실습 프로젝트에서 다룬다.

LLM 이후 연구 동향

지금 LLM 다음으로 논의되는 연구 방향이다. 아직 대부분 연구 단계다.

방향 핵심 예
강화학습 기반 학습 지금 가장 각광받는 학습 방법(Agentic RL 등). LLM을 강화학습으로 발전시키는 것으로, 커스텀 토큰과 연결된다

월드 모델 다음 단어 예측이 아니라 물리 세계 자체를 인식하도록 이미지, 오디오 위주로 학습 얀 르쿤의 랩, DeepMind Genie

피지컬 AI

  • 지금은 툴과 프롬프트로 구현했지만, 툴에 로봇이 붙거나 LLM이 커스텀 토큰으로 "팔을 몇 도 구부려라" 같은 로봇 제어 토큰을 생성하게 학습시킬 수 있다. 툴 개념은 로봇, 자동차 같은 피지컬 AI로도 확장되고 있다.
  • 안경을 배포해 작업자의 손 영상을 수집하는 스타트업도 있다. 실리콘밸리에서 큰 투자를 받는 회사들이 사실상 사람 노동자를 대체하는 작업을 하고 있으며, 생각보다 빨리 진행될 수 있다.

예시 휴머노이드 손가락을 5개로 만드는 이유: 사람 손(대부분 5개)을 보고 학습하므로 손가락이 5개가 아니면 학습에 문제가 생길 수 있다. 3개로 만들면 비용은 크게 줄겠지만, 사람을 학습해야 하니 사람 형태를 모방해야 하는 제약이 생긴다.

월드 모델

  • CNN을 만든 얀 르쿤이 메타를 나와 세운 랩에서 사람처럼 학습하는 모델을 연구한다. 알파고를 만든 DeepMind는 Genie 같은 월드 모델을 연구한다.
  • 논리: 사람은 시각, 청각 위주로 학습한다(촉각은 데이터화가 어렵다). 그러니 텍스트로 학습한 LLM은 사람과 맞지 않다. Gemini도 멀티모달로 학습했지만 LLM 기준이라 텍스트가 메인이었다.
  • 트랜스포머가 RNN의 규칙을 다시 정의했듯 완전히 새로운 모델이라, 나오면 지금 쓰는 "문법"이 크게 바뀔 수 있다. "더 사람 같아지면 사람과 같은 실수도 하지 않겠냐"는 논란도 있다.

연속 학습, 자가 학습, 그리고 구글

  • 지금은 매번 학습시키기 어려워 학습된 모델을 출시하지만, 구글 Nested Learning처럼 여러 주기로 갱신되는 메모리 시스템으로 언어 모델이 실시간으로 계속 학습하게 하는 연구가 있다. Anthropic도 연구 중일 것으로 보인다.
  • 견해: 사람들이 "Gemini 성능이 안 좋다"고 하지만 구글은 LLM보다 프론티어 연구(트랜스포머 같은 새 모델 만들기)에 더 집중하는 것 같다. Claude 같은 곳은 LLM으로 상품을 만들고, 실제 프론티어 연구는 구글이 많이 한다. 블로그나 기사로 발표는 했지만 실제 모델은 아직 나오지 않았다.
  • 커스텀 토큰과 강화학습은 → 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝에서 다룬다.

질문 Q. 노트북을 실행하면 langchain 같은 모듈이 없다고 나온다.

README의 setup 셸 스크립트를 실행하지 않아 패키지가 설치되지 않은 상태다. 스크립트를 실행하면 pyproject.toml 기준으로 전체 패키지가 설치된다.

질문 Q. dotenv가 없다고 나온다. .env 파일 문제인가?

.env 파일 문제가 아니라 같은 원인(셸 스크립트 미실행)이다. 스크립트를 실행하거나 python-dotenv를 따로 설치하면 된다.

질문 Q. Python이 3.13으로 잡히고 ipykernel 커널이 없다. 커널을 닫았다 열었더니 이상해졌다.

  • 커널은 초기화될 수 있으니 설치를 정리한 뒤 다시 실행하면 된다.
  • 노트북이 프로젝트 .venv에 연결되지 않으면 모듈을 못 찾는다. 커널이 안 보이면 "다른 커널 선택"에서 실제 파이썬 환경을 찾아 연결한다.

자세한 환경 구성은 → 개발 환경과 Git 협업.

질문 Q. Windows에서도 되나?

Windows에서도 진행할 수 있지만, setup 셸 스크립트의 줄바꿈 문자(CRLF) 때문에 오류가 날 수 있다. 줄 끝을 LF로 바꿔 실행하면 된다.

질문 Q. JSON으로 출력되면 세팅이 끝난 것인가?

맞다. 일정 체크 결과가 잘 나오면 완료다.

Tool과 에이전트 설계

질문 Q. "에이전트에 가까운 툴"과 "코드에 가까운 툴"은 무엇이 다른가?

LLM이 툴 메시지를 얼마나 주도적으로 해석, 생성하는지로 구분한다.

코드에 가까운 툴 에이전트에 가까운 툴
형태 기존 서비스 함수를 그대로 툴로 쓴다. 인자를 받아 DB 등에 저장한다(실습의 일정 생성 함수) 함수 리턴에 프롬프트만 담는다("검색 결과를 잘 찾아 이렇게 답하라" 같은 RAG 프롬프트 처리)
의존하는 것 고정된 값, 구조화된 입력 LLM의 텍스트 생성(스킬과 비슷)
쓰는 곳 DB를 쓸 때처럼 구조화가 필요할 때 사람처럼 답해야 할 때

실무에서는 둘을 섞어 쓴다. 툴 설계는 → Tool과 Function Calling.

프롬프트 작성

질문 Q. 유출된 시스템 프롬프트처럼 프롬프트가 길면 성능이 떨어지지 않나?

맞다. 컨텍스트가 얼마나 찼는지에 따라 누락이 생길 수 있다. 롱 컨텍스트 모델도 실제 활용률은 70~90% 수준이고 Lost in the Middle 현상이 있다. 그래서 마크다운으로 작업 단위를 나누는 등 컨텍스트 관리가 중요하다. 자세한 내용은 → 컨텍스트 엔지니어링과 하네스.

질문 Q. 프롬프트를 영어로 쓰는 것과 한국어로 쓰는 것은 차이가 있나?

  • 요즘 모델은 차이가 많이 줄었고 프런티어 모델은 크게 차이 없다. 다만 SLM이나 성능이 낮은 모델에서는 차이가 있다. 모델 성능이 낮을수록 영어로 쓰는 게 조금 더 잘 나올 때가 있다.
  • 예: 2024년 GPT-4o mini 시절, 2023년 인구 통계를 8억 명으로 내놓는 오류가 유명했다. "생각은 영어로, 출력은 한국어로"라고 하니 고쳐졌다.
  • 영어 프롬프트 작성이 어렵다면 "생각, 툴 통신은 영어로, 답변은 한국어로"라고 지시하는 방법이 있다. 중간 레이어부터 자기 언어로 생각한다는 논문도 관련 자료로 있다.

프롬프트 기법은 → 프롬프트 엔지니어링.

질문 Q. 결국 코드 레벨에서 직접 세세한 가이드를 주라는 뜻 아닌가?

그렇게 읽을 수 있다. 코드 레벨 구현에서는 세세한 가이드를 프롬프트로 주고 MD 쪽 제약은 가볍게 두는 방식이 실용적이다. Anthropic의 새 가이드도 "코드 레벨에서 컨트롤하고 CLAUDE.md에 괜히 규칙을 만들지 마라"는 느낌으로 읽힌다. CLAUDE.md 다루는 법은 → AI 코딩 도구 활용(Claude Code, Codex).

질문 Q. 사투리로 요청했더니 인식이 잘 안 됐다. 왜 그런가?

사투리 데이터셋이 소수라서다. 사투리를 번역하거나, 모델이 이해하기 쉬운 형태로 바꾸는 규칙을 만들거나, 사투리가 어떻게 동작하는지 정보를 넣어 주면 개선된다. 한국어, 전공 용어, 사투리 같은 소수 데이터는 모델을 흔들기 쉬우니 RAG로 증강하고 금지어 필터도 넣는다.

구조화된 출력과 Pydantic

질문 Q. Pydantic 클래스 하나로 여러 개를 파싱하기 부적합하다고 하는데, 정말 안 되나?

  • 무조건 안 되는 건 아니지만 번거롭다. 단일 클래스는 필드 하나에 값 하나라서, 일정 10개를 넣으려면 필드를 리스트로 만들어야 하고 참석자는 "리스트 안의 리스트"가 된다.
  • 파싱이 실패하기 쉽고, 결과를 인덱스로 분리해야 하며, 중간에 누락되면 인덱스가 깨진다. 단일 스키마에 일정 두 건을 넣으면 JSON 파싱 오류가 난다.
  • 권장 방식: ScheduleList처럼 list[ScheduleCreate]를 필드로 가진 래퍼 클래스를 만든다. 결과 리스트만 순회하면 각 항목을 클래스 단위로 꺼낼 수 있다.
  • 주의: response_format에는 클래스를 하나만 지정할 수 있다.

자세한 설계는 → 구조화된 출력과 Pydantic.

질문 Q. "안정적 출력"이라는 말은 ProviderStrategy 쪽 이야기인가?

  • 둘의 차이는 플랜 B가 있느냐다. Provider는 LLM의 구조화된 출력 기능을 쓰고, 모델이 이를 지원하지 않으면(SLM 등) 툴콜(ToolStrategy)로 넘어간다.
  • "안정적"이라는 말은 LangChain 문서의 주장이다. Provider는 상황에 따라 파싱 주체가 바뀌어 같은 프롬프트에도 결과가 달라질 수 있지만, ToolStrategy는 항상 같은 툴로 파싱하니 결과가 일정하다는 뜻이다.
  • 실제로 써 보면 Provider가 파싱을 더 잘 알아듣는 느낌이고 큰 차이는 없다.

두 전략 비교는 → 구조화된 출력과 Pydantic.

실습 코드 구조

질문 Q. 실습 코드의 프롬프트는 왜 두 개로 쪼개져 있나?

1~6주차 에이전트를 누적 구현하는 구조라서다. 뒤 주차가 앞 주차의 툴, 프롬프트를 재사용하고 일부는 빼야 한다. 그래서 공통 프롬프트 파츠와 2주차 전용 프롬프트를 나누고 join_system_prompt로 합친다.

질문 Q. 주차별 에이전트가 이전 주차의 툴, 프롬프트를 가져다 쓰는 구조인데, 이게 맞는 구조인가?

  • 특이한 구조가 맞다. 6주차까지 이어서 구현해야 하는 클론코딩 특성상, 주차별로 에이전트를 따로 만들고 이전 툴과 프롬프트를 가져와 누적하는 방식이 됐다.
  • 원래 에이전트는 시스템 프롬프트와 툴 description을 한 번에 가진다. 이를 흩어 두면 모델에는 거의 그대로 들어가더라도 사람이 헷갈려 디버깅, 튜닝이 어렵다.
  • 실제로는 하나의 에이전트 + 여러 툴로, 컨텍스트가 일관되게 구성돼야 한다. 모델 입장에서 툴과 시스템 프롬프트는 개수와 양에만 영향을 주므로, 파일이 늘어나는 것은 곧 툴이 늘어나는 것이다. 툴이 늘면 서브에이전트로 나누거나 프롬프트를 정제한다.

실습 구조는 → 주차별 실습 프로젝트, 서브에이전트 분리는 → 서브에이전트, 멀티에이전트, 워크플로.

RAG와 벡터 검색

질문 Q. 텍스트 말고 이미지, 오디오, 영상 검색에도 응용하고 싶다. 가능한가?

  • 벡터DB는 이미지, 오디오, 영상도 저장할 수 있다. 해당 데이터를 벡터로 바꿀 임베딩만 넣으면 된다. 이미지-텍스트용 CLIP, 오디오-텍스트용 CLAP, 최근의 Gemini 계열 멀티모달 임베딩이 있다.
  • 통합 임베딩 공간에서는 어떤 데이터든 같은 공간의 점으로 찍히므로, 텍스트와 오디오처럼 서로 다른 모달리티의 연관을 거리로 찾을 수 있다.

예시 이상탐지: 사람이 쓰러져 있는 영상이 검색되면, 공간 안에서 가까운 텍스트로 "지금 사람이 쓰러져 있다"는 문장을 멀티모달 모델이 만들어 낼 수 있다.

임베딩과 벡터DB는 → RAG: 임베딩 검색과 ChromaDB.

질문 Q. 한정된 시간, 자원에서 에이전트 성능을 올리려면 RAG와 파인튜닝 중 무엇을 먼저 해야 하나?

RAG 먼저다.

  • 사용자 대부분이 딥러닝에 익숙하지 않고, 파인튜닝은 난이도가 높다.
  • 파인튜닝은 데이터셋을 직접 만들어야 한다.
  • QLoRA로는 지식 주입이 어렵다.

딥러닝을 잘 알고 데이터가 많다면 RAG, Skills를 세팅한 뒤 파인튜닝을 하면 된다. 비교는 → RAG: 임베딩 검색과 ChromaDB, 파인튜닝은 → 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝.

질문 Q. RAG 확장이 어렵다.

RAG 자체도 낯선데 확장은 더 낯설 수밖에 없다. 검색 → 프롬프트 생성 → 모델 입력의 세 단계에서 전달되는 프롬프트를 하나씩 구현하고 확인해 보면 이해된다.

MCP와 A2A

질문 Q. 노션, 피그마 MCP를 써 보니 안정성이 아쉽고 시각적 작업은 툴로 구현할 수 있는 범위가 제한적이었다. MCP가 출시된 게 어떤 의미가 있나? 따로 공부해야 하나?

  • 시간을 들여 공부할 정도는 아니고 사용법만 익혀도 된다. MCP는 사실상 툴콜 기능이 전부이고, API를 직접 붙이는 것과 거의 같다.
  • 장점은 어떤 에이전트를 쓰든 MCP 서버만 있으면 툴을 안정적으로 불러올 수 있다는 정도다.
  • MCP가 유행하니 노션, 캔바 MCP 등이 나오지만 툴 기능이 제한적이라, 아직은 함수를 직접 구현해 부르는 것 이상은 어렵다.
  • 지금은 A2A가 MCP를 포함하는 프로토콜로 통합되는 중이고, 다른 프로토콜도 A2A로 들어가며 스펙이 업데이트되고 있다. MCP는 그 하위 프로토콜 정도로 여겨진다. A2A는 너무 큰 프로토콜이라 "보안을 어떻게 할지", "에이전트 카드 보안" 같은 논의를 하는 단계이니 지켜보면 된다.
  • 실무에서는 Function Calling 정도로 두고 사용법만 익힌 뒤 업데이트되면 따라가면 된다.

MCP와 A2A는 → MCP와 A2A.

질문 Q. 다른 MCP 서버를 붙이려면 무엇이 필요한가?

MCP를 구성하고 싶으면 문서의 접속 정보만 찾아 모델(에이전트나 Claude Code)에 넣어 주면 바로 구현된다. 공개 서버 연결 예는 → MCP와 A2A.

하네스, 서브에이전트, 여러 모델 쓰기

질문 Q. 하네스(Harness) 엔지니어링이 무엇인가?

  • 정립된 학술 용어라기보다 X(트위터)에서 퍼진 말이다. 프롬프트 엔지니어링 → 컨텍스트 엔지니어링 → 하네스 엔지니어링으로 이어진 에이전트 제어 방법론이다. 하네스는 말 고삐, 강아지 목줄이라는 뜻이다.
  • 싱글 → 멀티 → 서브에이전트로 오면서 작업이 커져 한 컨텍스트로 끝나지 않는 문제가 생겼고, 이를 md 파일, 스킬 등으로 제어하는 것이다.
  • 정답이 없으니 직접 써 보며 자기에게 맞는 조합을 찾는 수밖에 없다.

하네스는 → 컨텍스트 엔지니어링과 하네스, 도구 쪽 활용은 → AI 코딩 도구 활용(Claude Code, Codex).

질문 Q. 서브에이전트에 일을 맡기는 건 팀장님이 업무 지시하는 것과 같지 않나?

맞다. 그렇게 구성할 수도 있다. Claude Code 등에도 하위 에이전트에게 일을 시키는 기능이 있고, 다른 CLI를 이용해 일을 시키는 방식도 같은 느낌이다. 적극적으로 쓰면 토큰은 순식간에 없어지지만 일을 금방 처리할 수 있다. 서브에이전트 구조는 → 서브에이전트, 멀티에이전트, 워크플로.

질문 Q. CLI로 여러 모델을 조절해 함께 쓸 수 있지 않나?

가능하다. 여러 모델의 CLI를 설치한 뒤 모델별로 업무를 나누는 스킬을 만들고, Ollama, alias로 Claude Code에 다른 모델을 연결하면 된다. 상위 모델은 계획, 검증, 하위 모델은 구현, 테스트를 맡겨 토큰을 아끼는 식이다. 모델 분업은 → 모델 고르기와 여러 모델 조합, 설정은 → AI 코딩 도구 활용(Claude Code, Codex).

질문 Q. Ollama로 배포된 모델을 연결해서 쓸 수 있나?

API 키나 서버를 연결할 수 있다. Ollama, LM Studio, Codex 등 여러 앱에 모델을 연결해 직접 써 볼 수 있다. 성능이 낮은 모델일수록 프롬프트를 잘 써야 해서 연습이 된다. SLM 활용은 → 모델 고르기와 여러 모델 조합.

평가와 LLM-as-a-judge

질문 Q. LLM agent-as-a-judge는 무엇인가?

  • 관련 기본 논문이 있고 아직 연구 중인 분야다. 실습에서는 6주차에 LLM-as-a-judge로 다룬다.
  • 데이터셋 포맷을 만든 뒤 LLM으로 평가하는데, 시스템 프롬프트를 잘 쓰는 것이 핵심이다. 논문의 프롬프트 템플릿(옛 모델 기준)을 분석해 보고 스킬로 넣어도 된다.
  • LangChain의 dynamic prompt로 시스템 프롬프트를 바꿔 가며 쓰면 컨텍스트가 길어지는 문제를 줄일 수 있다.
  • 가장 필요한 건 평가용 질문, 답변 세트다. BERTScore 같은 벡터 기반 평가 → LLM 기반 평가로 넘어온 흐름을 보면 도움이 된다.

질문 Q. 평가용 QA, 데이터셋이 없으면 어떻게 하나?

만들어야 한다. 사람이 만들 수밖에 없다. 최소 30~50개를 만들고, 사람 채점과 AI 채점이 비슷한지 확인해 judge를 신뢰할 수 있게 한다. 최상위 모델(Opus 등)을 judge로 쓰면 신뢰성 검증을 생략해도 되지만 SLM이면 필요하다. 평가 항목이 적으면 정확한 평가가 어렵다.

질문 Q. 답은 맞았는데 툴콜이 틀렸다면 성공인가?

실패로 본다. 모델 기본 성능 덕분에 우연히 맞힌 것일 수 있다.

  • 툴 호출 절차를 항목으로 나눠 점수화한다. 예: 툴 1, 2, 3번을 다 맞게 부르면 3점, 일부를 빠뜨렸는데 답은 맞으면 감점, 툴을 빠뜨리고 답도 틀리면 1점.
  • 절차대로 동작하도록 프롬프트(description)를 수정한다.
  • 툴콜 오류는 컨텍스트를 오염시키고, 오염된 컨텍스트는 이후 생성에 계속 악영향을 준다. 툴콜이 잘 되면 답은 거의 맞을 수밖에 없다.

질문 Q. 툴콜이 맞는지 비교할 때 BERTScore를 써도 되나?

부적합하다. BERTScore는 두 문장의 뜻이 비슷한지만 본다. 같은 툴인지, 반대말인지, 2%와 22%의 차이인지 구분하지 못한다. 툴콜은 LLM judge에 절차 규칙과 전체 컨텍스트를 주고 평가한다.

질문 Q. temperature를 0으로 두면 항상 같은 답이 나오나?

원래는 그래야 하지만 아니다. 부동소수점 연산 차이와 GPU 배치 처리 때문에 다른 토큰이 한 번 뽑히면 이후 생성이 모두 바뀐다. 실험상 1000번 중 약 80번이 달랐다. 로컬 서빙에서는 막을 수 있지만 30~60% 느려지고, API 사용자는 통제할 수 없다. 그래서 결과를 룰 기반으로 처리하거나 모델로 재검증하고, judge 프롬프트로 가이드하는 쪽이 현실적이다.

평가 설계 전체는 → 에이전트 평가와 LLM-as-a-judge.

모델, Transformer 원리

질문 Q. 데이터가 들어가고 나오는 Transformer의 동작 흐름은 어떻게 정리되나?

단계 하는 일
토큰 ID 단어마다 붙은 번호표
임베딩 ID를 768차원 벡터로 바꾼다
어텐션 Q, K, V를 만들고, score에 V를 행렬곱한다

질문 Q. Word2Vec, Word Embedding과 임베딩 레이어는 어떤 관계인가?

  • 임베딩 레이어는 Word2Vec이 발전한 형태다.
  • Word2Vec은 원-핫 벡터와 가중치 행렬의 곱이라 단어 수가 늘면 계산 비용이 폭증한다(100만 단어면 100만×100만). 지금은 인덱스로 임베딩 레이어를 바로 조회한다.
  • CBOW, Skip-gram은 머신러닝 쪽 모델에 가깝지만 어텐션 가속 연구 등에 여전히 활용된다.

임베딩은 → Transformer 블록 해부.
