주제 1

구조화된 출력과 Pydantic

LLM의 자연어 출력을 시스템이 바로 쓸 수 있는 클래스, JSON으로 받는 방법을 정리한다. 퓨샷→JSON 모드→Pydantic으로 이어진 발전 과정, BaseModel, Field, Literal, ge/le, default 같은 스키마 설계 도구, response_format의 두 전략, 그리고 구조화된 출력이 툴 입력 필터(args_schema)로 확장되는 흐름까지 다룬다.

구조화된 출력이 필요한 이유

LLM은 사람이 말하고 글 쓰듯 자연어 문장을 만들도록 학습된 모델이라 기본 출력이 자연어다. 이것이 문제가 되는지는 쓰임에 따라 다르다.

상황 자연어 출력이 괜찮은가
모니터링 서버에 에이전트를 붙여 "지금 상태 어때?"라고 묻고 답을 받는다 괜찮다. 서버 관리자가 아니어도 상태를 물어볼 수 있다
기존 시스템의 일부 기능만 에이전트로 바꾸고, 결과를 DB에 저장하거나 다른 서버로 보낸다 문제가 된다. 자연어를 다시 파싱해야 한다

원하는 것은 "사람 이름, 정보" 같은 값인데 자연어로 쭉 나오면 작업을 두 번 하게 되고 오히려 더 어려워진다. 예전 NLP에서도 자연어 파싱은 손이 많이 가고 정규표현식을 써야 하는 등 문제가 많았다. 그래서 처음부터 정형 데이터, 클래스로 구조화해서 받는다. "자연어를 구조화된 요청으로 만든다"가 바로 이 단계다.

이 둘이 에이전트의 두 축이다. "툴 + 구조화된 출력" 두 가지만 있어도 원하는 시스템을 대부분 만들 수 있다. 1주차 툴콜(→ Tool과 Function Calling)과 2주차 구조화된 출력이 끝나면 3주차부터는 DB, RAG, MCP, 서브에이전트로 응용해 간다.

정리 에이전트를 실제 시스템(DB, API)에 연결하려면 출력 형식이 고정돼야 한다. 구조화된 출력은 그 고정 장치다.

발전 1: 퓨샷 프롬프트로 JSON 흉내 내기

초기 LLM에는 JSON 출력 기능이 없었다. 그래서 예시를 붙인 퓨샷 프롬프트(→ 프롬프트 엔지니어링)로 JSON을 만들게 했다.

예시 "철수가 아침 9시에 학교에 갑니다" → 이름: 철수, 시간: 아침 9시, 가는 곳: 학교처럼 다양한 예시를 많이 붙인다. 그러면 "나는 학교에 갑니다"가 들어왔을 때 "누구: 나, 어디: 학교"처럼 정리된다. 출력 형식은 {"name": "민수", "job": "소프트웨어 엔지니어"} 같은 모양이다.

한계: 결국 생성 모델이라 JSON 구조가 무너지거나, 형식은 맞는데 엉뚱한 데이터가 나오는 오류가 가끔 생긴다.

발전 2: JSON 모드와 치명적 단점 "키 누락"

이런 사용이 많아지자 OpenAI가 API에 JSON 포맷을 강제하는 기능을 넣었다. 타입을 지정하고 시스템 프롬프트에 "JSON" 키워드를 넣으면 항상 JSON으로 출력된다. 자연어를 간단한 프롬프트만으로 JSON으로 바꿀 수 있어 빠르고 편하다.

단점은 생각보다 치명적이다. 가끔 키가 누락된다. 이름, 장소 같은 키를 전제로 파싱 코드를 짜 두었는데 키가 빠지면 오류가 난다. try/except로 재시도할 수는 있지만, 프롬프트가 잘못돼 있으면 계속 누락돼서 해결하기 어렵다.

이 문제는 경험으로 알게 된다. 일정 에이전트를 JSON 저장으로 먼저 만들면 프롬프트가 조금만 잘못돼도 데이터가 없을 때 키 자체를 지워 버린다. 툴 입력을 스키마 없이 "이 JSON 형식을 채워라"로 넘길 때도 같은 일이 생긴다(→ 아래 args_schema).

발전 3: Pydantic 클래스 (키는 지키고 빈 값은 None)

키 누락을 처음 해결한 쪽은 OpenAI가 아니라 LangChain 같은 프레임워크였다. LangChain은 구조화된 출력을 (1) JSON, (2) Pydantic 클래스, (3) 둘을 섞은 형태의 세 가지로 먼저 선보였다. 이게 잘 쓰이자 OpenAI도 2024년 8월경 API에 Pydantic 구조화 출력을 넣었다(그전엔 JSON만). LLM 회사와 프레임워크가 기능을 주고받으며 발전해 온 셈이다.

Pydantic BaseModel은 파이썬 웹 개발(FastAPI 등)에서 데이터를 저장, 검증하는 클래스와 같은 것이다. 예전에는 LangChain용, LlamaIndex용으로 변형해 썼지만 지금은 원래 Pydantic을 그대로 쓴다.

JSON 모드 Pydantic 클래스
장점 프롬프트만으로 빠르게 JSON을 얻는다 키 누락 방지. 값을 못 찾으면 키를 빼는 대신 None을 채워 구조를 그대로 돌려준다
단점 가끔 키가 빠져 파싱 코드가 깨진다 파싱 단계가 길고 스키마 변환, 파싱에서 오류가 많다. description을 다듬는 데 손이 많이 간다
후처리 키가 있는지부터 검사해야 한다 None만 검사하면 시스템이 문제없이 돈다

한 번 description을 잘 만들어 두면 잘 파싱하지만, 거기까지 프롬프트를 여러 번 고쳐야 한다. 그래도 실제 시스템에서 데이터를 추출할 때는 대부분 Pydantic 클래스로 추출하고 관리한다.

정리 구조화된 출력은 퓨샷 JSON → JSON 모드 → Pydantic 클래스 순으로 발전했다. 핵심 진전은 "키가 사라지지 않는다"는 것이다.

구조화된 출력의 동작 원리: 자연어를 한 번 감싼 편의 기능

Pydantic 클래스로 받을 때 내부 흐름은 다음과 같다.

  1. 클래스를 JSON 스키마로 변환한다.
  2. 모델이 입력 조건과 필드 description을 보고 스키마에 맞춰 JSON을 먼저 생성한다.
  3. 그 JSON을 파싱해 다시 클래스 인스턴스로 돌려준다.

그래서 본질은 자연어 출력과 같다. 출력을 구조화된 형태로 한 번 감싼 것이고, LLM 앱에 필수라기보다 보조 기능(편의 기능) 에 가깝다. 이렇게 감싸 주면 원래 자연어만 내던 모델이 시스템, 프로그램 내부에서 쓸 수 있는 형식이 되고, 기존 프로그램의 일부를 LLM이 대체할 수 있다.

같은 이유로 JSON으로 받든 Pydantic으로 받든 모델에 넘어가는 건 결국 텍스트다. 동작 자체는 같다. 차이는 그 뒤 시스템이 얼마나 안전하게 받느냐다.

LangChain에서 쓰는 법: response_format과 structured_response

LangChain의 구조화된 출력은 두 방식이 있다.

방식 특징
dataclass 최근 추가된 방법. Pydantic과 비슷하지만 타이핑이 조금 더 많은 느낌
Pydantic LangChain 초창기부터 쓰인 고전적 방법. 전통적으로 가장 강력하게 쓰인다. 이 과정은 이쪽을 쓴다

에이전트를 만들 때 create_agent의 response_format에 클래스를 넣으면, 실행 결과의 result["structured_response"]에 그 클래스의 인스턴스가 담겨 출력이 고정된다. response_format을 지정하지 않으면 structured_response 자체가 생기지 않는다. 에이전트 없이 모델에 바로 쓰는 with_structured_output도 있는데, 같은 원리로 description에 맞춰 변수를 채운 클래스를 돌려준다.

agent = create_agent(model, tools=tools, system_prompt=SYSTEM_PROMPT,
                     response_format=ScheduleRequest)   # 클래스를 넣는다
result = agent.invoke({"messages": [{"role": "user", "content": "내일 10시 민수와 미팅 잡아줘"}]})
req = result["structured_response"]   # ScheduleRequest 인스턴스
print(req.kind, req.title, req.date)  # 변수로 꺼내 DB 저장, 다른 함수에 전달

BaseModel로 스키마 만들기

사용법은 단순하다. BaseModel을 상속하고, 변수와 타입을 쓰고, Field(description=...)를 붙인다. 그러면 description에 따라 값이 파싱된다.

(필드명은 예시)

from typing import Literal
from pydantic import BaseModel, Field

class ScheduleCreate(BaseModel):
    """스케줄 생성 시 필요한 정보를 저장하는 클래스"""   # 클래스 docstring
    title: str = Field(description="일정의 제목")
    date: str = Field(description="날짜(지정 형식)")
    time: str = Field(description="시간(지정 형식)")
    attendees: list[str] = Field(description="참석자가 있다면 추가")

기본 클래스는 데이터 1건을 담는다. 변수로 생각하면 쉽다. str 필드 하나에는 문자열 하나만 들어간다. 타입 자리에는 int, str, list 외에 Literal이나 직접 정의한 다른 클래스도 넣을 수 있다.

3주차 노트북의 요청 클래스는 사용자 원문(source_text)을 함께 저장하면서 kind, title, date, 시작, 종료 시간, members, priority, reason 등으로 파싱한다.

Field와 description: 파싱을 조종하는 프롬프트

Field(description=...)에는 그 값에 대한 설명(무엇을 넣을지, 예시, 형식)을 쓴다. 예: title에는 일정 제목, date, time은 지정 형식, 참석자는 있으면 추가. 이 description이 파싱용 프롬프트다. Field는 항상 description과 같이 쓴다고 생각하면 된다.

description으로 파싱 내용을 상당히 마음대로 컨트롤할 수 있어서, 없는 데이터도 만들어 낸다.

예시 뉴스 기사 제목만 있고 사회, 경제, 정치 분류 정보는 없다고 하자. description에 "제목을 보고 사회/경제/정치 중 무엇인지 구분해 저장하라"고 쓰면, 원래 따로 분류 모델을 학습시켜야 했던 일을 별도 모델 없이 해낸다. 분류와 요약을 구조화된 출력 안에서 해결하는 셈이다.

주의 description에는 저장된 값이 진짜인지 판별, 검증하는 기능이 없다. 모델은 설명을 보고 유추할 뿐이라 파싱이 안 되거나 엉뚱한 값이 들어갈 수 있다. 그래서 아래의 타입 제약(Literal, ge/le)과 기본값(default=None)이 생각보다 강력하게 작용한다.

클래스 docstring: 클래스의 동작 설명

툴의 docstring이 "이 툴이 어떻게 동작해야 하는지"를 알려 주듯(→ Tool과 Function Calling), 클래스 docstring은 "이 클래스가 어떻게 동작해야 하는지" 를 적는 곳이다. 예: "스케줄 생성 시 필요한 정보를 저장하는 클래스".

"요청 스키마입니다" 같은 형식적인 가이드 문구는 빼고 다시 써도 된다. 어차피 response_format으로 들어가 구조화된 출력에 쓰이므로 "사용자가 요청한 …" 정도로만 써도 누적된 프롬프트와 함께 인식되어 파싱된다.

Literal: 값을 정해 둔 키워드로 강제하기

Literal["low", "medium", "high"]로 두면 값이 반드시 셋 중 하나로 정해진다. 일정의 중요도를 들어오는 데이터를 보고 판단해 셋 중 하나로 답하게 하는 식이다. 후처리나 변환 없이 바로 쓸 수 있고, 데이터셋을 만들 때도 두 번 작업하지 않아도 된다. 정해 둔 값(키워드) 안에서만 저장되므로 데이터 수집, 정리, 크롤링에 강력하다.

RequestKind처럼 Literal로 타입을 따로 만들어 두는 것은 키워드(규칙)를 미리 정해 두는 것이다.

예제에서는 kind가 정해진 세 값(예: personal_schedule)만 허용하도록 돼 있다. 허용값을 넣으면 구조화된 출력이 잘 만들어지고 나머지는 빈칸으로 남는다. "meeting"처럼 범위를 벗어난 값을 넣으면 검증 오류가 난다.

title 같은 자유 문자열 필드는 모델이 잘못 동작하면 엉뚱한 값이 들어가 "골치 아파진다". 그래서 필요에 따라 자유 문자열을 Literal로 바꾸는 게 좋다. 예를 들어 priority를 자유 문자열에서 Literal로 바꿀 수 있다.

RequestKind = Literal["personal_schedule", ...]   # 허용값 3개(예시)

class ScheduleRequest(BaseModel):
    source_text: str = Field(description="사용자 원문")
    kind: RequestKind = Field(description="일정 종류")   # 범위 밖이면 검증 오류
    title: str = Field(description="일정 제목")
    priority: Literal["low", "medium", "high"] = Field(description="일정 중요도")  # 자유 문자열 → Literal

팁 클래스 전체를 처음부터 완벽하게 짤 필요는 없다. description이나 타입은 결과를 보며 그때그때 바꿔도 된다.

ge, le: 숫자 범위 제약

정수 필드에는 Field 안에 ge(greater or equal, 이상), le(less or equal, 이하)로 범위를 걸 수 있다. 예를 들어 star: int 필드에 ge=1, le=3을 넣으면 int이므로 1, 2, 3만 들어간다. 실제 의미는 1 이상 3 이하다.

star: int = Field(ge=1, le=3, description="일정의 중요도를 저장합니다")

예시 모델이 중요도를 정확히 못 찾을 수 있으니 입력 끝에 "중요한 약속이다" 같은 키워드를 붙였더니 star가 3으로 찍혔다.

이런 수치 필드가 생기면 그 값을 기준으로 필터링 같은 후처리가 가능하다. 구조화된 출력은 이런 클래스 제약을 얼마나 잘 쓰느냐가 도움이 많이 된다.

default=None, default_factory: 빈 값 안전장치

description에는 검증 기능이 없으니 이상한 값이 들어올 때를 대비한 안전장치가 필요하다.

장치 쓰는 곳 효과
str | None + default=None title, date, start_time, end_time 같은 단일 값 데이터가 이상하거나 안 맞으면 바로 None이 들어간다. 나중에 None만 검색해 확인, 편집하면 된다
default_factory=list members(일정 참여 멤버)처럼 여러 개일 수 있는 리스트 값이 없으면 빈 리스트. Pydantic은 값이 없으면 None을 넣는 경향이 있어, 리스트를 관리하려는데 None이 들어가면 문제가 된다

|(파이프)로 두 타입을 함께 쓸 수 있다.

class ScheduleRequest(BaseModel):
    """사용자가 요청한 일정 정보"""
    kind: RequestKind = Field(description="...")
    title: str | None = Field(default=None, description="일정 혹은 약속의 제목")
    date: str | None = Field(default=None, description="...")
    start_time: str | None = Field(default=None, description="...")
    end_time: str | None = Field(default=None, description="...")
    members: list[str] = Field(default_factory=list, description="일정 참여 멤버")

데이터가 많아지면 필터링이 매우 중요해지고, 시스템 내부에서는 키나 값 하나만 달라도 오류가 난다. 이런 장치가 클래스를 튼튼하게 만든다.

base_date: 에이전트는 오늘 날짜를 모른다

에이전트는 현재 시간을 모른다. 그래서 "내일", "다음 주" 같은 상대 표현을 해석하려면 기준일을 주입해야 한다. 실행 시점 날짜를 base date로 찍어 주거나, OS 시간을 반환하는 함수로 가져온다.

클래스에 base_date 필드를 두고 default_factory로 현재 날짜의 ISO 문자열을 넣는 방법이 있다. description에 "상대적 날짜를 잡기 위한 기준일"처럼 써 주면 모델이 그 값을 두고 날짜를 해석한다. 결국 어떤 description을 쓰느냐에 따라 값이 정해진다.

(함수명은 예시)

base_date: str = Field(
    default_factory=lambda: current_app_date().isoformat(),
    description="상대적 날짜(내일, 다음 주 등)를 해석하기 위한 기준일",
)

날짜를 시스템 프롬프트에 직접 넣는 방법도 있다. 다만 주차별로 누적되는 프롬프트를 그대로 가져가면 날짜가 고정돼 찍혀 버리므로, 프롬프트를 파츠로 나눠 필요할 때 넣고 빼는 구조로 만든다(→ 주차별 실습 프로젝트).

중첩 클래스: 클래스를 타입으로 쓰기

타입 자리에 직접 만든 클래스를 넣을 수 있다. 예를 들어 ScheduleCreate와 TodoCreate를 필드 타입으로 갖는 ExtractResult를 만들면, 한 번의 파싱으로 일정과 할 일을 각각 클래스 단위로 받는다. 이렇게 원하는 출력 형태를 설계해 리턴받거나 여러 개를 저장하는 쪽으로 발전시킬 수 있다.

class TodoCreate(BaseModel):
    ...
    priority: Literal["low", "medium", "high"]

class ExtractResult(BaseModel):            # 단일: 클래스를 필드 타입으로
    schedule: ScheduleCreate | None
    todo: TodoCreate | None

여러 건 파싱: 리스트 필드 대신 "클래스의 리스트"

"클래스 하나로 일정 여러 개를 파싱하면 안 되나?"라는 질문이 자주 나온다. 실제로 해 보면 이렇다.

  1. ScheduleCreate 하나로 "오늘은 7월 7일, 오후 3시에 보고서 제출" 같은 일정 1건을 넣으면 잘 파싱된다.
  2. 같은 스키마에 일정을 하나 더 넣자 JSON 파싱 오류(Extra data, parsing failed)가 났다. 단일 데이터 구조이기 때문이다.
  3. 필드마다 list를 붙이면 파싱은 되지만 비추천이다. 1건은 쉬워도 10건은 난이도가 확 오른다. 참석자는 "리스트 안의 리스트"가 되고, 결과를 인덱스로 하나씩 꺼내야 한다. 리스트 하나가 중간에 누락되면 인덱스가 전부 밀린다.
  4. list[ScheduleCreate]를 필드로 갖는 래퍼 클래스를 response_format에 넣자 결과에 스케줄 클래스 리스트가 깔끔하게 담겼고, 순회하며 바로 꺼낼 수 있었다.

이를 배치(Batch) 클래스라고 부른다. 필요한 타입을 클래스로 정의하고, 배치 클래스의 필드 타입을 그 클래스의 리스트로 둔다. default_factory=list도 넣으면 좋다(없어도 동작). 예컨대 StructuredRequest(1건)와 StructuredRequestBatch(여러 건)가 이 구조다.

class ScheduleList(BaseModel):
    schedules: list[ScheduleCreate] = Field(
        default_factory=list,
        description="사용자가 정한 일정의 리스트를 저장해주세요",
    )

agent = create_agent(model, tools=tools, response_format=ScheduleList)
result = agent.invoke(...)
for s in result["structured_response"].schedules:   # 인덱스 대신 클래스 단위로 순회
    print(s.title, s.date)

정리 클래스 작성의 핵심은 딱 두 가지다. ① 어떤 타입의 데이터를 받아올 것인가, ② 여러 개를 파싱하려면 클래스 단위로 파싱하면 안정적이다. "한 클래스 = 한 종류의 데이터"로 설계하고 복수는 래퍼로 감싼다.

response_format에는 최종 클래스 하나만

response_format에는 클래스를 하나만 지정할 수 있다. 두 클래스를 묶은 상위 클래스 하나를 넘기는 것은 괜찮지만, 두 클래스를 따로 동시에 넘기면 동작하지 않는다. 여러 클래스를 한 번에 리턴하면 편하겠지만 구조화된 출력은 하나의 클래스를 리턴하도록 되어 있다. 그래서 create_agent에는 최종으로 리턴할 클래스(예: 배치 클래스)를 넣는다.

파싱 대상 클래스가 여러 개면 오류 확률이 높아지므로 "한 클래스가 특정 데이터를 파싱하도록" 설계하는 것이 가장 좋다.

ProviderStrategy vs ToolStrategy

원래 LangChain이 선보인 Pydantic 구조화 출력을 이제 LLM 제공자(provider)도 자체 지원한다. 그래서 response_format에는 파싱 주체를 고르는 두 전략이 있다.

ProviderStrategy(공급자 전략) ToolStrategy
파싱 주체 LLM(공급자)의 구조화된 출력 기능 자체 LangChain에 구현된 툴콜(Function Calling)
선택 방법 클래스를 그냥 넣으면 기본값 ToolStrategy(Schema)로 감싸 지정
미지원 모델 지원하지 않는 모델(SLM 등)이면 ToolStrategy로 넘어간다. "플랜 B가 있다" 툴콜만 되면 쓴다
장점 체감상 파싱을 조금 더 잘 알아듣는 편이다(제공사가 파인튜닝한 것으로 보인다) 항상 같은 툴로 파싱해 결과가 일정하다(LangChain 문서 주장). 잘못 파싱되면 자동 재시도, 파싱 성공 메시지 같은 로그, 알림
단점 상황에 따라 파싱 주체가 LLM ↔ 툴콜로 바뀌어 같은 프롬프트에도 결과가 흔들릴 수 있다 파싱이 잘 안 되거나 엄청 느린 경우가 생각보다 많다

에이전트용 create_agent는 2025년 10월에 추가되면서 ProviderStrategy를 기본으로 두었다. 두 전략은 근본 동작이 달라서 같은 프롬프트라도 파싱 결과가 달라질 수 있다. LangChain으로는 되는데 provider로는 안 되거나 그 반대인 경우도 있다.

(import 경로는 LangChain 1.x 기준)

from langchain.agents.structured_output import ToolStrategy, ProviderStrategy

agent = create_agent(model, tools, response_format=Schema)                    # 기본: ProviderStrategy, 미지원이면 ToolStrategy
agent = create_agent(model, tools, response_format=ToolStrategy(Schema))      # LangChain 툴콜 기반, 재시도, 로그
agent = create_agent(model, tools, response_format=ProviderStrategy(Schema))  # 공급자 기능으로 고정

질문 "안정적 출력"이라고 한 건 ProviderStrategy 이야기인가? → 차이는 플랜 B가 있느냐다. "안정적"이라는 말은 LangChain 문서의 주장으로, ToolStrategy는 항상 같은 툴로 파싱하니 결과가 일정하다는 뜻이다. 제공사가 만든 기능이라 권장하는 면도 있으며, 실제로는 Provider가 더 잘 알아듣는 느낌이고 대부분 큰 차이는 없다.

ToolStrategy가 느리거나 잘 안 되면 ① Provider로 바꾸거나 ② ToolStrategy용 프롬프트를 보강한다. 툴콜 파싱이 실패하면 흔들리기 때문에 프롬프트를 보강하면 속도도 빨라진다. 로그를 남기거나 데이터셋을 만들며 알림이 필요할 때는 ToolStrategy가 유용하다.

파싱 실패 다루기: 대기 시간 신호와 JSON 파싱 오류

대기 시간이 신호다. 파싱을 돌렸는데 대기 시간이 길어지면 파싱이 실패하고 재시도 중이라는 뜻이다(실패하다가 성공하기도 한다). 기준은 30초 이상이면 의심할 만하고 15초는 애매하다. 데이터가 어렵거나 많으면 원래 오래 걸리기도 한다. 대처법은 (1) 파싱 제공자를 바꾸거나 (2) description을 보강하는 것이다. 설명이 부족해서 실패하는 경우가 많으므로 퓨샷 예시 등을 최대한 활용한다.

JSON 파싱 오류의 정체. 클래스로 파싱할 때도 모델 내부에서는 JSON으로 데이터를 한번 정리한 뒤 파싱한다. 이때 JSON 키 값 등이 잘못 생성되면 "JSON 파싱 오류"가 난다. 이것은 문법 문제가 아니라 생성 실패이므로 대부분 프롬프트 단, 즉 description으로 해결한다.

주의 에이전트는 오류가 나도 컴파일러처럼 어디서 무엇 때문에 실패했는지 알려 주지 않는다. 디버깅을 조심해서 해야 한다.

디버깅 순서는 이렇다.

  1. 실행 후 트레이스에서 어떤 데이터로 파싱했는지 확인한다(→ Tool과 Function Calling).
  2. description, 프롬프트를 고친다. 프롬프트는 처음부터 많이 쓰지 말고 간단히 시작해 안 되면 추가한다.
  3. 모델이 클래스를 못 찾으면 프롬프트에 클래스 이름을 직접 써 준다.
  4. 프롬프트를 바꿔 테스트하다 structured request 에러가 나면 처음부터 다시 실행해 본다.

툴 입력 필터: args_schema

구조화된 출력은 원래 출력을 담당하지만 툴 입력을 정제하는 데도 쓴다. 생각보다 쓸 일이 되게 많다. 구조화된 출력이 툴콜의 입력부에 필터로 작용하는 것이다. 3주차에서 실제로 구현한다.

Function Calling에서는 LLM이 description과 프롬프트를 보고 툴 인자를 직접 만들어 넣는다(예: get_weather 함수의 인자). 툴 정의에 name, description과 함께 args_schema로 Pydantic 클래스를 넣으면, 그 클래스가 인자의 필터가 된다. 필터링은 두 갈래다.

  • 타입 기반 필터링: Literal로 허용값을 묶거나, str 대신 int로 숫자를 강제한다.
  • description 기반 가이드라인: 필드 설명으로 데이터 작성 지침을 준다.
@tool(args_schema=ScheduleRequest)       # 툴 애너테이션 인자로 Pydantic 클래스 → 입력 필터
def save_schedule(kind, title, date):
    ...                                  # 검증된 인자만 들어온다 (DB 저장은 → 06장)

왜 중요한가. 상용 프로그램을 에이전트로 만든다고 하자. 모델은 프롬프트로 제어하지 않으면 인자를 마음대로 넣는다. 그렇다고 모든 정보를 시스템 프롬프트나 매 유저 프롬프트에 넣으면 누적돼 컨텍스트가 찬 상태로 시작한다. 회사명 같은 고유명사, 정해진 값은 툴 description과 args_schema에 넣고 Literal 등으로 입력 자체를 픽스하면 된다.

스키마 없이 넘기면. "이 JSON 형식을 채워라"로만 시키면 에이전트가 직접 JSON을 만들다 키를 누락해 툴콜이 실패한다. 프로그램이 멈추진 않지만 실패할 때마다 function call → 인자 생성이 반복돼 계속 손실(로스) 이 생긴다. 인자가 잘못 들어가면 다 구성해 놓고도 오류가 나는 것은 일반 프로그래밍에서 함수 인자를 잘못 넘기는 것과 같다.

팁 툴콜이 제대로 안 될 것 같으면 args_schema를 자주 쓰라. 툴에 전달되는 정보를 정제할 때 늘 쓸 수 있는 방법이다.

3주차까지 알게 된 것을 정리하면 이렇다. ① 툴을 만들어 두면 에이전트가 쓸 수 있다. ② 툴 입력을 구조화된 출력으로 필터링할 수 있다. ③ 에이전트의 최종 출력도 구조화된 출력으로 만들 수 있다. 이걸 알면 "스키마를 넣어 함수 입력을 거를 수 있다"는 사실을 설계에 쓸 수 있다. 이 필터를 DB 저장에 붙이는 이야기는 → 툴 입력 검증과 SQLite 저장에서 이어진다.

실무 용도: 데이터 정리, 학습 데이터 추출

실무에서 구조화된 출력은 데이터 정리 목적이 많다. 데이터셋 만들기, 크롤링한 데이터에서 값 뽑기, 특히 파인튜닝용 학습 데이터 만들기와 상위 모델에서 데이터 추출에 가장 많이 쓴다. 학습 데이터에는 system, user, assistant 같은 메시지 구조가 있어 이를 Pydantic 클래스로 구현해 저장한다.

예시 새 모델(예: Fable)이 나오면 SLM을 만드는 사람들은 시스템, 유저, 어시스턴트 구조로 질문을 던져 데이터를 뽑고, 모델이 학습한 내용을 어느 정도 "뱉어내게" 한 뒤 그것으로 다른 모델을 다시 학습시키기도 한다. 자연어로 뽑을 수도 있지만 구조를 만들어 추출하면 빠르다(학습 쪽 이야기는 → 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝).

쓰임을 크게 보면 툴 입력 필터링, 출력 필터링, 정리된 데이터에서 인사이트 만들기로 묶을 수 있다.

코드 에이전트가 만든 구현 검증하기

실습을 코드 에이전트로 구현하면 노트북과 다른 형태가 꽤 나온다. LLM이 학습한 데이터에 LLM 기반 에이전트, 툴콜 코드가 많지 않아서 문서를 참조하지 않으면 특이한 헬퍼 함수를 많이 만든다. 예전에는 헬퍼, 인터페이스 함수로 데이터를 정리해 던졌지만, 지금은 Pydantic 클래스 하나를 만들고 description으로 조절할 수 있다.

다만 description으로 다 되지는 않는다. 그래서 선택지가 두 가지다.

  • 직접 함수로 데이터를 변환해 준다.
  • LLM 성능을 믿고 맡긴다.

어느 쪽이 맞는지는 경험적으로 테스트해야 한다. 문서를 찾아 넣기 어려우면 노트북의 "기본 개념 실습", "확장 예제" 패턴을 프롬프트에 넣거나 그 파일을 참조하게 한다.

예시 "툴콜에 Pydantic 필터를 써야 하는데 에이전트가 이걸 빼고 JSON으로 바꿔 버렸네." 동작은 똑같이 한다. 모델에 넘어가는 건 어차피 텍스트이기 때문이다. 문제는 동작이 아니라 의도와 다르게 구현됐다는 것이다. 이럴 땐 수정하고, 시도해 보고 안 되면 롤백한다.

베이스라인은 "코드는 이렇게 짜야 한다"는 정답이 아니라 내 의도대로 구현됐는지 확인하는 기준이다. 결과가 "정답"인지보다 "최선"인지를 본다(코드 에이전트 다루는 법은 → AI 코딩 도구 활용(Claude Code, Codex)).

정리 Pydantic은 툴 입력과 에이전트 출력을 모두 다듬어, 정해진 시스템 안에서 에이전트가 문제없이 돌게 한다. 타입 제약을 얼마나 잘 쓰느냐, 클래스를 어떤 단위로 나누느냐가 성패를 가른다.

주제 2

툴 입력 검증과 SQLite 저장

3주차는 구조화된 출력을 툴 입력 필터로 옮기고, 검증된 데이터를 SQLite에 저장, 조회, 삭제하는 주차다. 왜 DB가 필요해졌는지, LLM을 DB에 바로 붙이면 무엇이 위험한지, 직접 테이블과 checkpointer는 어떻게 다른지, 저장 툴을 어떻게 짜고 확인하는지를 개념, 설계 중심으로 정리한다.

3주차의 위치: 툴과 구조화된 출력이 만나는 주차

1주차는 툴콜(→ Tool과 Function Calling), 2주차는 구조화된 출력(→ 구조화된 출력과 Pydantic)이었다. 3주차도 구조화된 출력이지만 툴과 구조화된 출력이 같이 쓰이는 단계다. 주제 이름은 데이터베이스(저장)지만, 정확히는 툴콜을 제어할 때 입력을 구조화된 출력으로 정리하고 출력도 정리하는 파트다.

주차 흐름
2주차 자연어 요청 → 클래스(고정된 출력) → 화면에 메시지로 출력
3주차 자연어 요청 → 구조화된 출력이 툴 입력 필터로 작동 → 툴이 외부 프로그램(DB)에 저장 → 저장됐는지를 다시 자연어로 받음

핵심은 "툴이 필요로 하는 데이터를 얼마나 잘 전달하느냐" 다. 3주차는 툴콜과 구조화된 출력이라는 두 축을 "쓰는 방법"을 보여 주는 예제 같은 주차라고 할 수 있다.

왜 DB가 필요해졌나: 일정 에이전트 설계 흐름

3주차 과제가 나오기까지의 문제 해결 순서는 다음과 같다.

  1. 일정 에이전트를 만든다. 우선 툴로 간단히 만들고 일정을 JSON 등으로 저장한다.
  2. JSON은 프롬프트를 쉽게 만들 수 있어 빠르다. 하지만 프롬프트가 조금만 잘못돼도 데이터가 없으면 키 자체를 지워 버린다. 이건 경험으로 알게 된다.
  3. 해결책으로 클래스 기반 파싱인 Pydantic을 쓴다.
  4. 툴을 실행할 때 입력도 걸러야 하니 Pydantic을 툴 입력 필터로 쓴다.
  5. 1, 2주차에는 툴과 클래스까지 만들었지만 저장이 안 돼서 한 번 종료되면 일정이 유지되지 않는다. 그래서 나온 데이터를 DB에 저장한다. 이것이 3주차 과제의 출발점이다.

결론은 "DB 저장은 툴 기반으로 동작하게 하고, 툴콜만 하면 위험하니 Pydantic 클래스를 붙여서 데이터를 안전하게 넣는다"이다.

정리 JSON 키 누락 → Pydantic → 툴 입력 필터 → DB 저장. 앞 단계의 한계가 다음 단계를 불렀다.

LLM을 DB에 바로 붙이면: 확률적 파싱 문제

LLM은 기본적으로 자연어를 출력하므로, DB에 넣을 데이터를 필드별로 나눠 주기 어렵다. 옛날에는 프롬프트를 아주 잘 쓰고 예시를 많이 넣어 "누가, 언제 요청했는지" 분석하게 해서 동작시키기도 했다. 하지만 파싱을 확률적으로 하기 때문에 잘못 파싱하는 경우가 확률적으로 생긴다. 무조건 생기는 건 아니지만 생길 수 있다(생성 원리는 → LLM과 딥러닝의 기본 원리).

해결은 툴에 Pydantic 필터링을 거는 것이다. 이렇게 도메인 지식을 적용해 프롬프트를 만드는 것이 핵심이다. 역할 분담도 분명하다.

담당 하는 일
LLM 자연어 요청을 구조화한다(어떤 종류, 어떤 제목, 언제)
Pydantic(args_schema) 툴로 들어가는 인자를 검증, 필터링한다
SQL 검증된 값을 저장, 조회, 삭제한다

정리 "구조화는 LLM이, 저장은 SQL이." 그 사이를 Pydantic이 지킨다.

3주차 아키텍처: 임시 저장 → 구조화된 출력 → 입력 검증 + DB

과제 코드는 주차별로 기능이 누적되는 구조다. 3주차에서 바뀌는 지점은 다음과 같다.

  • 1주차: 툴이 일정을 임시 저장한다.
  • 2주차: 그 부분이 구조화된 출력으로 확장된다. 출력이 클래스 형태로 나온다.
  • 3주차: 구조화된 출력이 입력 검증 파트로 빠진다. Pydantic 클래스가 툴 입력을 제어하고, 검증이 되면 SQLite 저장소에서 DB 기능(조회, 수정, 삭제)을 부른다.
  • 이후: 공유 저장소까지 확장된다(→ 마지막 소주제).

3주차 과제의 핵심은 저장, 조회, 수정, 삭제 기능의 입력 검증을 Pydantic 클래스로 하는 것이다. 검증 스키마는 2주차에 만든 요청 클래스를 누적해 가져다 쓴다. 과제 코드 뒤에는 DB 저장 같은 숨은 코드(fixed 파트)가 많은데, 학습 주제에 집중하기 위한 구성이라서 그 부분은 코드 에이전트에 분석을 요청해 동작만 확인하면 충분하다(과제 구조 상세는 → 주차별 실습 프로젝트).

DB를 쓰는 두 방식: 직접 테이블 vs MemorySaver, checkpointer

LangChain에서 DB를 쓰는 방법은 크게 두 가지다. 성격이 꽤 다르다.

① 직접 테이블 (3주차 예제) ② MemorySaver, checkpointer
무엇을 저장하나 필요한 정보만(일정의 종류, 제목, 날짜 등) 대화, invoke된 내용 전부
누가 만드나 테이블 생성, SQL 쿼리를 직접 작성. LangChain이 지원하는 부분이 아니다 에이전트 구현체의 일부로 붙는다
저장 경로 툴로 빼서 저장한다 그냥 MemorySaver는 메모리에만 올라가 있다가 invoke 때마다 불러온다. DB와 연결하는 checkpointer는 모든 대화를 DB에 저장한다
느낌 웹페이지 등을 만들 때 필요한 정보를 따로 저장하는 용도 대화를 이어서 진행하는 느낌

DB를 구성하는 일 자체는 에이전트와 크게 상관이 없을 수 있다. 3주차 예제는 ①이다. LangGraph 계열에서는 메모리용 InMemorySaver(예전 이름 MemorySaver)나 SQLite에 저장하는 SqliteSaver 같은 checkpointer를 에이전트에 넘기고, thread_id로 대화를 구분해 이어 간다. 대화 기록 같은 메모리 범위 이야기는 → 컨텍스트 엔지니어링과 하네스에서 다룬다.

SQLite 테이블 만들기

3주차 노트북 확장 예제는 Python 기본 모듈 sqlite3로 진행한다. 흐름은 단순하다.

  1. 옵션에 들어 있는 db_path로 sqlite3.connect한다.
  2. CREATE TABLE SQL을 실행해 필요한 테이블을 미리 만든다. request_id를 키로 원문 텍스트, kind, JSON 등을 넣는 테이블을 만들고, ID로 이어서 나중에 조회, 수정할 때 쓸 날짜 등을 정리한 테이블들도 만든다.
  3. 툴이 추출한 데이터를 execute()로 INSERT한다("push"가 아니라 execute에서 insert하는 형식).

아래는 흐름을 재구성한 예시다(테이블, 컬럼 이름은 설명용).

import sqlite3

conn = sqlite3.connect(db_path)
conn.execute("""
CREATE TABLE IF NOT EXISTS requests (
    request_id   TEXT PRIMARY KEY,   -- 키
    source_text  TEXT,               -- 사용자 원문
    kind         TEXT,               -- 요청 종류
    payload_json TEXT                -- 파싱 결과 JSON
)""")
# + 조회, 수정용으로 날짜 등을 정리한 테이블(정규화 데이터)을 ID로 연결해 추가 생성
conn.commit()

순서를 정리하면 DB를 미리 만들어 두고 → 거기에 저장할 데이터를 툴로 추출하고 → 추출한 데이터로 저장을 따로 실행하는 구조다.

원문(source_text)을 먼저 저장하는 이유

예제는 사용자 요청을 바로 파싱해서만 넣지 않고 원본 데이터(source_text)를 먼저 넣고 진행한다. 원문이 남아 있어야 나중에 필요한 정보를 다시 체크하거나 다른 방식으로 활용할 수 있기 때문이다. 원문과 함께 종류, 제목 등으로 파싱한 값을 같이 저장한다.

팁 파싱은 확률적으로 틀릴 수 있다. 원문을 함께 저장해 두면 잘못 파싱된 레코드를 나중에 다시 확인, 재처리할 수 있다.

저장 툴: 검증된 인자만 INSERT

저장 툴은 name, description, 그리고 args_schema로 앞에서 만든 Pydantic 클래스를 넣어 정의한다. args_schema가 인자(source_text, title, kind, 시작, 종료 시간, date, members, priority, reason …)의 필터가 되어, 툴 함수에는 검증된 인자만 들어온다(args_schema 개념은 → 구조화된 출력과 Pydantic).

툴 안에서는 두 가지 방식으로 값을 정리할 수 있다. 입력을 payload로 받아 정리하거나(model_dump()), 구조화된 입력 객체의 속성을 직접 꺼내 쓴다. 정리한 값으로 쿼리를 실행하면 DB에 저장된다. 여기까지가 툴이다. 툴이 좀 복잡한 편이다.

아래는 재구성한 예시다. 함수 내부는 설명용으로 단순화했고 new_id() 같은 보조 함수는 가정이다.

def save_structured_request(**kwargs):              # args_schema로 검증된 인자만 들어옴
    req = ScheduleRequest(**kwargs)
    payload = req.model_dump()                       # 검증된 값을 dict로 변환
    conn = sqlite3.connect(db_path)
    conn.execute(
        "INSERT INTO requests (request_id, source_text, kind, payload_json) VALUES (?, ?, ?, ?)",
        (new_id(), req.source_text, req.kind, json.dumps(payload, ensure_ascii=False)),
    )
    conn.commit()
    return "저장했습니다"

# name, description, args_schema를 따로 지정하는 LangChain 방식 중 하나
save_tool = StructuredTool.from_function(
    func=save_structured_request,
    name="save_structured_request",
    description="사용자 일정 요청을 검증해 DB에 저장한다",
    args_schema=ScheduleRequest,
)
agent = create_agent(model, tools=[save_tool, list_tool, delete_tool], system_prompt=SYSTEM_PROMPT)

모델은 temperature=0으로 두고 실행했다. 일정 요청을 넣으면 트레이스에 save_structured_request 툴콜과 arguments가 찍히고, "…일정을 잡았습니다" 같은 자연어 답이 돌아온다. "두 명이 진행하는 중요한 일정"처럼 프롬프트를 바꾸거나 개인 일정으로 바꾸면 kind가 달라지는 것을 확인할 수 있다.

주의 스키마 없이 "이 JSON 형식을 채워라"로 툴 인자를 넘기면 키가 누락돼 툴콜이 실패하고, 실패할 때마다 인자 생성이 반복돼 손실이 쌓인다. 저장 툴처럼 실제 시스템에 쓰는 툴일수록 args_schema를 건다.

조회, 삭제 툴과 "조회 후 삭제" 흐름

저장만 있는 게 아니다. 과제 앱에서는 조회(list 계열)와 삭제(delete) 툴이 함께 동작했다.

  • "지금 일정이 뭐가 있어?" → list 계열 툴로 조회.
  • "내일 10시 민수와 1:1 미팅 취소" → list로 조회한 뒤 delete. 상세 페이지에서 list → delete 순서로 호출된 것을 확인할 수 있다.

삭제는 ID 등을 확인해야 한다. 그냥 지우려 하면 대화가 새로 시작됐거나 컨텍스트가 끊긴 상태에서 어떤 레코드인지 몰라 실패한다. 그래서 삭제 요청은 조회 후 삭제가 가장 좋다. 1, 2주차가 툴 1개 실행이었다면, 고도화될수록 한 번에 2~3개 이상 툴을 실행한다.

툴(조회, 생성, 삭제)은 고정돼 있어도 어떻게 조합해야 동작이 정확히 끝나는지는 따로 고민해야 한다. 그 순서를 시스템 프롬프트에 CoT나 few-shot으로 넣으면 실패 없는 에이전트가 된다(툴 조합 일반론은 → Tool과 Function Calling, 프롬프트 기법은 → 프롬프트 엔지니어링).

프롬프트는 어디에 둘까: 시스템 프롬프트 vs 툴 description

에이전트 구성은 LLM + 시스템 프롬프트 + tools(툴이나 MCP 형식) + 실행 시 붙는 유저 메시지다. 저장 규칙을 어디에 쓸지가 고민거리다.

  • 지금 예제는 DB 저장 기능 하나라 시스템 프롬프트에 넣었다.
  • 툴별 기능이 여러 개면 그 내용은 툴 description에 넣는 편이 더 좋다. 다만 툴 description도 툴이 등록되면 같이 넘어가므로 성격이 조금 다르다.
  • 회사명 같은 고유명사, 정해진 값은 시스템 프롬프트에 다 넣지 말고 툴 description과 args_schema(Literal)로 고정한다. 모든 정보를 시스템 프롬프트에 넣으면 컨텍스트가 찬 상태로 시작한다.
  • 날짜 같은 기준 정보는 넣어도 되고 안 넣어도 된다. kind, 요청 분류가 스키마에 있으면 굳이 안 넣어도 동작한다.

3주차 과제는 프롬프트를 일부러 두 개로 나눠 두었다. 조회, 검색 규칙 프롬프트와 툴을 조정하는 프롬프트다. 수정할 때는 각각 해당 위치에서 고치는 편이 컨트롤하기 쉽다.

저장이 정말 됐는지 확인하기: tool trace와 실제 저장소

실행 결과의 tool call 파트에서 어떤 툴이 불렸는지, 어떤 arguments가 들어갔는지를 반드시 확인한다. 툴콜이 실행됐다는 것은 LLM이 요청을 만든 것에 그치지 않고, 그 툴 함수 코드가 로컬에서 실제로 다 실행됐다는 뜻이다. 거기 넣어 둔 DB 저장 같은 처리가 모두 동작한 것이다. 싱글 에이전트 디버깅의 약 80%는 tool call 확인이다(트레이스 디버깅은 → Tool과 Function Calling).

  • 노트북 뒤쪽 체크 셀은 특정 프롬프트에 대한 기대 출력을 고정해 두고 제약대로 나오는지 확인한다. 프롬프트를 바꾸면 통과하지 않을 수 있다.
  • 과제 앱에서도 채팅 화면보다 상세 페이지에서 어떤 툴, 어떤 argument가 쓰였는지 보는 게 가장 정확하다.

주의 트레이스만 믿지 말 것. 짧은 테스트와 트레이스만 보고 실제 저장소를 직접 확인하지 않으면 과제 코드의 버그를 놓치기 쉽다. 저장소를 직접 열어 보고, 경계 케이스를 테스트에 넣어야 한다.

DB 설계도 프롬프트로 써 보기

입출력 양, 원격 구성 여부 같은 DB 설계는 모델에 맡길 수도 있고 원하는 스펙을 직접 줄 수도 있다. 이 부분을 프롬프트로 직접 써 보는 연습이 도움이 된다. 이렇게 했을 때의 문제점과 한계도 함께 적어 넣는 것이 좋다.

코드 에이전트에게 구현을 맡길 때도 "DB와 툴이 이렇게 연결돼야 하는데 왜 함수 두 개를 끼워 넣었지?" 같은 지점을 잡아내야 한다. 도메인 지식과 어긋나는 계획을 찾는 연습은 → AI 코딩 도구 활용(Claude Code, Codex)에서 다룬다.

저장한 데이터의 이후 쓰임: SQL 검색, MCP 서버, 공유 저장소

3주차에 SQLite에 쌓은 데이터는 뒤 주차에서 계속 쓰인다. 각 주제는 해당 장에서 자세히 다룬다.

주차 SQLite 데이터의 쓰임
4주차 Pydantic 검증으로 저장했던 SQL 저장 기록과 대화 목록(이전 채팅) 을 출처별로 검색한다. 툴이 여러 개라 "SQL을 검색했을 때 결과가 없으면 대화 목록을 검색해라"처럼 시스템 프롬프트에 CoT 워크플로를 쓴다(→ RAG: 임베딩 검색과 ChromaDB)
5주차 "외부 멤버 대화, 일정 SQLite MCP stdio 서버"가 미리 구현돼 있고, 지난 대화 검색 같은 툴을 MCP 클라이언트로 불러 쓴다. DB 연동 툴을 직접 다 구현하기는 매우 어려우니 있는 MCP 서버를 활용한다(→ MCP와 A2A)
5~6주차 DB가 개인 저장소와 외부(공유) 저장소 두 개로 나뉜다. 공유 일정 검색에서 kind 필터를 잘못 넣은 버그가 6주차까지 영향을 줬다(→ 주차별 실습 프로젝트)

정리 3주차까지 알게 된 세 가지. ① 툴을 만들어 두면 에이전트가 쓸 수 있다. ② 툴 입력을 구조화된 출력으로 필터링할 수 있다. ③ 에이전트의 최종 출력도 구조화된 출력으로 만들 수 있다. DB 저장은 이 셋을 묶어 "에이전트가 실제 시스템에 안전하게 쓰는" 첫 사례다.

주제 3

RAG: 임베딩 검색과 ChromaDB

학습하지 않은 외부 데이터를 검색해 프롬프트에 넣어 주는 RAG를 Retrieval, Augmented, Generation 세 단계로 나눠 보고, ChromaDB 코드, 청크, top-k 설정, 저장소 분리(Agentic RAG), 하이브리드 검색, 리랭킹, 쿼리 리라이팅 같은 확장 기법, 파인튜닝과의 선택 기준까지 정리한다.

4주차의 주제다. 1주차 툴, 2주차 구조화된 출력, 3주차 툴과 구조화된 출력을 이용한 필터링에 이어 4주차에 RAG를 붙였다. 노트북은 4주차_나나가_기억을_찾아오다.ipynb다.

RAG의 위치와 정의: "검색 방법론"

  • RAG는 LLM을 공부하다 보면 가장 많이 나오는 용어 중 하나다. ChatGPT가 나온 뒤 LLM을 활용하는 과정에서 가장 먼저 만들어진 "보조적인 방법론"이다.
  • RAG = Retrieval-Augmented Generation. 데이터를 검색하고(Retrieval), 프롬프트를 증강하고(Augmented), 답변을 생성하는(Generation) 흐름이다.
  • 정확히는 "외부 데이터를 검색하는 방법론"이다. 특정 라이브러리가 아니라 구현 방법이라서 Python만 있어도, OpenAI 툴 몇 개만 있어도 만들 수 있다. 이 흐름대로 구현하면 모두 RAG라고 부른다.
  • 지금은 RAG가 에이전트 안에 흡수됐다고 봐도 된다. 에이전트가 RAG를 툴처럼 불러 데이터를 가져와 쓰는 형식이다.
  • 프레임워크로는 LangChain과 LlamaIndex가 있다. LangChain은 이름 그대로 프롬프트를 순차 실행해 더 좋은 답을 얻는 프롬프트 체인 프레임워크이고, LlamaIndex는 RAG를 구현하기 위한 프레임워크다. 둘 다 지금은 에이전트 구현 형식으로 코드가 많이 바뀌었다.
  • 여기서 배우는 개념은 LangChain으로 에이전트를 직접 코딩할 때도 거의 그대로 쓰인다. 프롬프트, 예제, 참고 자료 형태로 응용하려고 배우는 것이다.

정리 RAG는 라이브러리 이름이 아니라 "검색해서 프롬프트에 넣고 생성한다"는 흐름의 이름이다. 지금은 에이전트의 툴 하나로 들어가 있다.

RAG가 필요한 이유: 학습하지 않은 데이터를 프롬프트로

  • LLM은 최신 데이터를 반영하기 어렵다. 모델이 너무 커서 학습 시간과 비용이 크고, 새 데이터가 나올 때마다 학습시킬 수 없다. 그래서 학습하지 않은 데이터를 프롬프트로 전달해 참고하게 한다.
  • 초창기에는 모델의 입력 컨텍스트가 길지 않았다. 전체 데이터를 넣는 방식은 비효율적이었고, 원본을 청크(chunk)로 잘라 필요한 조각만 프롬프트에 넣는 방법이 발전했다. 그게 RAG다.
  • RAG 연구 전체를 "더 많은 데이터를 효율적으로 검색하는 법"이라고 요약할 수 있다.

"Retrieval"의 뜻과 벡터 검색의 뿌리

  • Retrieval은 "검색하다"로 번역하지만 평범한 search가 아니다. 벡터(임베딩)로 바뀐 데이터 안의 내재된 정보를 찾는 것이다.
  • 이 용어를 쓰는 연구 분야로 IIR(Image Information Retrieval)과 MIR(Music Information Retrieval)이 있다. MIR은 음악과 AI를 연구하는 ISMIR 학회의 주제이고, 최근 상용화된 예로 음원 분리가 있다.
    • 그림 예: "사람이 집으로 가고 있다, 남자인 것 같다, 집에 굴뚝이 있다". 단순히 "사람"이 아니라 "강아지 산책을 끝내고 집에 가는 중"이라는 정보를 찾는 것이다.
    • 음원 예: "여자 보컬, 피아노, 드럼, 베이스 소리가 들린다", 음 찾기.
    • 동작: 이미지, 음원을 딥러닝 모델에 넣으면 벡터가 나온다. 이를 해석, 분류, 예측해 텍스트 등 원하는 정보로 바꾼다.
  • RAG를 만든 사람들도 딥러닝을 다루던 사람들이라 모델이 내는 벡터로 검색하는 데 익숙했다. 콘텐츠 기반 추천 시스템은 데이터를 벡터로 만들고 유사도(거리)로 평가한다. 기준점과 거리가 작을수록 비슷한 것을 추천한다. 이 거리를 loss로 삼아 학습하는 contrastive learning 기반 추천 모델도 있다.
  • 그래서 LLM에서 텍스트를 검색할 때도 이 방법을 적용했다. 많은 데이터를 빠르게 검색할 방법으로는 지금 벡터 검색 말고는 마땅한 것이 없다. 이게 가능한 건 임베딩 모델이 잘 학습됐기 때문이다.
  • 사과 예시: (3,3,3) 근처에 있는 사과가 좋은 사과라면, 거리가 2 이하, 더 좁혀 1 이하인 것만 찾으면 더 좋은 사과를 고를 수 있다. 이런 거리 검색을 제공하는 것이 벡터DB다. 검색은 나중에 추천으로도 이어진다.

RAG 3단계 그림: Retrieval → Augmented → Generation

RAG의 전체 구조는 다음과 같다.

[원본 문서] ─청크로 자르기─▶ 임베딩 ─▶ 벡터DB(원본 텍스트 + 벡터)
                                              │
[사용자 질문] ─────────── 같은 임베딩 ─▶ 질문 벡터 ─▶ 거리 계산 → 가까운 청크 D1, D2   ① Retrieval
                                              │
        f"검색된 정보: {context}  사용자의 질문: {question}  위 두 내용을 참조해서 답해주세요"   ② Augmented
                                              │
                                        LLM 생성 → 답변                                ③ Generation

① Retrieval(검색)

  • 질문 "휴가 규정이 어떻게 되나요?"와 저장된 휴가 규정 문장 사이의 유사도를 계산한다. 사람은 어떤 문장을 참고할지 감으로 알지만, 계산하려면 유사함의 기준이 필요하다. 그래서 같은 기준, 같은 차원으로 벡터를 만드는 임베딩 모델(임베딩 레이어)을 쓴다. 실습은 OpenAI 임베딩 모델을 썼다.
  • 질문과 데이터가 같은 공간에 찍히면 거리로 유사도를 점수화할 수 있다. 예를 들어 "이 데이터는 질문과 거리 0.3"이고, 가까울수록 유사하다. 이것이 RAG의 가장 기본인 거리 기반 벡터 검색이다.

② Augmented(증강)

  • 앞에서 배운 프롬프트 synthesize(f-string으로 변수 넣기, 미리 만든 프롬프트 합치기)와 같다.
  • 검색된 D1, D2만 넣어도 모델 성능에 따라 답할 수는 있다. 하지만 청크는 글자 수대로 잘리는 경우가 많아 문장 중간을 뜯어 온 것처럼 앞뒤가 잘려 있기도 하고, 잘못 검색된 데이터가 들어갈 수도 있다. 그래서 검색 결과를 정제하고 두 내용을 정확히 참조하도록 프롬프트를 다시 만든다.
  • 프롬프트 예시(재구성):
prompt = f"""검색된 정보: {context}
사용자의 질문: {question}
위 두 내용을 참조해서 질문에 답해주세요"""
  • Augmented가 꼭 자연어일 필요는 없다. 원하는 형식으로 가공해 모델로 넘기면 된다.
  • 답이 없을 때 "모른다고 대답해라"를 붙이는 답변 컨트롤은 → 프롬프트 엔지니어링에서 다룬다.

③ Generation(생성)

  • LLM이 생성하는 단계라 우리가 개입할 여지가 없다. 결과는 어떤 데이터가 검색되고 어떤 프롬프트를 만들었느냐에 크게 좌우된다.
단계 하는 일 담당 우리가 조절할 수 있는 것
Retrieval 질문, 데이터를 같은 임베딩으로 벡터화하고 거리로 가까운 청크를 찾는다 임베딩 모델 + 벡터DB 검색 개수(top-k), 청크 크기, 임베딩 모델 선택
Augmented 검색 결과, 질문, 지시를 하나의 프롬프트로 합성한다 우리 코드(f-string 등) 프롬프트 문구와 형식. 동작은 주로 여기서 제어한다
Generation 합성된 프롬프트로 답을 만든다 LLM 직접 개입 불가. 앞 두 단계의 결과에 좌우된다
  • 한 줄로 정리하면 검색은 벡터 기반이지만, 모델에 들어갈 때는 다시 텍스트 컨텍스트(조건)로 구성된다. 프롬프트 합성 단계에서 검색된 데이터(조건), 사용자 질문(요청), 지시사항을 넣는다.
  • RAG는 LLM 이전의 언어 생성 모델에서도 비슷하게 쓰이던 방식인데, LLM 프롬프트와 결합하면서 널리 퍼졌다. "가장 초창기 방법"이고, 여기에 개선을 더하면 "새로운 RAG"가 된다.

정리 원하는 답이 안 나오면 Retrieval 쪽에서는 검색 개수 정도를, Augmented 쪽에서는 프롬프트를 고친다. Generation은 손댈 수 없다.

임베딩 공간, 청크, 거리 지표

  • 질문("휴가 규정이 어떻게 돼?")을 하나의 벡터로 만든다. 규정 전체를 하나의 벡터로 만들면 뜻이 뭉뚱그려져 제대로 인식되지 않으므로, 원본을 청크로 잘라 각각 벡터로 만든다. 같은 임베딩을 통과하면 같은 공간에 점으로 찍히고, 그 상태에서 질문과 가까운 점을 찾는 것이 Retrieval이다.
  • 모호한 자연어를 임베딩으로 의미적으로 가까운 데이터로 바꿔 연산 가능하게 만드는 것이 핵심이다. RAG에서 가장 이해하기 어려운 부분이지만 딥러닝 동작만 알면 당연한 방법이다.
  • 문장 임베딩은 토큰 벡터를 평균 내는 방식(mean pooling)이라 글 길이와 상관없이 1,536차원 벡터 하나가 된다. 임베딩, 차원, mean pooling의 원리는 → Transformer 블록 해부에서 다룬다.
  • 임베딩은 특징을 "뽑아낸다"기보다 학습한 대로 자기 기준을 보여 주는 것이다. ChatGPT, BERT 계열 임베딩을 쓰는 이유는 텍스트 이해 벤치마크에서 성능이 준수하고, 실제로 비슷한 문장을 찾아 준다는 실험들이 있기 때문이다.
  • 거리 계산은 데이터 사이언스에서 쓰는 것을 그대로 쓴다.

코사인 유사도 두 벡터의 방향(각도) 필요하면 쓴다
  • 임베딩 크기를 크게 하거나 작게 해서 정확도를 조절하기도 한다.

주의 외부 데이터와 질문은 항상 같은 임베딩 모델로 처리해야 한다. 서로 다른 임베딩 모델은 학습한 공간이 달라 기준점이 맞지 않으므로 비교 자체가 불가능하다.

  • 꼭 임베딩 모델만 되는 건 아니다. 텍스트를 벡터화할 방법이면 다 검색할 수 있다(BERT 등). 그래프 네트워크로 검색하면 Graph RAG, 온톨로지 같은 지식 그래프를 붙이면 또 다른 RAG가 된다. 어떤 방식이든 같은 기준으로 검색해야 한다.

벡터DB: 원본과 벡터를 짝지어 관리

  • 벡터DB는 실제 데이터(텍스트)와 그것을 임베딩한 벡터를 하나의 인덱스로 짝지어 관리하는 데이터베이스다. 벡터와 텍스트가 연결돼 있으니 검색 결과를 바로 텍스트로 돌려받는다.
  • 초기에는 ChromaDB, FAISS 같은 전용 벡터DB가 쏟아져 나왔다. 지금은 기존 DB도 임베딩을 지원해 상용 DB를 그대로 쓰기도 하고, 필요하면 직접 구현하기도 한다.
  • 원래는 벡터화, 입력, 검색을 다 수동으로 해야 했지만 벡터DB가 해 준다. 데이터와 질문만 넣으면 내부에서 벡터화하고 검색해 질문과 검색된 데이터를 돌려준다. 그걸 받아 프롬프트를 만들어 모델로 보내면 RAG가 완성된다.
  • 즉 벡터DB가 담당하는 범위는 Augmented 직전까지다.

정리 벡터DB = 원본 텍스트와 벡터를 페어로 저장하고 거리 검색을 제공하는 저장소. 프롬프트 합성은 우리 몫이다.

ChromaDB 핵심 코드: 클라이언트, 임베딩 함수, 컬렉션

  • 코드는 이론에 비해 매우 단순하다. 핵심은 ① 클라이언트 선언, ② 임베딩 함수, ③ create_collection이다. 컬렉션이 본체다.
  • 클라이언트는 3종이다.
클라이언트 저장 위치 용도
Client 메모리 연습용. 디스크에 저장되지 않는다
PersistentClient 로컬 디스크 노트북에서 쓰고, 실무에서도 주로 이것을 쓴다
remote(원격) 클라이언트 원격 서버 원격 접속. 협업, 배포 환경용
  • 클라이언트에는 "어디에 저장할지"만 입력하고, 바로 클라이언트에서 컬렉션을 만든다. 컬렉션에는 이름과 임베딩 함수가 들어간다.
  • 임베딩 함수에는 API 키, 프록시(base URL), 사용할 모델이 들어간다. 노트북은 OpenAI의 작은 임베딩 모델(text-embedding-3-small 계열)을 쓴다.
  • 벡터DB는 스스로 임베딩 모델을 갖고 있지 않다. 외부 모델을 꽂아 줘야 한다. OpenAI는 자주 쓰여서 전용 임베딩 함수가 있고, 다른 모델은 임베딩 함수 템플릿에 맞춰 "벡터를 리턴하는" 형식으로 커스텀하면 된다.

아래는 재구성한 예시다(인자명은 설명용).

import chromadb
from chromadb.utils import embedding_functions

# ① 클라이언트: "어디에 저장할지"만 정한다
client = chromadb.PersistentClient(path="...")     # 로컬 디스크 저장(주로 사용)
# client = chromadb.Client()                       # 메모리 전용(연습용)

# ② 임베딩 함수: 벡터DB에는 임베딩 모델이 없으니 외부 모델을 꽂는다
embedding_fn = embedding_functions.OpenAIEmbeddingFunction(
    api_key=...,
    api_base=...,                           # 프록시 주소
    model_name="text-embedding-3-small",    # 작은 임베딩 모델
)

# ③ 컬렉션: 이름 + 임베딩 함수. 컬렉션이 본체다
memory_collection = client.create_collection(
    name="...", embedding_function=embedding_fn
)
  • 실무에서는 벡터DB를 먼저 외부에 만들어 두고 불러 쓰므로 코드에 생성부가 들어가지 않는다. 노트북은 선언 과정도 보여 주려고 같은 코드에 넣었다.

주의 컬렉션 이름은 한 프로세스 안에서 중복되면 안 된다. 노트북 셀을 엔터로 다시 실행하면 같은 이름의 컬렉션을 또 만들려다 런타임 오류가 난다. 한 번 선언한 뒤에는 리셋하거나 이름을 바꿔야 한다. 생각보다 문제가 많이 발생하는 부분이다.

컬렉션의 add, query와 리트리버

  • add: ids는 필수(인덱스 번호만 넣어도 된다), documents는 실제 데이터, metadatas는 없어도 동작한다. 아이디와 도큐먼트를 넣고 add하면 데이터가 벡터DB로 들어간다.
  • query: 질문 같은 것을 컬렉션에 넣으면 그 시점부터 벡터 검색이 시작된다. 임베딩 함수가 질문과 저장된 데이터를 벡터로 만들고 거리를 계산해 가장 가까운 것을 돌려준다.

아래는 재구성한 예시다(데이터는 제주도 예시).

memory_collection.add(
    ids=["0", "1"],                                   # 필수. 인덱스만 넣어도 된다
    documents=["제주시에 대한 정보 ...",               # 실제 데이터(D1)
               "서귀포시에 대한 정보 ..."],            # (D2)
    # metadatas=[...],                                # 선택
)

found = memory_collection.query(
    query_texts=["서귀포는 제주시에서 얼마나 걸려?"],
    n_results=1,                                      # 몇 개를 가져올지(top-k)
)
# found에는 질문과 가장 가까운 D2(서귀포 쪽) 원문이 들어 있다
  • 컬렉션은 프롬프트를 만드는 데까지가 아니라 데이터를 찾아오는 데까지만 한다. 이걸 리트리버(retriever)라고 한다.

비유 강아지 리트리버와 똑같다. 뭔가 찾아서 데려오는 녀석이다. 저장한 원본 데이터를 그대로 물어 온다.

  • 컬렉션을 함수로 만들어 저장소를 여러 개 두기도 한다. 노트북은 단일 저장소이고, 이를 툴로 써서 검색하게 한다.

초기형 RAG에서 툴형 RAG로

  • 완전 초창기에는 에이전트가 없었다. 질문할 때마다 무조건 외부 데이터를 검색하고 프롬프트를 만든 뒤, 참고할 필요가 없으면 그냥 답하는 식이었다. Retrieval, Augmented 과정이 모델 앞단에 고정돼 있어 끌 수 없었고 매우 비효율적이었다.
  • LLM은 입력, 출력 토큰이 모두 과금되는데, 이 방식이 입력 토큰을 늘리는 주원인이었다. 그래서 프롬프트 캐싱이 생겼다. ChatGPT는 같은 프롬프트가 반복되면 비용을 깎아 주는 정책이 있고, Claude는 캐싱을 직접 설정해야 한다.
  • function calling이 나오면서 Retrieval, Augmented 부분을 툴로 만들 수 있게 돼 구조가 유연해졌다. 4주차 노트북은 리트리버를 만들고 툴콜로 검색하는 데까지 구현돼 있다.
  • 검색 툴의 인자는 두 가지다.
    • query: 사용자 프롬프트에서 검색할 키워드를 뽑거나 프롬프트 자체를 분석해 LLM이 채운다(툴콜 때 배운 방식, → Tool과 Function Calling).
    • 결과 개수(n_results): 몇 개를 검색해 올지 정한다.
  • 검색 결과(found)에는 찾아온 데이터 문자열이 들어가고, 이를 합쳐 프롬프트를 다시 만든다. 노트북은 SQL에 저장된 데이터도 함께 찾느라 별도 포맷으로 다시 만든다.

아래는 재구성한 예시다(툴 이름은 설명용).

@tool
def search_memory(query: str, n_results: int = 2) -> str:
    """저장된 기억에서 관련 내용을 검색한다."""     # LLM은 이 설명을 보고 query를 채운다
    found = memory_collection.query(query_texts=[query], n_results=n_results)
    return "\n".join(found["documents"][0])         # 찾아온 문자열을 합쳐 프롬프트 재료로
  • 저장소, 검색 툴이 여러 개가 되면 "찾아 줘"라고 해도 원하는 툴까지 안 가는 경우가 생긴다. 이때 시스템 프롬프트에 검색 순서를 CoT로 적는 방법은 → 프롬프트 엔지니어링에서 다룬다.

정리 RAG의 Retrieval, Augmented가 모델 앞에 붙박이였던 시절에서, 필요할 때만 부르는 툴로 바뀌었다. 지금 에이전트에서 RAG는 "검색 툴 하나"다.

청크 분할 전략 비교

  • 외부 데이터를 청크로 나눌 때 가장 간단한 방법은 길이로 자르기다. 256으로 설정하면 256씩, 2,000자 등 원하는 대로 자른다.
  • 예: 1만 자 문서를 통째로 넣으면 청크 1개, 5,000자씩 자르면 2개, 2,500자씩 자르면 4개다. 5,000자든 2,500자든 1만 자든 모두 1,536차원 벡터 하나가 되므로 검색이 빠르다.
  • 하지만 통째로 만든 것과 부분부분 만든 것은 정확도가 다르다. 잘게 자를수록 원하는 부분을 더 잘 찾지만 검색할 벡터가 늘어난다. 딱 필요한 부분을 찾아 넣어야 컨텍스트도 줄고 더 정확하다.
  • 조금 더 신경 쓰면 의미 단위로 자른다. 마크다운은 #으로 문단이 나뉘므로 제목 → 주제1 → 소주제1… 구조에서 주제나 소주제 기준으로 자른다. 어떤 청크는 100자, 어떤 건 300자가 되지만 결국 같은 크기의 벡터가 되고, 더 정확한 의미를 갖고 검색돼 성능이 오른다.
전략 자르는 기준 장점 단점
통째로(stuff) 자르지 않음, 문서 전체가 청크 1개 구현이 가장 쉽다 뜻이 뭉뚱그려져 검색이 부정확하고 컨텍스트가 커진다. 잘 쓰지 않는다
길이 기준 글자 수(256, 2,000자 등) 가장 간단하다. 잘게 자를수록 원하는 부분을 더 잘 찾는다 문장 중간이 잘린다. 잘게 자를수록 검색할 벡터가 늘어난다
의미 단위 마크다운 헤더(주제, 소주제), 문단 청크마다 뜻이 온전해 더 정확하게 검색된다 청크 길이가 들쭉날쭉하다(벡터 크기는 같다). 데이터 구조를 먼저 봐야 한다
  • 데이터 정제와도 이어진다. LLM, SLM을 학습할 때도 문장이 중간에 잘린 데이터는 정제하는 경우가 많다. 잘린 문장은 "데미지를 입은 채" 전달돼 답변 점수가 떨어진다. 데이터 정제는 모델을 다룰 때 항상 필요하니 데이터 쪽에 공을 들여야 한다.

팁 청크는 가능하면 의미 단위로, 문장이 중간에 잘리지 않게 자른다.

top-k: 가져올 청크 수 정하기

  • top-k는 검색할 때 몇 개의 청크를 가져올지다. 청크가 2개인데 k=2면 전체를 가져오는 것이고, 4개 중 2개면 절반만 가져온다.
  • 먼저 내 데이터가 청크 몇 개로 만들어졌는지 확인해야 한다. 보통 절반에서 1/3, 1/4 정도를 가져온다.
  • 정확한 값은 테스트 데이터를 만들어 찾아야 한다. 에이전트는 만들고 끝이 아니라 잘 동작하는지 검증해야 하고, top-k는 그때 맞추는 파라미터다. 검증 방법은 → 에이전트 평가와 LLM-as-a-judge에서 다룬다.

저장소 분리와 Agentic RAG

  • 원래 RAG는 하나의 데이터 세트로 동작했다. 예전에는 에이전트처럼 유연한 구조가 아니라서 어쩔 수 없이 저장소를 크게 만들었다.
  • 리트리버(컬렉션)를 여러 개 만들고 각각 툴로 연결하면, 프롬프트에 따라 원하는 저장소를 골라 검색할 수 있다. 검색할 자료가 분리되면 검색 효율이 올라간다.
  • 반대로 벡터DB에 데이터를 너무 많이 넣으면 검색이 잘 안 된다. 벡터화는 텍스트의 의미를 조금씩 잃으면서 만드는 것이라 잘못 검색될 수 있고, 데이터 크기에 따라 크게 흔들린다. PDF가 수백~천 페이지를 넘어가면 검색, 답변, 턴이 모두 오래 걸린다.
  • 이런 걸 Agentic RAG, Adaptive RAG라고도 부른다. 정식 명칭이라기보다 "그냥 에이전트가 붙은 RAG"에 가깝다. 검색 방식을 그래프 네트워크로 바꾸면 Graph RAG가 된다. 벡터로 검색하는 핵심만 지키면 다른 모델, 방법을 적용해도 다 RAG다.
  • 한 저장소에 데이터가 너무 몰리면 검색 능력 자체가 떨어진다. 데이터를 한 번에 저장할지 툴로 나눠 저장할지 잘 확인해야 한다.

주의 모든 데이터를 하나의 벡터DB에 넣는 것은 "매우 안 좋은 방법"이다. 데이터 구조를 직접 보고 계층, 분리를 해야 RAG를 툴로 제대로 구현할 수 있다.

멀티모달 임베딩과 통합 임베딩 공간

  • 벡터DB는 텍스트 대신 이미지, 오디오, 영상도 저장할 수 있다. 해당 데이터를 벡터로 바꿀 임베딩만 넣어 주면 된다.
  • 전통적으로 이미지-텍스트용 CLIP, 오디오-텍스트용 CLAP이 있다. 최근에는 Google이 Gemini 계열에 쓰이는 멀티모달 임베딩 모델을 내놓았다.
  • ChatGPT 쪽 임베딩이 텍스트에 집중했다면, Gemini는 멀티모달 모델이다. 그 임베딩에 오디오, 이미지, 영상(=이미지+오디오), 텍스트를 넣으면 같은 공간에 정리된다. 이를 "통합된 임베딩 스페이스"라고 부른다.
  • 논문 블록 그림에서 설명 없이 공간을 그려 놓는 것도 모두 이 얘기다. 데이터가 모델을 통과하면 텐서가 나오고, 그 데이터는 특징 차원만큼의 공간에 있는 점이 된다. 같은 공간에 찍을 수만 있으면 어떤 데이터든 벡터 검색이 가능하다. 이미지와 텍스트를 함께 다루려면 CLIP이나 Google의 멀티모달 임베딩 계열을 쓰면 된다.

예시 이상탐지: 사람이 쓰러져 있는 영상이 검색되면, 공간 안에서 가까운 텍스트로 "지금 사람이 쓰러져 있다"는 문장을 Gemini 같은 멀티모달 모델이 만들어 낼 수 있다. 시각적 해석, 이상탐지 모델을 만들기 쉬워진다.

RAG와 스킬, 플러그인의 선택 기준

  • 예시는 짧은 문장이었지만, RAG는 기본적으로 책이나 규정처럼 상대적으로 큰 데이터를 다룰 때 쓴다. 데이터를 잘라(청크) 검색한다.
  • 스킬, 플러그인은 일종의 작업지시서라서 길어도 잘리지 않고 통째로 들어가는 경우가 있다.
구분 RAG 스킬, 플러그인
성격 검색해서 참고할 자료 작업지시서
넣는 방식 청크로 잘라 필요한 조각만 길어도 통째로
맞는 대상 책, 규정처럼 큰 데이터 전체 흐름을 그대로 유지해야 하는 지시
  • 구현에 따라 고르면 된다. 스킬 자체는 → 프롬프트 엔지니어링에서 다룬다.

기본 RAG의 한계와 개선 세 갈래

  • 지금까지 본 RAG는 "가장 기초"적인 형태다. 검색이 마음에 안 들면 검색 부분을 직접 손대 새 모델을 쓰거나 임베딩을 다시 만드는 식으로 수정한다.
  • 실제로 돌려 보면 원하는 검색이 잘 안 되고, Augmented 프롬프트에 따라 결과가 달라진다. 사용자 질문(쿼리)과 저장된 데이터가 잘 맞지 않아 벡터 검색이 제대로 안 되기도 한다.
  • 벡터 검색 자체의 약점도 있다. 임베딩 청크 크기, 질문 형태, 에이전트가 쿼리를 스스로 고쳐 넣는 동작 때문에 결과가 달라질 수 있다.
  • 그래서 개선 연구가 계속 나온다. 크게 세 갈래로 정리할 수 있다.
갈래 대표 기법 손대는 곳
① 검색 방법 추가 하이브리드 검색 Retrieval(코드)
② 검색 결과 정제 리랭킹 Retrieval과 Augmented 사이
③ 질문 정제 쿼리 리파인, 리라이팅 검색 전 질문(프롬프트)
  • 초기 RAG에 아이디어를 적용해 테스트하고 정리하면 그게 논문이 된다. RAG, 리랭킹 같은 용어도 딱 정립된 정의라기보다 "이런 작업을 가리킨다" 정도로 이해하면 된다.

확장 ① 하이브리드 검색: 키워드 검색 + 벡터 검색

  • 가장 쉽게 추가할 수 있는 확장이다. 원래 쓰던 검색 엔진식 키워드 검색과 리트리버(벡터 검색)를 섞는다.
  • 예: "휴가 규정이 어떻게 되나요?"를 바로 임베딩할 수도 있지만, 구조화된 출력이나 LLM에 "키워드 뽑아줘"라고 시켜 "휴가", "휴가 규정" 같은 키워드를 뽑아 직접 검색할 수도 있다.
  • 결과적으로 ① 키워드 검색 결과와 ② 벡터 검색 결과가 나오고, 둘을 Augmented 프롬프트에 함께 넣어 답하게 한다.
  • 키워드 검색은 원본 데이터만 있으면 매칭 알고리즘으로 동작한다. 벡터화와 무관하니 질문이 들어올 때 검색하도록만 구현하면 바로 적용된다.

아래는 재구성한 예시다.

keywords = llm.with_structured_output(Keywords).invoke(
    f"다음 질문에서 검색 키워드를 뽑아라: {question}")
kw_results = keyword_search(keywords)              # ① 키워드(검색 엔진식) 검색
vec_results = collection.query(query_texts=[question], n_results=3)   # ② 벡터 검색
prompt = f"""[키워드 검색 결과]\n{kw_results}
[벡터 검색 결과]\n{vec_results}
질문: {question}"""
answer = llm.invoke(prompt)

정리 검색 쪽은 코드로 개선하고, 뒤쪽 Augmentation 개선은 프롬프트에서 한다.

확장 ② 리랭킹: 검색 결과 다시 줄 세우기

  • 원래는 검색된 내용을 그대로 프롬프트에 넣었다. 그러면 어떤 내용이 중요한지 구분하지 못하고 "질문과 벡터 유사도가 높다"는 이유만으로 들어간다.
  • 리랭킹(Re-ranking): 검색 결과의 중요도를 모델이 다시 정리하게 한다. 글자 수 기준으로 잘라 "중간이 뚝뚝 잘린" 청크가 들어가는 경우에도, 모델이 대화 맥락을 보고 중요한 내용을 다시 정리하고, 질문과 가장 유사한 것부터 덜 정확한 것까지 다시 정렬한다.
  • "별거 아닌 것 같아도" 이렇게 정리만 해도 답변 정확도가 오른다는 실험 결과가 있고, 할루시네이션, 잘못된 정보를 줄이는 데도 쓰인다.
  • 포지션 어웨어 리랭킹(position-aware re-ranking): 어텐션 동작과 이어진다. 중요한 것을 프롬프트의 첫 번째, 두 번째 자리에 배치하는 리랭킹이다. 앞의 LLM 리랭킹과는 다른 실험이므로 다른 종류로 보면 된다. 위치에 따른 어텐션 문제는 → 컨텍스트 엔지니어링과 하네스도 참고한다.
  • 구현 위치: 쿼리를 바꿔 검색하고 결과를 정리하는 과정에 LLM을 하나 더 넣어 "다시 정리"시키면 리랭킹이 된다.

확장 ③ 쿼리 리라이팅: 질문 자체를 정제

  • ①②가 검색 결과를 만들거나 정제하는 것이라면, ③은 질문 자체를 정제(refine)한다.
  • 예: 규정 문서에 연차 일수에 관한 예외 조항이 있다고 하자. 사용자의 "휴가 규정이 어떻게 되나요?"를 그대로 벡터 검색하기보다, 의도를 해석해 "사내 휴가 관련 일수가 어떻게 규정돼 있는지 검색"으로 바꾸는 편이 더 정확하다. 사용자의 진짜 의도는 "우리 사내 휴가 일수 규정을 찾아 달라"이기 때문이다.
  • 대화 중 "그럼 이거 찾아줘"처럼 툴콜이 일어날 때도 대화 맥락을 보고 무엇을 검색해야 하는지 뽑아내는 게 중요하다.
  • 구현: invoke된 입력을 그대로 쓰지 않는다. 앞서 연습한 메타 CoT처럼 "사용자가 이렇게 질문했다면 어떤 맥락에서 무엇을 검색하고 싶을지 유추해 문장을 만들어라"를 시스템 프롬프트나 툴 description에 넣는다. 그러면 질문이 검색하기 적절한 문장으로 바뀌고, 그 문장으로 벡터 검색한다.
  • 장점: 검색 코드나 알고리즘을 바꾸지 않아도 모델이 질문을 한 번 정제하는 것만으로 검색이 나아진다.
  • 프롬프트는 실험으로 찾는다. 구현 → 테스트 → 의도를 못 잡으면 질문 해석 프롬프트를 강화 → 다시 테스트. 에이전트 튜닝과 평가의 기본은 "내가 설계한 흐름대로 모델이 동작하는가, 아니라면 프롬프트를 어떻게 바꿔야 하는가"를 확인하는 것이다.

예시 "제주도 일정 만들어줘"에 대해 "여행지를 먼저 검색 → 검색 결과에서 무엇을 정리 → 일정, 식당을 벡터 검색" 같은 질문 개선 프롬프트를 미리 설계해 두면 RAG가 훨씬 촘촘하게 동작한다. 질문 정제는 구상에 따라 "거의 무한하게" 확장된다.

  • 이 밖에 그래프 네트워크 같은 새 모델을 학습시켜 검색을 개선하는 방향도 있다.

쿼리 정제를 에이전트 어디에 넣나

  • 구조는 Agent 안의 LLM → tool call → RAG 검색 tool(search_rag_memory 같은 이름)이다. 툴에 들어가는 입력(query)은 LLM이 만든다.
  • 예: 사용자가 "내일 일정을 찾아줘"라고 한다. 툴 description에는 "일정(개발 미팅, 시간, 날짜 등) 정보가 들어 있다"고 적혀 있다.
    • LLM은 오늘 날짜를 모른다. 그래서 시스템 프롬프트에 오늘 날짜(예: 2026년 7월 24일)를 명시하고 "내일 날짜를 직접 계산해 지정된 형식으로 쿼리에 넣어라"라고 지시한다. 그러면 툴로 넘어가는 쿼리가 "2026년 7월 25일 일정을 검색해줘"처럼 정제된다.
    • 날짜는 OS에서 가져오거나 메시지 수신 시각을 보고 명시적 데이터로 넣는다. "거창한 게 아니라" 모델이 실수할 여지를 줄이는 프롬프트다.

아래는 재구성한 예시다.

today = datetime.now().strftime("%Y-%m-%d")   # OS 시간 또는 메시지 수신 시각
system_prompt = f"""오늘 날짜는 {today}이다.
'내일', '다음 주' 같은 상대 표현은 날짜로 직접 계산해 query에 넣어라.
사용자의 질문 의도를 유추해 검색에 적합한 문장으로 바꿔 검색 툴을 호출하라."""
# "내일 일정을 찾아줘" -> search_rag_memory(query="2026-07-25 일정 검색")
  • 모델은 생각보다 미세한 실수를 많이 한다. 이름을 마음대로 바꿔 부르기도 하고, 최근 논문에 따르면 숫자를 고르라 하면 40이나 47을 자주 말하는 숫자 편향도 있다. 지시하지 않은 빈틈을 없애는 게 중요하다.
  • 쿼리를 정제할 수 있는 네 곳:
위치 하는 일 연결되는 장
시스템 프롬프트 날짜 등 컨텍스트를 주입하고 쿼리 작성 규칙을 준다 → 프롬프트 엔지니어링
툴 description 에이전트는 툴을 부르기 전에 description을 먼저 읽는다. 쿼리 작성법을 적어 두면 따른다. f-string으로 날짜나 DB의 시간, 사용자 데이터를 넣을 수도 있다 → Tool과 Function Calling
구조화된 출력 스키마로 입력 인자를 필터링, 정제한다 → 구조화된 출력과 Pydantic
툴 내부 코드(미들웨어, hook) 들어온 쿼리나 툴 결과를 코드에서 직접 고친다. Claude Code, Codex의 툴콜 hook, LangChain의 미들웨어와 같은 의미다. 고친 내용은 툴 response에 남아 모델로 돌아가고, 모델은 그것을 보고 답한다 → 서브에이전트, 멀티에이전트, 워크플로
  • 이런 작업 대부분이 "쿼리 리라이팅"이라는 키워드에 해당한다.
  • 오래된 RAG 논문은 에이전트 등장 이전 것이라 LLM을 바로 invoke하는 구조가 많다. 지금 구현하려면 에이전트 구조로 옮겨야 한다.

정리 하이브리드 검색은 코드, 리랭킹은 LLM 한 단계 추가, 쿼리 리라이팅은 프롬프트로 한다. 리라이팅은 시스템 프롬프트, 툴 description, 구조화된 출력, 미들웨어 네 곳 어디에든 넣을 수 있다.

RAG와 파인튜닝: 무엇을 먼저 할까

  • 자주 나오는 질문: "한정된 시간과 자원에서 에이전트 성능을 올리려면 무엇을 먼저 해야 하나?"
  • 답: 완벽한 정답은 없고 둘 다 하는 게 가장 좋지만, 대부분의 실험, 프로젝트에서는 RAG를 먼저 시도하길 권한다.
    • 이유 1: 사용자 대부분이 딥러닝을 잘 모른다.
    • 이유 2: 파인튜닝 난이도가 상당히 높다.
    • 딥러닝을 잘 알고 데이터도 많다면 RAG, Skills 세팅이 끝난 뒤 파인튜닝을 하면 된다.
  • 해 보지 않았기 때문에 "파인튜닝을 하면 더 잘 되겠지"라고 기대하기 쉽지만, 실제로 잘 되는 경우는 많지 않다. 데이터셋부터 직접 만들어야 하고(예: 일정 에이전트용 user/assistant 질문, 답변 데이터), 만들어 학습시켜도 잘 안 될 수 있다.
기대 더 잘 맞는 방법
"이 내용을 넣으면 그걸 말해 주겠지"(지식 반영) RAG
구조, 형식, 용어 같은 얕은 부분 맞추기 파인튜닝
전체 지식을 강하게 밀어 넣기 파인튜닝은 약하다
  • 가장 큰 어려움은 데이터셋이다. 모델 구조나 학습량은 공개돼도 어떤 데이터를 어떤 순서로 학습했는지는 잘 공개되지 않아, 직접 실험하며 경험을 쌓아야 한다.
  • 결론: RAG 기반 프롬프트 엔지니어링을 먼저 하고 그다음 파인튜닝으로 균형을 맞춘다. 파인튜닝이 모든 문제를 해결하지는 않으니 잘 해결하는 영역에 쓴다. 파인튜닝(LoRA, QLoRA 등)의 내부 동작은 → 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝에서 다룬다.
  • RAG는 뚝 떨어진 개념이 아니다. 딥러닝에서 데이터를 검색하고 평가하는 방법의 연장이고, 강화학습에서 상위 모델이 답변을 평가하는 것과도 닿아 있다.

정리 지식을 넣고 싶으면 RAG부터, 형식, 말투를 맞추고 싶으면 그다음에 파인튜닝. 둘 다 결국 데이터 싸움이다.

주제 4

MCP와 A2A

MCP를 "서버에 구현된 툴을 부르는 펑션콜"로 보는 관점을 축으로, 호스트, 클라이언트, 서버의 역할, FastMCP 서버와 MultiServerMCPClient 클라이언트 코드, 공개 서버(DeepWiki 등) 연결과 오류 해결, 툴 정보가 차지하는 컨텍스트, 프로토콜 업데이트 소식, 에이전트 간 통신 규약 A2A를 정리한다.

5주차의 주제다. 노트북은 5주차_카나가_지난대화를_불러오다.ipynb다.

프로토콜이란: HTTP와 MCP

  • MCP도 HTTP도 프로토콜이다. 프로토콜은 규약, 즉 서로 대화하거나 정보를 주고받을 때 지키는 규칙이다.

비유 영화 「캐리비안의 해적」에서 포로가 "팔레이(parley)"라고 외치면 데려가서 협상을 해야 한다는 규칙이 있다. 배, 해적, 해군 사이에 "팔레이"를 외치면 협상하는 약속이 있듯, MCP, HTTP도 데이터를 주고받는 부분을 규약으로 만든 것이다.

비유 98~00년대에는 로컬에서만 도는 프로그램과 인터넷에 연결되는 프로그램이 따로 있었다. 스타크래프트, 디아블로도 로컬에서 할 수 있었지만, 멀티플레이가 된다는 건 HTTP 같은 걸 지원해서 인터넷으로 다른 사람과 게임할 수 있었다는 뜻이다. HTTP를 쓸 수 있는 프로그램이 인터넷에 연결되듯, MCP를 쓰면 LLM과 데이터를 주고받을 수 있다.

  • 프로토콜에는 "데이터를 주고받겠다"뿐 아니라 어떻게 주고받을지, 누가 데이터를 줄지, 누가 요청할지가 함께 들어 있다. 그래서 MCP 자료는 양이 방대하다. 서버 만드는 법, 클라이언트 요청 방법, 내부 JSON 통신 규칙이 섞여 있고 SDK만 던져져 있어 "이걸로 뭘 만들라는 건지" 헷갈리기 쉽다.
  • 정리하면 MCP는 LLM이 외부와 통신하기 위한 규약이고, 서버 만드는 법, 클라이언트 구성법, JSON 통신 규칙을 다 담다 보니 볼륨이 커져 헷갈린다.

MCP = 툴콜: 서버에 구현된 툴을 부르는 펑션콜

이 장 전체를 꿰는 관점이다. 노트북 제목은 "MCP와 Tool Call"인데, 그림을 자세히 보면 1주차 펑션콜 그림과 똑같다. 차이는 로컬과 LLM 사이에 MCP 서버가 끼어 들어간다는 것 하나다.

구분 로컬 툴콜(1주차) MCP
툴이 있는 곳 로컬에 정의한 함수 MCP 서버에 미리 구현된 함수
누가 만드나 우리가 전부 직접 구현 서버 개발자가 만들어 둠. 우리는 불러오기만
통신 주체 로컬 ↔ LLM 로컬(클라이언트) ↔ MCP 서버 ↔ LLM
최종 동작 펑션콜 펑션콜(내부 데이터 흐름만 더 복잡)
  • 동작 순서(재구성):
    1. 로컬(클라이언트)이 MCP 서버와 먼저 통신해 서버에 구현된 툴 정보를 받는다.
    2. 툴 정보(이름, description, 어떤 함수가 있는지)를 사용자 쿼리와 함께 LLM에 전달한다. 펑션콜과 똑같은 구성이다.
    3. LLM이 쿼리와 툴 정보를 보고 인자를 만들어 돌려준다.
    4. 그 인자가 MCP 서버로 넘어가고, 서버가 함수를 실행한다.
    5. 결과를 반환한다.
  • 어떤 MCP 서버를 안다는 것은 라이브러리나 패키지를 아는 것처럼 "그 서버에 어떤 툴이 있고, 연결만 하면 불러올 수 있다"는 뜻이다. MCP 서버의 기능은 툴을 부르는 것밖에 없다. 라이브러리 기반으로 툴을 불러오는 것이다.
  • 모델 입장에서 툴콜은 "커스텀 토큰으로 불리는 형식"이다(→ 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝). MCP는 이 툴들을 잘 부를 수 있게 하는 프로토콜을 제공한다.
  • 에이전트를 구현하는 입장에서는 MCP를 "미리 제작한 툴" 정도로 보면 된다.

팁 용어가 새로 나왔다고 절대 당황하지 말 것. 이건 펑션콜이다. 펑션콜은 함수를 만들어야 했지만 MCP는 만들어진 걸 불러오기만 하면 되니 펑션콜보다 오히려 쉽다.

정리 MCP는 에이전트가 같은 함수를 반복해서 펑션콜하는 일을 지원하는 기능이고, 여기에 서버와 이를 요청하는 클라이언트를 구현하는 규칙까지 포함한 프로토콜이다.

MCP 서버는 누가 만드나

  • MCP가 처음 나왔을 때 함께 소개된 그림에는 MCP 서버(리모트 서비스) 자리에 Slack, Gmail, Google Calendar 같은 익숙한 앱이 있었다.
  • MCP 서버는 사람들이 많이 쓰는 툴(또는 내가 많이 쓰는 툴)을 서버로 만들어 둔 것이다. 서버를 만든다는 것은 여러 사용자가 그 안의 툴을 쓸 일이 많다는 뜻이다.
  • 예: Gmail 서버라면 "최근 메일을 요약하는 툴"을 만들어 둔다. 이런 툴은 Gmail을 관리하는 개발자가 직접 만들어야 한다. 공개 API가 있으면 우리가 만들 수도 있지만, API가 공개되지 않고 프로그램만 있다면 그 개발자가 서버와 툴을 구현해 둬야 우리가 쓸 수 있다.
  • 로컬 툴은 우리가 직접 만들어 썼다. MCP는 상용 서비스 개발자가 서버와 툴을 써 두면, 우리는 툴 목록, 도큐먼트를 보고 서버에 요청해 그 툴을 쓴다. "툴만 당겨오면 마치 구현한 것처럼" 쓰게 해 주는 프로토콜이다.
  • 크게 유행한 이유는 어떤 에이전트를 구현하든 재활용할 수 있다는 점이다. 그래서 많은 회사가 MCP를 구현하고 있다.

호스트, 클라이언트, 서버의 역할

  • 에이전트마다 구성이 다르다. ChatGPT를 쓰는 것도, SLM을 쓰는 것도 있다. 그래도 MCP 서버를 이용하면 미리 구현된 툴을 계속 가져다 쓸 수 있다.
  • MCP 서버가 떠 있으면 Claude Code, Codex, Antigravity 모두 각 서버에 접근할 수 있다. 이들 안에 MCP 프로토콜이 들어 있기 때문이다. 직접 만든 에이전트도 MCP 서버에 접근하도록 구성할 수 있다. Claude, Cursor, Gemini 등도 같은 서버와 통신할 수 있다.
  • 누가 클라이언트인가: LLM 쪽, 즉 에이전트를 만드는 우리가 클라이언트다. 툴이 있는 쪽이 MCP 서버다. 서버에 툴을 요청하므로 요청을 보내는 쪽이 클라이언트이고, 요청하면 툴이 넘어온다.
역할 무엇인가 예
호스트 MCP를 지원해 서버의 툴을 가져다 쓰는 에이전트, 앱 Claude Code, Codex, Antigravity, Claude Desktop, 우리가 만든 LangChain 에이전트
클라이언트 호스트 안에서 서버에 접속해 툴 목록을 받고 실행을 요청하는 쪽 LangChain MultiServerMCPClient
서버 툴을 구현해 두고 요청을 받아 실행하는 쪽 FastMCP로 만든 SQLite 서버, DeepWiki, Tavily, Gmail, Slack, Blender, Unity, Docker MCP Toolkit의 YouTube transcript

MCP 명세에서 호스트는 클라이언트를 품고 LLM과 연결된 애플리케이션을 가리킨다.

  • Anthropic이 처음 발표한 MCP 아키텍처 그림(클라이언트가 LLM과 연동되고, 클라이언트가 서버에 연결되어 툴을 불러옴)은 서버와 클라이언트를 모두 만들어야 하는 것처럼 보이게 한다. 하지만 실제로 쓸 때는 MCP 서버에 요청해 동작시키는 흐름이다.

정리 "원하는 프로그램의 기능을 툴로 만들어 두면, 원하는 에이전트나 모델에서 바로 불러 쓸 수 있는 구조." 우리는 기본적으로 MCP를 사용하는 쪽이다.

MCP 서버를 직접 만들 때: 이점과 특수한 경우

  • 로컬에서는 MCP로 만들든 그냥 function tool로 만들든 최종 동작은 똑같다. 내부에서 데이터가 도는 방식은 MCP가 더 복잡하지만 결과는 펑션콜이다.
  • 차이는 재사용 범위다. LangChain으로 툴콜을 구현하면 그 코드 안에서만 쓸 수 있다. MCP 서버로 만들면 Claude Code, Codex, Antigravity 같은 도구도 접근할 수 있다.
    • 예: Blender 같은 3D 도구나 음악 제작 프로그램을 MCP로 만든 서버를 쓰면 여러 에이전트가 실제로 그 프로그램에 접근해 동작한다.
  • 서버를 만들어 두면 인증된 사용자만 쓰게 하거나, 팀에서 공유하는 툴을 두거나, 일반 사용자에게 제공할 수도 있다. 로컬이나 접속 가능한 AWS 서버 하나를 띄워 나만의 MCP를 제공할 수도 있다.
  • 사용자 입장에서 서버 구현은 특수한 경우다.
    1. 자기 서비스를 직접 만들 때
    2. 로컬에서 Codex, Claude Code 등 여러 에이전트가 공통으로 쓰도록 할 때. 예를 들어 스킬을 도구마다 따로 넣거나 폴더를 공유할 수도 있지만, MCP 서버로 만들어 내 스킬을 불러오게 할 수도 있다.
  • 노트북에서 띄운 MCP 서버는 Claude Code나 Codex의 MCP 서버 등록 위치에 등록하고 필요한 변수(환경 변수 등)를 넣으면 다른 에이전트에서도 잡힌다. 연습까지는 필요 없고 "이렇게 연결된다" 정도로 알면 된다.

정리 MCP는 툴을 저장해 두고 여러 사람이 직접 구현하지 않고 불러 쓰게 만드는 작업이다.

FastMCP로 만드는 서버 구조

  • MCP 서버는 FastMCP 패키지로 구현하며 구현체가 매우 심플하다.
    • FastMCP(...)로 선언하면 바로 MCP 서버가 된다.
    • 그 아래 @mcp.tool 데코레이터를 붙인 함수에 이름과 description이 달려 있다.
  • 노트북 앞부분에 "툴 이름 + description" 형태로 툴을 써 둔 이유는 MCP에서 쓰는 메인 파트가 사실 툴이라는 걸 보여 주려는 것이다. "MCP라고는 하지만 여기에 툴이 있는 거고, 이 툴을 쓸 수 있는 에이전트와 연결만 해 준다고 생각하면 된다."
  • 만드는 순서: "이 서버에는 이런 함수들이 필요하겠다"를 먼저 정의, 구현하고, 그다음 MCP 서버로 동작시킨다.
  • 서버 내부는 사실상 "툴 구현이 전부"이고, 데이터를 주고받는 방식(transport)만 정하면 된다. 로컬이면 stdio(표준 입출력), 아니면 HTTP를 쓴다. 실제 MCP 서버를 뜯어 봐도 대부분 이 구조에 연결용 코드가 더해진 정도다.
  • 이 과정에서는 MCP 서버를 직접 만들지 않는다. 서버는 이미 구현돼 있다(설명문: "외부 멤버 대화, 일정 SQLite의 MCP 프로토콜 STDIO 서버"). 다만 코드를 보면 "MCP를 선언하고 필요한 것을 MCP 툴로 구현하면 서버로 동작한다"는 건 바로 확인된다.

아래는 재구성한 예시다(import 경로와 이름은 설명용).

from mcp.server.fastmcp import FastMCP     # 독립 패키지로는 from fastmcp import FastMCP

mcp = FastMCP("kana_sqlite")              # 서버 이름은 예시

@mcp.tool()
def search_previous_conversations(query: str) -> str:
    """툴 description. LLM이 툴을 고를 때 보는 설명이다."""
    ...  # SQLite에서 이전 대화, 일정 조회

if __name__ == "__main__":
    mcp.run(transport="stdio")            # 로컬이면 stdio, 원격이면 HTTP

MultiServerMCPClient와 get_tools()

  • LangChain에서 MCP 클라이언트를 선언할 수 있다. 클래스는 MultiServerMCPClient이고, 별도 패키지인 MCP 어댑터(langchain-mcp-adapters)를 설치해야 한다.
  • 클라이언트 코드는 async 함수로 되어 있고, client.get_tools()가 MCP 서버에 연결되는 부분이다.
  • 클라이언트 안에 JSON(dict) 형식으로 여러 서버를 입력할 수 있다. 그래서 이름이 "싱글"이 아니라 멀티 서버 MCP 클라이언트다. 서버를 더 추가하면 멀티 서버로 동작한다.
  • 설정 형식: 앱 등에서 쓰는 일반 MCP 설정 문법은 mcpServers 아래에 서버들을 쭉 적는다. LangChain은 그 안쪽(서버 이름 → 접속 정보)만 쓰면 된다. 다른 서버를 추가하려면 아래에 같은 형식으로 더 적는다.
  • MCP 서버마다 클라이언트가 그 서버에 요청하는 스펙이 문서에 적혀 있다. 예: Tavily MCP 서버 문서에는 클라이언트에 서버와 접근 방법을 넣는 법이 나와 있고, API 키를 입력해야 한다.
  • get_tools()가 반환하는 것은 그 서버가 가진 툴 리스트다. 출력해 보면 툴의 name과 description이 들어 있다. 클라이언트가 하는 일은 하나, 쓸 수 있는 툴 목록을 알려 주는 것이다.
  • 툴은 고정이라 우리가 바꿀 수 없다. 서버 코드가 없으면 수정도 못 하고 그냥 쓸 수밖에 없다. 그래서 툴을 전부 읽어오게 되어 있다.
  • 이후는 똑같다. 가져온 툴을 에이전트의 툴에 넣으면 펑션콜이 그대로 진행된다. 로컬 function tool 자리에 get_tools() 결과를 붙인다고 보면 된다. 우리가 구현하는 게 아니라 구현된 걸 가져와 붙이는 것이다.

아래는 재구성한 예시다(서버 이름, 파일명은 설명용).

from langchain_mcp_adapters.client import MultiServerMCPClient

client = MultiServerMCPClient({          # dict로 여러 서버 등록
    "kana_sqlite": {
        "command": "python",
        "args": ["<서버 파일>.py"],
        "transport": "stdio",
    },
    # Docker MCP Toolkit 예: "youtube_transcript": {"command": "docker", ...}
})
tools = await client.get_tools()          # 서버의 툴 리스트(name, description)
agent = create_agent(model, tools=tools)  # 로컬 function tool 자리에 붙이면 끝

공개 MCP 서버 연결: DeepWiki, Tavily, Docker MCP Toolkit

  • 공개 서버 예로 DeepWiki MCP를 붙여 본다. 위키피디아 같은 것이라고 보면 된다. GitHub 레포를 정리한 위키를 제공하는 서비스다.
  • 로컬에서 돌리면 localhost로 부를 수도 있지만, 주로 URL이나 외부 접속이 가능한 IP로 연결한다.
  • 서비스 도큐먼트에서 확인할 것은 두 가지다.
    1. 서버 주소, 접속 정보
    2. 어떤 툴을 쓸 수 있는지. DeepWiki는 위키 구조를 읽는 툴, 내용을 읽는 툴, 질문하는 툴이 있다(문서상 read_wiki_structure, read_wiki_contents, ask_question).
  • 문서에는 "대부분의 클라이언트에서 이렇게 쓰면 된다"며 서버 URL을 넣는 예가 나온다. Claude Desktop 같은 앱에 전달하는 방식도 있지만 URL로 넘기는 경우가 가장 많다. Claude Code, Codex에서도 같은 식으로 등록한다.
  • 인증: DeepWiki는 인증이 없어 URL만 넣으면 바로 동작한다. 다른 서버는 API 키가 필요한 경우가 있다. 가입, 로그인하면 키가 발급되니 복사해 URL이나 커맨드와 함께 넣는다.

DeepWiki GitHub 레포 위키 조회, 질문 URL만 넣으면 됨, 인증 없음, Streamable HTTP
Tavily 웹 검색 API 키 필요. 무료 사용량이 있다(월 1,000건 안팎). Google 검색 API를 붙이는 것보다 간편
YouTube transcript(Docker MCP Toolkit) 비디오 URL로 자막 가져오기 클라이언트에 command: docker 형태로 추가. 이미지를 Docker 안에서 실행
Blender, Unity 해당 프로그램 조작 소개만 함
  • Docker Desktop에도 MCP Toolkit이 있다. Clients에는 Claude Code 등 연결 가능한 클라이언트가, Catalog에는 Hugging Face 등 제공 MCP 서버 목록이 있다. 개인이 만든 서버도 많고, 웹에서 동작하는 MCP도 있다.
  • 누군가 RAG 형식의 MCP 서버를 만들어 뒀다면 RAG를 따로 구성하지 않고 서버를 불러 쓰면 된다.

팁 MCP 서버를 만들기보다 있는 MCP 서버를 이용해 에이전트를 잘 활용하라. 서비스를 만들 때 DB 연동, 웹 검색 같은 툴을 다 구현하기는 매우 어렵다.

transport 누락 오류 해결

  • 문서대로 해도 누락이 생길 수 있다. 첫 실행에서 transport 키가 누락됐다는 오류가 날 수 있다.
  • URL을 쓰고 있으니 HTTP 관련 값을 넣으면 될 것 같아 문서의 wire protocol 항목(Streamable HTTP)을 확인한다. transport에 "http"를 넣으면 get_tools()가 성공한다(안 되면 streamable HTTP 쪽 값을 넣어 본다).

아래는 재구성한 예시다.

client = MultiServerMCPClient({
    "deepwiki": {
        "url": "<DeepWiki 문서의 MCP 서버 URL>",
        "transport": "http",    # 빠지면 'transport 키 누락' 오류
    },
    # "tavily": {...},          # 다른 서버도 같은 형식으로 아래에 추가(API 키 필요)
})
mcp_tools = await client.get_tools()
print(mcp_tools)   # StructuredTool(name='ask_question', description=..., args=...) 등

팁 이런 문제는 서버마다 다르다. 도큐먼트나 오류 메시지를 찾아보고, 없으면 모델에 물어보며 고친다.

MCP 툴을 기존 툴과 합치고 비동기로 실행하기

  • MCP를 쓴다는 것은 MCP에 있는 툴을 쓰는 것이므로, 기존 에이전트가 쓰던 툴 리스트에 함께 추가해야 한다. 불러온 MCP 툴도 이미 리스트이므로 extend, append로 넣거나, 간단하게는 별표(*, 언패킹)를 붙여 넣는다.
  • 에이전트는 tools에 등록된 툴만 부를 수 있다. 등록돼야 툴 이름과 description이 전달되고, 그래야 펑션콜이 동작한다.
  • 툴 목록 요청은 각 서버에 보내는 것이라 서버 속도, 상태에 따라 응답이 다르게 들어온다. 그래서 await를 붙여 기다린다. 에이전트도 비동기로 부르려면 invoke 앞에 a를 붙인 ainvoke를 쓴다.

아래는 재구성한 예시다.

mcp_tools = await client.get_tools()            # 툴 로딩까지 반드시 기다린다
tools = [*existing_tools, *mcp_tools]           # 기존 더미 MCP 툴 + DeepWiki 툴
agent = create_agent(model, tools=tools, system_prompt=SYSTEM_PROMPT)
result = await agent.ainvoke({"messages": [
    {"role": "user", "content": "langchain-ai 레포에서 create_agent를 찾아서 설명해 줘"}
]})

주의 실행 중 StructuredTool이 동작하지 않는 오류가 날 수 있다. 진단은 "메시지가 바뀌기 전에 얘가 움직여서 툴을 못 받았다"였다. 로컬 실행이 훨씬 빨라서 await가 걸린 응답을 기다리지 않으면 생기는 문제다. MCP 툴을 읽어 오는 것까지 await로 기다리게 바꿔 해결했다. 서버를 여러 개 쓰거나 응답이 오래 걸릴 때 필요한 처리다.

툴 호출 결과를 보고 프롬프트로 보정하기

  • 트레이스를 보니 기존 대화 검색 툴과 DeepWiki 툴 read_wiki_contents가 호출됐다. 그런데 레포 이름 인자에 리눅스 관련 값을 넣어 검색은 실패했다.
  • 해결 방향: 도큐먼트를 보며 어떤 값이 필요한지 찾는다. DeepWiki 사이트에는 microsoft/vscode 같은 정리된 레포가 있으니 레포를 지정해 줘야 잘 찾는다. "리눅스 말고 langchain-ai 레포에서 create_agent를 찾아서 설명해 줘"처럼 명시하면 그 레포에서 찾고 답을 기다렸다 출력한다.
  • 사용자가 레포 이름을 다 알 수는 없으므로 시스템 프롬프트에 "에이전트 관련 라이브러리, 프레임워크 질문이면 DeepWiki에서 langchain-ai 같은 레포를 찾아라"(예시) 같은 지침을 넣고 테스트하며 고쳐 나간다.
  • MCP마다 입력, 동작 방식이 조금씩 달라 찾아서 연결하고 잘 동작하게 세팅하는 과정이 생각보다 오래 걸릴 수 있다. 트레이스 보는 법은 → Tool과 Function Calling에서 다룬다.

MCP 툴의 description은 서버 쪽에서 고친다

  • 과제에서 쓰는 툴의 description은 미리 작성돼 있지만, 튜닝이 필요하면 description도 손대도 된다. 펑션콜 때 description을 조절했던 것과 같은 이유다.
  • 단, MCP 서버는 따로 떨어져 있다. description을 바꾸려면 MCP 서버 쪽 코드를 건드려야 하고, 과제에서도 그 부분이 분리돼 있다.
  • 과제 코드는 서버를 직접 만들고 LangChain이 그 서버를 불러 동작시키는 구조다. 여러 계층을 거쳐 툴이 넘어가 트레이스가 어렵기 때문에, 단순한 예제로 "MCP 서버를 에이전트에 붙이는 작업"을 직접 확인해 보는 것이 좋다. "MCP가 에이전트에 붙는다 = 툴이 붙는다"를 확인하는 실습이다. 과제 자체는 → 주차별 실습 프로젝트에서 다룬다.

툴 정보는 컨텍스트를 차지한다

  • get_tools() 결과를 출력하면 StructuredTool로 툴 이름(ask_question 등), description, 인자(args)와 사용 예시 정보가 전부 넘어온다.
  • MCP 서버에 요청하고 툴을 에이전트에 등록하면, 모델 컨텍스트에 툴 이름, 설명, 인자 정보가 포함된다. MCP를 여러 개 쓰면 이미 그만큼 컨텍스트를 갖고 시작한다.
  • 예: Claude Code나 Codex에 플러그인, MCP를 여러 개 붙여 두면 "이미 요만큼 컨텍스트를 먹고 있어서 사실상 손해를 보고 있다." 최근 Opus, Fable 이야기에서 CLAUDE.md를 줄여 컨텍스트를 확보하라고 하는 것과 같은 맥락이다(→ AI 코딩 도구 활용(Claude Code, Codex)).
  • 툴 개수도 부담이다. 툴을 한 번의 컨텍스트로 부르는 구조라서, 툴이 2개, 3개, 10개로 늘면 모델이 툴을 고르는 선택 가이드가 어려워진다. 툴이 폭증할 때의 문제는 → 서브에이전트, 멀티에이전트, 워크플로에서 이어진다.
  • 최근 변화: 레이지 툴콜 같은 lazy 로딩 계열 기능이 나와서, 툴을 미리 컨텍스트에 로드하지 않고 필요할 때 로드하기도 한다. 최근 변경점이니 참고만 하고, 기본은 리스트로 등록해야 처리된다고 보면 된다.

주의 MCP 서버는 등록하는 순간 컨텍스트를 갖고 들어온다. 필요한 것만 연결하는 조절이 제일 중요하다. 컨텍스트 관리 전반은 → 컨텍스트 엔지니어링과 하네스 참고.

MCP 업데이트 소식: "필요할 때 툴만 부르는" 방식으로

  • MCP의 대규모 업데이트 소식이 있다. 대규모로 바뀌는 건 맞지만 핵심 동작이 크게 바뀌지는 않는다. 일반 사용자는 쓰던 대로 쓰면 되고, 구현체가 조금 바뀔 수 있는 업데이트다.
구분 기존 방식 바뀌는 방식
연결 TCP 핸드셰이크처럼 "연결한다 → 연결됐다 → 데이터 보냈다"로 확인하고, 연결된 상태에서 주고받음 서버와 클라이언트를 붙여 두지 않음
툴 호출 서버마다 1:1로 연결 서버 정보(MCP 목록)만 갖고 있다가 필요할 때 요청해 툴만 부름
문제, 장점 Slack, Gmail, Calendar를 오가면 서버마다 붙어 있어 불편 여러 서버에 언제든 요청하고 언제든 답을 받음
  • 펑션콜의 확장 버전이라고 볼 수 있다. 연결 상태를 유지하지 않는 방식에 가깝다.
  • LangChain은 이미 여러 서버를 묶어(MultiServerMCPClient) 새 방식처럼 동작하게 만들어 두어서, 쓰는 사람은 차이를 잘 체감하지 못한다. 이번 업데이트는 이걸 프로토콜 단에서 바꿔 더 편하게 만들겠다는 것이라 커뮤니티에서 이야기가 많다.
  • 영향 예측:
    • SDK로 직접 구현하는 사람은 구현 방법이 바뀔 수 있다. 특히 서버를 만드는 부분에 적용될 확률이 높다.
    • LangChain, LlamaIndex 사용자는 이미 멀티서버 클라이언트가 있어 구현체가 바뀌지 않을 가능성이 크다.
  • 통신 방식이 TCP/IP 같은 핸드셰이크에서 펑션콜 방식으로 바뀌고 있다.

툴콜 방식으로 수렴하고 판단은 모델에 맡기는 흐름

  • 결론: 1주차부터 배운 툴콜 방식으로 대부분의 구현체가 수렴하고 있다. 에이전트에서 가장 중요한 작업 중 하나가 펑션콜로 필요한 툴을 부르는 것이었는데, MCP도 툴콜 방식에 맞춰지고 있다.
  • 이는 모델 기능에 더 의존하는 방향이다.
    • 원래: MCP 서버를 지정해 붙이고 "여기서 이 MCP 툴을 써 줘"라고 시켰다.
    • 바뀌는 방향: 모델이 알아서 어떤 MCP 서버, 어떤 툴을 쓸지 판단한다.
  • 같은 흐름이 CLAUDE.md에도 있다. Opus 5 업데이트와 함께 Anthropic이 테크 블로그에 "프롬프트로 강제하지 말고 모델이 판단하게 하라"고 썼고, 근거는 "더 좋은 성능"이 아니라 "성능 차이가 없다는 걸 확인했다"였다. 어떻게 보면 사용자에게 손대지 말라고 하는 느낌이고, 모델 회사("건드리지 마라")와 사용자("우리 의도대로 하고 싶다")의 입장 차가 계속 화두가 될 것이다. CLAUDE.md 이야기는 → AI 코딩 도구 활용(Claude Code, Codex)에서 이어진다.
  • 코드 레벨 구현에서는 세세한 가이드를 프롬프트로 주고, MD 쪽에는 프로젝트 정도의 제약만 두는 방식도 있다.
  • 같은 "모델을 믿는" 흐름이 서브에이전트 구조에도 나타난다(→ 서브에이전트, 멀티에이전트, 워크플로).

A2A: 에이전트끼리의 통신 규약

  • MCP가 나온 직후 Google이 A2A(Agent to Agent)를 발표했다. Google은 sequence to sequence처럼 이런 식의 이름을 좋아한다.
  • A2A는 타이밍을 놓친 느낌이 있다. 지금은 개념 정도만 알면 된다.
구분 MCP A2A
통신 대상 LLM(에이전트) ↔ 서버의 툴 에이전트 ↔ 에이전트
방식 툴콜 방식 통신 에이전트의 이름, description을 적은 "비즈니스 카드(네임 태그)"를 보고 어떤 에이전트에게 보낼지 결정. 툴콜의 확장판
현재 위치 지금 널리 쓰임 간단한 구현은 나와 있지만 에이전트가 더 보편화된 뒤에 쓰일 것
  • 배경 비전: 에이전트가 상용화된 먼 미래를 가정한다. 휴가 관리 에이전트, 개인 PC 에이전트처럼 시스템마다 에이전트가 있고 각자 툴을 갖고 운영된다. 이들의 용어, 툴, 프레임워크(LangChain, LlamaIndex 등)는 다 다를 것이므로, 다르게 구현된 에이전트끼리 소통할 프로토콜이 필요하다는 개념이다.
  • 아직 뜨지 않은 이유: 지금 많이 쓰는 멀티에이전트는 서브에이전트 형식이라 A2A와 다르게 동작한다. 멀티에이전트를 쓸 때도 A2A 대신 MD 파일 저장, 서브에이전트로 컨텍스트 분리 같은 방식을 쓴다.
  • 멀티에이전트 구현은 A2A와 맞닿아 있다. 코드 안에서 직접 구현하기보다, 여러 에이전트를 A2A 프로토콜로 동시에 동작시키는 방향의 연구가 많이 진행 중이고, MCP를 포함한 프로토콜들도 계속 업데이트되고 있다. 서브에이전트, 멀티에이전트는 → 서브에이전트, 멀티에이전트, 워크플로에서 다룬다.

MCP 한 장 정리: 서버 등록 → 툴 불러오기 → 에이전트에 추가

  • 실습은 펑션콜을 하는 부분을 MCP로 옮겨 놓은 것이다. 찾은 MCP 툴을 직접 구현한 함수처럼 연결해 동작시키면 된다.
    1. 서비스 문서에서 서버 URL, 접속 정보, 제공 툴을 확인한다.
    2. MultiServerMCPClient에 서버 이름과 URL, transport(필요하면 API 키)를 dict로 넣는다.
    3. await client.get_tools()로 툴 목록을 받는다.
    4. 기존 툴 리스트에 합친다([*기존툴, *mcp_tools]).
    5. create_agent(..., tools=...)로 만들고 await agent.ainvoke(...)로 실행한다.
    6. 트레이스로 어떤 툴이 어떤 인자로 불렸는지 보고, 실패하면 문서, 시스템 프롬프트를 고친다.
  • 다른 API에서는 형태가 다를 수 있지만 "MCP 서버 정보를 입력하고 툴을 불러오는 과정"은 거의 같다. MCP를 구성하고 싶으면 문서의 접속 정보를 찾아 모델(에이전트, Claude Code)에 넣어 주기만 하면 된다.
  • 최종 정리: MCP를 쓴다는 말에는 서버 만들기와 클라이언트 만들기가 모두 포함될 수 있지만, 기본은 이미 구현된 MCP 서버의 툴을 요청하는 것이다. 원래 Function Calling은 파이썬 함수로 툴을 만들어야 했는데 MCP가 이것을 대신해 준다.

정리 MCP = 남이 서버에 만들어 둔 툴을 펑션콜로 부르는 규약. 붙이는 법은 쉽고, 어려운 건 "필요한 것만 붙이기"와 "의도대로 부르게 프롬프트 다듬기"다.

주제 5

서브에이전트, 멀티에이전트, 워크플로

싱글 에이전트가 툴 폭증으로 한계에 부딪히는 지점에서 출발해, Anthropic의 워크플로 5종, State, LangGraph로 흐름을 고정하던 옛 멀티에이전트, 툴콜 자리에 에이전트를 넣는 서브에이전트(슈퍼바이저), Swarm, handoff, 미들웨어, 그리고 토큰 비용과 구조 선택 기준까지 순서대로 정리한다.

6주차의 주제다. 노트북은 6주차_카나메이트가_약속을_결정하다.ipynb다. 6주 과정의 마지막 목표는 "서브에이전트를 표방한 멀티에이전트" 구현이다.

왜 멀티에이전트가 필요해졌나

  • 에이전트는 툴, 메모리, 플래닝, 프롬프트로 이뤄진다(에이전트 구성은 → 에이전트란 무엇인가).
  • 초기 LLM이 처리하던 일은 단발성 질문이라 에이전트 하나로 충분했다. 그런데 에이전트가 사람이 실제로 하는 일을 다루기 시작하면서 문제가 생겼다.
    • 사람의 업무에는 워크플로가 있다. 1번이 끝나면 2번, 그다음 3번으로 이어지고, 앞 단계의 결과가 다음 태스크에 영향을 준다.
    • 단계마다 다른 방법과 도구가 필요하다. 단일 에이전트로 구현하면 성격이 다른 여러 툴을 한 에이전트에 한꺼번에 넣어야 한다.
  • 한꺼번에 넣은 툴의 호출은 제어하기 어렵다. 툴 선택을 auto로 두면 LLM이 판단해 부른다. "특정 툴을 불러라"처럼 강제할 수는 있지만 일일이 하기 어렵고, 프레임워크도 대부분 auto로 넘긴다. 제대로 제어하려면 제약 조건, 프롬프트, 컨텍스트 연결 작업이 크게 늘어난다.
  • 결과적으로 툴 선택지가 복잡해지고, 프롬프트도 복잡해지고, 메모리, 컨텍스트가 길어져 수행 품질이 떨어진다.
  • 자연스러운 발상은 "에이전트 하나가 태스크 하나는 잘하니, 에이전트를 여러 개 만들면 되지 않을까?"다. 이것이 멀티에이전트다. 딥러닝에서 좋은 모델이 나오면 크기를 키워 온 것과 같은 흐름이다.

  • 그때부터 효율이 급격히 떨어진다. 툴을 잘못 부르는 순간 호출과 데이터 읽기에 쓴 토큰이 다 손실된다. 또 잘못된 정보가 컨텍스트에 들어가 다음 판단에 영향을 줘서, 계속 툴을 잘못 고르는 연쇄가 생긴다.
  • 특정 부분에서만 툴을 불러오게 하는 기능은 처음엔 없었고 지금은 생겼다(MCP의 lazy 로딩 이야기는 → MCP와 A2A). 없던 시절엔 이 문제를 피할 수 없어 멀티에이전트로 넘어가게 됐다.

정리 툴이 많아지면 컨텍스트가 차고, 비슷한 툴끼리 헷갈리고, 한 번 틀린 툴콜이 다음 판단까지 오염시킨다. 이것이 멀티, 서브에이전트의 출발점이다.

Anthropic의 워크플로 5종

  • Claude Code가 나오기 전, Anthropic은 에이전트 워크플로를 프롬프트만으로 제어할 수 있는지 실험했다. 기본 API와 프롬프트만으로 이런 구조가 실제 동작했다는 것이 Anthropic의 "효과적인 에이전트 구축" 글의 요지다.
  • 핵심 그림: augmented LLM 구조의 에이전트를 두고, 코드에서 for문을 돌다 특정 조건이면 탈출하고 조건에 따라 분기하듯 중간의 함수, 계산 자리를 LLM 처리로 바꿔 그 결과로 분기나 반복을 준다. (Augmented LLM은 → 에이전트란 무엇인가)

  • 구현은 쉽다. 퓨샷, CoT로 "답변 완료" 같은 키워드를 출력하게 하고, 파싱되면 체인을 멈추고 안 되면 계속한다. for/while문과 invoke만으로 만든다.

평가자-최적화자 구현 예

  • LLM을 선언하고 각각 다른 시스템 프롬프트를 주면 서로 다른 LLM처럼 동작한다. 에이전트를 따로 만드는 게 아니다.
  • Generator에는 "에세이를 써 줘", Evaluator에는 항목별 점수 규칙(예: 이 항목 80점, 이 항목 50점, 이 항목 20점, 합계 기준 미달이면 reject)을 다 써 둔다. 기준 미달이면 reject 프롬프트와 함께 Generator에 다시 넣는다. 이 생각은 LLM-as-a-judge로 이어진다(→ 에이전트 평가와 LLM-as-a-judge).
  • Karpathy 지침의 "목표 중심적 실행, 각 단계에서 확인하고 체크하라"는 흐름도 이런 식으로 프롬프트에 들어간다.

정리 Claude Code, Codex 같은 코딩 에이전트도 결국 프롬프트로 컨트롤되는 LLM이다. 이 워크플로들은 프롬프트만으로 구현할 수 있다.

자율 에이전트와 Claude Code의 탄생

  • 환경(environment)에서 툴을 부르는 것이 액션(action), 그 결과가 피드백(=관찰, observation)이다. LLM이 전체 프롬프트를 보고 다시 판단하고, 애매하면 사람에게 물어본다.
  • 워크플로 실험(루프, if문, 라우팅 등 프롬프트 제어)을 하다 보니 "환경 정보를 보고 필요한 툴을 불러 해결 시도 → 결과를 보고 다시 판단 → 사람에게 묻고 답 받고 → 다시 액션"하는 자율 에이전트로 발전했다. 이것이 코딩 에이전트의 고수준 흐름이자 Claude Code의 기본 모양이다. Anthropic 글 마지막 그림(LLM call → action → 환경과 상호작용 → 피드백)이 나중에 Claude Code의 기본 구조가 된다.
  • Claude Code, Codex도 프롬프트 기반으로 동작한다. 명령이 명확하지 않으면 사람에게 다시 묻고, 중요한 툴 사용을 내부에서 스스로 정제하는 과정이 프롬프트로 구성돼 있다. 코딩 에이전트 활용은 → AI 코딩 도구 활용(Claude Code, Codex)에서 다룬다.

멀티에이전트 구현체의 역사: 고정 워크플로에서 툴콜로

  • 멀티에이전트 개념은 서브에이전트보다 먼저, 싱글 에이전트가 나온 직후 일찍 정립됐다. 반면 구현체는 많이 뒤처져 나왔다.
  • 초창기에는 슈퍼바이저 출력이 "개인 일정"이면 개인 쪽으로, "공유 일정"이면 공유 쪽으로 보내는 식으로 개발자가 직접 조건 분기를 만들었다. 특정 키워드가 리턴되거나 대화에 포함되면 분기하는 방식이라 고정적이었다. 당시에는 LLM이 분기하는 것을 믿기 어려워 사람이 지정했다.
  • 당시 CrewAI, LangChain, LlamaIndex 같은 도구가 이런 방식으로 멀티에이전트를 만들었다. 2024~2025년이 과도기였고(특히 2025년이 가장 심했다), 이때 LlamaIndex와 LangChain 진영이 툴콜 기반 에이전트 방식으로 코드 자체를 업데이트했다. 사용자가 많은 프레임워크가 툴콜 방식을 정립하면서 지금 쓰는 스타일이 자리 잡았고, 같은 코드 패턴의 멀티에이전트까지 이어졌다.
구현 방식 결이 같은 것
툴콜로 구현하는 최신 에이전트(LangChain create_agent) 서브에이전트
create_agent 이전, 툴을 바인딩해 직접 엮던 원시적 방식 옛 멀티에이전트

옛 멀티에이전트: State와 LangGraph의 고정 워크플로

  • Swarm, 서브에이전트는 LLM의 판단으로 에이전트를 부른다. 옛 멀티에이전트는 사람의 판단을 코드로 반영한다. "특정 조건이 오면 이 툴(에이전트)을 부른다"를 사람이 정한다.
  • State 관리: 정확히는 TypedDict 형식의 클래스로 관리한다. Pydantic과 비슷하게 클래스로 표현하지만 내부 데이터는 JSON처럼 동작한다. 이 클래스를 State라는 이름으로 두고, 프롬프트 메시지와 각종 변수를 모두 담는다. 다른 에이전트들은 이를 바탕으로 동작한다.
  • 서브에이전트는 "쿼리 전달 → description 읽기 → 출력 보기"가 자동이지만, 옛 방식은 State를 보고 for문, if문으로 전부 직접 작성해야 했다.

아래는 재구성한 예시다.

class State(TypedDict):        # 클래스로 표현, 내부는 JSON처럼 동작
    messages: list
    schedule_type: str         # 분류기/슈퍼바이저가 채운다

# 분기를 사람이 직접 코딩한다
if state["schedule_type"] == "개인":
    personal_agent(state)
elif state["schedule_type"] == "공유":
    shared_agent(state)
# LangGraph에서는 이것을 노드, 엣지로 그래프를 그려 고정 흐름으로 만든다
  • 이런 방식이 필요한 경우도 있다. LLM, SLM 성능을 믿지 못해서 "이 모델은 펑션콜로 툴이나 서브에이전트를 잘 부르지 못하겠다"고 판단하면 코드로 흐름을 고정한다. 이때 그래프 형식(여기서 여기로, 저기서 저기로)으로 그리게 해 준 것이 LangGraph다.

비유 초창기 멀티에이전트는 C언어 같은 절차지향 프로그래밍처럼 정해진 흐름대로 흘러가게 만드는 고정 워크플로다.

  • 단점:
    • LangGraph 코드는 모델 만들기 → 툴 만들기 → bind → State 정의 → 모델 call → 툴 → 로직 → 연결까지 끝내야 툴 3개짜리 에이전트 하나가 완성된다. 기존 패턴과 너무 달라 어려워했고, 그래서 멀티에이전트 구현이 많이 제한됐다.
    • 컨텍스트가 분리되는 것도 아니었다. 65개 툴이면 65개 조건을 다 입력하고, classifier 모델이 출력한 키워드로 어떤 툴을 부르라는 식으로 작성한다. 작업량은 엄청 늘어나는데 성능은 극적으로 좋아지지 않았다.
    • 모델이 툴을 잘못 부르면 디버그가 오히려 더 힘들다. 모든 게 고정돼 있어 모델도 똑같이 대답하도록 만들어야 하고, 챗봇, 에이전트의 자유도가 크게 떨어진다.
    • LlamaIndex의 Workflow도 LangGraph의 영향을 받아 마찬가지였다. custom planner도 "커스텀할 수 있다"고 포장하지만 사실 옛 에이전트 코드다. 이벤트를 전부 클래스로 만들고 메시지를 파악해 워크플로를 짠다.

프레임워크 지형: LangChain, LangGraph, Deep Agents, LlamaIndex

  • LangChain 진영의 "안 좋은 습관", 즉 "고질병": 패러다임이 바뀌면 프레임워크를 새로 낸다. 최근 것이 Deep Agents다.
  • 순서는 LangChain이 먼저, 그다음 LangGraph다. 이후 LangChain이 LangGraph 기반 위에서 create_agent 함수로 에이전트를 만드는 방식으로 바뀌었다. 2025년 10월쯤 v1으로 올라가며 create_agent 기반으로 전부 바뀌었다. 지금 쓰는 패턴이 이것이다.
프레임워크 성격 평가
LangChain 프롬프트 체이닝에서 출발. 지금은 create_agent(LangGraph 기반)로 툴콜 에이전트를 만든다 기본으로 쓰는 방식. 메인, 서브에이전트, 툴 사용 모두 구현 가능
LangGraph 멀티에이전트를 표방하며 등장한 low-level orchestration, stateful 도구 "low-level orchestration, stateful"은 꾸미는 말. 유연하지 않아 싱글 에이전트가 정립된 뒤 많이 안 쓰였고 "거의 퇴화한 상태"로 느껴진다
Deep Agents 멀티에이전트나 Codex, Claude Code 같은 복잡한 에이전트, long-running 태스크용 새 프레임워크 LangChain이 가장 밀고 있다. Claude Code와 가장 유사한 형식. 다만 기존 구조를 문법, 패턴만 바꿔 다시 낸 것이고 LangChain만으로도 다 구현된다
LlamaIndex RAG 특화. 4줄 정도면 RAG를 만들어 유명해졌다 멀티에이전트 패턴 3가지(agent workflow pattern, orchestrator agent, custom planner). 최근 Swarm(handoff) 추가
  • LlamaIndex 오케스트레이터 패턴은 프레임워크가 달라도 LangChain과 거의 같다. FunctionAgent는 ReAct처럼 툴콜하는 에이전트이고 system prompt를 받아 run으로 실행한다. call_research_agent 같은 함수 안에서 미리 만든 research_agent.run(...)을 돌린다. 에이전트를 만들어 두고 함수로 감싸 툴처럼 부르는 것이 서브에이전트다.
  • 커뮤니티는 LangGraph보다 LangChain이나 LlamaIndex(Workflows)를 쓰는 경우가 많았다.

정리 패턴은 결국 비슷하다. 사용자 프롬프트의 일을 나누고 각 일을 수행하는 에이전트에 연결하는 것. 새 프레임워크는 그걸 더 쉽게 만드는 방법일 뿐이니 프레임워크보다 구조를 이해하라.

서브에이전트 = 툴콜로 부르는 에이전트

  • 정의: 툴콜을 하는 부분에 에이전트를 구현하는 것. 가장 상위의 슈퍼바이저(supervisor) 에이전트가 특정 목적을 가진 서브에이전트들을 펑션콜, 툴콜 하듯이 부르는 구조다. "펑션콜링 만드는 파트에 다시 에이전트를 집어넣는 방식"이고, 툴콜 방식의 확장이다.
  • 툴을 툴 목록에 넣고 부르던 것처럼 서브에이전트도 펑션콜 형태로 만든다. 다만 그 함수 내부에 에이전트(모델)가 들어 있다. 툴콜 때 원본 LLM이 만든 프롬프트(입력값)가 툴로 전달되고 툴의 결과값이 다시 모델로 돌아오는데, 이 "프롬프트 전달 → 결과 리턴" 자리에 서브에이전트가 들어간다.
  • 메인 쪽은 "슈퍼바이저" 또는 "오케스트레이터"라고 부르고 전체 컨텍스트를 관리한다. 컨텍스트가 독립된 하위 에이전트는 "isolated subagent(독립된 서브에이전트)"라고도 부른다.

예시 카나메이트 도메인: "내일 내 일정과 누군가의 일정을 보고 미팅을 잡아 줘"라고 하면, 내 일정은 나나 에이전트가, A, B 같은 다른 사람의 일정은 공유 일정을 참조하는 에이전트가 처리한다. 툴콜 하듯 태스크를 나눠 각 에이전트가 수행하고 결과를 메인 에이전트가 종합한다.

  • 이 개념을 제일 잘 쓴 것이 Claude Code이고, 사실상 Claude Code가 상용화시켰다(Cursor 등도 있음).
  • 서브에이전트는 지금 에이전트 기술 중 가장 고도화된 방식이고 가장 최신 연구에 속한다. 그러면서도 구현은 이미 해 본 툴 구현 방식 그대로라 어렵지 않다. 볼 것은 어떻게 동작하고 어떻게 병렬로 도는지다.
  • 서브에이전트의 출발점은 1주차 Function Calling이다. 에이전트 구조 전체가 툴콜이라는 하나의 메커니즘 위에 있다(→ Tool과 Function Calling).

가장 단순한 서브에이전트 패턴: 툴 안에서 create_agent

  • LangChain 문서의 multi-agent → subagents 예시: 툴 내부에서 create_agent로 에이전트를 만들고, request를 받아 invoke한 뒤 답을 반환한다. 가장 심플한 서브에이전트 패턴이다.
  • 구현 선택지:
    • 툴 안에서 에이전트를 만들면 요청마다 시스템 프롬프트를 바꿔 구현할 수 있다.
    • 시스템 프롬프트를 바꾸지 않는다면 툴 밖에서 미리 만들어 두고 툴 안에서는 호출만 해도 된다.
  • 모델이 서브에이전트를 부르면 그 에이전트가 생성되거나, 이미 생성된 에이전트를 불러와 동작한다.

아래는 재구성한 예시다(툴 배치는 설명용).

# 서브에이전트: 툴 밖에서 미리 만들어 둔다
nana_agent = create_agent(model, tools=[my_schedule_tool],
                          system_prompt=NANA_PROMPT)        # 실제 동작을 적는다
kana_agent = create_agent(model, tools=[shared_schedule_tool, past_conv_search_tool, ...],
                          system_prompt=KANA_PROMPT)

@tool
def ask_nana(request: str) -> str:
    """내 개인 일정 관련 요청을 처리한다."""              # 슈퍼바이저가 읽는 description
    result = nana_agent.invoke({"messages": [{"role": "user", "content": request}]})
    return result["messages"][-1].content                # 최종 답만 메인으로 돌아간다

@tool
def ask_kana(request: str) -> str:
    """공유 일정, 멤버 일정, 지난 대화 관련 요청을 처리한다."""
    ...

supervisor = create_agent(model, tools=[ask_nana, ask_kana],
                          system_prompt=SUPERVISOR_PROMPT)  # 서브에이전트들의 역할을 적는다

서브에이전트가 메인 컨텍스트를 아끼는 원리

  • 메인 에이전트 하나만 있으면 "내 일정 찾는 툴"과 "공유 일정 찾는 툴"을 메인이 혼자 실행한 뒤 답을 만든다. 툴 실행에서 생긴 컨텍스트가 모두 메인 컨텍스트에 쌓인다.
  • 서브에이전트로 나누면:
    1. 메인이 서브에이전트에게 요청(쿼리)을 보낸다.
    2. 요청을 해결하는 과정은 각 서브에이전트의 컨텍스트 안에서 진행된다. 서브에이전트 안에서 컨텍스트가 새로 만들어져 독립적으로 실행된다.
    3. 최종 답변만 메인 에이전트로 돌아온다.

예시 그림으로 보면: 원래 메인이 컨텍스트 4칸을 차지해야 하는 일이라면, 서브에이전트 구조에서 메인은 일을 시키는 2칸만 쓴다. 각 서브에이전트에 들어간 컨텍스트는 따로 돌고, 끝나면 결과만 추가된다.

  • 그래서 메인 컨텍스트를 압축하는 게 아니라 아껴서 쓴다. 메인이든 서브든 정돈된 컨텍스트로 동작해 성능이 좋아진다. LLM 성능은 컨텍스트 길이에 크게 영향을 받기 때문에, 지금 여러 서비스의 에이전트 대부분이 이 구조로 운영된다. "에이전트 구현의 약간 표준 같은 방식"이라 할 만하다. (컨텍스트 관리 전략은 → 컨텍스트 엔지니어링과 하네스)
  • 대가: 서브에이전트가 중간에 한 작업은 메인에 공유되지 않는다. 그래도 메인이 요청한 내용은 툴로 잘 만들어 리턴한다.
  • 다만 독립적으로 동작해도 어느 정도 공유는 되므로 컨텍스트가 완전히 분리되지는 않는다. 그래서 작업을 이어서 할 수 있다.
  • Claude Code, Codex도 비슷하다. 서브에이전트를 부르거나 모델에 일을 위임하면, 서브에이전트가 각자 컨텍스트를 처리해 결과를 돌려주고 메인이 종합한다.

정리 서브에이전트의 장점은 하나, 컨텍스트 독립이다. 메인에는 "시킨 일"과 "받은 결과"만 남는다.

서브에이전트 설계: 툴을 기능별로 나누기

  • 노트북 예제: 툴 4개가 구현돼 있다. 원래는 메인 에이전트가 4개를 다 갖고 제때 잘 부르길 바라며 동작시킨다. 툴이 많을수록 오동작 확률이 높아진다.
  • 서브에이전트 계층을 두면 서브에이전트 2개(하나는 툴 1개, 하나는 툴 3개)로 기능별로 분리한다. 각 에이전트가 오동작할 가능성 자체가 낮아진다.
구분 싱글 에이전트 서브에이전트 구조
툴 배치 메인이 툴 4개를 모두 보유 메인은 서브에이전트 툴 2개만 보유, 서브가 각각 툴 1개, 3개
시스템 프롬프트 하나 두 층: 메인에는 "서브에이전트들이 어떤 일을 맡는지", 각 서브에는 "실제 동작"
서브에이전트 구현 없음 메인의 툴로, 펑션콜 때 쓰던 function tool 형식 그대로
  • 에이전트를 두 번에 걸쳐 구현한다고 보면 된다.

비유 태스크를 잘게 쪼개 그 일의 전문가를 따로 만들고, 그 전문가들을 어떻게 관리할지 설계하는 것이다.

  • 설계할 때 고려할 점:
    • 서비스가 커질 것 같으면 기획 단계부터 서브에이전트까지 염두에 두는 것이 보편적인 흐름이다.
    • 핵심은 "서브에이전트로 만들면 되겠다"가 아니라 관리 에이전트 하나에 각 기능을 얼마나 할당할지다. 이 비율은 실험과 테스트로 조정한다.
    • 가벼운 시스템은 서브에이전트 몇 개로 충분하다. 규모가 커지면 계층(hierarchy)이 생겨 아래 계층에 다시 서브에이전트를 두는 식으로 확장된다. 객체지향, 디자인 패턴처럼 설계 패턴이 논의되고 있지만 아직 교과서 같은 정답은 없다.
  • 과제에서는 기존 툴(RAG, MCP)을 나나, 카나 서브에이전트로 옮기고 슈퍼바이저가 두 에이전트만 보게 했다. 과제 세부는 → 주차별 실습 프로젝트에서 다룬다.

Swarm 패턴과 handoff

  • 서브에이전트처럼 종속적(계층형)으로 만드는 방식과 달리 Swarm 패턴도 있다. 에이전트를 여러 개 만들어 두고 "이 에이전트는 저 에이전트로만 갈 수 있다", "이 에이전트는 두 곳으로 갈 수 있다", "마지막 에이전트는 출력만 만든다"처럼 이동 가능한 경로를 지정한다.
  • LlamaIndex 문서 예시: specialist agent마다 쓸 수 있는 툴과 handoff(넘겨줄 수 있는 에이전트)를 지정한다. 워크플로를 짜고 최초 상태만 설정하면 실행 시 root 에이전트부터 루프가 계속 돈다. 옛 방식보다 훨씬 이해하기 쉬운 코드다.
  • Deep Agents 같은 프레임워크에서도 swarm 패턴 등으로 툴콜을 통해 에이전트끼리 통신하게 할 수 있다. 이때는 스킬 파일이나 컨텍스트를 파일 형식으로 공유한다.
  • Swarm, 서브에이전트 모두 모델이 툴(에이전트) 내부에서 판단을 한 번 더 할 수 있게 해 주고, 서브에이전트별로 툴을 나눠 가질 수 있게 해 준다.
  • 지금은 대부분 서브에이전트를 쓴다. Claude Code의 에이전트 팀은 Swarm과 비슷한 멀티에이전트 방식이다(→ AI 코딩 도구 활용(Claude Code, Codex)).

컨텍스트 전달: 멀티에이전트의 핵심 과제

  • 툴콜 기반 멀티에이전트에서는 서브에이전트로 툴콜이 일어나기도 하지만, 문서로 컨텍스트를 만들어 전달하기도 한다. 코딩 에이전트가 문서로 작업 지시를 남기는 경우가 이것이다.
  • 에이전트가 각자 따로 동작하거나 태스크가 분리돼 동작할 때는 컨텍스트 전달이 가장 중요한 문제가 된다. 태스크가 끝나면 지금까지 한 일을 문서로 남기고, 다른 에이전트에게 일을 시키려고 컨텍스트를 남겨 전달한다. 이때 문서나 스킬을 참조하게 할 수 있다.

독립 에이전트(멀티에이전트) MD 파일 같은 문서로 만들거나, 가진 내용을 요약해 전달한다
State 방식 State가 모든 메시지를 관리하므로 필요한 만큼만 떼어서 준다. 가장 흔한 건 가장 최근 메시지를 넘기는 것. 여러 에이전트가 함께 붙어야 하면 MD 파일로 만들기도 한다
  • 이 분야는 아직 정립 중이다. 서브에이전트는 펑션콜링 기반으로 정리됐고, 멀티에이전트는 "에이전트 간 컨텍스트를 어떻게 효율적으로 전달할지", "각 에이전트가 한 일을 MD 파일로 두고 그걸 보고 동작하게 할지" 같은 시도가 나오고 있다. LangChain은 새 프레임워크(Deep Agents)로, LlamaIndex는 기존 코드에 멀티에이전트 패턴을 추가하는 식으로 대응한다.
  • 에이전트 간 통신 프로토콜 A2A는 → MCP와 A2A에서 다룬다.

미들웨어: Human-in-the-loop와 병렬 툴콜 제한

  • 미들웨어는 에이전트 제어를 돕는 장치다. 2025년 10월 업데이트(LangChain v1) 때 추가된 기능이고, 서브에이전트 패턴의 한계를 보완한다.
  • 제어 지점: LLM이 입력을 받을 때, 툴을 부를 때, 최종 출력을 만들 때.
미들웨어 하는 일
Human-in-the-loop(HITL) 사람이 개입하는 지점을 넣는다. 코딩 에이전트가 "1번, 2번, 3번 중 어떻게 처리하겠습니까?" 하고 선택지를 주고, 사람이 고르면 진행하는 것이 이것이다
병렬 툴콜 제한 펑션콜은 한 번에 여러 번(병렬) 호출될 수 있는데, 이를 막아 한 번에 툴 하나만 부르게 한다
  • 노트북은 HITL과 병렬 제한 미들웨어를 조합해 에이전트 제어를 강화했다. 직접 만들 수도 있지만 자주 쓰는 것은 이미 만들어져 있어 불러 넣기만 하면 된다.
  • 미들웨어로 툴에 들어온 쿼리나 툴 결과를 코드에서 직접 고치는 것도 가능하다. Claude Code, Codex의 hook과 같은 의미이고, RAG의 쿼리 정제 위치로도 쓰인다(→ RAG: 임베딩 검색과 ChromaDB).

주의 미들웨어는 특수한 경우에만 쓴다. 대부분은 프롬프트와 펑션콜 description을 잘 쓰는 것으로 해결된다.

판단을 모델에 맡기는 흐름

  • 에이전트, LLM 확장 기능 대부분이 펑션콜링 기반으로 만들어지는 이유는 편리하고 유연해서다. LangGraph나 Workflow로 만들면 65개 툴 분기를 다 입력해야 하지만, 서브에이전트는 분기를 description, 즉 프롬프트 레벨에서 처리하고 LLM이 알아서 판단하게 한다.
  • 아키텍처가 바뀐 이유는 신뢰도 차이다. 멀티에이전트가 처음 나올 때는 LLM 신뢰도가 낮아 분기를 다 맞춰 주고 시스템 프롬프트를 그때그때 바꿔 넣어야 잘 동작한다는 개념이었다. 툴콜 기반 에이전트가 나오면서 모델이 알아서 판단하는 패턴으로 넘어갔고, 이 흐름이 점점 가속화되고 있다. 서브에이전트까지 가면 에이전트가 하위 에이전트들을 자율적으로 동작시킨다.
  • "CLAUDE.md를 최소화하라"는 최근 흐름도 "Claude Code가 알아서 하게 둬라"에 가깝다. MCP가 툴콜 방식으로 수렴하는 것도 같은 흐름이다(→ MCP와 A2A).

서브에이전트의 비용: 병렬성, 메모리, 트레이스

  • 툴콜에 에이전트를 넣는 것이 강력한 이유: LLM의 툴콜에는 제약이 없다. 한 번에 여러 개, 같은 것을 여러 번, 다른 것을 여러 개 부를 수 있다. 다섯 개 정보를 검색, 요약해야 하면 펑션콜을 5번 하면 된다. 예제에서는 미들웨어로 막았지만, 빼면 서브에이전트 툴들은 모두 병렬로 호출할 수 있다.
  • 서브에이전트를 도입하면 확장성은 크게 좋아지지만 컨텍스트 부하가 커진다. 이를 어떻게 제어하느냐에 따라 성능이 크게 갈린다.
  • 서브에이전트 하나마다 시스템 프롬프트와 내부 툴 description이 계속 추가된다. 성능은 좋아지지만 작성할 프롬프트 양이 늘고, 디버그할 때 툴 트레이스가 어려워진다.
  • Claude Code, Codex에서 하위 에이전트로 많은 일을 시키면 메모리 사용량이 폭발할 때가 있다. 서브에이전트들이 각자 컨텍스트를 갖고 동작하기 때문이다. 메인은 능력만 되면 서브에이전트를 굉장히 많이 만들 수 있어서 사양이 많이 필요해진다. 컴퓨터가 느려지고 뜨거워진다.

주의 트레이스: 노트북의 기본 트레이스는 에이전트를 invoke한 결과(result)로 추적하므로 슈퍼바이저 메시지만 잡힌다(예제 출력도 "카나 툴까지만"). 서브에이전트 내부 툴까지 보려면 따로 구현해야 한다. 서브에이전트 자체의 result를 받아 계층별로 디버그한다. (트레이스 기본은 → Tool과 Function Calling)

토큰 비용과 멀티에이전트 논쟁사

  • 일반 채팅 모델 대비 토큰 사용량:
구조 토큰(일반 채팅 대비)
일반 채팅 1배
싱글 에이전트 약 4배
멀티에이전트 약 15배
  • 네트워크 트래픽을 개선하듯 토큰도 고려해 시스템을 구성해야 한다. 멀티에이전트 일부를 SLM으로 바꾸는 식으로 조절한다. 메인은 좋은 LLM, 서브는 SLM으로 구성할 수도 있다(모델 조합은 → 모델 고르기와 여러 모델 조합).
  • 서브에이전트도 기능 분리, 오동작 감소의 대가로 토큰 소비가 늘어날 수 있다. API를 쓰는 레벨에서는 성능뿐 아니라 비용도 함께 따져야 한다.
  • 멀티에이전트는 에이전트끼리 컨텍스트를 공유하고 통신시키기가 어렵고, 따로 관리되다 보니 중복 토큰을 다시 전달해 읽는 일이 생긴다. 캐싱도 잘 안 돼 서브에이전트 방식보다 토큰 소모가 많다는 연구 결과가 있었다. 그래서 효율 면에서 표준이 서브에이전트 쪽으로 옮겨 갔다.
  • 그래도 멀티에이전트가 안 쓰이는 것은 아니다. 파일을 만들어 두고 참조해 컨텍스트를 유지하면 장기 프로젝트에 강하다. 작업이 중간에 끊기거나 새 세션이 만들어져도 파일을 읽어 와 이어서 처리할 수 있다. "완전히 나빠서 밀려났다"고 말하기는 어렵다.
  • 논쟁사: 2025년 6월쯤 Anthropic에서 "멀티에이전트를 써야 한다"는 테크 블로그가 나왔고, 비슷한 곳에서 "멀티에이전트를 만들지 말라"는 글이 불과 24시간 차이로 올라왔다. 당시엔 확신이 없고 정립되지 않았기 때문이다. 후자는 보통 Cognition의 "Don't Build Multi-Agents"로 알려져 있다. 이런 논쟁을 거쳐 메인 에이전트+서브에이전트 구조가 산업 표준이 됐다.

주의 유명 테크 블로그가 "이렇게 됐다"고 해도 언제든 바뀔 수 있다. 롱 컨텍스트 때처럼 기술이 나와도 실제 쓰는 사람에게 어떤 결과로 이어지는지는 다른 이야기다. 현재 흐름을 항상 확인한다.

싱글 vs 서브/멀티에이전트 선택 기준

  • 핵심 개념은 컨텍스트 열화(degradation)다. 태스크가 길어지거나 실패가 반복돼 컨텍스트가 길어지면 성능이 떨어진다.
상황 추천 구조 근거
간단한 요청, 짧게 끝나는 일 싱글 에이전트 기본은 싱글로 구현한다
큰 태스크를 나눌 때(A, B, C 동시 처리, RAG 담당, 특정 데이터 담당 등) 서브에이전트(디폴트) 기능 분리, 컨텍스트 독립
대화 턴이 10번 이상 이어지거나 주제 변화(분산)가 매우 큼 서브에이전트가 유리 순수 텍스트 기준 연구 결과
작업이 끊겨도 이어 가야 하는 장기 프로젝트 파일로 컨텍스트를 공유하는 멀티에이전트 파일을 읽어 와 이어서 처리
  • 한계: 이 연구들은 툴을 쓰는 상황이 아니라 순수 텍스트 기준이다. 대화 턴을 분석하고 실제로 써 보면서 짧게 끝나는지 긴 대화가 필요한지를 따져 골라야 한다. 단일 vs 멀티를 비교한 연구도 완벽하지 않다.
  • 활용 전략도 갈린다. 토큰을 많이 녹일수록 좋다고 보는 토큰 맥시, 모델을 나눠 쓰는 토큰 절약형(예: 검색을 잘하는 Antigravity에 검색을 맡기고 Claude Code와 Codex로 교차 검증), 모델 레벨을 나눠 스킬로 만드는 방식이 있다. 어떤 게 정답인지 아직 알기 어렵고, 가장 중요한 건 무엇을 만들고 싶은지, 어떤 전략으로 갈지다.
  • 에이전트를 만들 때는 서브에이전트를 염두에 두고 구현하고, 멀티에이전트는 컨텍스트가 얼마나 쌓이는지, 대화 턴이 얼마나 많은지를 보고 고르는 것이 좋다.

정리 어떤 구조든 무엇을 만들어야 하는지에 대한 계획이 먼저다. AI가 툴로 쓰이는 시대에는 그 툴을 얼마나 잘 쓰느냐가 중요하므로 요즘 도메인 지식이 각광받는다.

주제 6

에이전트 평가와 LLM-as-a-judge

생성 모델을 검증하는 세 방식(사람, 벡터 거리, LLM)에서 출발해, BERTScore의 한계, 30~50개 QA 세트, 쌍비교, 항목별 판정 규칙, 위치, 길이 편향과 교차 평가, 툴콜 평가, 평가 기반 튜닝 루프, temperature 0에서도 답이 바뀌는 문제의 실무 대응까지 정리한다.

평가는 4주차 RAG에서 top-k 같은 "검증 파라미터"로 처음 등장하고, 6주차에 LLM-as-a-judge로 본격적으로 다룬다.

평가가 등장한 흐름: assert에서 LLM judge로

  • 에이전트 평가는 항상 직접 데이터셋을 만들어야 한다. 구조화된 출력이면 더미를 만들거나 프롬프트를 넣고 출력을 검사한다("누구랑 내일 9시 미팅 잡아줘" → 출력 체크). 고도화된 모델이면 Q&A 데이터 페어를 만들어야 한다.
  • RAG의 top-k 같은 값은 테스트 데이터를 만들어 찾아야 한다. 에이전트는 만들고 끝이 아니라 잘 동작하는지 검증해야 하고, 그때 맞추는 파라미터다(→ RAG: 임베딩 검색과 ChromaDB).
  • 쿼리 리라이팅에서 보았듯 에이전트 튜닝과 평가, 검증의 기본은 "내가 설계한 흐름대로 모델이 동작하는가, 아니라면 프롬프트를 어떻게 바꿔야 하는가"를 확인하는 것이다.
  • 1~5주차 과제는 특정 툴이 호출됐는지, 기능이 동작했는지를 코드로 조건 체크(assert 등)했다. 6주차 마지막은 LLM으로 평가하는 방식(LLM-as-a-judge)이다.

정리 생성 모델의 가장 어려운 점은 생성이 컨트롤되지 않는다는 것이다. 그래서 구현하고 끝이 아니라 평가하면서 프롬프트, 파라미터를 조정해 원하는 결과에 가깝게 만들어 간다.

생성 모델 검증 3방식

방식 어떻게 장점 한계
① 사람이 직접 보기 사람이 생성 결과를 채점한다. 논문의 MOS(Mean Opinion Score)가 이 방식 골드 스탠다드. 가장 전통적이고 지금도 많이 쓴다 여러 명이 해야 해서 비용, 시간이 많이 든다
② 전통적 딥러닝(벡터 거리) 정답과 생성 결과를 딥러닝 모델로 각각 벡터로 만들고 거리를 계산한다. 가까울수록 유사 가장 쉽게 할 수 있다 뜻이 반대인 문장도 비슷하게 볼 수 있다(아래 BERTScore)
③ LLM(LLM-as-a-judge) LLM에 평가 규칙과 컨텍스트를 주고 채점하게 한다 사람에 가깝고, 놓치는 부분을 프롬프트로 처리할 수 있다 모델 편향이 있어 보정, 신뢰성 검증이 필요하다
  • ③은 6주차에서 다룬다.

BERTScore의 한계와 LLM judge

  • BERTScore: 벡터 공간에서 두 문장의 뜻이 비슷한지(유사도)를 보는 LLM 이전 방식이다. 일종의 "필터" 같은 간단한 검사이고, BERT 모델의 학습, 성능에 따라 결과가 달라질 수 있다. RAG 검색 때 두 문장 유사도를 보는 것과 같은 원리다.
    • 장점: 사용자가 "고양이"라 했는데 생성 결과가 "야옹이"면 비슷하다고 잘 처리한다.
    • 한계: "된다"와 "안 된다"처럼 반대말도 비슷하게 처리할 수 있다. 토큰화가 잘못 잘리면 거의 같은 점수가 나온다. 2%와 22% 같은 숫자 차이도 잘 구분하지 못한다.
  • LLM judge: 조금 더 사람 같은 평가자다. BERTScore가 놓치는 부분을 프롬프트로 어느 정도 처리할 수 있다. 그래서 생성 모델 검증에는 LLM을 쓰는 게 더 정확하고 맞는 접근이다.
  • 토큰화, 임베딩 원리는 → Transformer 블록 해부에서 다룬다.

정리 BERTScore = "뜻이 대충 비슷한가"만 보는 필터. 반대말, 숫자, 세부 사실을 따지려면 LLM judge를 쓴다.

QA 세트: 평가의 뼈대

  • 평가하려면 질문-답변 쌍(QA pair)이 필수다. 에이전트가 동작하는 도메인 지식 기반으로 질의응답이나 생성 문장을 직접 작성해야 한다.
  • 생성된 답변을 비교할 기준(정답)이 항상 필요하다. 가장 중요한 구조는 "에이전트가 활동하는 분야에서 잘 맞는 QA 세트를 갖고 있느냐"다.
  • 규모: 30~50개 정도의 QA 쌍을 만든다. 그러면 30~50개 질문에 대해 답변이 얼마나 유사한지 비교적 객관적으로 볼 수 있다.
  • QA 세트가 없으면 사람이 만들 수밖에 없다.
  • 결국 만들고 싶은 에이전트가 활동하는 도메인의 정확한 정보를 수집하고, 에이전트가 어떤 대답을 해야 하는지 정리해 둔 뒤 검증하는 것이다.
  • 파인튜닝 데이터와 평가 데이터는 결이 같다. 파인튜닝 데이터는 "모델이 이렇게 답했으면 좋겠다"를 담으니 평가에도 쓸 수 있고, 평가용 데이터(어떤 툴을 부르고 어떤 thinking을 하는지)는 벤치마크로도 학습에도 쓰인다. 그래서 잘 만들어 두면 큰 자산이 된다. 데이터셋이 없으면 에이전트는 결국 모델의 기본 성능에 기대어 동작한다. 모으기만 하지 말고 ChatGPT나 Claude로 정제, 검증해 세트의 결을 맞춰 두는 것이 좋다.

평가 프롬프트 구성과 judge 에이전트

  • 평가 입력 구성: 시스템 프롬프트 + 유저 질문 + 예시(정답) 답변 + 모델 A 답변 + 모델 B 답변. 이런 입력을 넣어 원하는 방식으로 모델이 평가하게 만드는 것이 목표다.
  • 노트북 구성:
    • judge context: 위에서 출력된 내용을 모두 담는다(어떤 컨텍스트를 판별할지). 에이전트가 동작한 내용, 즉 펑션콜이 어떻게 되고 트레이스가 어떻게 됐는지가 다 들어가므로 절차 평가가 가능하다.
    • 판단문 프롬프트(판정 규칙)
    • create_agent로 판단 전용 에이전트를 하나 만들어 judge 모델에 연결한다. judge를 서브에이전트로 구현해도 되고(→ 서브에이전트, 멀티에이전트, 워크플로), 필요에 따라 변형해도 된다.

아래는 재구성한 예시다(판정 규칙은 항목을 모은 예시).

JUDGE_RULES = """너는 에이전트 답변을 채점하는 평가자다.
아래 항목을 각각 O/X로 판정하라.
1. 생성된 답변이 정답 답변과 같은 정보를 담고 있는가?
2. 생성된 답변이 질문의 의도와 일치하는가?
3. 필요한 툴을 절차대로 호출했는가? (툴 트레이스 확인, 누락 시 X)
길거나 짧다고 편향을 두지 말고, 사용자 요청에 얼마나 잘 답했는지를 평가하라."""

judge = create_agent(judge_model, tools=[], system_prompt=JUDGE_RULES)

for qa in qa_set:                         # 사람이 만든 30~50개
    ctx = {"question": qa.q, "reference": qa.a,
           "answer": agent_output, "tool_trace": trace}
    verdict_ab = judge.invoke(build_prompt(ctx, order="AB"))   # 정답 → 생성 답 순서
    verdict_ba = judge.invoke(build_prompt(ctx, order="BA"))   # 순서를 바꿔 위치 편향 확인

판정 방식: 단독 점수 vs 쌍비교 vs 항목별 규칙

방식 질문 형태 출력 예 특징
단독 점수 "이 문장 어때?" "자연스럽습니다", "0.7점 주겠습니다" 절대 평가. LLM이 상대적으로 덜 정확하다
쌍비교 "두 문장 중 어느 게 자연스러워?" "A가 자연스럽습니다", "생성된 문장이 자연스럽습니다" LLM은 절대 평가보다 쌍비교를 더 잘 구분한다. 논문 실험에서 GPT-4가 쌍비교로 사람과 약 80% 비슷하게 분류했다
항목별 판정 규칙 채점 항목을 4~5개로 나눠 각각 O/X 항목별 O/X와 합계 어떤 부분을 잘하고 못하는지 보인다. 단순 비교보다 더 좋은 평가를 얻었다는 연구가 있다
  • 쌍비교를 30개에 대해 돌려 생성 쪽이 더 낫거나 비슷하게 나오면 모델 성능이 좋다고 볼 수 있다.
  • 항목별 규칙의 예:
    1. 정답(A) 답변과 유사한 정보를 담고 있는가?
    2. 생성된 답변이 질문(Q)의 의도와 일치하는가?
  • 무엇을 고를지(문장만 넣고 점수를 받을지, 두 문장을 비교해 고르게 할지, 항목별로 채점할지)를 직접 설계해야 한다. 이를 가능하게 하는 프롬프트를 어떻게 만드느냐가 핵심이다. 평가 항목을 늘리면 "6점 정도" 같은 식으로 항목별 비교도 할 수 있다.

주의 기본 평가 항목이 적으면 정확한 평가가 어렵다.

judge 편향: 위치, 길이 편향과 교차 평가

  • 모델별로 편향이 존재한다.
편향 현상 대응
위치 편향 앞쪽, 뒤쪽 단어에 어텐션이 몰려서, 앞에 놓인 문장을 정답으로 판단하는 경우가 실제로 있다(실험 논문도 있음) 정답 답변을 먼저 주고 생성 답변을 뒤에 준 버전(AB)과 순서를 바꾼 버전(BA)을 둘 다 돌려 같은 판정이 나오는지 확인한다
길이 편향 더 긴 문장을 좋게 보는 경향. 최근 모델은 파인튜닝 과정에서 어느 정도 제거돼 덜하다 프롬프트에 "길거나 짧다고 편향을 두지 말고, 사용자 요청에 얼마나 잘 답했는지를 평가하라"고 쓴다
  • 단순히 "뭐가 더 좋냐"가 아니라 항목(기준)별로 나눠 평가하면 더 정확해진다.
  • LLM 평가 논문들은 대부분 이런 특성(앞쪽을 더 중요하게 보는 등)을 상쇄하는 프롬프트를 소개하므로 찾아 적용하면 된다.
  • 위치에 따른 어텐션 쏠림은 실무 관점에서 → 컨텍스트 엔지니어링과 하네스, 어텐션 원리는 → Transformer 블록 해부에서 다룬다.

팁 같은 QA를 AB, BA 두 순서로 돌려 판정이 뒤집히면 judge 프롬프트를 의심한다.

judge 신뢰성 검증: 사람 채점과 비교

  • 모델을 평가자로 쓴다는 건 절대적 지표가 아니다. "이 정도 성능이면 우리 의도대로 채점해 준다, 이 채점자는 믿을 만하다"는 근거를 우리가 만들어야 한다.
  • 방법: 같은 QA에 대해 사람이 한 번, AI가 한 번 검증한다. 결과가 비슷하면 AI가 사람의 검증을 잘 재현한다고 보고, 그 상태에서 생성 답변을 평가하게 한다.
judge 모델 신뢰성 검증
현재 최고 성능 모델(Opus, GPT 최상위 모델 등) 벤치마크로 이미 검증돼 있고 이들을 넘는 모델도 많지 않아 스킵해도 된다
SLM 성능을 믿기 어려워 사람이 만든 정답을 비슷하게 맞추는지 검증이 필요하다
  • LLM이든 SLM이든 "의도한 답을 맞출 수 있는 지표"는 직접 구성해야 한다. 모델 선택은 → 모델 고르기와 여러 모델 조합 참고.

툴콜 평가: 답이 맞아도 툴콜이 틀리면 실패

질문 답은 맞았는데 툴콜이 잘못된 경우는? → 실패로 보는 게 맞다. 툴콜이 틀렸는데 답이 맞았다면 모델 기본 성능 덕분에 우연히 맞힌 것일 수 있다.

  • 평가 방법: 절차상 툴콜이 제대로 됐는지를 평가 항목으로 나눈다. 예:
상황 점수
툴 1, 2, 3번을 다 맞게 부르고 답도 맞음 3점
1번, 3번만 부르고 답은 맞음 감점된 점수
툴 몇 개를 빠뜨리고 답도 틀림 1점
  • judge context에 펑션콜, 트레이스 정보가 다 들어 있으니 그 안에서 절차가 틀렸으면 틀렸다고 판정한다. 그리고 그 절차대로 동작하도록 프롬프트(description)를 수정한다.
  • 이유: 에이전트는 펑션콜을 잘해야 하는 존재다. 서브에이전트도 펑션콜 기반으로 동작한다. 펑션콜이 잘못되면 다시 호출하거나 잘못된 정보가 들어온다. 메인 에이전트가 서브에이전트 답을 받아들일지 고를 수는 있지만, 잘못된 정보가 계속 들어오면 컨텍스트 자체가 오염된다. 오염된 컨텍스트는 수치로 바로 드러나지 않아도 이후 생성에 계속 악영향을 준다.

정리 툴콜이 잘 되는 게 제일 베스트다. 툴콜이 잘 되면 답은 거의 맞을 수밖에 없다.

툴콜 평가에 BERTScore가 안 맞는 이유

  • BERTScore는 두 문장의 뜻이 비슷한지만 본다.
  • 툴 트레이스에는 툴 내용이 툴용 커스텀 토큰에 감싸져 들어간다. 그래서 모든 툴 호출을 비슷하게 비교해 버릴 수 있다. 문장이 비슷한지만 보고 같은 툴인지는 구분하지 못한다. 내부에서 한꺼번에 계산하니 어떤 지표 때문인지도 확인할 수 없다. (커스텀 토큰은 → 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝)
  • 에이전트 오동작은 실제로 숫자가 틀리거나, 부정 표현이 잘못 나오거나, 외국어가 섞이는 식으로 정해진 데이터가 틀리는 경우가 많다. BERTScore는 이를 잡지 못한다. 출력 구조가 대략 비슷한지는 볼 수 있지만 세부 트래킹 능력이 많이 떨어진다.
  • 결론: 툴콜 평가는 LLM judge로 한다. 절차 규칙을 프롬프트로 주고 컨텍스트를 전부 넘겨, thinking을 잘했는지와 툴을 제대로 불렀는지를 평가하게 한다. 에이전트 구조 안에 프롬프트로 규칙을 구현하면 되니 "사실 글만 쓰면 된다."
평가 대상 BERTScore LLM judge
뜻이 대략 같은가("고양이"/"야옹이") 잘한다 잘한다
반대말("된다"/"안 된다") 놓칠 수 있다 프롬프트로 잡는다
숫자(2%/22%) 놓친다 프롬프트로 잡는다
같은 툴을 불렀나, 절차가 맞나 구분 못 한다 트레이스를 보고 판정한다

평가 기반 튜닝 루프: "컴파일러를 직접 세팅하는 것"

흐름(재구성):

  1. 에이전트가 입력, 출력을 만든다.
  2. 평가 에이전트를 만든다. 입력, 출력에 대한 QA를 미리 만들어 두고, 입력, 출력 컨텍스트를 조사하게 한다.
  3. 평가 에이전트를 고정한다. 이것이 기준점이 된다.
  4. 우리 에이전트 내부의 프롬프트를 튜닝해 평가 점수에 맞춰지게 한다.
  5. 반복하면 에이전트 출력이 원하는 답변 쪽으로 점점 이동한다.

비유 프로그래밍으로 치면 컴파일러를 직접 세팅하는 것이다. "이런 답을 내고 이런 툴을 불러야 한다"는 평가 에이전트를 세워 두고, 에이전트가 좋은 점수를 받도록 프롬프트를 고치면 의도한 에이전트가 된다.

  • 난이도가 높게 느껴질 수 있다. 만들고 싶은 에이전트가 명확하지 않으면 설계가 매우 어렵다. 풀려는 도메인 문제를 이미 잘 알고 있어야 좋은 에이전트와 평가를 만들 수 있다.
  • 평가 프롬프트에는 SLM, LLM의 특성(편향 등)이 반영돼야 하므로, 이를 잘 이해할수록 좋은 평가 모델을 만든다.
  • 같은 맥락에서, 개선은 모델 평가 방식을 기준으로 디버그라기보다 프롬프트를 계속 고쳐 가며 한다. 일반 프로그래밍은 컴파일 오류나 자료형 오류를 고치면 딱 떨어지지만, LLM, 에이전트는 A가 나올 수도 B가 나올 수도 있는 것을 원하는 쪽으로 끌고 가는 과학 실험에 가깝다.
  • Anthropic 워크플로의 평가자-최적화자 패턴도 같은 구조다(→ 서브에이전트, 멀티에이전트, 워크플로).

temperature 0 비결정성의 실무 대응

  • temperature를 0으로 둬도 원래는 같은 답이 나와야 하지만 실제로는 다르게 나올 때가 있다. 원인은 부동소수점 처리와 GPU 서버의 배치 처리다. temperature, 샘플링, 부동소수점이 모델 내부에서 어떻게 작용하는지는 → Transformer 블록 해부에서 다룬다.
  • 참고할 숫자:
상황 수치
API에서 temperature를 최대한 낮춰도 100번 중 2번쯤은 다른 답이 나올 수 있다
배치 처리 비결정성 실험(별도 처리 없이) 1000번 중 약 80번 다른 답
로컬 서빙에서 이를 통제하도록 고치면 속도가 30~60% 느려진다
  • API를 빌려 쓰는 입장에서는 temperature를 최대한 낮추는 것까지만 통제할 수 있다. 나머지는 어쩔 수 없다.
  • 대응:
    • 결과를 룰 베이스로 처리하거나 다시 모델로 검증한다.
    • 완전히 없애려면 모델을 로컬에서 직접 서빙하고 계산 단에서 처리해야 한다. 하지만 30~60% 느려져 사실상 잘 쓰이지 않는다.
    • temperature나 코드를 직접 고치기는 어렵다. LLM judge의 프롬프트를 바꿔 가이드하는 방식이 훨씬 쉽게 적용된다.

팁 평가 결과가 매번 조금씩 흔들리는 건 정상이다. 한 번의 결과로 판단하지 말고, 룰 기반 후처리나 재검증을 붙인다.

  • week04, week05 과제 버그는 휴먼 에러(테스트 설계 실수)였다. 버그 자체의 내용은 → 주차별 실습 프로젝트에서 다룬다.
과제 놓친 테스트
week04(RAG 임베딩) 테스트 대화를 짧게(티키타카 10번 이하) 했다. 대화가 길어지면 폭발하는 구조를 못 봤고, 벡터DB를 직접 확인하지 않고 트레이스만 봤다
week05(공유 일정 검색) 테스트 문장이 모두 "내 일정" 기준이었다. 내 일정 없이 공유 일정만 조회하는 케이스를 테스트하지 않았다
  • 앞서 말한 것처럼 컨텍스트(툴 트레이스 포함)를 불러와 검증했다면 잡혔을 문제다. LLM이 데이터를 찾고 검색하는 과정을 정확히 평가하지 못해 버그가 생겼다.

정리 구현하려는 기능의 정확한 동작과 유저가 쓸 상황의 테스트 케이스 설계가 문제를 많이 잡아 준다. 얼마나 다양한 형태로 테스트하느냐가 중요하다. 팀원들과 다양한 사례를 의논하고, 어떤 케이스에서 에이전트가 오동작할지 예상해 대비한다.

LLM-as-a-judge는 아직 연구 중인 방법론

  • 사용법이라기보다 LLM을 채점자로 활용하는 방법론이다. 정해진 표준이 없고 연구가 진행 중이다.
  • 각자 의도대로 만들되, 모델 특성 때문에 벗어나거나 이상하게 동작하는 부분을 잘 케어하는 방향으로 만든다.
  • 근거 있는 자료는 사실상 논문뿐이다(실험 결과를 소개하는 블로그는 있다). 그 논문들도 검사 방법론이 확립되지 않았다. "그냥 점수를 주기보다 항목을 만들어 pass/fail로 해라" 정도의 권고 수준이다.
  • 이런 평가를 설계하는 것 자체가 연구 주제가 될 수 있다.
  • LLM agent-as-a-judge는 관련 기본 논문이 있고 아직 연구 중인 분야다. 데이터셋 포맷을 만든 뒤 시스템 프롬프트를 잘 쓰는 것이 핵심이고, 논문의 프롬프트 템플릿(옛 모델 기준)을 분석해 스킬로 넣어도 된다. LangChain의 dynamic prompt로 시스템 프롬프트를 바꿔 가며 쓰면 컨텍스트가 길어지는 문제를 줄일 수 있다. (질의응답 모음은 → 자주 묻는 질문)

강화학습 파인튜닝과 평가는 닮았다

  • 강화학습은 모델 답변을 평가해서 그 점수로 학습하는 것이다. 1단계 SFT에서 쓴 Q&A(정답)가 있을 때 모델이 여러 답변을 생성하게 하고, 생성된 답변들을 평가 함수로 점수 매긴다. 정답과 얼마나 차이 나는지, 규칙을 따랐는지를 점수로 정리하고, 그 점수가 모델 파라미터를 튜닝하는 신호가 된다. 그래서 평가 파트와 매우 비슷할 수밖에 없다.
  • 지금 가장 연구가 많이 되는 분야다. LLM 크기를 키우는 시대는 거의 끝나 가고, "어떻게 잘 학습시키느냐"가 핵심이 됐으며 여기서 가장 영향력 있는 것이 강화학습이다.
  • 새 기법이 계속 나온다. DeepSeek가 GRPO를 내놓았지만 긴 컨텍스트에서 성능이 떨어지는 등 문제가 있어 대안이 계속 나온다. 연구 주제가 될 수도 있고, 새 모델을 고를 때 비교 기준이 될 수도 있다. 강화학습, SFT의 자세한 내용은 → 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝에서 다룬다.

정리 QA 세트로 답을 채점하는 일은 평가에서도, 강화학습에서도 똑같이 쓰인다. 좋은 QA 세트는 평가와 학습 양쪽의 자산이다.
