에이전트의 기초

LLM이 어떻게 에이전트가 되는지부터 정리했습니다. 에이전트의 구조와 ReAct, 모델이 툴을 고르고 인자를 채우는 Function Calling, 원하는 동작을 끌어내는 프롬프트 기법, 모델에 들어가는 정보 전체를 설계하는 컨텍스트 엔지니어링까지 다룹니다.

주제 1

에이전트란 무엇인가

LLM은 조건에 따라 다음 말을 확률적으로 고르는 텍스트 생성기다. 에이전트는 여기에 툴, 플래닝(프롬프트), 메모리를 붙여 조건을 강화한 Augmented LLM이다. 6주 과정 전체가 "모델에 들어갈 조건을 잘 만드는 일"이라는 큰 그림을 이 장에서 잡는다.

LLM 본연의 기능은 텍스트 생성뿐이다

이 과정이 다루는 범위는 딥러닝 → 생성 모델 → 텍스트 생성(text generation) 모델 → GPT 기반 LLM 순으로 좁혀진다. LLM(Large Language Model)은 언어 모델 중 사이즈가 큰 모델이고, 텍스트 생성 모델 가운데 지금 성능이 가장 좋은 모델들이다.

ChatGPT나 Claude Code 같은 LLM 도구를 쓰면 두 갈래 동작이 보인다.

  1. 순수하게 텍스트를 생성하는 부분
  2. "생각 중", "파일 읽는 중", "검색 중"처럼 기능을 수행하는 부분

핵심은 이 둘을 분리할 수 있다는 점이다. LLM 본연의 기능, 즉 바닐라 LLM이 하는 일은 1번 텍스트 생성뿐이다. 2번은 모델 바깥에서 붙인 기능(툴)이고, 그 바깥 부분을 구현하는 것이 이 과정의 내용이다.

정리 "검색 중", "파일 읽는 중"은 모델이 아니라 모델 바깥에 붙은 툴이 하는 일이다. 이 과정은 그 바깥을 만든다.

프롬프트는 조건이다: 아이템 박스와 바다 이야기

모델에 넣는 프롬프트는 "조건"이다. "나는 학교에"라는 조건을 넣으면 뒤에 올 수 있는 후보마다 확률이 붙는다(갑니다 10%, 간다 9%, 가는 중이다 8% …). 모델은 그중 하나를 골라 "갑니다"를 만든다. 질문을 넣으면 답이 나오는 흐름 전체가 이 과정이다.

확률 모델은 두 비유로 이해할 수 있다.

  • 아이템 박스: A 70%, B 20%, C 10%가 나오는 상자를 100개 열면 A 약 70개, B 약 20개, C 약 10개, 1000개를 열면 A 약 700개를 기대할 수 있다. 가장 익숙한 확률 모델이다. "그럼 딥러닝 모델은 뭐가 다를까?" 답은 조건이다.
  • 바다 이야기: 확률 조작으로 뉴스에 나왔던 사행성 게임이다. 사장님이 버튼을 누르면 확률이 A 80%, B 20%, C 0%로 바뀐다. 사람들은 이를 확률 조작이라 부르지만 딥러닝 모델이 바로 이렇게 동작한다. "사장님이 버튼을 눌렀을 때"를 "입력이 들어왔을 때"로 바꿔 보면 된다.

고양이 사진을 넣으면 "고양이일 확률"이, "나는 학교에"를 넣으면 "갑니다"의 확률이 달라진다. 딥러닝 모델은 항상 조건부로 동작하고, 이 조건부 예측을 사람 수준으로 잘하는 모델이 지금의 LLM이다. 조건부 확률 P(y|x), 자기회귀 생성 같은 원리는 → LLM과 딥러닝의 기본 원리에서 따로 다룬다.

비유 프롬프트를 넣는 일은 바다 이야기 사장님이 버튼을 누르는 일과 같다. 버튼(조건)에 따라 나올 수 있는 결과의 확률 분포가 바뀐다.

기반 모델의 한계: 확률적 생성이 낳는 문제

조건에 텍스트가 들어오면 다음을 예측하는 모델을 기반 모델(Foundation Model)이라 부른다. 예: GPT-3.5, GPT-4, GPT-4o(옴니). 이 모델들은 확률적으로 고르기 때문에 문제가 생긴다.

한계 내용
환각(hallucination) 잘못된 정보를 만들어 낸다
통제 어려움 모델이 어떻게 확률을 맞춰 다음 단어를 내는지 모르니 "사람이라면 이렇게 말하겠지" 하고 프롬프트를 쓸 수밖에 없다. 프롬프트 엔지니어링이 나온 이유다
성능 부족 프롬프트를 줘도 원하는 결과가 안 나와 파인튜닝이나 RAG를 붙이게 된다

이 설명을 더 정확하게 고치면 이렇다. 에이전트를 쓰는 이유가 "LLM의 성능 부족"이라는 말은 맞지만, 정확히는 LLM의 특성상 착시(환각)나 생성 오류가 생길 수 있는 상태이기 때문이다. 원인은 확률적 생성이다. 샘플링을 하므로 출력이 비결정적이고, 이것이 할루시네이션, 툴 잘못 선택, 이상한 검색, 의도와 다른 동작의 원인이 된다. "이 모델은 100%가 없다." 성능이 좋아져도 이 구조적 한계 때문에 잘못된 출력은 생긴다.

그래서 우리가 하는 일은 비결정적인 모델에 가이드라인을 만들어 변동성을 줄이는 것이다. 컨텍스트, 툴을 쓰는 이유도 모델이 더 정확한 단어를 예측하도록 잡아 주기 위해서다. 샘플링 원리는 → Transformer 블록 해부, temperature 0에서도 남는 비결정성은 → 에이전트 평가와 LLM-as-a-judge을 본다.

Vertical & Horizontal AI: 두 축으로 보는 LLM 발전

LLM이 좋아지는 방향은 "Vertical & Horizontal AI"라는 두 축으로 정리할 수 있다.

축 이름 단계
세로축 컨텍스트 및 도구 개선 단순 프롬프트 → 더 나은 프롬프트(또는 체인) → 검색 증강 생성(RAG) → 에이전트 AI 워크플로 → 다중 에이전트 워크플로
가로축 기반 모델 개선 gpt-3.5-turbo → gpt-4 → gpt-4o

이 그림에 아이템 박스(A 70%/B 20%/C 10%), "조건", 바다 이야기(확률 조작) 비유를 겹쳐 볼 수 있다. 가로축은 모델 자체가 조건부 예측을 더 잘하게 되는 방향이고, 세로축은 같은 모델에 더 좋은 조건을 넣는 방향이다.

  • 세로축의 "더 나은 프롬프트"는 프롬프트 엔지니어링이며, 지금은 하네스 같은 개념으로 발전하고 있다(→ 컨텍스트 엔지니어링과 하네스).
  • ChatGPT, Gemini, Claude 같은 서비스도 모델 단독이 아니라 세로축 기법으로 단점을 보완한 형태다. 프롬프트 처리에 따라 다중 에이전트로 동작하거나, 웹을 검색하거나, 툴을 부른다. 지금 쓰는 대부분의 도구(웹 서비스 포함)는 마지막 두 단계에 있다.
  • 이 과정은 조건부 확률 모델을 만드는 과정이 아니다. LLM의 특성을 코드, 기술로 보완, 제어해 활용하는 과정, 즉 세로축을 구현하는 과정이다. 결국 Claude Code, Codex의 동작을 LangChain으로 코드 구현해 본다.
  • 같은 흐름을 "단순 프롬프트 → 더 나은 프롬프트(프롬프트 엔지니어링, 프롬프트 체이닝) → RAG → Agent → Multi-Agent"로 다시 짚어 보면, 지금 만드는 싱글 에이전트는 이 단계 중 3단계 정도다. RAG까지는 모델에 들어가는 조건을 개선하는 단계였고, 그 한계를 툴콜이 넘어섰다(→ Tool과 Function Calling).

정리하면 조건을 강화하는 것이 세로축, 모델이 스스로 좋아지는 것이 가로축이고, 오른쪽 위로 갈수록 좋은 에이전트다. 우리가 에이전트를 만드는 방향도 그쪽이다. 이 과정에서 다룬 내용 전체가 결국 이 그림 위에 놓인다.

두 축은 성격도 다르다. 기반 모델(컨텍스트 이해, 생성 능력)은 "우리 의지와 상관없이" 발전한다. 반면 프롬프트, 쿼리, 시스템 프롬프트는 우리가 의지를 갖고 개선하기 상대적으로 쉽다. 그래서 RAG를 쓰고, 프롬프트에 필요한 정보를 넣는 Skills 같은 방법론도 계속 발전한다.

정리 싸움은 두 가지다. ① 사람이 조건을 더 잘 만들어 예측을 돕거나(세로축), ② LLM이 똑똑해져 조건을 더 잘 따르거나(가로축). 우리가 손댈 수 있는 것은 ①이다.

Cognitive Architecture: 연주자에게 악기를, 레이서에게 레이싱카를

에이전트를 개념적으로는 Cognitive Architecture(CA)라고 부르고, 지금 시대에는 이 CA를 "에이전트"로 구현하고 있다. 나중에 교과서에는 "CA라는 개념이 있고, 2020년대에는 에이전트로 구현했다"고 쓰일 수 있다. 개념은 남고 구현 방법은 바뀌어 갈 것이다.

LLM은 일종의 "디지털 지능", 즉 능력이다. CA는 여기에 툴과 프롬프트를 붙여 그 능력을 지원한다.

비유 LLM이 연주자라면 툴, 프롬프트는 악기, 악보다. 아무것도 없이 연주하라면 책상을 두드리겠지만, 피아노, 바이올린을 주면 훨씬 잘 연주한다. LLM이 레이서라면 툴, 프롬프트는 자동차, 내비게이션이다. 경차보다 레이싱카를 주면 능력이 좋아진다.

지금 에이전트 연구는 구현이 이론보다 앞서 나가 있어 둘이 잘 안 맞는 부분도 있다. 기반 모델, 컨텍스트, 도구 개선 같은 개념은 국내외 강의에서 공통으로 쓰는 레퍼런스 기반 내용이다.

에이전트 아키텍처: LLM + 메모리 + 플래닝 + 툴

실제 구현은 에이전트 아키텍처로 한다. 마이크로소프트가 제안한 구조로, 구성 요소는 LLM, 메모리, 플래닝(= 프롬프트), 툴이며 지금 쓰는 대부분의 에이전트 프로그램이 이 구조다. 1주차는 이 중 툴과 플래닝의 관계를 다뤘다.

메모리는 "대화 목록 기억"으로 정리할 수 있고, 툴을 쓸 수 있느냐가 에이전트가 될 수 있느냐를 가른다. LLM은 툴의 이름과 설명을 보고 어떤 툴을 어떻게 부를지 정한다. "에이전트는 결국 툴로 귀결된다." MCP도 "툴을 쓰기 위한 도구 중 하나"다(→ MCP와 A2A).

코드로 보면 에이전트 구성은 LLM + 시스템 프롬프트 + tools(툴이나 MCP 형식) + 실행 시 붙는 유저 메시지다.

각 구성 요소는 따로 발전한다. 에이전트는 확률적으로 생성하지만, 프롬프트, 조건 같은 제어 장치로 원하는 답을 내게 만든다.

구성 요소 하는 일 발전 방향
LLM 텍스트 생성(능력) 더 정확한 예측
툴(제어) 로컬 함수 실행 원하는 기능 구현, MCP 사용
메모리 대화 목록 기억 중요한 것을 기억해 답변할 때 참조
플래닝(프롬프트) 어떻게 동작할지 정함 간단히 CoT만 쓰거나, 필요하면 분기, 반복을 준다

Augmented LLM과 회사별 에이전트 구조도

원래 모델을 Vanilla LLM, 성능 부족을 보완(증강)한 것을 Augmented LLM이라 부른다. 우리가 "에이전트"로 구현하는 것이 Augmented LLM이다. 증강하는 이유는 모델 혼자서는 장기 목표 유지, 질문, 답변 유지, 컨텍스트 처리 같은 부분에 문제가 생기기 때문이다. 당시 거의 모든 회사가 이런 구조를 발표했다.

회사 구조도의 이름 해석
마이크로소프트 LLM + 메모리 + 플래닝 + 툴 1주차부터 본 그림
Anthropic LLM 주변에 Retrieval(Query/Results), Tools(Call/Response), Memory(Read/Write) Retrieval은 프롬프트, Tools는 툴, Memory는 대화 목록
Google planning 대신 orchestration, Retrieval이라는 말도 씀 프롬프트 단의 이름만 다르다

프롬프트 단의 이름은 회사마다 다르지만 공통으로 들어가는 것은 툴콜이다.

LLM과 에이전트의 차이: Tool과 Action

에이전트와 LLM의 가장 큰 차이는 Tool이다. 실습에서 만든 툴은 파이썬 함수이고, 그 위의 LLM이 함수를 부르거나 데이터를 넣는다. 지금의 에이전트는 "코드 형태의 제어 + 프롬프트 형태의 제어"로 다룬다.

모델을 원하는 대로 만드는 길은 크게 둘이다.

  • 파라미터를 업데이트하는 방식: 파인튜닝, 강화학습 기반 파인튜닝(→ 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝)
  • 코드로 외부 데이터를 관리하는 방식: 이 과정이 집중하는 쪽, 특히 툴

툴 개념은 로봇, 자동차 같은 피지컬 AI로도 확장되고 있다.

에이전트는 툴을 사용한다. 에이전트가 툴을 부르는 행위 자체를 Action이라 부르며, Action은 "LLM이 툴 설명을 보고 거기에 인자를 입력하는 것"이다. 에이전트는 LLM과 독립된 존재가 아니라 LLM에 프롬프트를 전달하는 역할이다. LLM은 자연어로 답하고, 에이전트는 LLM이 툴을 쓰게 만들어 준다.

툴콜, Function Calling 기반 에이전트는 요즘 "AX(AI 전환)" 교육의 핵심이고, 현직 개발자뿐 아니라 다른 분야 종사자도 도구처럼 배우고 있다. 급하게 하지 말고 복습하며 따라가면 된다.

전통 프로그래밍과 무엇이 다른가: main 함수를 에이전트가 짠다

전통적 프로그래밍(C, Python, Java 무엇이든)은 main 함수가 우리가 만든 함수, 클래스를 순서대로, 기능별로 조합해 실행한다. 에이전트로 넘어오며 달라진 점은 하나다. 사람이 자연어로 요청하면 그 조합과 실행 순서를 에이전트가 대신 정한다.

비유 에이전트 만들기는 코딩과 똑같다. 다른 점은 "메인 함수"를 내가 짜는 대신 에이전트가 자연어 요청을 보고 함수를 골라 실행한다는 것이다. 문제를 풀 함수들을 구현해 두면 에이전트가 적재적소에 불러 사용자 문제를 해결한다.

그래서 에이전트 개발도 결국 프로그램을 만드는 일이고, 구현된 함수들을 얼마나 잘 조합해 실행하는지가 곧 에이전트의 성능이다. 함수(툴)를 만들고 부르는 구체적인 방법은 → Tool과 Function Calling에서 다룬다.

ReAct: 생각하고 행동하는 플래닝 프롬프트

ReAct(Reason + Act)는 대표적인 플래닝 프롬프트다. "제주도 날씨" 예시로 흐름을 보자.

  1. 질문 이해: 사용자가 "제주도 날씨는 어때?"라고 묻는다.
  2. 툴 검색: 구현해 둔 함수 중 get_weather(장소를 넣으면 기온, 날씨 반환)가 있다. 이걸 쓰면 답할 수 있겠다고 판단한다.
  3. 인자 선정: 툴에 맞는 키워드, 즉 함수 인자로 질문에서 "제주도"를 뽑는다. 사람이 함수를 실행할 때 값을 넣는 일을 모델이 대신한다.
  4. 툴 실행: "제주도"로 함수를 돌리면 기온: 35도, 날씨: 맑음 같은, 자연어가 아닌 결과가 나온다.
  5. 결과 해석과 답변: "현재 제주도의 기온은 35도이고 날씨는 맑습니다."라고 자연어로 답한다.

LangChain create_agent 내부에 이미 이 ReAct 플래닝이 들어가 있다. 세부 구현은 다를 수 있지만 이 프롬프트 개념을 바탕으로 동작한다.

정리 ReAct = 질문 이해 → 툴 고르기 → 인자 뽑기 → 툴 실행 → 결과를 자연어로. 이 뼈대가 Function Calling(→ Tool과 Function Calling)이다.

ReAct 루프 안의 분기: "질문에 답이 되는가?"

ReAct식으로 동작하는 지금의 에이전트는 요청에 한 번만 생각하고 답하지 않는다. 흐름을 그려 보면 이렇다.

  1. 사용자 질문에 따라 툴을 검색한다.
  2. 툴 결과와 질문을 종합해 답변한다. 사용자 질문 → assistant 답변이 오가며 컨텍스트가 쌓이고, 툴, 스킬, RAG로 증강된 프롬프트로 답한다.
  3. 그 답변을 다시 평가한다. "사용자의 질문에 답이 되는가?" → yes/no
  4. no면 1번으로 돌아가고, yes면 사용자에게 답을 준다.

이런 분기가 내부에 구현돼 있으며, 플래닝 같은 부분은 프롬프트만으로 컨트롤한다.

최근 나오는 goal, loop 같은 명령어도 이 ReAct 구조와 비슷하다. 입력해 둔 목표를 달성할 때까지 동작 → 달성 여부 체크 → 다음 단계로 분기를 반복한다.

정리 적절한 툴과 플래닝으로 문제를 해결하는 것이 에이전트이고, 이것이 싱글 에이전트 구조다. 여러 에이전트를 엮는 방법은 → 서브에이전트, 멀티에이전트, 워크플로에서 다룬다.

에이전트 = 안쪽 LLM에게 줄 조건을 만드는 장치

그림으로 그리면, 가운데 에이전트가 있고 그 안에 LLM이 있다. 에이전트가 툴 등을 이용해 하는 일은 결국 안쪽 LLM에게 줄 프롬프트를 구성하는 것, 즉 프롬프트 엔지니어링이다.

  • LLM은 "질문을 넣으면 답이 나온다"(주로 텍스트, 가끔 이미지, 오디오).
  • RAG, 에이전트, Tool/Function Calling, MCP(툴을 웹에서 불러오는 것)는 모두 컨텍스트를 잘 만드는 과정이다. 어떻게 해야 더 잘 되는지, 어떻게 하면 아껴 쓸 수 있는지를 배우는 것이다.
  • 반대로 모델 내부 구조(GPT 구조) 연구는 주어진 컨텍스트를 얼마나 잘 이해해 답을 잘 만드느냐를 다룬다(→ Transformer 블록 해부). 두 축이 "맞물려" 동작한다.
  • 리랭킹, 리라이팅(→ RAG: 임베딩 검색과 ChromaDB)도 모델이 답을 잘 찾도록 컨텍스트를 바꿔 주는 방법이다. 정답이 없어 실험적으로 개선해 가는 것이 에이전트 빌드 과정이다.

결국 에이전트나 LLM을 더 잘 동작하게 하는 작업 대부분은 프롬프트, 곧 컨텍스트를 더 잘 만드는 데 초점이 있다. 프롬프트를 만드는 일은 조건을 강화하는 일이다.

비유 예전 딥러닝에서 "데이터를 잘 정제하고 확실한 데이터만 학습시켜야 원하는 결과가 나온다"고 했던 것과 같다. LLM에서 프롬프트를 잘 쓰는 일은 이미지 도메인에서 정확한 이미지와 정답 세트를 맞춰 학습시키는 것과 같은 역할이다. 모델은 입력 조건에 따라 출력하므로, 조건을 잘 만들지 못하면 정확한 답이 나올 수 없다.

툴콜, RAG, 스킬은 모두 "조건 강화"다

초반 연구 이후 LLM 활용은 펑션콜, 다른 에이전트, 외부 데이터를 불러와 조건을 강화하는 쪽으로 발전했다.

  • 툴콜을 왜 하나: 기능에 해당하는 함수를 실행해 그 결과를 컨텍스트에 추가한다. 즉 조건을 강화하는 것이다.
  • 시스템 프롬프트를 쓰는 것, 툴콜, RAG, 스킬 모두 조건을 강화한다. "이거 다 프롬프트들이죠?"
  • 이것이 앞에서 본 Vertical & Horizontal AI 그림의 세로축이다. LLM에 들어가는 조건을 잘 만드는 방법이 곧 원하는 출력을 만드는 작업이다.

결론도 같은 말이다. 툴을 쓰는 것도, 프롬프트 엔지니어링도, 컨텍스트 엔지니어링도 결국 모델에 들어갈 프롬프트를 얼마나 잘 구성하느냐의 문제다. 프롬프트 기법은 → 프롬프트 엔지니어링, 컨텍스트 관리는 → 컨텍스트 엔지니어링과 하네스에서 이어진다.

정리 툴콜 = 함수 실행 결과를 컨텍스트에 붙이는 조건 강화. RAG, 스킬, 시스템 프롬프트도 같은 일을 다른 형태로 한다.

에이전트의 두 핵심 축과 도메인 지식

에이전트에서 가장 핵심은 툴콜(Tool Call)(→ Tool과 Function Calling)과 구조화된 출력(Structured Output)(→ 구조화된 출력과 Pydantic) 두 가지다. 3주차(SQLite 저장, → 툴 입력 검증과 SQLite 저장)는 이 둘을 "쓰는 방법"을 보여 주는 예제 같은 주차다.

  • "프롬프트를 이렇게 쓰는 게 맞나" 하고 혼란스러울 수 있다. 코드 AI를 접한 시기는 처음 배우는 사람이나 전 세계 현업 개발자나 거의 같다. 잘 다루는 사람과 낯선 사람이 섞여 있지만 "이렇게 쓰면 되겠다"는 흐름이 생기는 중이다.
  • AI 발전은 막을 수 없다. "수많은 박사과정 학생이 이걸 만들어내야 박사가 되기 때문에" 발전은 무조건 계속된다. 그러니 흐름에 올라타야 한다.
  • 이 흐름에서 핵심 경쟁력은 도메인 지식(domain knowledge), 즉 전공이나 관심 분야의 지식이다. 실습에서 배운 기반 지식(에이전트 구현법, structured output 만드는 법)을 자신의 프로젝트에 접목하는 구조도 그 연습이다.

정리 기술(툴콜, 구조화된 출력)은 모두가 비슷한 시기에 배우고 있다. 차이를 만드는 것은 그 위에 얹는 도메인 지식이다.

주제 2

Tool과 Function Calling

에이전트의 뼈대인 Function Calling을 다룬다. 모델은 함수 설명을 보고 툴을 고르고 인자를 뽑을 뿐, 함수 실행은 로컬에서 일어난다. LangChain `@tool`, `create_agent`, `invoke`로 에이전트를 만들고, 툴 트레이스로 디버깅하는 법까지 정리한다.

Function Calling이란: 판단은 LLM, 실행은 로컬

Function Calling(Tool Calling)은 LLM이 로컬에 있는 실행 가능한 함수를 부르는 기능이다. 예전엔 IoT 서버 등 일부에서만 쓰였지만 지금은 에이전트 동작의 가장 필수 개념이 됐다.

역할 분담이 핵심이다.

  • LLM: 사용자 프롬프트와 함수 설명을 보고, 어떤 함수를 쓸지 판단하고 그 함수를 실행할 인자를 추출한다.
  • 로컬(코드): 그 인자로 함수를 실제로 실행한다. 모델 입장에서 함수가 코드로 어떻게 구현됐는지는 중요하지 않다.

인자 추출은 원래 사람이 하던 일이다. 사람이 일정 함수를 쓰려면 "개발 미팅" 같은 값을 직접 넣어 실행해야 했다. 그 일을 LLM이 대신한다. 인자를 넘겨 함수를 실행하는 과정은 프레임워크 내부에 숨겨져 있어 평소엔 보이지 않는다.

모든 에이전트 동작은 Function Calling 기반이며, 어떤 함수를 어떻게 동작시킬지는 LLM이 판단한다. LLM은 입력 조건대로 움직이므로 프롬프트와 함수 설명을 잘 써야 Function Calling이 잘 된다. 이 뼈대는 이후 장에서도 "외울 정도로" 반복해서 쓰인다.

정리 모델은 "어떤 함수에 어떤 값을 넣을지"만 정한다. 실행은 내 컴퓨터(로컬)에서 일어난다.

Function Calling의 등장: IoT 서버에서 에이전트의 뼈대로

RAG까지는 모델에 들어가는 조건(프롬프트)을 개선하는 단계였다. 자주 쓰는 프롬프트를 만들어 두거나, GPTs에 자료를 올리고 프롬프트를 작성해 두는 방식이었다. 그런데 용도별로 모델을 따로 만들고 관리해야 해서 한계가 분명했다.

Function Calling은 처음부터 OpenAI ChatGPT 모델에 들어 있었고, 초기엔 IoT 서버 관리 예제로 소개됐다. 원래는 개발자가 IoT 서버의 함수를 직접 불러 인자를 넣고 실행해야 했다. 툴콜이 붙으면 개발자가 아니어도 자연어로 함수를 부를 수 있다.

핵심은 "직접 구현한 함수를 에이전트가 부를 수 있다"는 점이다. 예전엔 주제 A, B, C마다 RAG를 따로 만들어야 했지만, 툴로 만들면 에이전트 하나가 모든 데이터를 불러 처리할 수 있어 더 유연하고 강력하다. 그래서 Function Calling이 1주차 주제가 됐다.

주의 이런 흐름은 6개월만 지나도 바뀔 수 있다. 다만 툴콜은 워낙 강력해서 멀티 에이전트 구현 방식에도 변화를 주고 있다(→ 서브에이전트, 멀티에이전트, 워크플로).

Function Calling 동작 순서

OpenAI 저수준 코드로 "내일 10시에 민수랑 회의를 잡아줘"가 처리되는 과정을 한 단계씩 따라가 보자.

[사용자]  "내일 10시에 민수랑 회의를 잡아줘"
   │
   ▼
[에이전트 코드]  질문 + 모든 툴의 설명(name, description, parameters)을 함께 모델에 보낸다
   │
   ▼
[LLM]  ① 툴 선택  ② 인자 추출  →  1차 응답 = function_call(툴 이름, arguments)
   │
   ▼
[에이전트 코드]  ③ 받은 인자로 로컬 함수 실행  →  실행 결과(JSON)
   │
   ▼
[LLM]  ④ 실행 결과를 다시 받아 자연어 답변 생성
   │
   ▼
[사용자]  최종 답변
단계 누가 무엇이 오가나
1. 질문과 툴 설명 전달 코드 → 모델 사용자 질문과 함께 등록된 모든 툴의 설명이 컨텍스트에 들어간다
2. 툴 선택 모델 설명을 보고 "이 툴로 이 요청을 수행할 수 있다"고 판단한다
3. 인자 추출 모델 → 코드 1차 응답은 자연어가 아니라 function_call(status completed)이다. "이 함수에 이 값을 넣으라"는 인자(제목 "프로젝트 회의", 날짜 "7월 3일" 등)가 온다
4. 로컬 실행 코드 그 인자를 로컬 함수에 넣어 실행하고 결과를 받는다
5. 결과 재전달과 최종 답변 코드 → 모델 → 사용자 실행 결과를 모델에 다시 넘기면 모델이 자연어로 최종 답을 만든다

특히 3단계가 중요하다. 응답 아웃풋은 "입력된 프롬프트의 정답"이 아니라, 모델이 프롬프트를 보고 "이 값이 이 함수에 들어갈 거야"라고 판단한 인자 값이다.

비슷한 예시로 보면, "내일 10시에 개발 미팅을 잡아줘" + 일정 생성 함수(create_schedule)의 설명 → 모델이 인자 추출 → 로컬이 일정 등록 → 결과를 다시 모델에 → "내일 10시에 개발 미팅 일정이 등록되었습니다"라고 알려 준다.

정리 질문 → (모델) 툴 이름, 인자 생성 → (로컬) 함수 실행 → (모델) 결과를 보고 최종 답변. 모델은 두 번 불린다.

모델은 코드를 보지 못한다: 툴 스키마

모델은 코드를 보지 못한다. "실제 코드가 도는 게 아니라 여러분들이 설명한 내용을 기반으로 모델이 값을 유추"한다. 컨텍스트에 사용자 질문과 함께 들어가는 것은 함수 이름, description, 파라미터 이름, 필수 인자(required) 같은 설명뿐이다.

OpenAI API를 직접 쓸 때는 이 설명을 JSON 스키마로 써 준다(프레임워크에서는 직접 쓰지 않는다). 예로 별자리 운세 함수를 보자.

필드 값
type function
name 별자리 운세 함수(OpenAI 공식 문서의 get_horoscope 예제와 같은 구조)
description "별자리에 대해 오늘의 운세를 가져오는 함수"
parameters sign(별자리)
required sign

모델은 이 설명을 보고 사용자 질문에서 sign에 들어갈 별자리를 추출한다. LangChain도 내부적으로는 같은 방식이다. 툴 정보는 결국 LLM이 이해하는 툴콜 프롬프트 템플릿으로 변환돼 모델에 들어간다(모델이 그 형식을 어떻게 학습하는지는 → 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝).

저수준 코드로 따라가 보기

LangChain에서는 이 과정이 상위 계층에 감싸져 보이지 않는다. 그래서 Colab 노트북(OpenAI Function Calling.ipynb)으로 내부를 "한 번만" 확인해 본다. 실제로 이렇게 구현하라는 뜻은 아니다.

(OpenAI Responses API 형태의 예시이며, 세부 필드 이름은 설명용이다)

import json

tools = [{
    "type": "function",
    "name": "create_schedule",
    "description": "사용자 요청에 따라 일정을 등록한다 ...",  # 모델이 보는 것은 코드가 아니라 이 설명
    "parameters": {
        "type": "object",
        "properties": {"title": {...}, "date": {...}, "start_time": {...}, "attendees": {...}},
        "required": ["title", "date", "start_time", "attendees"],
    },
}]

# 1~3단계: 질문 + 툴 설명을 보내면, 1차 응답으로 function_call이 온다
resp = client.responses.create(
    model=MODEL,
    input=[
        {"role": "system", "content": "오늘 날짜는 ..."},  # '내일'을 계산할 기준 정보
        {"role": "user", "content": "내일 10시에 민수랑 회의를 잡아줘"},
    ],
    tools=tools,
    tool_choice="auto",  # 특정 툴을 지정할 수도 있다. 기본 auto면 모델이 판단
)
call = next(item for item in resp.output if item.type == "function_call")
args = json.loads(call.arguments)  # 예: {"title": "프로젝트 회의", "date": "7월 3일", ...}

# 4단계: 로컬에서 실제 함수 실행
result = create_schedule(**args)

# 5단계: 실행 결과를 다시 모델에 넘기면 최종 자연어 답변이 나온다
resp2 = client.responses.create(
    model=MODEL,
    input=[..., call, {"type": "function_call_output",
                       "call_id": call.call_id, "output": json.dumps(result)}],
    tools=tools,
)
print(resp2.output_text)

tool_choice로 특정 툴을 지정할 수도 있고, 기본값 auto로 두면 모델이 알아서 판단한다.

툴콜의 취약 지점: "내일"은 며칠인가

"내일 10시에 민수랑 회의를 잡아줘"에서 인자를 뽑으면 제목=회의, 시작=10시, 참석자=민수(와 나)가 나온다. 그런데 "내일"이 며칠인지는 모델이 알 수 없다. 모델은 온라인에 연결돼 있거나 다른 정보를 받지 않으면 날짜나 최신 데이터를 모른다.

  • 이런 빈칸은 코드 실행 시점 날짜를 OS에서 불러오거나 검색해서 시스템 프롬프트 등으로 채워 줘야 한다. 그래야 "내일"을 "7월 3일"로 파악한다.
  • 툴콜을 직접 따라가 보면 이런 취약 지점이 보이고, 디스크립션, 시스템 프롬프트에 하나씩 추가하게 된다. 그러면 꽤 길어지지만 "시스템 프롬프트는 많이 길어져도 크게 상관은 없다."
  • 디버그 지점: 사용자가 정보를 덜 줬을 때 그냥 등록할지, 실패 처리할지, 다시 물어볼지를 프롬프트로 설계해야 한다.

주의 사용자 프롬프트는 언제나 변수다. 노트대로 쓰지 않고 "내일 3시에 프로젝트 회의 일정 만들어줘"처럼 대충 쓸 수 있다. 이런 입력을 어떻게 처리할지 고민하는 것이 툴콜 설계다.

툴의 실체: 파이썬 함수 + @tool

툴의 실체는 파이썬 함수다. def 함수명(인자: 타입) 형태이고, 타입 힌트는 파이썬 옛 버전엔 없다가 추가된 기능으로 여러 사람이 쓸 때 변수 타입을 체크하게 해 준다.

함수 위에 붙인 @tool(어노테이션이라고도 부른다)이 함수를 툴로 바꿔 준다. 여기에 담긴 툴 이름과 description이 에이전트(LLM)가 보는 정보다. 이 설명이 모델에 전달돼야 모델이 인자를 만들어 넘길 수 있다.

  • @tool만 붙여도 동작한다.
  • 이름을 바꾸고 싶으면 @tool("personal_schedule", ...)처럼 지정한다.
  • description은 데코레이터 인자로 줘도 되고, 함수의 docstring(주석)으로 써도 같은 툴이 된다. 둘 다 있으면 데코레이터 쪽을 먼저 본다.
  • 기존 함수를 고쳐 쓰거나 새로 정의해 툴로 만들 수 있다. 로컬에서 실행 가능한 함수는 모두 에이전트 툴이 될 수 있다.

기본 툴은 일정 목록(딕셔너리 리스트)에 일정을 추가하고, 추가될 때마다 번호를 붙여 "등록됐다"는 결과를 돌려주는 평범한 함수다.

(함수, 인자 이름은 예시)

from langchain.tools import tool  # LangChain v1 기준 import

SCHEDULES = []  # 일정 목록(딕셔너리 리스트)

@tool("personal_create_schedule", description="개인 일정을 생성한다 ...")
def create_schedule(title: str, date: str, start_time: str, attendees: list[str]) -> dict:
    schedule_id = f"schedule_{len(SCHEDULES) + 1}"  # 일정이 추가될 때마다 번호 증가
    SCHEDULES.append({"schedule_id": schedule_id, "title": title, "date": date,
                      "start_time": start_time, "attendees": attendees})
    return {"ok": True, "schedule_id": schedule_id, "title": title,
            "date": date, "start_time": start_time}  # 등록됐다는 결과를 돌려준다

@tool 작성 방식 두 가지: 새 함수와 기존 함수

툴을 만드는 방식은 두 가지로 정리할 수 있다. 툴은 기본적으로 함수 형태이고, 툴 이름(name)과 설명(description)을 가진다.

방식 쓰는 법 언제
① docstring형 함수에 @tool을 붙이고 docstring을 설명으로 쓴다 새로 구현하는 함수를 바로 툴로 만들 때
② 인자 지정형 어노테이션에 이름, 설명을 지정한다 이미 구현된 함수를 툴로 만들 때

방식 ②에서는 이름, 설명이 어노테이션을 따르므로, 기존 코드의 함수 이름을 바꾸지 않고도 에이전트용 툴로 쓸 수 있다. 기존 코드베이스의 함수를 손대지 않고 에이전트에 연결할 수 있다는 점이 중요하다.

(legacy_add_event는 설명용 예시 이름)

# 방식 ①: 새 함수 (docstring이 description이 된다)
@tool
def create_schedule(title: str, date: str, start_time: str, attendees: list[str]) -> dict:
    """개인 일정을 생성한다. 제목, 날짜, 시작 시간, 참석자를 받는다."""
    ...

# 방식 ②: 기존 함수 (툴 이름, 설명은 어노테이션을 따른다)
@tool("personal_create_schedule", description="개인 일정을 생성한다 ...")
def legacy_add_event(title: str, date: str, start_time: str, attendees: list[str]) -> dict:
    ...  # 함수 이름은 그대로 두고, 에이전트에는 personal_create_schedule로 보인다

데코레이터를 함수 호출처럼 써서 tool("이름", description="...")(기존_함수)로 감싸면 원래 정의를 건드리지 않고도 툴을 만들 수 있다. 툴 입력을 Pydantic 클래스로 거르는 args_schema 방식은 → 구조화된 출력과 Pydantic에서 다룬다.

description 쓰는 법: 툴도 프롬프트로 통제된다

LLM은 툴의 이름(name)과 설명(description)을 보고 어떤 툴을 어떻게 부를지 정한다. 툴은 20~30개를 등록해도 문제없다. 다만 잘 고르게 하려면, 툴 선택에 가장 강하게 영향을 주는 description을 "이 툴을 쓰면 이 요청을 수행할 수 있겠다"고 판단하기 쉬운 설명서처럼 써야 한다. 파라미터 이름, 요구하는 값, 함수 이름도 같이 들어가 영향을 준다.

반환 구조가 원하는 대로 안 나오면 description에 입력, 출력 예시(퓨샷)를 넣는다. 툴을 언제 선택해야 하는지, 어떤 형태로 리턴해야 하는지가 분명해져 선택 정확도가 올라간다.

@tool("personal_create_schedule", description=(
    "사용자의 개인 일정을 등록한다.\n"
    '예시) 입력: "내일 멘토랑 개발 미팅 잡아줘"\n'
    '      출력: {"title": "개발 미팅", "date": "...", "start_time": "...", ...}'
))
def create_schedule(...): ...

지금은 툴이 3개라 간단하지만 실무에선 툴이 20~30개를 넘고 조합에 따라 해결 여부가 갈린다. MCP로 붙인 툴도 같은 방식으로 불린다(→ MCP와 A2A).

이 원칙은 "툴도 결국 프롬프트로 통제된다"로 정리할 수 있다. 원하는 입력, 출력과 툴 description으로 툴이 원하는 대로 동작하게 설정한다.

  • 정답 프롬프트는 없다. 각자 만든 에이전트의 전체 맥락, 데이터에 따라 조건이 다 다르다. 같은 프롬프트가 어떤 에이전트에서는 되고 다른 에이전트에서는 안 될 수도 있다. 그러니 CoT나 few-shot으로 직접 설정하는 연습을 해야 한다(→ 프롬프트 엔지니어링).
  • 처음부터 많이 쓰지 않아도 된다. 떠오르는 대로 간단히 쓰고 결과를 보며 바꿔 나간다. 원치 않는 데이터가 나오면 시스템 프롬프트나 툴 description에 "이런 경우에는 이렇게 동작해라"를 명확히 적는다.
  • 소수 데이터 문제: 모델이 학습할 때 소수 조건(특히 한국어, 특수 기술, 전공 분야)은 데이터가 많지 않다. 이런 것이 조건으로 들어가면 단어를 샘플링하는 확률이 크게 흔들릴 수 있다. 그래서 RAG 등으로 증강한 뒤 출력시키고(→ RAG: 임베딩 검색과 ChromaDB), 툴 내부에서는 들어가면 안 되는 단어를 필터링하는 처리가 필수다.

정리 "문법 자체가 어렵지는 않다." 에이전트를 구성하는 코드는 복잡하지 않다. 어려운 건 원하는 대로 동작하도록 description과 프롬프트, 예시를 쓰는 일이다.

create_agent로 에이전트 구성하고 invoke로 실행하기

LangChain은 에이전트를 쉽게 만드는 프레임워크다(역사는 → 서브에이전트, 멀티에이전트, 워크플로). create_agent가 에이전트 아키텍처의 LLM, 메모리, 플래닝, 툴을 한 번에 구성한다(→ 에이전트란 무엇인가). 인자는 셋이다.

  • model: LLM. 노트북에서는 make_model로 만든 ChatOpenAI 모델을 쓴다. 요청을 모아 응답해 주는 프록시 서버를 쓰므로 base_url을 지정한다. temperature, max_tokens 같은 생성 파라미터의 원리는 → Transformer 블록 해부.
  • tools: 툴 리스트
  • system_prompt: 이 에이전트가 어떻게 동작할지 쓰는 프롬프트. 이것도 일종의 플래닝이다.

create_agent 내부에는 이미 ReAct 플래닝이 들어가 있다(→ 에이전트란 무엇인가). 그 위에 LLM 기본 프롬프트 → ReAct 프롬프트 → 시스템 프롬프트 → 유저 프롬프트 순으로 프롬프트 계층이 쌓인다(→ 프롬프트 엔지니어링).

에이전트를 선언한 뒤 invoke에 role: user, content로 사용자 프롬프트를 넣는다. 채팅하는 것과 똑같다.

from langchain.agents import create_agent  # LangChain v1 기준 import

nana_basic_agent = create_agent(
    model=make_model(),         # LLM (ChatOpenAI, 프록시 base_url)
    tools=[create_schedule],    # 툴 리스트
    system_prompt="...",        # 이 에이전트가 어떻게 동작할지(일종의 플래닝)
)

result = nana_basic_agent.invoke(
    {"messages": [{"role": "user", "content": "내일 10시에 민수와 회의 일정을 잡아줘"}]}
)

에이전트의 핵심 역할은 툴이 20~30개가 되어도 사용자 요청에 맞는 툴을 정확히 골라 정확한 인자를 넣고 실행한 뒤 답을 주는 것이다. 같은 프롬프트라도 어떤 툴을 구현했는지, 어떤 모델을 썼는지에 따라 편차가 생긴다. 그래서 툴 구현 → description 작성 → 시스템 프롬프트 작성을 반복 연습한다.

실행 결과 읽기: 최종 답변과 툴 트레이스

실행 결과는 두 부분으로 나눠 본다.

  1. 에이전트의 최종 답변
  2. 에이전트가 수행한 동작(툴 트레이스)

1주차 노트북에는 이를 보기 위한 show_json, final_text, tool_trace 같은 헬퍼가 있다. 에이전트가 정상 동작하는지 추적하려고 구현해 둔 것이다.

위 예시를 실행했을 때 나온 결과는 이렇다.

구분 내용
최종 답변 "내일 10시에 민수와 회의 일정을 잡았습니다"
tool_call 이벤트 툴 personal_create_schedule이 불림
인자(arguments) 모델이 프롬프트에서 뽑은 title, date, start_time, attendees
툴 반환값 성공, schedule_1, "민수와의 회의", 날짜, 시간이 담긴 JSON

답변만 온 게 아니라, 모델이 직접 함수를 고르고 인자를 채워 실행했다는 기록이 남는다. 원래 사람이 인자를 넣어야 했던 일을 모델이 한 것이다.

(아래는 LangChain 메시지 구조에서 같은 정보를 꺼내는 일반적인 예시다)

for msg in result["messages"]:
    if getattr(msg, "tool_calls", None):        # AIMessage: 모델이 만든 툴 호출 요청
        for call in msg.tool_calls:
            print("tool_call:", call["name"], call["args"])
    elif msg.type == "tool":                     # ToolMessage: 로컬에서 실행된 함수의 반환값
        print("tool_result:", msg.content)

print("final:", result["messages"][-1].content)  # 마지막 AIMessage = 최종 답변

툴 트레이스로 디버깅하기

Claude Code, Codex를 쓰는 게 아니라 LangChain 등으로 에이전트를 코드로 구현할 때는 툴 트레이스를 보는 것이 디버깅 방법이다. 툴콜을 가장 먼저 다루는 이유다. 트레이스를 보고 툴, 프롬프트를 계속 개선한다.

트레이스에서 확인할 것:

  • tool call 파트에서 어떤 툴이 불렸는지(예: 3주차의 save_structured_request), 어떤 arguments가 들어갔는지를 반드시 본다.
  • 툴콜이 실행됐다는 것은 LLM이 요청을 만든 것뿐 아니라 그 툴 함수 코드가 로컬에서 실제로 다 실행됐다는 뜻이다. 거기에 넣어 둔 시스템적 처리(DB 저장 등)가 모두 동작한 것이다.
  • 싱글 에이전트 디버깅의 약 80%는 tool call 확인이다. 에이전트 성능은 툴이 어떻게, 몇 번 불리는지에 따라 바뀐다. 실습 노트북에 tool trace가 계속 들어가 있는 이유다.
  • 실습 앱에서도 채팅 화면보다 상세 페이지에서 어떤 툴, 어떤 argument가 쓰였는지 보는 게 가장 정확하다. 원하는 대로 안 되면 description이나 프롬프트를 고친다.

주의 좋은 모델은 이전 대화 컨텍스트를 잘 유지한다. 그래서 툴이 실제로 동작하지 않아도 대화 기억만으로 일정 관리가 되는 것처럼 보일 수 있다. 답변만 보지 말고 트레이스로 툴이 실제로 불렸는지 확인해야 한다.

노트북 마지막 셀은 프롬프트별로 기대한 툴이 제대로 불렸는지 룰 기반으로 체크한다. 확인 포인트는 "내 프롬프트에 대해 생각한 툴이 선택되는지, 어떤 인자가 들어가는지"다. 체계적인 평가는 → 에이전트 평가와 LLM-as-a-judge에서 다룬다.

지금은 코드 안에서 트레이스를 보지만, 나중엔 LangSmith(오픈소스 버전도 있음)처럼 LLM과 사람의 프롬프트 상호작용을 보여 주는 도구로 큰 프로그램 전체를 최적화한다. 서브에이전트를 쓰면 서브에이전트 동작이 첫 번째 툴콜에 나오지 않아 하위 툴콜까지 추적해야 하고, 이때부터 이런 트레이싱 도구가 필요하다(→ 서브에이전트, 멀티에이전트, 워크플로).

좋은 에이전트 = 최소한의 툴 호출

모델은 툴을 동시에 여러 개 부를 수 있고, 프롬프트와 LLM 성능에 따라 같은 문제(예: 수학 문제)에서도 툴 호출 횟수가 달라진다. 잘못 설계해 툴을 잘못 부르면 토큰을 더 쓰고 결과도 틀린다. 그래서 좋은 에이전트는 최소한의 툴 호출로 문제를 해결한다.

방법은 네 가지다.

  1. 최적의 프롬프트 구성
  2. 툴콜이 잘 되도록 디스크립션을 잘 쓰기
  3. 시스템 프롬프트 등을 튜닝
  4. 트레이스(툴콜 메시지)를 보고 의도대로 불렸는지 추적. 이건 디버그이자 최적화 작업이다.

어려운 점은 LLM이 강력하다는 것이다. 툴콜이 잘못돼도 스스로 정제(refine)해 답을 내는 경우가 많다. 일단 "동작은 잘 되고", 컴파일러처럼 버그도 띄워 주지 않는다.

예시 A→B→C 순서로 툴이 불리길 기대했는데 A→A→B→C로 불렸다면, 답이 맞더라도 시스템, 유저 프롬프트나 함수 디스크립션을 고쳐야 한다.

한 질문에 여러 툴: 중복, 다중 호출과 "조회 후 삭제"

한 질문에 툴 호출은 중복, 다중으로 일어날 수 있다.

  • "월요일 민수, 화요일 철수, 수요일 영희와 회의 잡아줘" → 같은 생성 툴 3번
  • "화, 수요일은 철수, 영희와 일정 잡고 월요일 민수 회의는 취소해 줘" → 생성 툴 2번 + 삭제 툴 1번

1, 2주차는 툴 1개 실행이 중심이었지만, 고도화될수록 한 번에 2~3개 이상의 툴을 실행한다. 대표적인 조합이 조회 후 삭제다.

  • "지금 일정이 뭐가 있어?" → list 계열 툴로 조회
  • "내일 10시 민수와 1:1 미팅 취소" → list로 조회한 뒤 delete. 상세 화면에서 list → delete 순서로 호출된 것을 확인할 수 있다.
  • 삭제는 ID 등을 확인해야 한다. 대화가 새로 시작되거나 컨텍스트가 끊긴 상태에서 바로 지우려 하면 실패한다. 그래서 삭제 요청에는 조회 후 삭제 흐름이 가장 좋다.
  • 3주차에서 신경 쓸 점: 구조화는 LLM이, 저장은 SQL이 담당한다(→ 툴 입력 검증과 SQLite 저장).

툴(조회, 생성, 삭제)은 고정돼 있지만, 어떻게 조합해야 동작이 정확히 끝나는지 고민하고 그 흐름을 시스템 프롬프트에 CoT나 few-shot으로 넣으면 실패 없는 에이전트가 된다. 시스템 프롬프트에 워크플로를 쓰는 방법은 → 프롬프트 엔지니어링에서 다룬다.

코드에 가까운 툴 vs 에이전트에 가까운 툴

툴은 두 성격으로 나눠 볼 수 있다.

구분 코드에 가까운 툴 에이전트에 가까운 툴
예 기존 서비스를 에이전트로 전환할 때 이미 있던 함수를 툴로 쓰는 경우. 인자를 받아 DB나 실제 데이터에 저장한다(실습의 일정 생성 함수) RAG의 프롬프트 처리처럼 함수 리턴에 프롬프트만 들어 있는 경우("검색 결과를 잘 찾아 이렇게 답하라")
동작 고정된 값을 받아 처리 스킬처럼 LLM이 만드는 텍스트에 의존해 자연어로 자유롭게 처리. 더 에이전틱하다
쓰임 DB를 쓸 때처럼 구조화가 필요할 때 사람처럼 답할 때

구분 기준은 LLM이 툴 메시지를 얼마나 주도적으로 만들고 해석하는지다. 실무에선 섞어 쓴다. 함수가 프롬프트를 돌려주는 스킬 방식은 → 프롬프트 엔지니어링에서 다시 본다.

툴콜 지원 모델

툴콜은 모델이 학습한 능력이라 툴콜을 지원하는 모델만 에이전트로 쓸 수 있다. Gemini, Claude 같은 주요 LLM은 대부분 지원하지만, SLM 중엔 지원하지 않는 모델이 있다(→ 모델 고르기와 여러 모델 조합).

그런 모델도 출력 형식을 학습시키는 파인튜닝으로 툴콜이 되게 만들 수 있다. 다만 처음 모델링할 때부터 학습한 모델과는 차이가 날 수 있다(툴콜 형식 학습은 → 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝).

Thinking 모델을 에이전트에 쓸 때: 툴 페어 불일치

thinking 모델은 파인튜닝으로 thinking 도중 tool call까지 하도록 학습돼 있다(내부 구조는 → 모델 학습: 사전학습, SFT, 강화학습, 파인튜닝).

  • 단점: 모델을 파인튜닝할 때 쓴 검색, 요약 같은 한정된 툴만 모델이 "네이티브"로 부를 수 있다.
  • LangChain 같은 프레임워크로 에이전트를 만들 때 thinking 모델을 잘 안 쓰는 이유: 모델이 부르려는 내장 툴을 우리 환경은 갖고 있지 않은 경우가 있어서, 결국 우리가 구현한 툴콜을 따로 진행해야 한다.
  • 그래서 thinking을 아예 안 쓰거나, 쓰더라도 thinking만 하고 모델 자체 펑션콜은 쓰지 않게 하거나, 우리가 구현한 툴만 쓰게 튜닝해서 쓰는 편이다.
  • Codex, Claude Code에서는 thinking과 툴이 잘 붙어 있어 그냥 써도 된다. 하지만 코드로 에이전트를 구현하면 "페어가 안 맞는" 부분이 생길 수 있다. 페어가 안 맞아 잘못 생성하거나 툴을 다시 부르면 토큰이 낭비된다.

팁 thinking 모델을 에이전트에 쓴다면 "thinking은 하되 자체 툴은 쓰지 말고, 우리가 구현한 툴만 써라"라고 프롬프트에 넣어 주는 것도 실제로 영향이 있다.

큰 흐름으로 보면, 세부 처리는 대부분 모델이 하겠지만 우리가 다뤄 주면 더 좋은 접근이 된다. 또 모델은 우리가 구현하는 에이전트를 기반으로 그 기능을 흡수한다. 에이전트와 모델이 같이 발전하고 있으니 이를 체크해 구성하면 더 효율적인 에이전트를 만들 수 있다.

주제 3

프롬프트 엔지니어링

프롬프트 엔지니어링은 확률적으로 생성하는 모델을 자연어로 제어하는 방법이다. 제로샷, 퓨샷, 인스트럭션, CoT 네 기법, 프롬프트 계층, 시스템 프롬프트에 툴 워크플로를 쓰는 법, 스킬로 조건을 꺼내 쓰는 법까지 정리한다.

프롬프트 엔지니어링 = 모델을 제어하는 방법

프롬프트 엔지니어링은 처음 나왔을 때 논란이 많았지만, 본질은 모델을 컨트롤하는 방법이다. RAG로 프롬프트를 잘 만드는 것, 에이전트의 시스템 프롬프트, description을 잘 쓰는 것, 코드 에이전트 안의 마크다운 문서, 플러그인, 스킬이 모두 결국 프롬프트이고 모델을 제어하기 위한 것이다.

RAG도 그중 하나였다. 긴 과정 같지만 RAG가 결국 하는 일은 프롬프트를 만드는 것이다. 텍스트를 잘 검색하는 시스템으로 모델의 프롬프트를 잘 만드는 것을 구현한 게 RAG이고, 지금은 에이전트 쪽으로 흡수됐다(→ RAG: 임베딩 검색과 ChromaDB).

이것을 "조건" 관점에서 다시 보자. 비결정적인 출력을 줄이는 방식이 컨텍스트 엔지니어링(→ 컨텍스트 엔지니어링과 하네스)이고, 그중 가장 먼저 연구된 것이 프롬프트 엔지니어링이다. "우리의 의도대로 잘 컨트롤되지 않는 이 모델"을 컨트롤하려는 첫 시도다.

  • 딥러닝은 항상 조건이 있어야 실행되고, 조건에 맞는 결과가 나온다. 바다 이야기 비유(→ 에이전트란 무엇인가)를 다시 떠올려 보자. 사람, 강아지, 고양이 사진이 들어가면 결과가 다르듯, 프롬프트가 들어가면 단어 예측 확률 분포가 달라지고 나올 수 있는 단어도 달라진다.
  • few-shot, CoT를 쓰는 의미는 예시나 과정을 세세하게 만들어서, 어차피 확률적으로 만드는 모델의 확률을 원하는 쪽으로 가이드하는 것이다. 모델은 우리 언어로 학습했으므로 언어적 강조나 예시를 파악할 수 있다.
  • ReAct처럼 순차적으로 생각해 답을 만드는 것도 결국 조건을 잘 만들어 원하는 단어를 생성하도록 가이드하는 작업이다.
  • "이걸 지금 튜닝하고 있는 거예요. 튜닝을 뭘로 한다? 자연어로 하고 있는 겁니다." CLAUDE.md든, 마크다운이나 HTML로 모델을 컨트롤하든 모두 이 흐름 안에 있다.

정리 프롬프트 엔지니어링은 "이런 조건이면 이걸 만들 수밖에 없겠지" 하는 방향으로 쓰는 것이다. 다른 걸 만들 여력을 최대한 없애 버리는 일이다.

정답 없는 최적화 과정

좋은 조건은 코드로 정해지거나 해답이 있는 것이 아니다. 모델과 상황을 종합해 찾아가는 최적화 과정이다. 모델을 다 뜯어 확률을 보는 방법도 있지만 실제로는 어렵다.

  • 텍스트가 임베딩으로 바뀐 뒤부터는 사람이 통제하기 어렵고 학습의 영역이다(→ Transformer 블록 해부). 그래서 모델 내부를 직접 튜닝하기보다, 특징과 패턴을 모델이 잘 인식하도록 프롬프트, 컨텍스트 엔지니어링을 한다. 이것이 "모델을 잘 쓰는 방법론"이다.
  • 프롬프트 엔지니어링은 LLM과 함께 갑자기 나온 것이 아니다. GPT-1, 2, 3 시절부터 "어떤 방식으로 조건을 넣어야 답을 더 잘 생성하나"를 연구해 온 결과다.
  • 책이나 유튜브의 "이 프롬프트를 쓰면 다 된다"식 프롬프트도 있다. 하지만 원하는 기능과 목적을 직접 써서 넣어야 모델이 특징과 패턴을 잘 뽑는다. 프롬프트를 잘 만드는 것 자체가 중요한 능력이다.

주의 "프롬프트 100제, 1000제" 같은 자료가 거짓은 아니지만 순서가 거꾸로다. 기법을 조합하면 그런 문장이 나오는 것이지, 만들어진 문장을 가져다 쓰는 게 핵심이 아니다.

네 가지 기법: 제로샷, 퓨샷, 인스트럭션, CoT

OpenAI가 개발자들과 정리한 글에서 메인으로 다루는 프롬프트 기법은 네 가지다. 이 분류는 OpenAI 쪽의 분류를 따른 것이다.

기법 하는 일 감정 분석 예
제로샷(Zero-shot) 예시 없이 요청한다 "이 영화는 재미없다"의 감정을 분석하라 → "부정적인 문장입니다". 답은 맞혀도 형식이 일정하지 않다(부정적/부정 …)
퓨샷(Few-shot) 예시를 함께 준다 "이 영화는 재미있습니다 → 긍정", "이 영화는 별로입니다 → 부정"을 먼저 주면 정해 둔 형식("부정")으로 답한다
인스트럭션(Instruction, 지시문) 시스템 프롬프트처럼 규칙을 박아 둔다 "앞으로 주는 문장을 긍정 혹은 부정으로만 답해"
CoT(Chain of Thought, 생각의 사슬) 어려운 문제를 단계별로 풀도록 순서를 나눠 준다 (어려운 수학 문제의 풀이 순서를 지시)

CoT는 이후 thinking, reasoning 모델로 이어진 최초 연구 중 하나다.

같은 감정 분석 예를 조금 더 보자. 제로샷으로 "아래 문장의 감정을 분석하세요: 이 영화는 재미있다"를 주면 "긍정"이 나오면 다행이지만 "긍정적인 문장입니다"처럼 들쭉날쭉할 수 있다. 퓨샷으로 "이 영화를 다시 보고 싶다 → 긍정", "이 영화는 별로다 → 부정"을 앞에 깔면 뒤 출력이 그 형식을 따라간다.

이 중 가장 중요한 것은 Few-shot과 CoT다. 둘 다 시스템 프롬프트와 툴 description을 쓸 때 많이 쓴다.

제로샷, 퓨샷의 원래 의미: 딥러닝 용어에서 온 말

제로샷, 퓨샷은 원래 딥러닝(예: 추천 모델) 용어다.

용어 딥러닝 시절 의미 프롬프트에서 의미
제로샷 러닝 이미 학습된 모델이 추가 학습 없이 분류, 생성을 해낸다 예시 없는 프롬프트
퓨샷 러닝 적은 데이터로 약간 파인튜닝해서 분류, 생성, 탐지(detection)를 한다 예시가 있는 프롬프트

예시 음악 추천이라면 제로샷 모델은 음악을 넣자마자 추천하고, 퓨샷은 특정 장르로 "학습을 조금만 해서" 빠르게 찾아낸다. 프롬프트로 넘어오면서 이 말이 "예시를 주냐 안 주냐"의 의미로 바뀌었다.

퓨샷이 가장 강력한 이유: 자기회귀

"프롬프트 중 가장 강력한 기능은 퓨샷이다." 예시를 주면 굉장히 잘 동작한다.

이유는 GPT의 생성 원리 때문이다. LLM은 자기회귀(autoregressive) 모델이라 앞 내용을 보고 뒤를 만든다. 앞에서 강제하는 내용이 많을수록 뒤의 출력이 그것을 참조한다. 그래서 예시가 뒤 출력에 강하게 작용해 출력 형식을 강제할 수 있다. 자기회귀의 원리는 → LLM과 딥러닝의 기본 원리에서 다룬다.

  • 특히 툴 인자처럼 무언가를 추출할 때 형식을 지정할 수 있다. 그래서 2주차 구조화된 출력에서도 쓰인다(→ 구조화된 출력과 Pydantic).
  • 예: "지금 제주도에 있습니다" → 위치: 제주도처럼 출력하는 예시를 주면, 모델이 이를 보고 JSON(구조화된 출력)으로 만들어 준다.
  • 예시를 넣는 few-shot은 "보고 싶은 결과를 다 넣어 주거나", "이런 질문이 들어오면 이렇게 처리해라"라는 흐름과 예시를 알려 주는 것이다. "어떤 함수/툴을 어떻게 써라"를 예시로 주는 것이 가장 강력하다.

정리 프롬프트는 대부분 few-shot과 CoT로 정리된다. 둘을 많이 연습하라.

CoT: 큰 문제를 작은 문제로 나누는 동작 순서

CoT = 큰 문제를 작은 문제로 나누는 것이다. 어려운 수학 문제의 풀이 순서를 넣어 주거나, 어떤 순서로 해결할지 가이드를 준다. 에이전트에서 CoT는 곧 "동작 순서", 즉 워크플로다.

예시 "45인승 버스에 골프공이 몇 개 들어갈까?"를 그냥 풀게 하기보다 "부피를 먼저 계산 → 골프공을 넣는 방식 가정 → 기물 부피, 공 겹침 처리"처럼 쪼개 준다. thinking 모델이라면 사람이 단계를 나눠 주는 것보다 알아서 더 잘 풀 수도 있다.

대부분의 모델은 CoT를 따르지만 말을 안 듣는 경우도 있다. 그럴 땐 프롬프트를 직접 손대서 단계를 거치게 하고, 그 결과를 기반으로 동작하도록 만든다.

에이전트 프롬프트 = 문제 해결 방법을 이식하는 일

LLM은 일반적인 문제를 풀지만, 에이전트는 특정 지점의 문제를 뾰족하게 해결하는 존재다. Claude Code, Codex도 범위는 넓지만 기본적으로 코딩 에이전트다.

그래서 에이전트 프롬프트에는 두 가지를 이식한다.

  • CoT: 그 문제를 어떻게 풀지
  • 퓨샷: 어떤 답을 끌어내야 하는지

두 가지를 조합하는 게 핵심이고, 원하는 결과가 나오면 그게 맞는 프롬프트다.

쿼리형에서 챗봇형으로: 짧게 시작해 늘려 가기

프롬프트 엔지니어링은 ChatGPT 같은 채팅 모델 이전, GPT-2 같은 언어 모델(텍스트 생성 모델) 시절부터 쓰였다. 모델 사용 방식은 둘로 나뉜다.

방식 구조 당시 프롬프트
쿼리형 쿼리 하나에 답 하나로 끝나는 단발 구조 단발 질의응답으로 성능을 평가했고 모델 성능도 낮아서, "너는 파이썬 개발자다, 가족을 위해 코딩한다, 철저히 ~해야 한다"처럼 처음부터 빽빽하게 썼다
챗봇형 답이 다시 입력으로 들어가 다음 답이 나오는 구조 모델이 좋아지고 챗봇 기반으로 동작하므로 간단히 넣어 보고, 의도대로 안 되면 그때 추가한다

결론은 비슷하지만 순서가 바뀐 것이다. 추가할 때 쓰는 도구가 퓨샷, 제로샷, 인스트럭션이다.

같은 조언은 지금도 유효하다. 처음부터 많이 쓰지 않아도 된다. 떠오르는 대로 간단히 쓰고 결과를 보며 바꿔 나간다. 원치 않는 데이터가 나오면 시스템 프롬프트나 툴 description에 "이런 경우에는 이렇게 동작해라"를 명확히 적는다.

프롬프트 계층: 무엇이 먼저 쌓이는가

에이전트에는 프롬프트가 계층으로 쌓인다.

  1. LLM 기본 프롬프트: ChatGPT, Gemini 등 서비스 모델에 이미 들어간 프롬프트
  2. ReAct 프롬프트: 툴을 활용하게 하는 프롬프트(create_agent에 내장, → Tool과 Function Calling)
  3. 시스템 프롬프트: 이 에이전트가 어떻게 동작할지
  4. 유저 프롬프트: 사용자가 실제로 입력하는 것

자기회귀 특성 때문에 앞에 쌓인 내용은 단어를 하나 생성할 때마다 매번 조건으로 쓰인다. 앞의 정보가 항상 뒤에 영향을 주므로 시스템 프롬프트에 쓴 대로 에이전트가 움직인다.

컨텍스트 구성을 그림으로 보면, 모델이 실행되면 가장 먼저 모델 쪽 시스템 프롬프트를 보고, 그다음 사용자가 만든 시스템 프롬프트, 마지막으로 유저 프롬프트가 들어간다. 새 대화나 새 프로젝트를 열면 뒤쪽 한두 칸만 바뀌고 모델 쪽 기본 프롬프트는 유지된다. 이 안에서 컨텍스트 길이가 카운트된다(→ 컨텍스트 엔지니어링과 하네스).

여기에 툴, Pydantic description이 들어가는 자리를 추가하면 모델 자체의 최하위(로우레벨) 프롬프트 → 시스템 프롬프트 → (질문에 따라) 툴, Pydantic description → 유저 프롬프트 순이다.

명시, 중복 기재와 반복 강조

시스템 프롬프트에만 써 두면 툴, Pydantic description이 누적되면서 모델이 "까먹는" 경우가 생긴다. 그래서 툴 description이나 유저 프롬프트 안에도 같은 내용을 써야 할 때가 있다.

  • 실습에서 쓰는 GPT-4.1은 상당히 좋은 모델이다. 하지만 회사, 창업에서 마주칠 SLM은 컨텍스트 유지 능력이 많이 떨어져서 같은 내용을 중복해서 써 줘야 할 때가 있다(→ 모델 고르기와 여러 모델 조합).
  • 처음부터 그럴 필요는 없다. 모델이 작아서 못 찾을 때 프롬프트로 찾게 하는 것이 가장 단순한 방법이다. SLM은 서버에서 컨텍스트 길이를 조정하는 등 파라미터로도 손볼 수 있다.

반복은 실제로 강조 효과를 낸다. 중요한 내용을 자연어로 반복하면 "어텐션에서 스코어들이 누적되기 때문에" 모델이 그 부분을 중요하게 보는 경향이 있다. 다만 사람이 의도해 만든 기능이 아니라 모델이 그렇게 학습한 결과다. 어텐션 구조를 이해하면 "프롬프트를 중복해서 쓰는 게 도움이 될까"에도 답할 수 있다(→ Transformer 블록 해부).

시스템 프롬프트 vs 툴 description: 어디에 쓸까

코드로 보면 에이전트는 LLM + 시스템 프롬프트 + tools(툴이나 MCP 형식) + 실행 시 붙는 유저 메시지로 구성된다. 지시를 어디에 둘지가 고민거리다.

위치 언제
시스템 프롬프트 기능이 하나일 때(예: 3주차 예제의 DB 저장 기능 하나), 툴 사용 순서처럼 전체 흐름을 정할 때
툴 description 툴별 기능이 여러 개일 때. 그 툴에 관한 내용은 description에 넣는 편이 더 좋다. 다만 description은 툴이 등록되면 함께 넘어가므로 성격이 조금 다르다
  • 3주차 예제는 사용자 요청을 바로 파싱해 넣지 않고 원본 데이터(source_text)를 먼저 넣고 진행한다. 나중에 필요한 정보를 다시 체크할 수 있게 하는 구조다(→ 툴 입력 검증과 SQLite 저장).
  • 날짜 같은 기준 정보는 프롬프트에 넣어도 되고 안 넣어도 된다. 요청 분류(kind)가 스키마에 있으면 굳이 안 넣어도 동작한다.

시스템 프롬프트에 툴 워크플로 쓰기: 일정 삭제 버그

예시 생성, 조회, 삭제 기능을 트레이스로 다 테스트하고 출시했는데 "삭제가 안 된다"는 버그 리포트가 들어온다. 툴은 메모리에 일정을 저장하지만, 새 대화 등으로 컨텍스트가 사라지면 모델은 일정 ID를 "자기의 컨텍스트로 볼 수가 없기 때문에" 삭제 툴에 넣을 인자를 못 채운다. 실제로 흔한 일이다.

삭제 툴 디스크립션만 잘 써도 툴 선택은 되지만 ID는 못 채울 수 있다. 그래서 시스템 프롬프트에 흐름을 직접 써 준다.

  1. 목록 조회 툴로 전체 일정을 컨텍스트에 올린다.
  2. 사용자가 지목한 일정의 ID를 찾는다.
  3. 삭제 툴로 삭제한다.

이렇게 하나씩 추가해 가는 것이 일종의 "프롬프트로 하는 코딩"이다. 자유도를 얼마나 줄지(고정할지, 풀어 줄지)도 프롬프트만으로 조절된다.

프롬프트 문자열을 쓰는 세 가지 방법과 마크다운 형식을 보자. 내용은 마크다운 형식(# 제목 등)으로 쓰는 게 가장 좋다.

p1 = "따옴표 한 쌍으로 쓴 한 줄 프롬프트"
p2 = """따옴표 3개 안에 쓴
여러 줄 텍스트가 그대로 프롬프트가 된다"""
p3 = ("괄호로 감싸 한 줄씩 써도 "
      "줄바꿈 없이 하나로 이어 붙는다")

SYSTEM_PROMPT = """
# 역할
너는 카나, 사용자의 개인 일정을 관리하는 어시스턴트야.

## 일정 등록
- personal_create_schedule을 사용해 사용자 요청에 따라 일정을 등록해 줘.

## 일정 조회
- personal_list_schedules를 사용해 조회해 줘.

## 일정 삭제
사용자가 삭제를 요청하면 아래 순서대로 처리해 줘.
1. personal_list_schedules로 일정을 조회한다.
2. 사용자가 삭제 요청한 일정의 ID를 찾는다.
3. personal_delete_schedule로 일정을 삭제한다.
"""

주의 Codex, Claude Code에 "해결해 줘"라고 맡기면, 툴 방식 코드가 나온 지 얼마 안 돼서 별도 함수를 만들거나 룰베이스로 찾아 지우는 로직을 짜는 등 기존 방식으로 고치려 한다. 그러면 에이전트를 만들었는데 실제로는 룰베이스로 도는 경우가 많다. 자연어 처리 영역은 최대한 툴 쪽으로 끌어와 에이전트 판단으로 동작하게 하라.

툴이 많아질 때: 워크플로를 CoT로 정의하기

4주차부터는 저장 방식과 검색 툴이 여러 개라서, 프롬프트만 쓰면 원하는 툴까지 안 가는 경우가 생긴다. 예를 들어 "찾아 줘"라고 하면 SQL 검색만 돌고 대화 목록 검색 툴은 안 불릴 수 있다. description을 조정해도 되지만 가장 좋은 방법은 시스템 프롬프트에 워크플로를 CoT로 정의하는 것이다.

예를 들어 "SQL을 검색했을 때 결과가 없으면 대화 목록을 검색해라"처럼 툴 사용, 검색 순서를 명시하면 그대로 따른다. 질문 한 번에 두 저장소를 다 검사해 가져오도록 만드는 것이 목표다.

툴만 구현해도 동작은 한다. 하지만 의도대로 동작하게 하려면 시스템 프롬프트 튜닝이 필요하다.

6주 실습을 돌아봐도 같은 점이 보인다. 주차마다 툴과 프롬프트가 늘었고, 누적되고 많아지면 부르면 안 되는 툴을 부르거나 툴 순서를 틀리는 오동작이 생긴다. 오류가 날 때마다 CoT를 따르도록 description이나 시스템 프롬프트에 넣어 최적화하는 단계가 필요하다. 조회 후 삭제 같은 툴 조합은 → Tool과 Function Calling를 본다.

유출된 시스템 프롬프트에서 배우기

한 유명 모델의 유출된 시스템 프롬프트(원문 + 한국어 번역)를 보면 다음과 같다.

  • 약 1,500줄에 줄도 길다.
  • 정보 정리, 키를 어떻게 쓰는지, 툴을 어떻게 부르는지, f-string으로 변수를 불러오는 부분, 퓨샷 예시, 스킬 불러오기 예시까지 들어 있다.
  • "너는 이건 할 수 있고 이건 못 한다", 길이 제한 같은 규칙을 명시적으로 쓴다.

모델이 실행되면 가장 먼저 보는 것이 이 모델 쪽 시스템 프롬프트다(앞의 프롬프트 계층). 말투나 구성이 막히면 이 스타일을 비슷하게 따라 쓰면 대부분 모델이 비슷하게 잘 동작한다. 시간 날 때 한 번 읽어 볼 만하다.

답변 컨트롤: "모르면 모른다고"

검색된 데이터가 늘 질문의 답이 되는 건 아니다. 그래서 RAG의 Augmented 프롬프트 뒤에 답변 컨트롤을 넣는다.

예시 "검색된 내용이 사용자의 질문에 답이 되지 않으면 모른다고 대답해라." 이 한 줄이 있으면 정보가 들어 있어도 답할 정보가 없을 때 모른다고 답한다.

  • 모든 경우를 다 제어할 수는 없지만 한 줄로 효과가 있다.
  • 이런 컨트롤은 데이터를 찾아오는 부분, 모델을 invoke하는 부분, 시스템 프롬프트 어디에든 넣을 수 있다.
  • 검색 내용의 진위를 검증해야 할 때 프롬프트 엔지니어링으로 처리한다. RAG 구성은 → RAG: 임베딩 검색과 ChromaDB.

스킬: 필요할 때 꺼내 쓰는 프롬프트

퓨샷의 응용으로, 만들어 둔 구현을 기반으로 요청해 생성하게 할 수 있다. 더 나아가 "LangChain 에이전트 구현은 이런 패턴으로 해 줘" 같은 패턴(파이썬 구현 예)을 정리해 스킬(Skill)로 만들어 넣으면 매번 코드 예시를 주지 않아도 된다. 스킬 같은 트릭은 코딩 에이전트뿐 아니라 LLM 웹서비스에서도 쓸 수 있다.

스킬의 실체는 단순하다. 함수를 만들어 두고, 부르면 MD 파일의 문자열을 읽어 return한다. 툴을 만들 때는 이름과 description만 모델에 들어가므로, 모델이 description을 보고 선택하면 그 내용이 스킬로서 조건에 들어간다. 즉 프롬프트가 추가된다. 함수가 프롬프트를 돌려주는 "에이전트에 가까운 툴"(→ Tool과 Function Calling)의 대표 예다.

(함수, 파일 이름은 설명용 예시)

from pathlib import Path
from langchain.tools import tool

@tool("essay_writing_skill", description="에세이를 쓸 때 지켜야 할 원칙을 불러온다")
def essay_writing_skill() -> str:
    # 부르면 MD 파일 내용을 그대로 돌려준다 → 그 문자열이 컨텍스트(조건)에 추가된다
    return Path("skills/essay.md").read_text(encoding="utf-8")

Claude Code 같은 코딩 도구에서 스킬을 쓰는 법은 → AI 코딩 도구 활용(Claude Code, Codex)에서 다룬다.

조건을 어떤 형태로 구현할까: 글쓰기 에이전트 예시

툴콜, RAG, 스킬, CLAUDE.md 구성 같은 방법론은 배웠지만 괴리가 있다. 실제로 잘 동작하는 조건은 직접 커스텀해야 한다. 어떤 에이전트를 만들지, 좋아하는 분야나 전공에서 어떤 정보와 워크플로를 넣을지 정하고, 그것을 툴, MCP 서버, RAG, 스킬, MD 문서 중 무엇으로 구현할지 결정하는 싸움이다.

예시 글 쓰는 에이전트를 만든다면

  1. 먼저 글을 잘 쓰는 법을 알아야 한다. 내가 알면 제일 좋고, 모르면 잘 쓰는 사람의 책이나 스킬을 찾는다.
  2. 조사, 연구로 그것을 문서화한다. 마크다운이면 더 좋다.
  3. 문서화하면 선택지가 생긴다. 데이터가 방대하면 RAG로 중요한 부분만 가져온다. "에세이를 잘 쓰는 5개 원칙"처럼 정리된 것이면 스킬로 저장해 글을 쓸 때 가져온다. 소설, 논문, 에세이별 방법론을 각각 스킬로 만들어 두고 모델이 판단해 필요할 때 불러오게 할 수도 있다.
  4. 확정적으로 동작시키려면 스킬 내용을 아예 프롬프트에 넣을 수도 있고, 툴콜을 이용하면 원할 때마다 불러올 수 있다.

5주차쯤이면 조건을 강화하는 방법들의 개념은 다 숙지돼 있어야 한다. 일일이 다 구현하는 것도 좋지만 "이런 흐름으로 만들어진다"만 알아도 기능은 충분히 구현할 수 있다.

few-shot, CoT 연습법: SLM으로 훈련하기

프롬프트에서 가장 강력한 기능은 few-shot, 즉 예시를 만드는 것이다. CoT는 "어떤 순서로 처리하라"를 쓰는 것이다. 이 둘의 큰 구조는 유지하되, 얼마나 더 자세히 쓸지와 예시를 더 만들지를 연습한다.

팁 LLM과 SLM은 다르다. SLM으로 낮추면 답변을 잘 못해서 프롬프트 쓰는 연습이 굉장히 많이 된다. Ollama 같은 곳은 Ollama Cloud로 이런 모델을 쓸 수 있게 해 준다(모델 고르기는 → 모델 고르기와 여러 모델 조합).

정리 "이 프롬프트를 쓰면 된다"고 정해 줄 수는 없다. 에이전트마다 맥락과 데이터가 다르기 때문이다. few-shot과 CoT로 직접 쓰고, 트레이스를 보며 고치는 연습이 답이다.

주제 4

컨텍스트 엔지니어링과 하네스

모델이 받을 수 있는 컨텍스트는 길어졌지만 그 안을 고르게 보지는 못한다. 컨텍스트를 낮고 깨끗하게 유지하는 실무 요령과 외부 저장, 선택, 압축, 분할 네 전략, 그리고 에이전트를 끌고 가는 제어 규칙인 하네스를 정리한다.

컨텍스트 = 모델에 들어가는 입력 조건

컨텍스트는 "이 모델의 조건, 입력 조건, 이 모델에 입력되는 프롬프트"다. "내일 10시에 민수랑 회의를 잡아줘"를 보내면 이 질문과 툴 디스크립션이 함께 컨텍스트에 들어간다(→ Tool과 Function Calling).

대화 쪽에서 보면, 프롬프트를 바탕으로 AI와 대화하며 쌓이는 대화 목록이 컨텍스트이고, 이를 어떻게 관리하느냐를 다루는 것이 컨텍스트 엔지니어링이다.

주의 모델이 아는 것은 컨텍스트에 있는 것뿐이다. 툴이 메모리에 일정을 저장해도, 새 대화 등으로 컨텍스트가 사라지면 모델은 그 일정을 "자기의 컨텍스트로 볼 수가 없기 때문에" ID를 모르고 삭제하지 못한다(→ 프롬프트 엔지니어링의 일정 삭제 버그).

프롬프트 엔지니어링에서 컨텍스트 엔지니어링으로

비결정적인 출력을 줄이는 방식이 컨텍스트 엔지니어링이고, 그중 가장 먼저 연구된 것이 프롬프트 엔지니어링이다(→ 프롬프트 엔지니어링).

프롬프트 엔지니어링이 실습에서 직접 쓴 시스템 프롬프트 작성이라면, 컨텍스트 엔지니어링은 최근에 정립된 개념이다.

  • 트랜스포머 자체를 다룰 때는 이야기하기 어려웠다. LLM 챗봇, 특히 에이전트가 되면서 에이전트들이 공유하는 내용을 두고 나온 이야기다. 정립된 지 오래되지 않았다.
  • 에이전트가 하는 일도 결국 컨텍스트가 들어왔을 때 다음 단어를 예측하는 것이다. GPT 구조가 바뀐 것이 아니라, 컨텍스트를 어떻게 관리하느냐에 대한 논의가 떠오른 것이다.
  • 서브에이전트가 등장하면서 컨텍스트 관리 규칙이 특히 중요해졌다(→ 서브에이전트, 멀티에이전트, 워크플로).

초반에 "RAG"라고 불렀던 부분도 이제 컨텍스트 엔지니어링에 포함된다고 봐도 된다. 컨텍스트 엔지니어링이 1.0, 2.0, 3.0으로 발전하는 흐름에서 관심이 "벡터DB를 만드는 것"보다 "컨텍스트를 어떻게 조정하느냐"로 넘어가고 있다.

정리 프롬프트 엔지니어링(시스템 프롬프트 쓰기)은 컨텍스트 엔지니어링의 한 부분이다. 컨텍스트 엔지니어링은 에이전트가 쌓고 공유하는 모든 입력을 관리하는 일이다.

무엇이 컨텍스트를 차지하는가

에이전트가 컨텍스트로 관리하는 것은 다양하다.

구성 요소 예
프롬프트 시스템 프롬프트, 유저 입력
스킬, 플러그인 필요할 때 불러오는 지침 파일(→ 프롬프트 엔지니어링)
MD 파일 CLAUDE.md 같은 문서(→ AI 코딩 도구 활용(Claude Code, Codex))
메모리 기본 메모리, 대화 목록
기타 소스 MCP라고 생각해도 된다(→ MCP와 A2A)

문제는 이것들이 기본으로 할당된다는 점이다. 시스템 프롬프트, 스킬, 플러그인, MD 파일, 기본 메모리, MCP 내용이 대화를 시작하기도 전에 자리를 차지하고, 매 동작의 결과에 영향을 많이 준다.

롱 컨텍스트의 한계: 넣을 수 있다고 다 보는 것은 아니다

에이전트를 다룰 때 가장 분명해지는 사실 중 하나가 "컨텍스트가 관리가 잘 되어야 한다"는 것이다. Claude Code 해커톤 1위 수상자의 주장이고 많은 사람이 공감한다. 컨텍스트가 성능에 큰 영향을 준다는 연구 결과도 있다.

  • 롱 컨텍스트 튜닝으로 입력 길이가 약 8,000 토큰에서 수십만, 50만을 거쳐 100만 토큰까지 늘었다.
  • 하지만 입력을 받을 수 있다고 해서 100% 활용되는 건 아니다. Claude 4.5, GPT-5, Gemini 3 무렵 실험에서 긴 컨텍스트에서도 90% 이상 유지한 건 Gemini뿐이었고, 나머지는 70~80% 수준이었다는 결과가 있다(대략적인 수치이므로 최신 결과는 다시 확인할 필요가 있다).
  • 같은 숫자가 여러 번 반복해서 언급된다. 모델이 100만 토큰을 볼 수 있다고 해도 실제로는 70~80% 정도만 인식한다.

질문 긴 시스템 프롬프트는 성능이 떨어지지 않나? → 전체 프롬프트가 얼마나 차 있는지에 따라 누락이 생길 수 있다. 시스템 프롬프트는 많이 길어져도 크게 상관은 없다는 말도 앞서 나왔으니, 길이 자체보다 컨텍스트가 얼마나 찼는지가 문제라는 맥락이다.

Lost in the Middle: 중간을 놓치고, 압축하면 또 잃는다

어텐션 메커니즘의 한계로, 프롬프트 위치에 따라 컨텍스트 중간의 내용을 놓치는 Lost in the Middle 현상이 생긴다. 왜 그런지는 어텐션 구조(→ Transformer 블록 해부)와 관련된다.

실무에서 중요한 것은 압축 쪽이다. Claude Code, Codex는 컨텍스트가 차면 압축(요약)해서 넘기는데, 이때도 데이터 손실이 계속 일어난다. 꽉 차서 요약하면 정보 손실(로스)이 생기고 정확도가 떨어진다.

정리 컨텍스트는 ① 넣어도 70~80%만 보이고 ② 요약할 때마다 또 잃는다. 그래서 "많이 넣기"보다 "필요한 것만, 낮게" 유지해야 한다.

RAG 무용론 논쟁과 그 결론

초창기에는 입력 토큰이 약 8000 수준이었고, 입력과 출력 길이가 같던 시기도 있어 컨텍스트에 넣을 수 있는 양이 매우 짧았다. 그래서 RAG가 강력했다. 이후 롱 컨텍스트 트레이닝으로 입력 길이를 늘리는 기술이 나오자 "다 때려 넣으면 되는데 굳이 RAG를 왜 하냐"는 RAG 무용론이 등장했다.

결론은 무용론은 틀렸다. RAG는 여전히 강력하다. 롱 컨텍스트 주장자들이 놓친 것은 모델이 컨텍스트를 고르게(균일하게) 보지 못한다는 점이다. 100만(1M) 토큰을 넣을 수 있어도 모든 내용을 동일하게 보지 못한다. 초창기에는 이를 확인하지 못했다.

그래서 지금도 RAG, MCP, Function Calling, 스킬을 만드는 것이 잘 동작한다. 롱 컨텍스트 인식 기술이 완전히 해결되면 모두 넣는 편이 나을 수도 있지만 현재는 아니다. 컨텍스트 엔지니어링은 이 롱 컨텍스트의 한계를 알고, 모델이 잘 인식하도록 컨텍스트를 수정, 조절하는 작업이다. RAG 자체는 → RAG: 임베딩 검색과 ChromaDB.

컨텍스트가 쌓일수록 생기는 문제: 길이, 잘못된 정보, 노이즈

컨텍스트가 쌓일수록 문제가 생긴다. 가장 주의할 것은 두 가지다.

  • 컨텍스트가 길어지는 것
  • 잘못된 정보가 들어가는 것

GPT는 어텐션으로 특징을 뽑고 패턴을 인식한다. 틀린 정보 같은 노이즈가 끼면 모델이 스스로 걸러 내기도 하지만 못 걸러 낼 때도 있다. 너무 많이 쌓이거나 길어지면 모델이 원래 가진 패턴 인식보다 컨텍스트에 더 의존한다는 실험도 있다. 그 결과 긴 컨텍스트에서 중요한 부분을 놓친다. 압축 전략이 필요한 이유다.

컨텍스트를 낮게 유지하라: 태스크마다 새로 시작

툴 입력, 대화가 계속 누적되므로 컨텍스트를 항상 최적으로, 낮게 유지해야 한다. 한 목표가 달성되면 새 컨텍스트를 만들고, 쓰는 툴, 스킬 양을 줄인다.

  • 요약할 때마다 손실이 또 생긴다. 그래서 태스크 하나 끝날 때마다 새로 시작하는 쪽이 요약해서 넘기는 것보다 손실이 적다.
  • SNS에서 보이는 "요약하고 계속 돌리기"는 따로따로 돌리면 괜찮다. 하지만 하나의 컨텍스트에서 계속 이어 가면 성능에 좋지 않다.
  • 구체적인 방법: 한 단계 작업이 끝나면 내용을 마크다운 파일로 정리하고 새 대화에서 그 파일로 이어 간다. 작업 단위를 줄이는 방식이고 토큰도 아낀다. 사람들이 이런 방식을 스킬로 만들어 배포, 홍보하는데, 그걸 더 효율적으로 만드는 것이 개발자의 몫이다.

주의 Superpowers 같은 좋은 스킬 모음도 잘 동작한다. 하지만 토큰이 남발, 누적되면 한 번에 끝까지 가지 말고 하나의 태스크가 그 토큰 안에서 끝나게 하라. 잘못 쓰면 토큰비가 어마어마하게 나간다.

컨텍스트 엔지니어링의 네 가지 전략: 외부 저장, 선택, 압축, 분할

컨텍스트를 다루는 전략은 넷으로 정리할 수 있다.

전략 하는 일 예
외부 저장 컨텍스트를 MD, HTML 파일, DB, 메모리(체크포인트) 등 밖에 저장해 두고, 다음 대화나 새 모델로 시작할 때 참조한다. 모델에 계속 들어가 있는 게 아니라 바깥에 두고 필요할 때 교체한다 서비스에서 사용자와의 대화를 외부에 저장. 스킬 파일, MD 파일로 저장해 두고 모델이 선택하면 불러오기
선택(Select) 필요한 부분만 골라 넣는다 RAG를 포함해 외부 데이터를 가져와 컨텍스트로 불러오는 흐름(→ RAG: 임베딩 검색과 ChromaDB)
압축 그동안의 대화를 압축한다 compact. 태스크가 끝났을 때 압축으로 정리하고 컨텍스트를 비운 상태에서 다시 시작하면 성능이 더 좋다
분할(Isolate) 세부 작업을 서브에이전트에게 맡긴다 서브에이전트가 작업한 세부 내용은 메인 컨텍스트에 아예 포함되지 않는다(→ 서브에이전트, 멀티에이전트, 워크플로)

외부 저장은 스킬과도 비슷하다. 툴 기반으로 스킬을 만들거나 description을 쓰거나, 스킬 파일, MD 파일로 저장해 두고 모델이 선택하면 불러온다. 분할에서는 메인이 전체 흐름만 기억하고 세부 동작은 서브가 맡으므로, 메인 에이전트가 컨텍스트 부담 없이 자유롭게 동작한다.

외부 저장, 선택, 압축은 에이전트를 구현할 때 최대한 정리해서 쓸 수 있는 부분이다. 컨텍스트를 얼마나 잘 다루느냐가 곧 에이전트를 잘 구현하는 능력이 되었다. 이 네 분류는 LangChain 블로그 등에서 Write/Select/Compress/Isolate로 소개된 분류와 같다.

도구 사례: Claude Code /compact와 Codex의 압축

Claude Code나 Codex도 간단한 컨텍스트 관리를 해 준다.

  • compact 같은 명령어를 쓰면 이전 컨텍스트에서 중요한 내용 위주로 요약한다.
  • Codex는 스킬, MCP 관련 컨텍스트가 많이 들어가 있으면 그 부분을 압축하기도 한다.

LangChain에서 직접 적용하기보다 Claude Code나 Codex를 쓰면서 이런 동작을 확인할 수 있고, 운영할 때 많이 쓰인다. 코딩 도구 활용은 → AI 코딩 도구 활용(Claude Code, Codex).

서브에이전트와 마크다운 파일로 컨텍스트 이어 가기

서브에이전트로 넘어가며 새 문제가 생겼다. 작업이 커져 한 번의 컨텍스트로 끝나지 않는다.

  • 서브에이전트의 핵심 장점은 컨텍스트가 아껴진다는 것이다. 메인 에이전트가 서브에이전트에 태스크를 이관하면 입력과 출력만 받는다. 생각 과정은 컨텍스트가 분리되므로 메인 컨텍스트가 줄어든다(어텐션과의 관계는 → Transformer 블록 해부).
  • 작업량이 더 많아지면 압축, 요약으로도 감당이 안 된다. 그때는 요약보다 정리된 마크다운 파일로 남기는 것이 효과적이다. 태스크 하나 끝날 때마다 파일에 저장, 업데이트하며 그 파일을 기준으로 진행한다.
  • 진짜 멀티에이전트는 컨텍스트가 완전히 독립이다. 툴콜로 연결되지 않으면 컨텍스트가 이어지지 않으므로, 문서로 컨텍스트를 두고 읽어오게 한다(→ 서브에이전트, 멀티에이전트, 워크플로).

정리 md 파일 활용은 결국 컨텍스트를 잘 유지하기 위한 방법이다.

메모리 범위: 단기로 쓸까, 누적해서 쓸까

이 과정의 LangChain 예제는 메모리를 단기로만(invoke 하나 안에서만) 써서 전체 채팅 내용을 보지 못하게 했다.

방식 특징
단기 메모리(예제의 방식) invoke 하나 안에서만 기억한다. 전체 채팅 내용은 보지 못한다
메모리와 연결해 계속 정리 누적된 내용까지 모델이 보고 답하게 구성할 수 있고, 앞서 본 워크플로들도 구현할 수 있다. 대신 메모리 리셋을 따로 해 줘야 하는 문제가 생긴다

필요에 따라 고르면 된다. 대화를 DB나 checkpointer로 저장하는 방법은 → 툴 입력 검증과 SQLite 저장에서 다룬다.

하네스 엔지니어링: 고삐로 에이전트를 끌고 가기

하네스(harness)는 정립된 학술 용어라기보다 X(트위터)에서 누군가 쓴 말이 퍼진 것이다. 흐름은 프롬프트 엔지니어링 → 컨텍스트 엔지니어링 → 하네스 엔지니어링이고, 그다음 "루프" 같은 말도 나왔다가 사라진 듯하다. 결국 모두 에이전트를 제어하는 방식이다.

  • 하네스 = 말 고삐, 강아지 목줄이다. 에이전트를 제어하는 방법론이며 계속 연구 중이다. 모델은 결국 프롬프트로 제어되므로, 어떤 제약을 줄지 정리해 두는 것이다. md 파일뿐 아니라 Skills를 커스텀으로 만들어 그때그때 참조하게 할 수 있다.
  • "모델은 계속 좋아지고, 우리가 할 수 있는 건 워크플로를 구성하는 것"(→ 에이전트란 무엇인가의 Vertical & Horizontal AI)에서 그 워크플로 구성이 곧 하네스 구성이다.
  • 목적에 따라 짠다. TDD로 오류 없는 개발이 중요하면 그쪽으로, 빠른 선점, 프로토타이핑이 중요하면 그쪽으로 하네스를 짠다. 파일, 스킬, 데이터 저장, Obsidian 연결 등이 재료다.
  • 정답이 없으니 직접 써 보고 평가하고, 안 좋으면 버리고 다시 만든다(모래성 쌓고 부수기).

비유 말을 타 보면 생각보다 말을 안 듣고 자기 가고 싶은 대로 간다. 고삐, 박차를 잘 쓰는 사람은 달리게도 하고 끌고 가기도 한다. 에이전트를 다루는 기술에 "하네스"라는 이름이 붙은 이유다.

결국 에이전트를 잘 쓴다는 것은 도메인 지식을 얼마나 주입하면서 끌고 갈 수 있느냐다.

하네스와 사용자 성향: Superpowers, 직접 입력, 루프

Claude Code 사용자는 성향이 나뉜다.

성향 쓰는 방식
Superpowers 같은 유명한 스킬, 프롬프트 모음을 쓰는 사람 개발을 시작할 때 쓰면 테스트를 만들고 흐름에 따라 잘 동작하도록 가이드해 준다. 기능 하나를 만들면 테스트를 돌리는 식의 스킬, 프롬프트를 제공한다
원래 개발을 해 온 사람 기본으로는 잘 안 쓰고 그때그때 필요한 스킬, 프롬프트를 직접 입력한다. 토큰을 최대한 절약하는 성향이 많다
토큰이 넉넉한 사람 여러 도구를 쓰고, Ralph loop 같은 걸로 계속 돌면서 체크, 동작하며 멈추지 않고 쓰는 걸 좋아한다

하네스는 이런 제어가 필요한 부분, 즉 제어 규칙이다. 하네스를 잘 구성해 모델이 원하는 요청을 처리하게 하는 접근법을 찾는 게 커뮤니티의 주된 이야기였다. 하네스는 필요에 따라 커스텀할 수 있다.

Anthropic의 새 가이드: "Claude를 풀어 주라"

Anthropic이 CLAUDE.md 작성법을 바꾸는 글을 냈다. 이 글은 이전 방식을 "옛날 방식"이라고 지칭한다.

  • 적용 범위: 글을 읽어 보면 최근 나온 Opus 5와 Fable 모델에만 해당하는 것으로 보인다. Sonnet 등 다른 모델 가이드는 아직 없다. 글의 취지도 "Opus, Fable을 쓸 때는 하네스를 다시 살펴야 하고, Sonnet 등을 쓸 때는 이전처럼 하네스를 진행하라"로 읽힌다.
  • 핵심 메시지는 "Claude 해방", 즉 하네스를 풀어 주라는 것이다. 과도한 제약을 걸지 말라는 뜻이다.

CLAUDE.md, AGENTS.md를 쓰는 실제 요령은 → AI 코딩 도구 활용(Claude Code, Codex)에서 다룬다.

정리 하네스는 모델에 맞춰 바뀐다. 모델이 좋아지면 제약을 풀고, 약한 모델에는 여전히 촘촘한 제어가 필요하다.

결론: 모든 일은 컨텍스트를 잘 만드는 일

정리 가장 중요한 것은 이것이다. 우리가 하는 모든 일은 컨텍스트를 잘 만들기 위한 일이고, 컨텍스트를 잘 만드는 것은 우리가 원하는 출력을 만들어 내는 작업이다.

그래서 에이전트를 잘 만들려면 결국 프롬프트를 잘 만드는 연습을 해야 한다(→ 프롬프트 엔지니어링). 지금까지 배운 것을 구현하고 활용할 수 있으면, 특정 태스크에 에이전트를 만들어 최적화하는 데까지는 무리 없이 구현할 수 있다.
